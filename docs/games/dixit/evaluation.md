# Dixit(`dixit`) 게임 평가 및 개선안

- 작성일: 2026-07-06
- 분석 범위: `games/dixit/host/main.js`, `games/dixit/host/DixitDemoSimulator.js`, `games/dixit/host/index.html`, `games/dixit/host/style.css`, `games/dixit/mobile/DixitMobile.js`, `games/dixit/mobile/index.html`, `games/dixit/mobile/style.css`, `games/dixit/shared/constants.js`, `games/dixit/shared/deck.js`, `games/dixit/shared/scoring.js`
- 분석 방식: 소스 코드 정적 분석 기반 평가. 실제 다기기 실기기 QA, 브라우저 시각 검증, 사운드 체감 검증은 이번 문서 범위에 포함하지 않았다.
- 추가 메모: `games/dixit/IMPLEMENTATION_PLAN.md`는 카드 수를 54장으로 기록하지만, 현재 실제 구현은 `CARD_COUNT = 200`이며 `assets/cards/`도 200장 기준으로 구성되어 있다. 문서 정합성 부채가 존재한다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`dixit`의 기본 구조는 이 플랫폼과 궁합이 좋다.

1. 공용 화면은 현재 라운드의 힌트, 제출 진행 상태, 투표 보드, 결과와 점수판을 보여 준다.
2. 모바일은 각 플레이어의 비공개 손패와 입력 장치 역할을 맡는다.
3. 이야기꾼은 자기 카드 1장과 힌트를 제출한다.
4. 다른 플레이어는 힌트에 어울리는 자기 카드를 제출한다.
5. 공용 화면에서 카드가 섞여 공개되고, 비-스토리텔러는 이야기꾼의 카드를 추리해 투표한다.
6. 일부만 맞히는 절묘한 힌트 설계가 핵심 점수 재미로 연결된다.

이 게임의 강점은 "정답을 찾는 게임"이 아니라 "정답이 너무 obvious해도, 너무 난해해도 손해 보는 게임"이라는 점이다. 같은 그림을 보고도 각자 다른 상상을 하게 만들고, 그 차이를 읽어내는 과정에서 자연스럽게 웃음과 토론이 나온다. 공용 TV를 함께 보며 "저건 네 카드 아니야?", "힌트가 너무 세다", "왜 그걸 골랐어?" 같은 대화가 생기기 때문에, connect-dise가 지향하는 "같은 공간에서 시선을 교환하며 즐기는 디지털 보드게임"의 목적에 잘 맞는다.

특히 구현상 다음 요소는 재미의 핵심을 잘 보존하고 있다.

- `shared/scoring.js`가 Dixit의 대표 규칙인 `일부만 정답 / 전원 정답 / 전원 오답 / 미끼 득표 보너스`를 분리해 계산한다.
- 모바일 손패는 개인 기기에만 보이고, 투표 보드는 호스트에만 공개되어 역할 분리가 선명하다.
- 호스트는 라운드별 힌트 배너, 제출 현황, 결과 카드 공개, 최종 순위까지 한 화면에서 처리해 관전자 경험을 유지한다.
- 카드 전체 갤러리 버튼이 있어 운영자나 첫 플레이어가 분위기를 빠르게 이해하기 쉽다.

반면 현재 구현은 재미의 잠재력에 비해 감정 곡선이 약간 평평하다. 이유는 세 가지다.

- 이야기꾼의 힌트 제출, 카드 제출, 투표 성공이 모두 기능적으로는 처리되지만 "잘했다"는 감정 보상이 시각/청각적으로 약하다.
- 모바일은 라운드 결과에서 개인 점수만 간단히 보여 주기 때문에, "내 카드가 몇 표를 유도했는지", "왜 이번 라운드가 성공/실패였는지"를 감정적으로 복기하기 어렵다.
- 힌트를 만드는 행위 자체는 매우 재밌지만, 초심자에게는 가장 부담스러운 순간이기도 하다. 현재는 이를 완화하는 온보딩 보조 장치가 거의 없다.

#### 재미 요소 평가 요약

| 평가 항목 | 판단 | 코멘트 |
| --- | --- | --- |
| 공용 화면 적합성 | 매우 높음 | 투표 보드와 결과 공개가 TV/태블릿 중심 플레이에 잘 맞는다. |
| 소셜 추리/블러핑 재미 | 높음 | 힌트의 절묘함과 심리전이 자연스럽게 대화로 이어진다. |
| 가족/지인 파티 적합성 | 높음 | 공격적 경쟁보다 상상력과 해석의 차이에서 재미가 난다. |
| 초심자 진입성 | 중상 | 룰은 짧지만 "좋은 힌트 만들기"는 생각보다 부담이 있다. |
| 관전자 재미 | 중상 | 결과 공개는 좋지만 과정 연출이 더 강해질 여지가 크다. |
| 감정 피드백 밀도 | 중 | 결과 정보는 충분하지만, 순간 손맛과 연출 보상이 약하다. |
| 반복 플레이 매력 | 높음 | 카드 수가 많고 플레이어 구성에 따라 분위기가 크게 달라진다. |

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

전체 구조는 프로젝트 권장 패턴을 잘 따른 편이다.

- 호스트는 `HostBaseGame` 상속 기반으로 `lobby → storytelling → card-selection → voting → round-result → final` 흐름을 유지한다.
- 모바일은 `MobileBaseGame` 상속 기반으로 `setup`, `waiting`, `storyteller-clue`, `card-select`, `vote`, `round-result` 화면을 분리한다.
- 공통 룰은 `shared/constants.js`, `shared/deck.js`, `shared/scoring.js`로 분리돼 있어 Host/Mobile 간 규칙 불일치 위험이 낮다.
- `rejoinState`와 `phaseTimerRemaining`까지 전송해 재접속 복구를 의식한 점은 분명한 장점이다.
- 타임아웃 시 자동 제출, 자동 결과 공개가 들어가 있어 행사장 운영에서 라운드가 멈춰 버리는 위험을 줄였다.

현재 완성도는 "플레이 가능한 프로토타입"을 넘어 "행사 시연 가능한 베타"에 가깝다. 다만 안정형 콘텐츠로 보기에는 구조적으로 손봐야 할 부분이 명확하다.

#### 장점

##### 1. 공통 룰 로직 분리가 적절하다

`DeckManager`와 `calculateRoundScores()`는 각각 카드 흐름과 점수 계산 책임을 분리한다. 특히 점수 계산이 순수 함수에 가까운 형태라 룰 검증과 문서화가 쉽다. 이런 구조는 향후 AI 힌트 추천, 라운드 리플레이, 데모 시나리오 자동화 같은 확장에도 유리하다.

##### 2. 모바일-호스트 역할이 분명하다

호스트는 공개 정보 중심, 모바일은 비공개 정보 중심으로 설계되어 있다. Dixit류 게임에서 가장 중요한 "내 손패는 나만 보고, 전체 보드는 모두가 본다"는 원칙이 잘 구현되어 있다. 모바일의 카드 선택, 투표, 타이머 UI도 흐름에 맞춰 단순하다.

##### 3. 재접속과 타이머 복구 의식이 있다

`_sendRejoinState()`는 현재 페이즈, 라운드, 이야기꾼, 손패, 제출 여부, 투표 여부, 남은 시간까지 복구한다. 대부분의 파티게임 프로토타입이 놓치기 쉬운 부분인데, 이 게임은 적어도 페이즈 복구를 고려한 뼈대가 있다.

##### 4. 호스트 운영 편의성이 좋다

- 카드 전체 갤러리
- 최종 랭킹
- 강퇴 버튼
- 데모 플레이 진입 버튼

운영자 입장에서 "지금 무엇을 설명해야 하는지"가 비교적 명확하다. 카드 자산이 200장까지 확장된 점도 반복 플레이 가치를 높인다.

#### 구조적 약점

##### 1. 호스트 파일이 단일 거대 클래스에 집중되어 있다

현재 `games/dixit/host/main.js`는 상태 관리, 메시지 라우팅, 렌더링, 점수 집계, 타이머, 재접속, 디버그 UI까지 사실상 모두 한 파일에 모아 두고 있다. 기능이 동작하는 동안에는 문제가 덜 드러나지만, 플레이어 이탈 처리나 데모 모드 같은 예외 케이스가 들어오는 순간 상태 간 결합이 높아진다.

이 구조는 다음 문제를 유발하기 쉽다.

- 특정 예외 케이스 수정이 다른 페이즈 렌더링 로직을 건드린다.
- 디버그용 상태와 실제 게임 상태가 한 클래스에 혼재한다.
- 테스트가 함수 단위가 아니라 사람 손 검증에 의존하게 된다.

##### 2. `_broadcastPlayerList()`가 중복 정의되어 준비 상태 동기화가 깨진다

`host/main.js`에는 `_broadcastPlayerList()`가 두 번 정의되어 있다. 앞쪽 정의는 `ready` 필드를 포함하지만, 뒤쪽 정의가 클래스 메서드를 덮어써 실제 런타임에서는 `ready` 정보가 빠진 버전만 사용된다.

이로 인해 모바일 대기 화면에서 의도했던 `준비 완료 배지`가 안정적으로 표시되지 않는다. 더 근본적으로는 준비 상태를 플랫폼 `readyUpdate`와 게임 메시지 `playerReady` 두 경로로 나눠 관리하고 있어, 구조적으로 drift 위험이 있다.

정리하면 현재 로비 흐름은 "전체 준비 인원 수는 맞는데, 개별 플레이어 준비 표시는 틀릴 수 있는 구조"다.

##### 3. 스토리텔러 카드 제출 검증이 불완전하다

`submitCard`는 해당 카드가 실제 손패에 있는지 검증하지만, `submitClue`는 `storyteller`의 손패에 그 카드가 있는지 검증하지 않는다. 악의적 클라이언트나 버그성 입력이 들어오면 다음 문제가 생길 수 있다.

- 스토리텔러가 손패 밖의 카드를 제출할 수 있다.
- 라운드 종료 후 손패 보충 시 원래 손패에서 빠진 카드가 없으므로 카드 수가 늘어날 수 있다.
- 덱과 디스카드 상태가 실제 손패와 어긋날 수 있다.

파티게임이라도 호스트 authoritative 설계라면 최소한의 카드 소유권 검증은 반드시 필요하다.

##### 4. 플레이어 퇴장 시 활성 라운드 정리가 충분히 안전하지 않다

현재 `onPlayerLeave()`는 프로필, 점수, 손패는 지우지만, 이미 제출한 카드나 투표 기록을 상황별로 정리하지 않는다. 그래서 다음과 같은 이상 상태가 생길 수 있다.

- 카드 제출 후 퇴장한 플레이어의 카드가 보드에는 남는데, 결과 화면에서는 소유자가 `익명`으로 보일 수 있다.
- 이야기꾼이 `storytelling` 단계에서 나가면 `_nextRound()`를 바로 호출하는데, 이 함수는 "이번 라운드에서 카드가 이미 사용되었다"는 전제를 갖고 있어 남은 플레이어 손패 보충이 틀어질 수 있다.
- 중간 이탈자가 많은 라운드에서는 점수 계산 대상과 보드 카드 소유 정보가 어긋날 위험이 있다.

즉, "퇴장 이벤트는 받는다" 수준은 달성했지만, "활성 라운드의 상태 일관성을 보장한다" 수준에는 아직 도달하지 못했다.

##### 5. 재접속 복구는 페이즈별로 좋지만 결과 화면 복구는 얕다

`rejoinState`는 대체로 충실하지만, 모바일이 `round-result`나 `final`에 재진입했을 때는 `_showRoundResultScreen(0, ...)`만 호출한다. 다시 들어온 플레이어는 이번 라운드에 왜 몇 점이 났는지, 어떤 카드가 공개됐는지, 어떤 판정(`partial`, `all-correct`, `all-wrong`)이었는지를 개인 화면에서 복원받지 못한다.

공용 화면을 함께 보는 게임이라 치명상은 아니지만, 끊겼다 돌아온 플레이어 입장에서는 맥락 손실이 있다.

##### 6. 데모 시뮬레이터는 존재하지만 QA 도구로는 미완이다

`DixitDemoSimulator`가 별도 파일로 존재하는 것은 장점이다. 다만 현재 구현은 "봇 3명을 내부 상태에 직접 꽂아 넣고 자동 진행하는 attract mode"에 가깝고, "핵심 루프를 검증하는 시뮬레이터"라고 부르기에는 부족하다.

현재 한계는 다음과 같다.

- `game.players`, `_profiles`, `_scores`를 직접 변형한다.
- `sdk._messageHandlers`를 직접 호출하는 내부 침투 방식이라 공개 API 기반 테스트가 아니다.
- 중단 배너나 수동 정지 버튼이 없다.
- 부분 정답, 전원 정답, 전원 오답, 타임아웃, 재접속 같은 케이스를 의도적으로 재현하지 않는다.
- 실제 사용자가 데모 중 입장했을 때의 takeover 절차가 없다.

프로젝트 공통 규칙의 "데모 시뮬레이션 모드 필수"는 형식상 충족했지만, 운영/검증 측면의 완성도는 더 올려야 한다.

##### 7. 문서와 구현 사이에 작은 명세 불일치가 있다

`IMPLEMENTATION_PLAN.md`는 여전히 54장 카드 기준으로 적혀 있고, 실제 자산과 상수는 200장 기준이다. 또한 문서상 구조는 `host/DixitGame.js` 분리를 가정하지만 현재 구현은 `host/main.js` 단일 클래스에 가깝다.

실행 코드는 더 앞서가고 있지만, 팀 협업 관점에서는 문서가 뒤처진 상태다. 이후 개선 작업에서 이 불일치가 새로운 오해를 만들 가능성이 높다.

| 이탈/예외 처리 | 중하 | 활성 라운드 상태 정리가 충분히 방어적이지 않다. |
| 데모 모드 품질 | 중하 | attract mode는 되지만 검증 시뮬레이터 수준은 아니다. |
| 문서 정합성 | 중하 | 카드 수와 파일 구조 설명이 구현과 어긋난다. |

#### 종합 평가

`dixit`은 기획 자체가 강하다. 이 프로젝트 안에서도 "함께 같은 화면을 보고, 각자 다른 해석을 내놓는" 경험을 가장 잘 만들 수 있는 축에 속한다. 카드 200장, 투표 보드, 점수 공개, 모바일 손패 분리까지 기본 토대도 나쁘지 않다.

다만 현재 상태를 냉정하게 보면 "재미있는 베타"이지 "안정형 대표 콘텐츠"는 아니다. 가장 큰 이유는 다음 두 가지다.

- 코어 게임 규칙은 구현되어 있지만, 예외 상태에서의 무결성 보호가 약하다.
- 감정 연출과 온보딩 보조가 부족해 대중적 흥행력은 구현 잠재력만큼 올라오지 못했다.

즉, 이 게임은 버려야 할 프로토타입이 아니라, 우선순위를 정확히 잡고 한 번 더 다듬으면 플랫폼 대표작이 될 수 있는 후보라고 보는 편이 맞다.

## 2. [대중성 강화 요소]

대중성 강화를 위해 가장 먼저 필요한 것은 "카드가 예쁘다"보다 "처음 보는 사람도 바로 웃고, 잘못 눌러도 억울하지 않고, 힌트를 말하는 순간이 멋있다"는 체감이다. 아래 3가지를 우선 제안한다.

### 2.1 힌트 공개와 결과 공개를 강화하는 마이크로 애니메이션 + 사운드 패키지

현재도 카드, 배너, 결과 UI는 갖춰져 있지만 감정 피크가 약하다. Dixit은 룰보다 "이 힌트 뭐야?"라는 순간의 감정이 중요하므로, 공용 화면 연출을 더 강하게 밀어주는 것이 흥행에 직접적이다.

권장안:

- 이야기꾼 힌트 제출 직후 호스트 화면에 짧은 카드 뒤집기 연출과 힌트 reveal 애니메이션 추가
- 투표 시작 시 카드 보드에 순차 등장(staggered reveal) 적용
- 결과 화면에서 스토리텔러 카드 금빛 펄스, 미끼 카드 득표 수 pop-up, 점수 증감 카운트업 적용
- 정답 판정, 전원 정답, 전원 오답, 우승 확정에 서로 다른 짧은 사운드 큐 적용
- 모바일은 강한 연속 진동 대신 `선택`, `제출 성공`, `투표 확정` 정도에 짧은 햅틱만 적용

왜 중요한가:

- 같은 공간의 비참여자도 "지금 중요한 순간"을 즉시 알아차릴 수 있다.
- 이야기꾼의 힌트가 시스템 이벤트가 아니라 공연 장면처럼 느껴진다.
- 카드 공개와 득표 결과가 감정적으로 더 잘 기억되어 재플레이 의지가 올라간다.

### 2.2 초심자 친화형 파티 프리셋과 힌트 부담 완화 장치

초심자는 규칙보다 "어떤 힌트를 내야 하지?"에서 막힌다. Dixit의 매력은 힌트 자유도에 있지만, 첫 판부터 자유도를 너무 크게 주면 오히려 침묵이 길어진다.

권장안:

- 로비에 `패밀리 모드 / 파티 모드 / 자유 모드` 3단 프리셋 추가
- 패밀리 모드에서는 라운드 타이머를 길게, 투표 타이머를 짧게 분리
- 이야기꾼 화면에 "감정", "장면", "한 단어", "짧은 문장" 같은 힌트 형식 예시만 제공
- 첫 1라운드 한정으로 호스트 화면에 아주 짧은 규칙 오버레이 표시
- 모바일 결과 화면에 "좋은 힌트는 전원이 맞히지도, 전원이 틀리지도 않는 힌트입니다" 같은 가이드 카피 삽입

왜 중요한가:

- 첫 판의 침묵 시간을 줄일 수 있다.
- 어린 플레이어와 비보드게이머가 더 빨리 즐거운 실패를 경험한다.
- 자유도를 유지하면서도 "어떻게 놀아야 하는지"에 대한 최소한의 안전 레일을 제공할 수 있다.

### 2.3 조작감 피드백과 개인 맥락 복원 강화

현재 모바일은 기능 수행은 되지만, 조작의 손맛과 개인 피드백이 다소 절제되어 있다. 특히 라운드 결과에서 "내 카드가 몇 표를 먹었는지" 같은 개인 서사가 약하다.

권장안:

- 카드 선택 시 확대/기울기 미세 모션과 즉시 햅틱 제공
- 제출 완료 후 카드 썸네일 고정 및 "이 카드 제출됨" 배지 표시
- 투표 완료 후 내 선택 카드와 내 제출 카드에 대한 명확한 상태 라벨 제공
- 모바일 결과 화면에 `이번 라운드 점수`, `내 카드 득표 수`, `내 카드/내 선택 카드 복기` 추가
- 재접속 시 `연결 복구 중...` 전용 화면을 잠깐 거친 뒤 복구된 상태를 명확히 보여 주기

왜 중요한가:

- 플레이어가 "내 행동이 시스템에 정확히 반영됐다"는 확신을 갖게 된다.
- 공용 화면을 보면서도 개인 화면에서 자신의 서사를 유지할 수 있다.
- 재접속이나 대기 중에도 UX가 덜 끊겨 보인다.

#### 대중성 강화 요소 우선순위 제안

| 우선순위 | 요소 | 이유 |
| --- | --- | --- |
| 1 | 조작감 피드백과 개인 맥락 복원 강화 | 체감 품질과 공정성 인식을 즉시 끌어올린다. |
| 2 | 힌트/결과 연출 + 사운드 패키지 | 관전자 반응과 행사장 주목도를 크게 높인다. |
| 3 | 초심자 친화형 프리셋과 힌트 부담 완화 | 첫 판 이탈률을 줄이고 가족층 확장에 유리하다. |

## 3. [가상 전문가 회의록 (Decision Making Meeting)]

- 회의 목적: `dixit`의 대중성 강화 요소 3건의 적용 타당성을 검토하고, 실제 반영 우선순위와 도입 범위를 결정한다.
- 참석자: `PMOrchestrator`, `GameScout`, `KidsBoardGameExpert`, `OnlineGameProducer`, `UIUXDesigner`, `TechAnalyst`, `SeniorGameDev`
- 전제: 코어 룰은 유지한다. 단, 현재 구조 결함이 UX를 훼손하는 부분은 개선 요소 적용의 선행 조건으로 함께 고려한다.

### 3.1 전문가별 주요 발언

| 참석자 | 핵심 의견 | 판단 |
| --- | --- | --- |
| PMOrchestrator | Dixit의 본질은 "좋은 힌트를 둘러싼 사회적 반응"이다. 따라서 시각 연출은 필요하지만, 그보다 먼저 플레이어가 자신의 제출과 투표가 제대로 반영됐다고 느끼게 해야 한다. | 조작감 피드백 강화 1순위 |
| GameScout | 파티게임은 첫 3분 안에 웃음을 만들어야 한다. 현재 코어는 강하지만 첫 판에서 힌트 부담과 대기감이 있다. reveal 연출과 쉬운 첫 판 프리셋이 있으면 바이럴성이 커진다. | 연출과 온보딩 모두 필요 |

| UIUXDesigner | 모바일 입력은 충분히 단순하지만, 상태 피드백이 얌전하다. 선택 즉시 강조, 제출 후 고정, 재접속 복구 문구, 카드 reveal 리듬이 있으면 완성도가 확 올라간다. | 미세 피드백 개선 강력 찬성 |
| TechAnalyst | 현재는 준비 상태 동기화와 active round 이탈 정리, storyteller 카드 검증 누락 같은 구조 리스크가 있다. 이걸 잡지 않고 연출만 넣으면 화려한 불안정 상태가 된다. | 구조 보강 선행 조건 제시 |
| SeniorGameDev | 기능은 이미 많고, 더 넣기 전에 상태 경계를 정리해야 한다. 특히 DemoSimulator는 직접 내부 상태를 찌르는 방식이라 QA 도구로 약하다. 개선 요소는 `상태 무결성 보강 → UX/연출 추가` 순서가 맞다. | 구현 순서 재정렬 필요 |

### 3.2 핵심 쟁점 토론

#### 쟁점 1. 무엇을 가장 먼저 반영해야 하는가

- `PMOrchestrator`: 사용자는 "내 카드가 제출됐는지", "내 투표가 먹혔는지"를 가장 먼저 체감한다. 이 감각이 흔들리면 어떤 연출도 소용없다.
- `OnlineGameProducer`: 동의한다. 결과 화면의 감정 회수가 약하면 한 판 끝나고도 기억에 덜 남는다.
- `TechAnalyst`: 조작감 피드백 강화는 단순 UX가 아니라 구조 안정성 보강과 묶여야 한다. 지금은 잘못된 카드 제출이나 이탈 시 상태 일관성 문제가 있다.
- 결론: `조작감 피드백 + 상태 무결성 보강 패키지`를 최우선으로 채택한다.

#### 쟁점 2. 연출을 얼마나 강하게 넣을 것인가

- `GameScout`: 파티게임은 한눈에 재밌어 보여야 한다. 힌트 reveal과 결과 공개는 더 드라마틱해져야 한다.
- `UIUXDesigner`: 맞지만 과한 사운드나 번쩍임은 카드 자체의 해석 몰입을 방해할 수 있다. reveal, 득표, 점수 상승 3개 포인트만 확실히 잡는 편이 좋다.
- `KidsBoardGameExpert`: 어린 플레이어에게는 짧고 분명한 효과가 좋지, 계속 번쩍이는 화면은 피로하다.
- 결론: `항상 화려한 UI`가 아니라 `중요 순간만 강조하는 절제된 마이크로 연출`로 반영한다.

#### 쟁점 3. 온보딩을 어디까지 단순화할 것인가

- `KidsBoardGameExpert`: "힌트 예시 형식"은 필요하지만, 카드별 힌트 추천까지 가면 상상력 게임의 본질이 죽는다.
- `SeniorGameDev`: 로비 프리셋, 첫 라운드 규칙 오버레이, 결과 화면 팁 정도면 구현 난이도 대비 효과가 좋다.
- `GameScout`: 첫 판을 쉽게 만드는 것만으로도 회전율이 오른다.
- 결론: `패밀리/파티/자유 모드 프리셋 + 힌트 형식 예시`까지만 반영하고, 카드 의미를 직접 추천하는 기능은 넣지 않는다.

### 3.3 최종 의사결정

#### 의사결정 결과

| 안건 | 결정 | 반영 수준 |
| --- | --- | --- |
| 조작감 피드백과 개인 맥락 복원 강화 | 채택 | 즉시 반영 우선순위 1 |
| 힌트 공개와 결과 공개 마이크로 연출 + 사운드 | 채택 | 구조 보강 후 우선순위 2 |
| 초심자 친화형 파티 프리셋과 힌트 부담 완화 | 부분 채택 | 우선순위 3 |

#### 실행 원칙

1. 상태 무결성 보강 없이는 어떤 연출도 먼저 넣지 않는다.
2. Dixit의 자유 해석 재미를 해치지 않는 범위에서만 온보딩을 추가한다.
3. 모바일은 입력 확신과 개인 복기, 호스트는 관전성과 순간 드라마를 담당하게 분업한다.

#### 회의 최종 한줄 결론

`dixit`은 연출을 더하는 게임이 아니라, 먼저 "내 행동이 정확히 반영되고 있다"는 믿음을 강화한 뒤 그 위에 감정 연출을 쌓아야 가장 대중적으로 강해진다.

## 4. [테스트 결과 및 수정 방향]

본 절의 "테스트 결과"는 실제 실기기 실행 로그가 아니라, 현재 소스 코드를 기준으로 한 정적 분석 판정이다. 따라서 아래 상태는 `PASS`, `RISK`, `FAIL`보다는 `정적 분석상 양호`, `보완 필요`, `구조 리스크` 성격의 판정으로 읽는 것이 정확하다.

### 4.1 전체 동작 검증 시나리오

| 시나리오 | 검증 포인트 | 정적 분석 판정 | 수정 방향 |
| --- | --- | --- | --- |
| 로비 입장 → 닉네임 설정 → 준비 완료 | 프로필 저장, 플레이어 목록 갱신, 준비 표시 | 보완 필요 | 개별 플레이어 `ready` 표시가 `_broadcastPlayerList()` 중복 정의 때문에 깨질 수 있으므로 준비 동기화 구조를 단일화해야 한다. |
| 3인 기본 한 판 진행 | `storytelling → card-selection → voting → round-result` 정상 진행 | 정적 분석상 양호 | 기본 루프는 갖춰져 있다. 이 흐름을 기준 시나리오로 E2E 수동 검증을 먼저 돌리면 된다. |
| 4~8인 확장 플레이 | 손패 장수, 제출/투표 인원 증가, 카드 보드 배치 | 정적 분석상 양호 | 카드 수와 보드 생성은 대응 가능하다. 다만 대인원에서 호스트 보드 연출과 모바일 스크롤 가독성은 별도 시각 QA가 필요하다. |
| 스토리텔러 정상 제출 | 힌트 + 카드 제출, 손패 유지 | 보완 필요 | `submitClue`에도 `submitCard` 수준의 손패 소유 검증을 추가해야 한다. |
| 비-스토리텔러 카드 제출 | 자기 손패 카드만 제출 가능 | 정적 분석상 양호 | 서버 측 손패 포함 여부를 검사하고 있어 기본 가드는 있다. |
| 자기 카드 투표 방지 | 자기 제출 카드에 투표 불가 | 정적 분석상 양호 | 서버에서 `myCard`와 동일한 `cardId`를 차단한다. |
| 존재하지 않는 카드에 대한 투표/제출 변조 | 악성 입력 방어 | 구조 리스크 | 투표 카드가 보드에 존재하는지, 스토리텔러 카드가 손패에 존재하는지 검증을 추가해야 한다. |
| 타임아웃 자동 처리 | 스토리텔러/제출자 미응답 시 게임 정지 방지 | 정적 분석상 양호 | 구조는 좋다. 다만 phase별 시간 분리와 timeout 사유 노출 문구 보강이 필요하다. |
| 플레이어 퇴장(로비) | 목록 정리, 준비 수 갱신 | 정적 분석상 양호 | 로비 상태는 단순하다. 다만 개별 준비 배지 동기화는 위 문제와 함께 정리해야 한다. |
| 플레이어 퇴장(활성 라운드) | 제출/투표/점수 상태 정리 | 구조 리스크 | 이탈한 플레이어의 제출 카드, 투표, 손패 보충, 이야기꾼 교체를 페이즈별로 명시적으로 정리해야 한다. |
| 이야기꾼 퇴장 시 다음 라운드 전환 | 라운드 스킵 안전성 | 구조 리스크 | `_nextRound()`를 그대로 호출하지 말고 `abortRoundAndRotateStoryteller()` 같은 별도 복구 경로를 두는 편이 안전하다. |
| 모바일 재접속(로비) | 닉네임/플레이어 목록/준비 상태 복구 | 보완 필요 | `rejoinState`에 로비 준비 정보와 현재 프리셋 정보까지 포함시키는 편이 좋다. |
| 모바일 재접속(진행 중 페이즈) | 손패, 힌트, 타이머, 제출/투표 여부 복구 | 정적 분석상 양호 | 구조는 있다. 실제 브라우저에서 시간차 재접속 QA만 추가하면 된다. |
| 모바일 재접속(결과 화면) | 개인 점수와 결과 맥락 복구 | 보완 필요 | 개인 delta, 득표 수, 내 제출 카드/내 투표 카드 요약을 재복원하도록 payload를 확장해야 한다. |
| 최종 순위 및 종료 | 30점 도달 또는 덱 소진 종료 | 정적 분석상 양호 | 랭킹 계산은 단순하고 충분하다. 공동 순위 표시는 현재 방식으로도 자연스럽다. |
| 카드 전체 갤러리 | 운영자 온보딩/카드 감상 | 정적 분석상 양호 | lazy build 구조가 적절하다. 단, 처음 열 때 로딩 느낌을 조금 보강하면 더 좋다. |
| 데모 플레이 | 봇 자동 입장, 라운드 자동 진행, 종료 후 복귀 | 보완 필요 | attract mode는 가능하지만, stop UI, deterministic scenario, 상태 스냅샷이 없어 QA 도구로는 부족하다. |

### 4.2 우선 수정해야 할 구조 이슈

#### 1. 로비 준비 상태 동기화 단일화

현재는 `readyUpdate`와 커스텀 `playerReady`가 분리돼 있다. 아래 중 하나로 정리하는 편이 맞다.

- 플랫폼 `readyUpdate`를 기준으로 개별 준비 정보까지 호스트가 관리하도록 확장
- 또는 게임 전용 준비 상태를 완전히 제거하고 플랫폼 ready만 사용

핵심은 "준비 인원 수"와 "누가 준비했는지"가 같은 소스에서 나와야 한다는 점이다.

#### 2. 카드 소유권 및 보드 소속 검증 추가

호스트는 authoritative 상태 머신이므로 아래 검증을 반드시 넣어야 한다.

- `submitClue`: 스토리텔러 손패에 `cardId`가 실제 존재하는지 검사
- `submitVote`: `cardId`가 현재 `boardCards`에 포함되는지 검사
- 필요 시 라운드 ID를 함께 검증해 늦게 도착한 메시지를 버리기

이것만 해도 변조, 지연 메시지, 상태 꼬임 대응력이 크게 올라간다.

#### 3. 활성 라운드 이탈 처리 분기 재설계

플레이어 이탈은 페이즈마다 별도 전략이 필요하다.

- `storytelling`: 이야기꾼 퇴장 시 라운드 abort 후 다음 이야기꾼으로 회전
- `card-selection`: 이탈자의 기존 제출이 있으면 보드 포함 여부를 즉시 정리
- `voting`: 이탈자의 투표/제출/점수 반영 범위를 명확히 결정
- `round-result`: 이미 완료된 라운드는 결과만 유지하고 다음 라운드 인원 기준으로 정리

지금처럼 하나의 `onPlayerLeave()`에서 일부 분기만 처리하면 장기적으로 예외가 누적된다.

#### 4. 결과 화면 rejoin payload 강화

모바일은 공용 화면을 함께 보더라도, 재접속 직후에는 맥락을 잃기 쉽다. 아래 정보를 `roundResult`와 `rejoinState`에 함께 담는 편이 좋다.

- 내 라운드 delta
- 내 제출 카드
- 내 카드 득표 수
- 내가 선택한 카드
- 판정 케이스(`partial`, `all-correct`, `all-wrong`)

이 정보만 있으면 모바일 결과 화면도 훨씬 설득력 있어진다.

### 4.3 🤖 `DixitDemoSimulator.js` 개선점 및 수정 가이드라인

현재 `games/dixit/host/DixitDemoSimulator.js`는 attract mode로서는 출발점이 괜찮다. 하지만 프로젝트 규칙 수준의 "데모 시뮬레이터"가 되려면 아래 기준을 충족하는 것이 바람직하다.

#### 개선점 1. 시작/중단 UI를 정식 기능으로 승격

현재 호스트 로비에는 `🤖 데모 플레이 실행` 버튼만 있고, 명시적인 중단 배너나 정지 버튼이 없다. 다음을 추가하는 편이 좋다.

- 로비 상단 또는 하단에 `데모 진행 중` 고정 배너
- 배너 내부에 `중단`, `다음 시나리오`, `실사용자 입장 허용` 버튼
- 데모 중 실제 플레이어가 들어오면 `데모 종료 후 실제 세션 전환` 또는 `입장 거절`을 명확히 선택

즉, 데모는 일회성 스크립트가 아니라 운영 모드여야 한다.

#### 개선점 2. 내부 상태 직접 변형 대신 상태 스냅샷/복원 구조 도입

현재는 봇을 `game.players`, `_profiles`, `_scores`에 직접 삽입한다. 이 방식은 빠르지만 복구가 취약하다. 다음 구조가 더 안전하다.

- `startDemo()` 직전에 현재 세션 상태 스냅샷 저장
- 봇 플레이어는 별도 `demoPlayers` 컬렉션으로 관리
- `stopDemo()`에서 타이머 해제뿐 아니라 스냅샷 전체 복원
- 실제 세션 플레이어와 데모 봇을 혼합하지 않도록 분리

이렇게 해야 중간 정지, 데모 실패, 실제 사용자 takeover가 안전해진다.

#### 개선점 3. `sdk._messageHandlers` 직접 호출 제거

지금은 `mockMessageFromPlayer()`가 SDK 내부 Map을 직접 찌른다. 이 방식은 리팩터링 내성이 약하고, 공개 API 기반 테스트라고 보기 어렵다.

권장 방향:

- 호스트 클래스에 `handleDemoAction(playerId, action)` 같은 공개 테스트 훅 추가
- 또는 `submitClue`, `submitCard`, `submitVote`에 대응하는 내부 메서드를 명시적으로 분리
- DemoSimulator는 그 공개 메서드만 호출

이렇게 하면 QA용 시뮬레이터와 실제 메시지 처리 로직의 경계를 선명하게 유지할 수 있다.

#### 개선점 4. 랜덤 봇이 아니라 시나리오형 시뮬레이션으로 확장

현재 데모는 랜덤 카드 선택과 랜덤 투표 중심이라, "게임이 돌아간다"는 인상은 주지만 핵심 케이스 검증에는 약하다. 다음 시나리오 세트를 고정적으로 제공하는 편이 좋다.

- `Scenario A`: 일부만 정답
- `Scenario B`: 전원 정답
- `Scenario C`: 전원 오답
- `Scenario D`: 타이머 만료 자동 제출/자동 공개
- `Scenario E`: 중간 재접속/중간 이탈 복구

이 시나리오를 seed 기반으로 재현 가능하게 만들면, 데모가 단순 홍보 기능을 넘어 회귀 검증 도구가 된다.

#### 개선점 5. 로그와 관찰 포인트를 남기는 QA 모드 추가

운영형 데모와 QA형 데모를 분리하는 편이 좋다.

- 운영형 데모: 관객에게 보여 주는 빠른 자동 플레이
- QA형 데모: 콘솔 또는 오버레이에 `phase`, `storyteller`, `submissionCount`, `voteCount`, `scoreDelta`를 표시

특히 QA형 모드에서는 다음 항목이 잘 드러나야 한다.

- 누구 손패에서 어떤 카드가 빠졌는지
- 어떤 판정 케이스가 나왔는지
- 점수 계산 결과가 예상과 일치하는지
- 종료 후 초기 상태가 깨끗하게 복원됐는지

#### 개선점 6. 구현 권장 순서

1. `DemoSimulatorStateSnapshot` 개념 도입
2. 데모 배너와 중단 버튼 추가
3. 공개 테스트 훅 기반으로 호출 구조 교체
4. 랜덤 시나리오를 `scenario presets`로 분리
5. QA용 상태 로그 오버레이 추가

이 순서가 좋은 이유는, 겉보기 연출보다 먼저 "중단해도 안전한 데모"를 만드는 것이 중요하기 때문이다.

### 4.4 최종 수정 방향 요약

가장 현실적인 개선 순서는 다음과 같다.

1. 로비 준비 상태 동기화, 카드 소유권 검증, 활성 라운드 이탈 정리부터 수정한다.
2. 그 다음 모바일 개인 피드백과 결과 맥락 복원을 보강한다.
3. 이후 호스트 reveal 연출, 사운드, 패밀리 프리셋을 추가한다.
4. 마지막으로 `DixitDemoSimulator.js`를 attract mode와 QA mode를 겸하는 운영 도구로 승격한다.

이 순서를 지키면 `dixit`은 "규칙은 좋은데 조금 거친 게임"에서 "처음 보는 사람도 쉽게 빠져드는 플랫폼 대표 파티게임"으로 올라설 가능성이 높다.
