# 패닉 콕핏 (`panic-cockpit`) 평가 및 개선안

- 작성일: 2026-07-07
- 분석 대상: `games/panic-cockpit/host/`, `games/panic-cockpit/mobile/`, `games/panic-cockpit/host/DemoSimulator.js`
- 참고 문서: `docs/meetings/meeting_minutes_rev3.md`, `docs/agents/roles.md`
- 분석 방식: 정적 코드 리뷰 + `npm run build` 검증
- 검증 한계: 실제 다기기 플레이, P2P 직접 연결 로그 확인, 브라우저 시각 QA, Playwright E2E 실행은 이번 문서 범위에 포함하지 않았다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`패닉 콕핏`의 코어 아이디어는 명확하고 플랫폼 적합성이 높다. 각 플레이어는 자신의 모바일에 배치된 레버, 스위치, 버튼을 조작하지만, **수행해야 할 지시문은 다른 사람의 화면에 나타난다.** 따라서 "내가 본 정보를 남에게 외쳐 전달하고, 남은 그 말을 듣고 손을 움직인다"는 구조가 자연스럽게 형성된다. 이 구조는 TV/태블릿의 공용 화면과 개인 모바일을 함께 쓰는 이 프로젝트의 목적과 잘 맞는다.

재미의 중심은 아래 네 가지다.

| 항목 | 분석 |
| --- | --- |
| 실시간 협동 혼선 | 누가 무엇을 해야 하는지가 분리되어 있어, 한 공간에서 소리치고 겹쳐 말하는 혼란 자체가 재미로 작동한다. |
| 역할 분리 | 지시를 읽는 사람과 실제 조작하는 사람이 다르므로, 단순 반사신경 게임보다 사회적 상호작용이 강하다. |
| 짧은 이해 비용 | "남의 화면에 뜬 지시를 말해 주고, 내 화면의 버튼을 눌러라"라는 한 문장으로 설명 가능하다. |
| 공용 화면 관전성 | 호스트는 선체 내구도, 이동 거리, 활성 명령 목록을 동시에 보여 줘서 현재 위기 수준을 즉시 파악하게 한다. |

특히 호스트 쪽 `distance`와 `hullHealth` 구조는 파티 게임답게 목표가 단순하다. 성공하면 앞으로 나아가고, 실패하면 선체가 깎인다. 이 덕분에 처음 보는 사람도 규칙을 빠르게 이해할 수 있다.

다만 현재 구현은 코어 아이디어에 비해 장기 플레이의 변주성과 대중적 쇼맨십이 약하다.

1. 명령 종류가 사실상 `lever`, `switchA`, `switchB`, `btnAction` 네 가지뿐이라 몇 판 지나면 패턴이 빠르게 읽힌다.
2. 성공 보상은 `거리 +25m`, 실패 패널티는 `선체 -15`로 명쾌하지만, 체감 연출은 비교적 얇다.
3. 공용 화면이 보여 주는 우주 비행 연출은 분위기는 좋지만, 플레이어의 정확한 협동 결과와 시각적으로 강하게 결합되지는 않는다.
4. 최소 시작 인원은 2명이지만, 이 게임의 대표 재미는 3~4명이 동시에 말이 꼬일 때 훨씬 강하게 살아난다.

종합하면 `패닉 콕핏`은 **한 공간 협동 소동극**이라는 코어 재미가 분명하다. 문제는 아이디어가 약한 것이 아니라, 현재 구현이 그 아이디어를 실서비스 품질로 끝까지 밀어 올리지 못했다는 점이다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

호스트 구현은 기본 구조만 보면 비교적 준수하다.

- `HostBaseGame`를 상속하고 `setPhase('lobby' | 'playing' | 'result')`로 화면 책임을 분리했다.
- 호스트 CSS는 `.hidden` 규약과 `position: relative; z-index: 10;` 규약을 충족한다.
- 데모 버튼, 결과 화면, 리셋 흐름까지 기본적인 운영 UI는 갖췄다.
- `onPlayerRejoin()`에서 진행 중 명령과 상태(`statusSync`)를 다시 보내려는 시도도 있다.

반면 모바일은 프로젝트 권장 패턴과 거리가 있다.

- `MobileBaseGame`를 상속하지 않고 `MobileSDK`를 직접 붙여 단일 파일에서 모든 DOM 상태를 관리한다.
- `join`, `rejoin`, `allReady` 같은 라이프사이클 이벤트를 거의 활용하지 않고, `connect` 이벤트와 수동 DOM 토글에 많이 의존한다.
- 결과적으로 로비 복귀, 재연결 복구, 저장된 닉네임 자동 복원 같은 경계 상황이 취약하다.

구현 완성도는 아래 표처럼 평가할 수 있다.

| 평가 축 | 판정 | 근거 |
| --- | --- | --- |
| 코어 컨셉 적합성 | 높음 | Host/Mobile 역할 분리가 게임 규칙과 잘 맞는다. |
| 호스트 상태 관리 | 중상 | 페이즈, HUD, 명령 큐, 결과 전환은 단순하고 읽기 쉽다. |
| 모바일 상태 관리 | 보통 이하 | 단일 파일 직접 제어 구조라 재연결과 확장에 약하다. |
| 재접속 복구 | 미흡 | 인게임 일부만 복구하며 로비/리셋 이후 상태 동기화가 비어 있다. |
| 데모 모드 신뢰성 | 취약 | 데모가 실제 플레이 경로를 우회해 결함을 가린다. |
| E2E 테스트 신뢰성 | 취약 | 현재 스펙은 데모 결과 화면만 검증해 실제 모바일 상호작용을 증명하지 못한다. |

현재 코드에서 가장 중요한 리스크는 아래 여섯 가지다.

#### 1. 실제 멀티플레이 코어 루프가 깨져 있을 가능성이 매우 높다

호스트의 `controlAction` 핸들러는 `HostSDK.onMessage()`가 넘겨주는 첫 번째 인자를 `player 객체`가 아니라 `playerId 문자열`처럼 사용하고 있다.

- `HostSDK`는 `handler(player, payload)` 형태로 호출한다.
- 그런데 `panic-cockpit/host/main.js`는 `(playerId, { key, value }) => { ... this._playerWidgets.get(playerId) ... }`처럼 구현돼 있다.
- 따라서 실제 모바일에서 메시지가 오면 `Map` 키 조회가 실패해, 명령 해결 판정이 동작하지 않을 가능성이 높다.

이 이슈는 단순한 코드 스타일 문제가 아니라, **실제 플레이에서 "남이 외친 버튼을 눌러도 성공 처리되지 않을 수 있다"는 치명 결함**이다.

#### 2. 데모 시뮬레이터가 위 치명 결함을 가리고 있다

`PanicCockpitDemoSimulator`는 실제 네트워크 경로를 통하지 않고 `sdk._messageHandlers.get('controlAction')`를 직접 꺼내 호출한다. 더 중요한 점은 이때 첫 번째 인자로 `command.targetPlayerId` 문자열을 넣는다.

즉:

- 실플레이: `player 객체`가 들어와 실패 가능
- 데모: `playerId 문자열`이 들어와 성공

따라서 현재 데모와 데모 기반 E2E는 "시뮬레이터가 잘 도는지"는 보여 주지만, "실제 모바일 조작이 정상 판정되는지"는 증명하지 못한다. 이는 테스트 신뢰성을 크게 떨어뜨린다.

#### 3. 재접속 복구가 진행 중 게임에만 부분적으로 존재한다

호스트의 `onPlayerRejoin()`은 `_gameActive`가 `false`이면 즉시 반환한다. 이 말은 다음 상태에서 복구 패킷이 없다는 뜻이다.

- 로비 대기 중 재접속
- 결과 화면 상태 재접속
- 호스트가 리셋한 뒤 플레이어가 뒤늦게 복귀하는 경우

모바일 쪽도 `rejoin` 이벤트를 따로 처리하지 않는다. 따라서 플레이어가 게임 중 새로고침했다가, 복귀 시점에 이미 로비나 결과로 넘어가 있었다면 예전 화면을 붙든 채 멈춰 있을 가능성이 있다. 프로젝트 규약에서 강조한 "로비 재연결 프리징 가드" 관점에서 완성도가 낮다.

#### 4. 저장된 닉네임 자동 복원 흐름이 취약하다

모바일은 `connect` 시점에 `localStorage`에서 닉네임을 읽고 즉시 `setProfile`을 보낸다. 그런데 `MobileSDK`는 같은 `connect` 이벤트 안에서 `platform:joinSession`보다 먼저 `connect` 커스텀 이벤트를 발행한다. 그 결과:

- 자동 복원 경로에서는 `setProfile`이 세션 정식 입장 전에 먼저 전송될 수 있다.
- 서버는 이 메시지를 호스트로 릴레이하지만, 아직 stable player ID 매핑이 없을 수 있다.
- 호스트는 임시 소켓 기준 이름을 잡아두었다가 실제 입장 후 플레이어 카드와 이름이 엇갈릴 수 있다.

즉, "처음 접속은 되는데 닉네임 표시나 재입장 프로필 복원이 가끔 이상해지는" 류의 운영성 버그가 숨어 있을 가능성이 있다.

#### 5. 모바일 구현은 동작하지만 프로젝트 공통 패턴의 이점을 거의 못 쓰고 있다

현재 모바일은 `MobileBaseGame`를 쓰지 않기 때문에 아래 장점들을 잃고 있다.

- `showScreen()` 기반 화면 전환 일관성
- `onJoin`, `onRejoin`, `onAllReady`, `onReset` 같은 단계별 복구 훅
- 재접속 시 화면 유지/복구 정책 표준화

지금 구조는 파일 규모가 더 커지거나, 튜토리얼/옵션/추가 계기판이 붙는 순간 빠르게 복잡해질 가능성이 높다.

#### 6. 데모 모드의 수명주기 관리가 불완전하다

`PanicCockpitDemoSimulator.stopDemo()`는 봇 목록과 닉네임 맵만 비우고 끝난다. 그러나 다음 정리가 빠져 있다.

- 진행 중 게임 타이머 정지
- `_gameActive` 해제
- `_commands`, `_playerWidgets`, HUD, 페이즈 원상 복구
- 실제 플레이어가 대기 중이던 세션 상태 보존

또한 `startDemo()`는 `game.players`, `sdk._players`, `_playerNicknames`를 직접 갈아치운다. 이 구조는 자동 데모가 켜졌을 때 실제 입장 대기 플레이어를 덮어쓸 위험이 있다.

### 1.3 종합 평가

`패닉 콕핏`은 컨셉 점수는 높고, 호스트 비주얼도 분위기를 잘 잡았다. 하지만 현재 완성도를 냉정하게 평가하면 **"보기에는 거의 완성형인데, 실제 운영과 실플레이 검증 신뢰성은 아직 부족한 상태"**에 가깝다.

| 항목 | 점수(10점 만점) | 코멘트 |
| --- | --- | --- |
| 코어 게임성 | 8.4 | 아이디어가 좋고 같은 공간 협동 구조가 강하다. |
| 첫 판 직관성 | 7.8 | 기본 규칙은 쉽지만, 실제 역할 체감은 튜토리얼 보강이 필요하다. |
| 관전성 | 7.2 | 위기감은 보이나 성공/실패의 쇼맨십은 더 키울 수 있다. |
| Host 구현 완성도 | 7.0 | 상태 루프는 읽기 쉽지만 디테일한 복구가 부족하다. |
| Mobile 구현 완성도 | 5.0 | 기본 동작은 있으나 패턴 일관성과 복구 설계가 약하다. |
| Demo/Test 신뢰성 | 3.5 | 데모가 실제 경로를 우회해 거짓 양성을 만들 수 있다. |
| 상품화 잠재력 | 8.0 | 기반 결함만 정리하면 대중성이 빠르게 올라갈 수 있다. |

한 줄 총평:

> `패닉 콕핏`은 "재미없는 게임"이 아니라, **좋은 코어를 가진 상태에서 실플레이 신뢰성과 연출 패키지가 아직 덜 마무리된 게임**이다.

## 2. [대중성 강화 요소]

대중적으로 더 크게 터뜨리려면 새 규칙을 무리하게 추가하기보다, 현재 코어를 더 명확하고 더 시끄럽고 더 손맛 있게 보여 줘야 한다. 우선순위가 높은 요소는 아래 세 가지다.

### 제안 1. 지시 전달 자체를 쇼타임으로 만드는 마이크로 애니메이션 + 사운드 패키지

지금 `패닉 콕핏`의 대표 장면은 "누군가의 화면에 뜬 지시가 다른 사람의 손을 움직이게 만드는 순간"이다. 그런데 현재는 성공/실패가 기능적으로만 처리되고, 감정 곡선이 충분히 커지지 않는다.

구체 제안:

- 호스트 명령 카드에 `3초 이하` 경고 점멸, 비상 사이렌, 카드 흔들림 추가
- 성공 시 명령 카드가 푸른색으로 수축 사라지고, 실패 시 붉은 파열 효과 후 선체 경고음 출력
- 모바일 지시 패널에 도착 애니메이션, 타이머 막대 진동, 만료 직전 점멸 추가
- 거리 증가나 선체 손상 시 호스트 배경 우주창 연출도 함께 반응
- 라운드 클러치 상황에서는 `COMBO SAVE`, `HULL CRITICAL` 같은 짧은 방송 자막 추가

기대 효과:

- 지금도 있는 "소리치며 협동하는 재미"가 외부에서 보기에도 선명해진다.
- 실패가 단순 수치 감소가 아니라 기억나는 사건이 된다.
- 행사장, 스트리밍, 매장 시연에서 구경꾼이 상황을 더 빨리 읽게 된다.

### 제안 2. 조작자와 전달자 모두에게 돌아가는 양방향 피드백 패키지

현재는 지시를 읽은 사람은 `resolveInstruction` 성공/실패 피드백을 받지만, 실제 손으로 조작한 사람은 대부분 "내가 누른 게 먹혔는지"를 강하게 확인하지 못한다. 반대로 조작자는 자기 기기를 만지는 재미는 있는데, 팀 성공에 기여했다는 즉시 보상이 약하다.

구체 제안:

- 정답 조작 시 지시를 본 플레이어와 실제 조작 플레이어 모두에게 차등 햅틱 제공
- 레버는 `0 / 50 / 100` 디텐트 감각이 느껴지도록 스냅 애니메이션과 짧은 진동 추가
- 스위치/버튼 성공 시 해당 위젯에 `OK` 글로우를 300ms 정도 표시
- 오조작 시 즉시 약한 경고음과 붉은 테두리를 주어 "틀렸다"를 빠르게 알림
- 모바일 하단 HUD에 `거리 +25m`, `선체 -15` 같은 짧은 토스트를 넣어 개인 기여를 가시화

기대 효과:

- 손맛이 올라가고, "누가 방금 구했다"는 감각이 개인 단위로 남는다.
- 말하는 사람과 누르는 사람 사이의 협업 만족도가 더 커진다.
- 초보자도 피드백을 통해 규칙을 몸으로 빨리 학습한다.

### 제안 3. 첫 40초 온보딩 + 명령 세트 레이어링

이 게임은 설명이 긴 편은 아니지만, 첫 판에서 "내 화면에 뜬 건 내가 누르는 게 아니라 남에게 말해야 하는 정보"라는 포인트를 놓치면 재미가 급락한다. 여기에 현재 명령 종류가 제한적이라 반복 플레이 시 단조로움도 빨리 온다.

구체 제안:

- 로비에 `예시 1회성 튜토리얼` 삽입
  - 예: "민수 화면에 '지영의 빨간 스위치 켜기'가 뜬다 -> 민수가 외친다 -> 지영이 누른다"
- 로비에서 `추천 인원 3~4명`을 명시하고 2인 플레이는 보조 모드로 분리 검토
- 1라운드는 활성 명령 수를 적게 두고, 2라운드부터 난이도 상승
- 중반 이후 `연속 버튼 2회`, `5초 내`, `둘 중 하나 먼저` 같은 경량 변주를 추가
- 계기판 이름을 단순 색상/위치 기반에서 세계관형 서브시스템 이름과 병행해 브랜딩 강화

기대 효과:

- 첫 판 이탈률을 줄이고, 룰 이해를 "읽는 설명"이 아니라 "보는 예시"로 바꿀 수 있다.
- 5분 이상 플레이했을 때 반복감이 늦게 온다.
- `Spaceteam`류 실시간 소동 게임의 팬층뿐 아니라 일반 파티게임 이용자에게도 진입 장벽이 낮아진다.

### 3.3 쟁점 토론

#### 쟁점 1. 대중성 강화보다 선행해야 할 기술 수정이 있는가

회의는 만장일치로 "있다"라고 판단했다. 구체적으로는 아래 세 가지가 선행 조건으로 지목됐다.

1. `controlAction` 판정 경로 정상화
2. 로비/리셋 이후 재접속 동기화 보강
3. 데모 시뮬레이터가 실제 판정 경로를 우회하지 않도록 구조 수정

이 셋이 해결되지 않으면, 데모에서만 잘 보이고 실플레이에서 무너지는 상태가 계속될 수 있다.

#### 쟁점 2. 세 가지 대중성 강화 요소 중 무엇을 먼저 적용해야 하는가

논의 결과 우선순위는 `A -> B -> C`였다.

- `A`는 외부 관전 가치와 장면성을 즉시 키운다.
- `B`는 실제 플레이 만족도와 손맛을 키운다.
- `C`는 첫 판 친화성과 장기 반복성을 높이지만, 기반 판정이 안정화된 뒤 붙여야 효과가 가장 크다.

#### 쟁점 3. 2인 플레이를 메인 경험으로 둘 것인가

결론은 "기술적으로 허용하더라도 추천 경험으로 밀지는 않는다"였다.

- 2인은 정보 전달 구조는 성립하지만 소동극 밀도가 약하다.
- `패닉 콕핏`의 대표 장면은 3인 이상에서 더 잘 나온다.
- 따라서 로비에서는 `3~4명 추천`을 전면에 두는 편이 낫다.

### 4.3 🤖 `DemoSimulator.js` 개선점 및 수정 가이드라인

현재 `games/panic-cockpit/host/DemoSimulator.js`는 파일 위치와 목적 자체는 맞지만, 운영 가능한 Attract Mode이자 신뢰 가능한 QA 도구로 쓰기에는 구조가 거칠다. 아래 방향으로 고쳐야 한다.

#### 1. 실플레이와 동일한 판정 경로를 강제해야 한다

지금은 데모가 `sdk._messageHandlers`를 직접 호출해 실제 멀티플레이보다 더 유리한 경로를 사용한다. 이 구조는 반드시 제거해야 한다.

가이드:

- 호스트에 공개 메서드 `handleControlAction(playerId, { key, value })`를 만든다.
- 실제 모바일 메시지 핸들러와 데모는 모두 이 메서드만 호출한다.
- 이 메서드 안에서 위젯 상태 갱신, 명령 매칭, 성공 보상, 새 명령 생성까지 처리한다.

이렇게 해야 데모가 실제 결함을 숨기지 않는다.

#### 2. 데모 시작 전 상태 스냅샷을 저장하고 종료 시 완전 복구해야 한다

현재 `startDemo()`는 봇을 주입하지만, 실제 세션이 비어 있다는 보장이 없고 복구도 불완전하다.

가이드:

1. 데모 시작 전 아래 상태를 스냅샷한다.
   - `players`
   - `sdk._players`
   - `_playerNicknames`
   - 현재 `phase`
   - `_commands`, `_playerWidgets`
   - HUD 값
2. 데모 종료 시 봇, 타이머, 명령, HUD를 모두 정리한다.
3. 스냅샷된 실제 상태를 복원한 뒤 로비를 다시 렌더링한다.

#### 3. `stopDemo()`는 반드시 공통 정리 루틴을 호출해야 한다

지금처럼 `Map`만 비우면 인게임 타이머와 `_gameActive`가 남아 UI가 계속 진행될 수 있다.

가이드:

- `game.cleanupRuntime()` 같은 공통 정리 메서드를 둔다.
- 여기서 `clearInterval(this._gameTimer)`, `clearInterval(this._flightTimer)`, `clearTimeouts()`, `_commands = []`, `_playerWidgets.clear()`, `_gameActive = false`, `_isDemo = false`를 한 번에 정리한다.
- `stopDemo()`, `onReset()`, 실제 플레이어 입장 시 강제 중단 모두 이 메서드를 공유한다.

#### 4. 데모 상태 머신과 호스트 배너를 추가해야 한다

권장 상태:

- `idle`
- `booting`
- `running`
- `stopping`
- `cleanup`

권장 UI:

- 로비 상단 또는 하단에 `데모 진행 중`, `실제 플레이어 입장 시 자동 중단`, `데모 종료 후 로비 복귀` 배너 노출
- 버튼은 `🤖 데모 플레이 실행` / `⏹️ 데모 중지` 토글 외에도 현재 상태 텍스트를 보여 주는 편이 좋다

#### 5. 데모는 "무조건 완주"만 하지 말고, 의도된 실패 장면도 보여줘야 한다

현재 데모는 거의 성공 위주로만 흘러갈 가능성이 높다. 하지만 이 게임의 묘미는 위기, 선체 경고, 막판 구조에도 있다.

가이드:

- 1~2회 정도 의도적 지연을 넣어 선체 손상을 연출한다.
- `hullHealth < 30` 구간을 반드시 한 번 지나가게 해 경고 플래시와 긴박감을 보여 준다.
- 결과는 항상 승리만 보이지 말고, 설정에 따라 실패 엔딩도 재생 가능하게 만든다.

#### 6. 데모는 회귀 테스트 모드와 시연 모드를 분리하는 편이 좋다

권장 모드:

- `showcase`: 사람이 보기 좋은 성공 중심 흐름
- `stress`: 일부러 실패와 중단, 재시작을 반복
- `deterministic`: 고정 seed로 같은 명령 순서를 재생

이렇게 분리하면 데모가 단순 홍보 도구를 넘어, 실제 QA 재현 장치가 된다.

### 4.4 우선 수정 방향

#### P0. 즉시 수정해야 할 항목

1. `controlAction` 핸들러 인자 타입 문제 수정
2. 데모와 실플레이가 같은 판정 메서드를 쓰도록 구조 통합
3. 로비/리셋/결과 단계 재접속 상태 동기화 패킷 추가
4. `stopDemo()` 공통 정리 루틴 도입
5. 저장 닉네임 자동 복원 시점을 `joined` 이후로 조정

#### P1. 체감 품질을 크게 올리는 항목

1. 지시 도착/성공/실패 마이크로 애니메이션
2. 조작자/전달자 양방향 햅틱과 토스트 피드백
3. 선체 위기 구간의 사운드와 배경 연출 강화

#### P2. 상품성 확장 항목

1. 추천 인원 정책 재정의
2. 튜토리얼 라운드 추가
3. 중반 이후 명령 세트 변주 및 세계관 브랜딩 강화

## 결론

`패닉 콕핏`은 아이디어와 분위기만 놓고 보면 라인업 안에서 충분히 눈에 띄는 게임이다. 그러나 현재는 **데모가 잘 보이는 것과 실제 멀티플레이가 신뢰 가능하게 작동하는 것이 분리되어 있는 상태**다.

따라서 가장 올바른 개선 순서는 다음과 같다.

1. 실플레이 판정과 재접속, 데모 경로를 바로잡는다.
2. 지시 전달의 장면성과 조작 피드백을 강화한다.
3. 첫 판 온보딩과 중반 변주를 더해 대중성과 반복성을 키운다.

이 순서를 따르면 `패닉 콕핏`은 "아이디어가 좋은 프로토타입"에서 **현장 반응이 나는 협동 파티 게임**으로 올라설 가능성이 크다.
