# Dobble(`dobble`) 게임 평가 및 개선안

- 작성일: 2026-07-06
- 분석 범위: `games/dobble/host/DobbleGame.js`, `games/dobble/host/DobbleDemoSimulator.js`, `games/dobble/host/index.html`, `games/dobble/host/style.css`, `games/dobble/mobile/DobbleMobile.js`, `games/dobble/mobile/index.html`, `games/dobble/mobile/style.css`, `games/dobble/shared/DobbleEngine.js`
- 분석 방식: 소스 코드 정적 분석 기반 평가. 실제 다기기 실기기 QA와 브라우저 시각 검증은 이번 문서 범위에 포함하지 않았다.
- 추가 확인: `DobbleEngine.generateDeck()`는 로컬 스크립트로 검증했으며, 현재 구현은 `57장`, `카드당 8심볼`, `모든 카드 쌍이 정확히 1개의 공통 심볼을 가짐` 조건을 만족한다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`dobble`의 코어 루프는 매우 강하다.

1. 호스트는 공용 화면에 중앙 카드와 전체 점수판을 띄운다.
2. 각 플레이어는 모바일에서 자신의 카드만 본다.
3. 중앙 카드와 자신의 카드에서 공통 심볼 하나를 찾은 뒤 모바일에서 탭한다.
4. 정답이면 내 카드가 새 중앙 카드가 되고, 나는 새 카드를 받으며 1점을 얻는다.
5. 오답이면 3초 패널티가 걸리고, 먼저 목표 점수에 도달한 플레이어가 승리한다.

이 설계는 "같은 화면을 함께 바라보는 멀티플레이"에 잘 맞는다. 호스트는 전체 흐름과 경쟁 구도를 보여 주고, 모바일은 개인 입력 장치로만 사용되기 때문에 TV/태블릿 + 개인 폰 조합의 장점이 분명하다.

특히 다음 요소는 분명한 강점이다.

- 설명이 짧다. "가운데와 내 카드에서 같은 그림을 찾아 먼저 누른다" 한 문장으로 이해된다.
- 판단 주기가 짧다. 매 턴이 1~3초 안에 끝나므로 템포가 늘어지지 않는다.
- 공용 화면 적합성이 높다. 중앙 카드와 점수 카드만 봐도 지금 누가 앞서는지 바로 이해된다.
- 실력 차가 즉시 드러난다. 관찰력, 반응속도, 긴장 관리가 그대로 결과에 반영된다.
- 모드 확장성이 좋다. 단순 그림 모드뿐 아니라 한자, 히라가나, 가타카나 모드를 지원해 "가족 파티 게임"과 "학습형 두뇌 게임" 사이를 오갈 수 있다.

현재 구현은 오리지널 Dobble의 핵심 재미를 모바일 환경에 꽤 잘 옮겼다. 특히 "정답자가 가진 카드가 곧 새 중앙 카드가 된다"는 규칙은 템포를 좋게 만든다. 정답 순간 다음 라운드가 자동으로 시작되기 때문에 턴 대기감이 거의 없고, 호스트 화면에서 연속 득점 흐름이 자연스럽게 이어진다.

다만 대중성 관점에서는 몇 가지 마찰이 있다.

- 텍스트 모드의 진입장벽이 생각보다 높다. 그림 모드는 직관적이지만 한자/일본어 모드는 초심자에게 즉시 긴장을 만든다.
- 오답 패널티 3초는 경쟁성을 높이지만, 캐주얼 파티 환경에서는 다소 가혹하게 느껴질 수 있다.
- 현재는 "정답", "오답"은 분명하지만 "조금 늦었다", "누가 먼저 먹었다", "왜 점수가 안 올랐는지" 같은 경계 피드백은 약하다.

#### 재미 요소 평가 요약

| 평가 항목 | 판단 | 코멘트 |
| --- | --- | --- |
| 즉시 이해도 | 높음 | 그림 모드는 30초 이내 설명이 가능하다. |
| 공용 화면 적합성 | 매우 높음 | 중앙 카드와 점수판만으로 관전이 성립한다. |
| 반응성 기반 재미 | 높음 | 관찰력과 속도가 즉시 점수로 바뀐다. |
| 재플레이성 | 중상 | 카드 조합이 계속 바뀌고 템포가 빨라 반복 플레이가 가능하다. |
| 학습 모드 확장성 | 높음 | 한자/가나 모드는 차별화 포인트다. |
| 초심자 친화성 | 중상 | 그림 모드는 쉬우나 텍스트 모드는 난도가 갑자기 오른다. |
| 피드백 밀도 | 중상 | 정오답 피드백은 있으나 선점 실패/근소한 차이 피드백은 약하다. |

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

구조 자체는 이 프로젝트의 권장 패턴을 상당히 잘 따른다.

- 호스트는 `HostBaseGame`을 상속해 `lobby`, `playing`, `result` 페이즈를 분리한다.
- 모바일은 `MobileBaseGame`을 상속해 `setup`, `waiting`, `game`, `result` 화면을 분리한다.
- 공통 수학 로직과 심볼 데이터는 `shared/DobbleEngine.js`에 모여 있어 Host/Mobile 간 룰 불일치 위험이 작다.
- 재접속은 stable player ID 기반으로 처리되며, 플레이 중 재합류를 위한 `rejoinState` 복구도 구현돼 있다.

프로토타입 완성도는 나쁘지 않다. 구현 상태를 항목별로 보면 다음과 같다.

#### 장점

##### 1. Shared Engine의 역할 분리가 깔끔하다

`DobbleEngine.js`가 덱 생성, 심볼 인덱스, 텍스트 모드 데이터를 한곳에서 관리한다. 이 구조 덕분에 규칙의 핵심인 "모든 카드 쌍은 공통 심볼 1개" 조건이 클라이언트마다 어긋날 여지가 적다.

이 부분은 단순한 데이터 보관이 아니라 게임 무결성의 중심 축이다. 정적 검증 결과도 양호하다.

##### 2. 호스트는 관전 중심 UI를 잘 잡았다

- 점수 카드 스트립
- 중앙 카드
- 정답자 플래시 배너
- 결과 랭킹 오버레이

이 네 요소만으로도 TV 화면 역할이 분명하다. 특히 `round-flash`와 점수 카드 pulse는 "누가 먹었는지"를 멀리서도 알아보기 쉽게 해 준다.

##### 3. 모바일은 한 손 조작에 맞춰 단순화돼 있다

- 닉네임 입력
- 대기
- 카드 탭
- 결과

흐름이 짧고, 점수와 패널티를 상단에 고정해 시선 이동을 줄였다. `safe-area`를 고려한 레이아웃도 들어가 있어 최신 모바일 브라우저 대응 의식이 있다.

##### 4. 재접속과 세션 리셋을 최소한의 수준으로는 챙겼다

플레이 중 재접속 시 개인 카드, 점수, 패널티 상태를 복구하는 것은 분명한 장점이다. 단순 프로토타입에서 자주 빠지는 부분인데, 이 게임은 그 지점까지 구현돼 있다.

#### 구조적 약점

##### 1. 입력 무결성에 치명적 취약점이 있다

현재 가장 큰 문제는 "정답 직후 연속 탭 악용 가능성"이다.

호스트 로직은 정답이 나오면 아래 순서로 상태를 바꾼다.

1. 플레이어 점수를 올린다.
2. 플레이어의 기존 카드를 새 중앙 카드로 바꾼다.
3. 플레이어에게 새 카드를 보낸다.

문제는 모바일이 정답 후 `300ms` 동안 기존 카드 DOM을 그대로 보여 준다는 점이다. 이 시간 동안 플레이어는 이전 카드 화면을 다시 탭할 수 있고, 서버는 `symbolIndex`가 현재 중앙 카드에 포함되는지만 확인할 뿐 "그 심볼이 지금 이 플레이어의 최신 개인 카드에 실제로 존재하는가"를 검증하지 않는다.

결과적으로 아주 빠른 더블탭만으로 추가 득점을 노릴 수 있다. 이는 단순 UX 문제가 아니라 게임 공정성을 깨는 핵심 버그다.

이 이슈는 출시 전 반드시 수정해야 한다.

##### 2. 재접속 복구는 플레이 중에는 좋지만 로비 동기화는 약하다

플레이 중 재접속은 `rejoinState`로 복구하지만, 로비 상태에서는 별도 `lobbyState` 동기화가 없다.

현재 구조에서도 모바일은 `onRejoin()` 시 프로필을 다시 보내고 `waiting` 화면으로 돌아가므로 완전히 멈추지는 않는다. 하지만 다음 정보는 명확히 복원되지 않는다.

- 내가 이미 준비 완료 상태였는지
- 현재 방 인원과 닉네임 목록
- 호스트가 선택한 모드와 목표 점수

즉, "끊기지 않는 게임 경험"보다는 "다시 들어오면 대충 이어지는 경험"에 가깝다.

##### 3. 결과 화면의 재시작 경로가 일관되지 않다

모바일은 `requestRematch`를 통해 호스트 `resetSession()` 흐름으로 복귀한다. 반면 호스트 결과 화면의 `다시하기` 버튼은 `location.reload()`를 사용한다.

이 차이는 운영 UX를 흐리게 만든다.

- 어떤 버튼은 세션 리셋이다.
- 어떤 버튼은 페이지 새로고침이다.

멀티플레이 게임에서는 리매치 경로가 하나여야 상태 관리가 단순해지고 예외가 줄어든다.

##### 4. DemoSimulator는 존재하지만 QA 도구 수준으로는 미완이다

`DobbleDemoSimulator.js`가 있다는 점 자체는 좋다. 하지만 현재 구현은 "봇 3명을 내부 Map에 직접 삽입하고 자동 플레이를 돌리는 연출"에 가깝다.

문제는 다음과 같다.

- 실제 세션 계층을 거치지 않고 `game.players`, `_profiles`, `_scores`를 직접 조작한다.
- 중단 배너나 수동 종료 버튼이 없다.
- 실제 플레이어 입장 시 데모에서 자연스럽게 넘겨주는 절차가 없다.
- 정답 시나리오만 강하게 재현하고, 오답/패널티/재접속/리매치 검증에는 약하다.

즉, Attract Mode는 있으나 "게임의 핵심 루프를 검증하는 시뮬레이터"라고 보기는 어렵다.

##### 5. 호스트 레이어링 규칙 준수에 빈틈이 있다

프로젝트 공통 규칙상 호스트 메인 컨테이너는 배경 felt 레이어 뒤로 숨지 않도록 `position: relative; z-index: 10;`이 필요하다. 하지만 현재 `#game-board`에는 해당 보강이 없다.

공통 `src/style.css`에서 `body.host-board::before`, `::after`가 `z-index: 0`, `1`을 차지하고 있기 때문에, 지금 당장은 우연히 문제없더라도 다른 스타일 변경 시 시각 버그가 발생할 여지가 있다.

#### 아키텍처 평가 요약

| 평가 축 | 판단 | 코멘트 |
| --- | --- | --- |
| BaseGame 패턴 준수 | 높음 | Host/Mobile 책임 분리가 깔끔하다. |
| 공통 룰 엔진 구성 | 높음 | 수학적 무결성과 데이터 중앙화가 좋다. |
| 관전형 호스트 UX | 높음 | 중앙 카드, 점수판, 플래시 연출이 명확하다. |
| 모바일 조작 단순성 | 높음 | 카드 탭 중심이라 진입이 쉽다. |
| 입력 공정성 | 낮음 | 정답 직후 연속 탭 악용 가능성이 치명적이다. |
| 재접속 완성도 | 중상 | 플레이 중 복구는 좋지만 로비 복구가 얕다. |
| 리셋/리매치 일관성 | 중 | 경로가 이원화돼 있다. |
| 데모 모드 완성도 | 중하 | 연출은 되지만 QA 시뮬레이터 수준은 아니다. |

#### 종합 평가

`dobble`은 기획력과 순간 재미는 강하다. 구조도 프로젝트 표준에 비교적 잘 올라가 있다. 다만 현재 상태를 "상용화 직전 완성도"로 보기에는 어렵다.

핵심 이유는 두 가지다.

- 첫째, 입력 무결성 취약점이 게임 공정성을 직접 훼손한다.
- 둘째, 데모 모드와 리매치/재접속 운영 UX가 행사장 운영 기준으로는 아직 거칠다.

따라서 이 게임은 "재미있는 프로토타입" 단계는 통과했지만, "많은 사람 앞에서 반복 시연 가능한 안정형 콘텐츠"가 되려면 한 번 더 다듬어야 한다.

## 2. [대중성 강화 요소]

대중성 강화를 위해 가장 먼저 필요한 것은 단순한 화려함이 아니라 "누가 해도 잘 이해되고, 누가 봐도 재미있고, 져도 억울하지 않은 상태"를 만드는 것이다. 아래 3가지를 우선 제안한다.

### 2.1 입력 무결성 + 선점 실패 피드백 패키지

현재는 정답/오답만 있고, 선점 실패나 늦은 입력에 대한 설명이 약하다. 여기에 입력 취약점까지 겹쳐 있어 체감 공정성이 떨어질 수 있다.

권장안:

- 모바일에서 탭 즉시 카드 입력을 잠시 잠근다.
- 서버는 `tapSymbol` 처리 시 `roundId` 또는 `cardVersion`을 함께 검증한다.
- 서버는 "현재 중앙 카드 포함 여부"뿐 아니라 "현재 플레이어의 최신 카드에도 존재하는 심볼인지"를 함께 검증한다.
- 늦게 눌렀을 때는 무시하지 말고 `tooLate` 같은 피드백을 준다.
- 정답 후 새 카드 반영을 지연시키지 말고 즉시 렌더하거나, 지연이 필요하면 카드 전체를 잠금 오버레이로 가린다.

왜 중요한가:

- 게임 공정성을 회복한다.
- 플레이어가 "버그 때문에 졌다"는 인상을 받지 않는다.
- 입력 감각이 또렷해져 반응속도 게임의 손맛이 살아난다.

### 2.2 공용 화면 중심의 마이크로 연출 + 사운드 강화

Dobble은 플레이어만 재밌어서는 부족하다. 같은 공간에 있는 사람이 함께 웃어야 흥행한다.

권장안:

- 라운드 시작 시 짧은 카운트다운 또는 "준비" 플래시 추가
- 정답 순간 중앙 카드 주변 링 이펙트, 점수 카드 리드 전환 하이라이트 추가
- 연속 득점 시 작은 콤보 배지나 "2연속" 같은 텍스트 연출 추가
- 정답, 오답, 승리, 패널티 해제에 짧은 사운드 큐 적용
- 모바일에는 강한 진동보다 짧고 명확한 햅틱 패턴을 분리 적용

왜 중요한가:

- TV 화면만 봐도 누가 잘하고 있는지 더 쉽게 읽힌다.
- 플레이어 주변 사람도 반응 포인트를 함께 공유할 수 있다.
- 같은 룰이라도 체감 몰입도와 행사장 주목도가 크게 올라간다.

### 2.3 대중형 기본 프리셋 + 온보딩 단순화

지금의 모드 구성은 장점이지만, 처음 만나는 사람에게는 선택지가 많아 보일 수 있다. 흥행형 콘텐츠는 처음 1분이 가장 중요하다.

권장안:

- 기본 프리셋을 `그림 모드 + 5점 + 짧은 경기`로 고정한다.
- 한자/히라가나/가타카나는 "학습 모드" 또는 "고급 모드"로 한 단계 뒤로 뺀다.
- 모바일 첫 화면이나 대기 화면에 "공통 심볼은 항상 1개"라는 튜토리얼을 시각적으로 보여 준다.
- 첫 라운드만 패널티를 약하게 하거나 비활성화하는 입문 규칙을 고려한다.
- 호스트 로비에서 현재 모드의 난이도를 짧은 한 줄로 설명한다.

왜 중요한가:

- 초심자 이탈을 줄인다.
- 학습형 확장 모드의 장점은 살리되, 기본 진입 경험은 더 가볍게 만든다.
- 가족/행사장/카페 시연처럼 다양한 현장에서 실패율이 낮아진다.

### 쟁점 토론

#### 쟁점 1. 연출보다 공정성 수정을 먼저 할 것인가

회의 결과, 전원 합의에 가깝게 "예"로 정리됐다.

이유는 명확하다.

- Dobble은 반응속도 경쟁 게임이다.
- 반응속도 경쟁 게임은 입력 신뢰가 무너지면 전체 재미가 무너진다.
- 지금의 연속 탭 취약점은 단순한 밸런스 조정 수준이 아니라 승부 결과를 왜곡할 수 있다.

따라서 `2.1 입력 무결성 + 선점 실패 피드백 패키지`는 선택이 아니라 필수 보수 항목으로 결정됐다.

#### 쟁점 2. 사운드와 마이크로 연출은 1차 릴리즈에 넣을 가치가 있는가

회의 결론은 "예, 다만 범위를 제한해서"였다.

권장 범위는 아래와 같다.

- 정답
- 오답
- 승리
- 리드 전환

즉, 무거운 사운드 시스템보다는 짧고 명확한 큐 위주로 넣는 것이 맞다는 판단이다.

#### 쟁점 3. 고급 모드를 뒤로 미루면 게임 개성이 약해지지 않는가

결론은 "아니다"였다.

한자/가나 모드는 이 게임의 차별화 포인트이지만, 그것이 첫 진입 화면에서 전면에 나와야 할 필요는 없다. 오히려 기본 진입은 그림 모드로 단순하게 만들고, 재플레이를 유도하는 확장 옵션으로 배치하는 편이 대중성 측면에서 유리하다는 합의가 나왔다.

### 최종 의사결정

1. `입력 무결성 + 선점 실패 피드백 패키지`는 즉시 반영한다.
2. `대중형 기본 프리셋 + 온보딩 단순화`는 1차 대중화 개선안으로 함께 반영한다.
3. `공용 화면 중심의 마이크로 연출 + 사운드 강화`는 위 두 항목 다음 순위로 반영하되, 짧고 가벼운 큐부터 도입한다.
4. 별도 품질 과제로 `DobbleDemoSimulator` 구조 개선과 리매치/재접속 UX 통합을 병행한다.

즉, 회의체의 최종 판단은 "연출 강화도 필요하지만, 현재 Dobble의 가장 큰 흥행 리스크는 공정성과 운영 완성도"라는 것이다.

### 4.3 전체 동작 검증 시나리오

아래 시나리오는 최종 수동 QA 기준으로 권장한다.

#### 시나리오 A. 기본 로비 진입 및 경기 시작

1. 호스트에서 세션 생성 후 QR과 방 코드가 노출되는지 확인한다.
2. 모바일 2대 이상이 입장하고 닉네임을 설정하는지 확인한다.
3. 플레이어 목록과 닉네임이 호스트/모바일 모두에서 갱신되는지 본다.
4. 모든 플레이어가 준비 후 호스트 시작 버튼이 활성화되는지 확인한다.
5. 선택한 모드와 목표 점수로 실제 게임이 시작되는지 검증한다.

예상 결과:

- 호스트는 `playing` 페이즈로 진입한다.
- 각 모바일은 `game` 화면으로 전환된다.
- 각 플레이어는 서로 다른 개인 카드를 받는다.

#### 시나리오 B. 정답/오답/패널티 루프

1. 한 플레이어가 올바른 공통 심볼을 탭한다.
2. 점수 증가, 중앙 카드 교체, 새 개인 카드 수령이 즉시 일어나는지 확인한다.
3. 다른 플레이어가 틀린 심볼을 탭한다.
4. 3초 패널티와 해제가 정상적으로 동작하는지 확인한다.

중점 관찰 포인트:

- 정답자의 점수 카드가 즉시 반응하는가
- 오답자의 카드가 실제로 입력 불가 상태가 되는가
- 패널티 해제 후 다시 바로 입력 가능한가

#### 시나리오 C. 정답 직후 연속 탭 악용 방지

이 시나리오는 반드시 별도로 검증해야 한다.

1. 플레이어가 정답을 맞힌 직후 같은 자리를 빠르게 두 번 이상 연속 탭한다.
2. 새 카드가 화면에 완전히 렌더되기 전 추가 입력이 들어가는지 본다.
3. 점수가 부당하게 2점 이상 연속 상승하는지 체크한다.

현재 코드 기준 예상 결과:

- 실패 가능성이 높다.
- 수정 전에는 실제 악용이 재현될 가능성이 있다.

#### 시나리오 D. 재접속 복구

1. 대기 화면에서 모바일 새로고침 후 재접속한다.
2. 플레이 중 모바일 새로고침 후 재접속한다.
3. 결과 화면에서 새로고침 후 재접속한다.

중점 관찰 포인트:

- 로비에서 준비 상태가 올바르게 복구되는가
- 플레이 중 내 카드와 점수가 유지되는가
- 결과 화면에서 랭킹이 다시 보이는가

#### 시나리오 E. 리매치 및 세션 초기화

1. 경기 종료 후 모바일의 `다시하기`를 누른다.
2. 호스트 결과 화면의 `다시하기`도 눌러 본다.
3. 두 경로가 동일한 세션 초기화 경험을 만드는지 비교한다.

현재 코드 기준 예상 결과:

- 모바일 경로는 비교적 안정적일 가능성이 높다.
- 호스트 결과 버튼은 전체 새로고침이라 체감과 상태 복구가 다를 수 있다.

### 4.4 우선 수정 방향

#### 1. 입력 검증 모델 강화

가장 먼저 필요한 수정이다.

권장 가이드:

- `cardVersion` 또는 `roundId`를 도입한다.
- `cardDealt`, `centerCardUpdated`, `tapResult`에 현재 버전을 포함한다.
- 모바일은 탭 시 `symbolIndex`와 `cardVersion`을 함께 보낸다.
- 호스트는 아래 두 조건을 모두 만족해야만 정답 처리한다.
  - 탭된 버전이 현재 플레이어의 최신 카드 버전과 일치할 것
  - 탭된 심볼이 현재 중앙 카드와 현재 플레이어 카드 모두에 존재할 것
- 모바일은 응답이 올 때까지 카드 입력을 잠시 잠근다.

이 수정이 들어가면 공정성 문제와 손맛 문제를 동시에 해결할 수 있다.

#### 2. 로비 재접속 상태 동기화 추가

권장 가이드:

- 호스트는 로비 단계 재접속 시 `lobbyState`를 보내도록 확장한다.
- `lobbyState`에는 최소 아래 정보를 포함한다.
  - 현재 플레이어 목록
  - ready 인원
  - 내 ready 상태
  - 선택된 모드
  - 목표 점수
- 모바일은 `onRejoin()` 직후 임시 복구 화면 또는 `waiting` 화면에서 해당 데이터를 적용한다.

이렇게 해야 "다시 접속했더니 왜 준비 버튼이 살아 있지?" 같은 혼선을 줄일 수 있다.

#### 3. 리매치 경로 단일화

권장 가이드:

- 호스트 결과 화면의 `다시하기`도 `resetSession()` 기반으로 바꾼다.
- 새로고침 기반 초기화는 디버그 상황이 아니면 제거한다.
- 모든 리매치가 동일한 세션 초기화 함수를 타도록 통일한다.

멀티플레이에서는 이 일관성이 매우 중요하다.

#### 4. 호스트 메인 컨테이너 레이어 보강

권장 가이드:

- `games/dobble/host/style.css`의 `#game-board`에 `position: relative; z-index: 10;`을 명시한다.
- 향후 호스트 내부 컴포넌트가 추가되더라도 felt 배경 pseudo element 뒤로 밀리지 않도록 기준 레이어를 고정한다.

이 수정은 작지만, 공용 화면 게임에서는 예상치 못한 투명화/가림 버그를 예방하는 데 효과적이다.

### 4.5 🤖 DemoSimulator.js 개선점 및 수정 가이드라인

현재 `games/dobble/host/DobbleDemoSimulator.js`는 존재 가치가 분명하지만, 프로젝트 규약상 요구되는 "검증 가능한 데모 시뮬레이션 모드"로 보강이 필요하다.

#### 핵심 개선점

1. 중단 가능한 데모 UX가 필요하다.
2. 실제 세션과 분리된 봇 상태 계층이 필요하다.
3. 정답만이 아니라 오답, 패널티, 종료, 복귀까지 검증할 수 있어야 한다.
4. 데모 종료 시 원상태 복구가 확실해야 한다.

#### 구체 수정 가이드

##### 1. 시작/중단 상태를 명시적으로 관리한다

- `idle`
- `preparing`
- `running`
- `stopping`

같은 내부 상태를 두고, 외부에서 `isDemoActive()`로 조회 가능하게 만든다.

##### 2. 호스트 화면에 중단 배너를 추가한다

현재는 QR 블러 오버레이만 있을 뿐, 사용자가 데모를 중단할 공식 경로가 없다.

권장안:

- 상단 또는 로비 영역에 `데모 플레이 진행 중` 배너 추가
- `중단` 버튼 제공
- 배너에 현재 봇 수, 현재 라운드, 남은 목표 점수 등 간단한 상태 표시

##### 3. 실제 게임 상태와 데모 상태를 분리한다

지금처럼 `game.players`, `_profiles`, `_scores`를 직접 만지는 방식은 유지보수 리스크가 크다.

권장안:

- `attachDemoPlayers()` / `detachDemoPlayers()` 같은 전용 helper를 `DobbleGame`에 추가
- 데모용 플레이어 레지스트리를 별도로 보유
- 실제 세션 플레이어가 들어오면 데모를 우선 정지하고 안전하게 로비로 복귀

##### 4. 시나리오 기반 시뮬레이션으로 확장한다

최소 아래 장면은 데모가 재현할 수 있어야 한다.

- 봇 입장
- 준비 완료
- 게임 시작
- 정답 득점
- 오답 패널티
- 승리 연출
- 리셋 후 로비 복귀

이렇게 해야 데모가 단순 전시가 아니라 QA 도구 역할도 할 수 있다.

##### 5. 결정론적 모드를 지원한다

지금처럼 완전 랜덤 지연만 사용하면 재현성이 떨어진다.

권장안:

- 고정 시드 덱
- 고정 반응 지연 프리셋
- "항상 3라운드 후 종료" 같은 deterministic script 모드

이 기능은 시각 검증과 회귀 테스트에 유리하다.

##### 6. 종료 시 원상 복구를 `resetSession()` 또는 전용 cleanup으로 통일한다

데모 종료는 아래를 반드시 보장해야 한다.

- 모든 bot timer 제거
- QR 블러/오버레이 제거
- 데모 전용 플레이어/점수/프로필 제거
- 호스트 페이즈를 `lobby`로 복귀
- 실제 접속 플레이어가 있다면 그 상태 기준으로 로비 다시 렌더

현재처럼 일부 DOM과 타이머만 치우는 수준으로는 운영 신뢰가 부족하다.

#### DemoSimulator 개선 우선순위

| 우선순위 | 항목 | 이유 |
| --- | --- | --- |
| 1 | 중단 배너 + 중단 버튼 | 운영자가 데모를 제어할 수 있어야 한다. |
| 2 | 상태 cleanup 일원화 | 데모 후 실제 플레이 전환 안정성을 확보해야 한다. |
| 3 | 데모 플레이어 계층 분리 | 내부 구현 결합도를 낮춰야 한다. |
| 4 | 오답/패널티/리매치 시나리오 추가 | QA 도구 가치가 커진다. |
| 5 | 결정론적 시뮬레이션 | 회귀 테스트와 재현성 확보에 유리하다. |

## 결론

`dobble`은 플랫폼 적합성과 순간 재미가 모두 강한 편이다. 특히 공용 화면 관전성, 짧은 의사결정 루프, 학습형 확장 모드는 충분히 경쟁력이 있다.

하지만 지금의 최우선 과제는 더 화려한 연출이 아니다. 먼저 입력 공정성, 재접속/리매치 일관성, 데모 시뮬레이터 복구 안정성을 바로잡아야 한다. 이 세 가지가 정리되면, 그 다음의 마이크로 애니메이션과 사운드 보강은 높은 확률로 대중성 상승으로 연결될 것이다.
