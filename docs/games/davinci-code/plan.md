# 다빈치 코드 (Da Vinci Code) 기획 및 개발 규약 문서

원작 보드게임 Da Vinci Code(= Coda / 일본 Algo 계열, 국내 정식 발매판 룰 기준)를 Connect Dise 플랫폼(TV/PC 호스트 보드 + 스마트폰 컨트롤러, Socket.IO)에 충실하게 이식하기 위한 설계 문서. 구현 담당 엔지니어가 이 문서만으로 개발 가능한 수준을 목표로 함.

루미큐브(`docs/games/rummikub/plan.md`)와 동일한 문서 체계를 따르며, 다빈치 코드 고유의 핵심 차이는 **"공용 보드가 없고, 비공개 정보(각자 타일의 숫자)가 게임의 전부"**라는 점임. 따라서 이 문서는 정보 가시성(누가 무엇을 볼 수 있는가)을 별도 절(§9)로 승격해 프로토콜 전반을 그 기준으로 설계함.

## 0. 이 문서에서 확정한 결정 사항 (요약)

| # | 항목 | 결정 | 근거 요약 |
|---|------|------|-----------|
| D1 | 인원수 | **minPlayers: 2, maxPlayers: 4** | 원작 공식 인원이 2~4인. 5인 이상 공식 사양이 존재하지 않고(루미큐브 XP 같은 공식 확장 없음), 24장 타일로 5인을 지원하려면 시작 장수 축소 등 순수 창작 변형이 필요해 "원작 왜곡 없음" 목표와 충돌. 폰 화면의 4방향 좌석 레이아웃(나+상/좌/우)과도 정확히 일치 (→ §13) |
| D2 | 시작 타일 장수 | **2~3인: 각 4장, 4인: 각 3장** (공식 룰) | 요구사항 문서의 "일괄 4장"과 다른 부분 — 공식 룰북이 4인일 때 3장으로 명시함(4인 4장이면 시작 배분 16장으로 더미가 8장뿐이라 게임이 지나치게 짧아지는 것을 원작이 이미 보정한 것). 원작 충실 원칙에 따라 공식 사양 채택 (→ §5.2) |
| D3 | 타일 구성 (조커) | **로비(대기실) 옵션 "조커 포함"(기본 꺼짐)을 v1부터 구현.** 꺼짐 = 숫자 0~11×흑/백 24장(사용자 기본 사양). 켜짐 = 흑/백 조커("–") 1장씩 추가한 **26장**(공식 발매판 표준 구성). 조커 상세 규칙은 §6.7·§17 | 사용자가 조커 포함 여부를 대기실에서 직접 선택하고 싶다고 명시함. 공식 발매판 표준 구성(26장)을 로비 토글로 그대로 노출하면 원할 때 "원작과 완벽 동일"을 100% 충족하면서도, 기본값(꺼짐)으로 사용자가 처음 지정한 24장 사양도 그대로 유지됨 (→ §6.7, §17) |
| D4 | 동점(같은 숫자) 타일의 좌우 순서 | **기본값 = 공식 룰: "같은 숫자면 흑이 백의 왼쪽"** → 모든 타일의 삽입 위치가 완전 자동 확정(플레이어 선택 없음). **로비 옵션 "동점 자유 배치"**(기본 꺼짐)를 두어 사용자가 요구사항에 기술한 변형(동점 타일의 좌우를 소유자가 선택)도 지원 | ⚠️ **요구사항 문서와 공식 룰이 상충하는 최대 지점.** 사용자는 "동점 좌우 자유 배치가 추리를 어렵게 만드는 핵심 장치"라고 기술했으나, 공식 룰북(Da Vinci Code 국내판·Coda·Algo 공통)은 "같은 숫자일 경우 검은색 타일을 흰색 타일 왼쪽에 놓는다"로 순서를 강제함. "원작 룰과 완벽히 동일"이 최상위 요구이므로 공식 룰을 기본값으로 하고, 사용자 기술 사양은 하우스룰 옵션으로 보존. 자유 배치 옵션이 켜진 경우에만 동점 존재 시 좌/우 선택 UI가 등장 (→ §3.2, §6.6) |
| D5 | 시작 타일 분배 방식 | **턴 순서대로 각자 흑/백 장수 구성을 직접 선택**(예: "흑 3 + 백 1"). 1인당 15초, 미선택 시 랜덤 구성 자동 배정 | 원작은 뒷면 상태에서도 색이 보이므로 "원하는 색 조합으로 집어가는 것"이 공식 세팅의 일부임. 동시 선택으로 하면 색별 재고(각 12장) 초과 요청이 발생할 수 있어, 순차 선택으로 원작의 "차례로 집어가기"를 그대로 재현하며 수량 충돌도 자연 해소 (→ §5.3) |
| D6 | 턴 드로우 방식 | **흑/백 중 원하는 색을 선택해서 1장 뽑기** (같은 색 내에서는 랜덤 = 물리적으로 구분 불가와 동치). 한쪽 색 소진 시 남은 색만 선택 가능 | 원작에서 더미 타일도 색이 노출되므로 색 선택은 플레이어의 공식 권리. "아무 타일이나 집는다"의 정확한 디지털 번역 (→ §6.1) |
| D7 | 더미 소진 후 턴 | 드로우 없이 **추측 의무는 그대로 유지**. 오답 시 (공개할 뽑은 타일이 없으므로) **자기 비공개 타일 중 1장을 스스로 골라 공개** (15초 미선택 시 랜덤 자동 공개) | 공식 룰. 더미가 비어도 "패스" 개념은 여전히 없음 (→ §6.5) |
| D8 | 폰 좌석 레이아웃 (인원별) | 하단 = 항상 내 타일판. 내 차례에 노출되는 상대판: **4인 = 좌/상/우 3면, 3인 = 좌/우 2면(상단 비움), 2인 = 상단 1면.** 배치 순서는 **내 다음 턴 플레이어부터 시계방향(좌 → 상 → 우)** — 실제 테이블에서 시계방향으로 도는 착석 메타포 그대로 | 4인이 4방향과 정확히 맞아떨어짐. 3인을 좌/우로 한 것은 실제 3인 테이블(삼각형 착석)의 메타포이자, 상단 영역을 턴 정보/추측 결과 배너에 양보해 세로 화면을 효율적으로 쓰기 위함. 2인은 마주보기 메타포로 상단 (→ §11.3) |
| D9 | 비차례 폰의 상대판 표시 | **내 차례가 아니면 상대판 영역 숨김**, 내 타일판 + "테이블 전황은 TV에서" 안내만 표시 (루미큐브 D15 패턴 계승) | 다빈치 코드는 비공개 정보가 '숫자'뿐이고 색/위치/공개 여부는 전부 공용 정보라, **TV가 손실 없는 완전한 관전 보드로 성립**함(루미큐브와 달리 미러링 문제 자체가 없음). 폰에 중복 표시하면 시선이 갈라지고, 추측 선언 순간 전원이 TV를 보게 만드는 것이 파티게임 연출상 이득. 트래픽·렌더 부담도 절감 (→ §11.1, §11.3) |
| D10 | 호스트(TV) 화면 구성 | **전원의 타일판을 테이블 뷰(4방향)로 상시 표시** — 단 뒷면 타일은 색만, 숫자는 공개 타일만. + 더미(흑/백 잔량), 턴 스포트라이트, 추측 선언 말풍선("P2의 왼쪽 3번째, 흑 7!"), 정오답 판정 연출, 연속 성공 콤보 카운터, 추측 히스토리 로그 | 원작을 실제 테이블에서 할 때 관전자가 보는 것과 정확히 같은 정보량. 추측 선언·판정이 이 게임의 유일한 공개 이벤트이므로 TV는 그것을 최대한 극적으로 보여주는 무대로 설계 (→ §11.1) |
| D11 | 추측 선언의 공개 범위 | 추측(대상 플레이어·타일 위치·선언 숫자)과 정오답 결과는 **전원 브로드캐스트** | 원작에서 추측은 소리 내어 선언하는 공개 행위. 오답도 "그 타일은 7이 아니다"라는 공용 정보를 남기며, 이것이 게임의 추리 재료임 (→ §12) |
| D12 | 숫자 패드 보조 표시 | 0~11 패드에서 **이미 어딘가에 공개된 동일 (색, 숫자) 조합은 dim 처리하되 선택은 가능** | dim은 공개 타일을 다시 보면 누구나 아는 공용 정보의 재표시일 뿐이라 추리 보조(원작 왜곡)가 아님. 선택 자체를 막지 않는 것은 원작이 "바보 같은 추측"도 허용하기 때문 (→ §11.3) |
| D13 | 턴 타이머 | 로비 옵션 30/60/120초/무제한, **기본 60초** (추측 페이즈 기준. 뽑기·선택 등 보조 페이즈는 15초 고정). 타임아웃 처리: **이번 턴 성공 0회면 "오답"과 동일**(뽑은 타일 공개 삽입), **1회 이상 성공했으면 "멈춤"과 동일**(비공개 삽입) | 원작엔 타이머가 없으나(장고 허용) 파티게임 템포상 필요. 타임아웃을 별도 벌칙으로 창작하지 않고 원작에 존재하는 두 종료 경로(오답/멈춤) 중 상황상 자연스러운 쪽에 매핑해 룰 왜곡 최소화 (→ §6.8) |
| D14 | 타일 참조 체계 | 클라이언트에 노출되는 타일 식별자는 **숫자 정보를 인코딩하지 않은 불투명(opaque) uid** + 공개 속성 `{ color, revealed, number(공개 시에만) }`. 비공개 숫자는 소유자 본인 폰에만 전송 | 루미큐브의 "ID에 색·숫자 인코딩" 방식은 여기선 금지(메모리 스니핑으로 즉시 치팅 가능). 더미 내용·타인 비공개 숫자는 어떤 메시지에도 싣지 않음 — §9 가시성 매트릭스로 전 메시지 검증 (→ §9) |
| D15 | 데모(봇) 모드 | **제약 전파 라이트 버전**: 각 뒷면 타일의 후보 숫자 집합을 (색별 공개/자기 손 타일 소거) ∩ (좌우 공개 이웃의 값 범위)로 계산 → 후보가 가장 적은 타일을 골라 후보 중 무작위 선언. 후보 1개짜리(확정) 타일이 있으면 계속, 없으면 30% 확률로만 계속 | 완전 무작위보다 훨씬 그럴듯하면서 구현이 단순(베이지안 추론·상대 추측 이력 역추론 등은 미구현 명시). 원작의 "확신 있을 때만 무리하는" 플레이 패턴이 자연 재현됨 (→ §14) |
| D16 | 모션/연출 강도 | 루미큐브 D14와 동일하게 **"움직임이 많은 액티브한 UI"를 명시 목표로** — 뽑기/추측 선언/판정 드럼롤/공개 플립/콤보/탈락/승리 전 이벤트에 연출. 특히 **정오답 판정 직전의 드럼롤(긴장 유발 지연 0.8~1.2초)**을 이 게임 연출의 중심 장치로 삼음 | 다빈치 코드의 재미의 정점은 "선언 → 판정 사이의 긴장"임. 기존 게임 이펙트 패턴(`flash-pop`, `shake-screen`, `gyf-badge-pop` 등) 재사용으로 플랫폼 시각 일관성 유지 (→ §11.4) |
| D17 | 중도 이탈 처리 | 유예(60초, 플랫폼 공통) 후 확정 이탈 시 **그 플레이어의 전 타일을 공개 처리 = 탈락과 동일 취급**. 남은 생존자 1명이면 즉시 그 사람 승리 | 이탈자 타일을 더미에 환원하면 "이미 관측된 색·위치 정보"가 왜곡되고, 비공개 유지하면 게임이 영원히 안 끝남. 전부 공개(탈락)가 정보 정합성을 지키는 유일한 중립 처리 (→ §7.3) |
| D18 | 라운드/점수 | 1라운드 단판, 순위 = **탈락의 역순**(늦게 탈락할수록 상위, 승자 1위). 누적 점수제(여러 판 합산) 없음 | 원작이 단판 승부 게임(점수 체계 자체가 없음). 플랫폼 세션 길이 일관성 |

## 1. 개요 및 파일 구조

- 경로: `games/davinci-code/`
- CSS 접두사: `dv-`
- 인원: 2~4명 (registry: `minPlayers: 2, maxPlayers: 4`)
- 썸네일: 🀫 (뒷면 타일 이미지의 메타포. 또는 전용 PNG)

```
games/davinci-code/
├── shared/
│   ├── DavinciEngine.js     # 타일 생성/셔플, 삽입 위치 계산(공식 흑좌 룰/자유배치),
│   │                        # 추측 판정, 탈락 판정, 봇용 후보 집합 계산 (host/bot 공유.
│   │                        # 모바일은 비공개 값을 모르므로 삽입 위치 계산 유틸만 사용)
│   ├── TileRenderer.js      # 타일 1장 DOM 렌더 유틸 (흑/백 몸체, 숫자면/뒷면, 크기 변형)
│   └── motion.js            # 모션 상수(FLIP_MS, DRUMROLL_MS 등) + FLIP 트윈 유틸 (§11.4)
├── host/
│   ├── index.html
│   ├── main.js
│   ├── DavinciGame.js       # HostBaseGame 상속, 게임 상태의 단일 권위(authority)
│   └── style.css
└── mobile/
    ├── index.html
    ├── main.js
    ├── DavinciMobile.js     # MobileBaseGame 상속
    └── style.css
```

- 로비는 `<game-lobby>` 컴포넌트 재사용. 로비 옵션: 턴 타이머(30/60/120/∞, 기본 60), 동점 배치 규칙(공식/자유, 기본 공식 — D4), **조커 포함(기본 꺼짐 — D3, §6.7, §17)**.
- 상태 권위는 **호스트 브라우저의 게임 인스턴스**. 서버(Socket.IO)는 릴레이만 담당. **호스트 인스턴스는 모든 타일의 숫자를 알고 있지만, TV 렌더 계층은 §9의 "공개 뷰" 데이터만 사용해야 함**(TV 화면에 비공개 숫자가 그려지는 순간 게임이 붕괴 — 렌더 함수에 비공개 값을 아예 전달하지 않는 구조로 강제).
- `vite.config.js`에 host/mobile 엔트리 추가, `games/registry.js` 등록 필요.

## 2. 구성물 (타일)

### 2.1. 구성 (D3)

- 기본: 숫자 **0~11** × 색상 **흑/백** = **24장**. 중복 없음 — 같은 숫자라도 색이 다르면 서로 다른 타일이며 동시에 존재함(흑5와 백5).
- **로비 옵션 "조커 포함"(기본 꺼짐)**: 켜면 흑 조커 1장 + 백 조커 1장이 추가되어 **26장** 구성(공식 발매판 표준). 조커는 숫자가 없고, 뒷면 상태에서는 같은 색 숫자 타일과 구분되지 않음(색만 보임 — "조커라는 사실"이 곧 이 타일의 비공개 정보). 상세 규칙 §6.7·§17.

### 2.2. 타일의 정보 구조 — 공개 속성과 비공개 속성

물리 타일의 성질을 그대로 옮김: **타일은 세워둔 뒷면 상태에서도 색이 보인다.** 즉,

- **공개 속성** (항상 전원에게 보임): 색(흑/백), 소유자, 타일판 내 위치(왼쪽부터의 인덱스), 공개(앞면) 여부, 공개된 경우 숫자.
- **비공개 속성** (소유자 본인만): 뒷면 타일의 숫자.

이 구분이 이 게임 설계 전체의 축임. 더미 역시 "흑 n장 / 백 m장 남음"까지는 공용 정보고, 그 안의 숫자 구성만 비밀임.

### 2.3. 타일 식별자 (D14)

- 호스트 내부 표현: `{ uid, color: 'B'|'W', number: 0~11, joker: boolean, revealed: boolean }`. 조커 옵션이 켜진 게임의 조커 타일은 `joker: true`이며 `number` 없음(숫자 타일은 반대로 `joker: false`/생략).
- `uid`는 게임 시작 시 셔플 후 발급하는 **불투명 문자열**(예: `t00`~`t23`을 셔플 순서로 부여 — 발급 순서가 숫자와 무상관이면 충분). **uid·인덱스 어디에도 숫자를 인코딩하지 않는다.** 루미큐브의 `r07a` 같은 자기서술 ID 체계를 여기 쓰면 클라이언트 메모리만 봐도 전 타일이 읽히므로 금지.
- 메시지에서 특정 타일 지정은 `(targetPlayerId, tileIndex)` 위치 기반 + uid 병기(연출·애니메이션 추적용). 위치는 삽입 때만 변하고 삽입은 턴 종료 처리 중에만 일어나므로(추측은 항상 그 전), 위치 기반 참조의 레이스는 구조적으로 없음.

## 3. 타일판 배치 규칙 — 정렬·삽입 사양

### 3.1. 오름차순 강제

- 각자의 타일판은 항상 **왼쪽→오른쪽 숫자 오름차순**. 이 정렬은 플레이어가 하는 것이 아니라 **호스트(엔진)가 강제 계산**함 — 디지털판에서 정렬 실수/조작이 원천 불가능.
- 시작 분배 시와 매 삽입 시 `DavinciEngine.insertPosition(tiles, newTile, tieRule)`이 유일한 삽입 지점을 계산.

### 3.2. 동점(같은 숫자, 다른 색) 타일 (D4)

- **공식 룰(기본값)**: 같은 숫자는 **흑이 백의 왼쪽**. 따라서 삽입 위치는 항상 유일하게 확정되고 플레이어 입력이 필요 없음. 전 타일의 정렬이 `(number, colorRank)` 사전순으로 완전 결정적.
  - 주의: 이 규칙 하에서는 "위치 + 색"만으로 상대 타일 간의 대소·동점 관계가 원작 그대로의 정보량으로 노출됨(예: 흑-백이 붙어 있으면 "백 ≥ 흑"이고 같을 수도 있음). 이것이 원작의 추리 재료이며 시스템이 추가로 요약해 주지는 않음(§11.3의 dim 처리 외 추리 보조 금지).
- **자유 배치 옵션(로비에서 켠 경우)**: 삽입하려는 타일과 **같은 숫자의 반대색 타일을 이미 갖고 있을 때만** 소유자에게 좌/우 선택 프롬프트가 뜸(§6.6). 그 외에는 공식 룰과 동일하게 자동. 최종 위치는 어차피 전원에게 보이는 공용 정보이므로 선택 행위 자체는 비밀이 아님.

### 3.3. 공개 타일의 위치

- 추측당해 공개된 타일은 **제자리에서 앞면으로 뒤집힐 뿐 위치 불변**. 공개 타일 좌우의 뒷면 타일 값 범위를 좁혀주는 것이 원작 추리의 핵심 재료.

## 4. 게임 흐름 총괄

```
로비(<game-lobby>) → 시작
  ↓
[세팅] 24장 셔플(호스트 메모리) → 턴 순서 랜덤 결정·공개
  → 턴 순서대로 각자 시작 타일의 흑/백 구성 선택(§5.3, 15초 타임아웃)
  → 각자 타일판 자동 정렬 완료, 각 폰에 자기 숫자 전송
  ↓
[턴 루프] 현재 플레이어만 조작 (§6)
  ├─ (더미 잔여 시) 흑/백 선택해 1장 드로우 → 본인만 숫자 확인
  ├─ 추측 의무: 상대 뒷면 타일 1개 탭 + 숫자 선언 (최소 1회, 전원에게 공개)
  ├─ 정답 → 그 타일 공개 → [계속 추측 / 멈춤] 선택 (성공하는 한 무한 반복 가능)
  │         └ 이 과정에서 상대가 전부 공개되면 즉시 탈락 처리, 생존자 1명이면 즉시 승리
  ├─ 오답 → 턴 즉시 종료. 뽑은 타일을 **공개 상태로** 자기판에 자동 삽입
  │         └ 더미 소진으로 뽑은 타일이 없으면: 자기 뒷면 타일 1장 선택 공개 (§6.5)
  └─ 멈춤 → 턴 종료. 뽑은 타일을 **비공개 상태로** 자기판에 자동 삽입
  ↓
[탈락] 비공개 타일 0장이 된 플레이어는 탈락(전 타일 앞면). 턴 순서에서 제외
  ↓
[종료] 생존자 1명 → 승리. 결과 화면(전 타일 공개, 순위 = 탈락 역순) → 다시하기/로비
```

"패스"는 어떤 국면에도 존재하지 않음: 더미가 있으면 반드시 뽑고, 뽑았든 못 뽑았든 반드시 1회 이상 추측하며, 뽑은 타일은 반드시 판에 편입됨.

## 5. 세팅 (시작 분배)

### 5.1. 턴 순서

- 원작은 합의/가위바위보로 선을 정함 → 디지털에선 랜덤 셔플로 대체하고 호스트 화면에 순서 공개(플랫폼 관례. 루미큐브와 동일한 대체 근거).

### 5.2. 시작 장수 (D2)

- **2인·3인: 각 4장 / 4인: 각 3장.** 공식 룰북 사양. `startTileCount = playerCount === 4 ? 3 : 4` 한 줄로 분기.
- 분배 후 더미 잔량: 2인 16장, 3인 12장, 4인 12장. **조커 옵션 켜짐 시** 총 26장 기준으로 각 +2 (2인 18장, 3인 14장, 4인 14장).

### 5.3. 색 구성 선택 (D5)

- 턴 순서대로 1명씩: 폰에 "시작 타일 고르기 — 흑 몇 장?" UI(0~`startTileCount` 스테퍼 + 남은 흑/백 재고 표시). 확정하면 호스트가 해당 색 더미에서 랜덤으로 그 수만큼 인출(같은 색끼리는 구분 불가이므로 랜덤 = 원작의 "집기"와 동치).
- 색별 재고(각 12장)를 초과하는 요청은 UI에서 스테퍼 상한으로 차단(예: 앞 사람들이 흑을 많이 가져가 흑이 2장 남았으면 상한 2).
- 15초 미입력 시 랜덤 구성 자동 배정(잔여 재고 내에서).
- **조커 옵션 켜짐 시**: 색별 재고가 각 13장(숫자 12 + 조커 1)이 되며, 색 선택 시 조커도 같은 색 안에 섞여 랜덤으로 뽑힐 수 있음(뒷면에서 숫자·조커 구분 불가 — 원작 그대로). 분배받은 타일 중 조커가 있으면 자동 정렬 전에 §6.7의 위치 선택을 거쳐야 최종 판이 확정됨.
- 전원 완료 시 각자 판이 §3 규칙(+조커 옵션 시 §6.7)으로 자동 정렬되고, 각 폰에 자기 타일 전문(`handDealt`)이 **개별 전송**됨. TV에는 색·장수만 반영.
- 데모(봇) 모드에서는 봇이 랜덤 구성을 즉시 선택하고, 조커를 받으면 §6.7 위치도 즉시(랜덤) 선택.

## 6. 턴 진행 상세

턴은 호스트가 관리하는 **턴-내 상태 머신**으로 진행됨:

```
turnPhase: 'draw' → 'guess' → (정답) → 'choose' → 'guess' → ...
                          └→ (오답) → 'insert' 또는 'revealOwn' → 턴 종료
            'choose'에서 멈춤 → 'insert' → 턴 종료
(더미 소진 시 'draw' 스킵하고 'guess'부터 시작)
(조커 옵션 켜짐 + 삽입 대상이 조커인 경우: 'insert' 직전에 'jokerPlace' 위치 선택이 끼어듦 — §6.7)
```

### 6.1. draw — 드로우 (D6)

- 더미에 타일이 남아 있으면 반드시 1장 뽑음. 폰에 흑/백 두 개의 큰 버튼(각 잔량 표시). 한쪽이 0장이면 그 버튼 비활성.
- 호스트가 해당 색 풀에서 랜덤 1장 인출 → **본인 폰에만 숫자 전송**(`drawnTilePrivate`), 전원에게는 색만 브로드캐스트(`tileDrawn`).
- 뽑은 타일은 아직 판에 삽입되지 않은 "손에 든" 상태로, 폰 하단 내 타일판 옆 전용 슬롯에 표시(§11.3). TV에는 해당 플레이어 패널 옆에 뒷면(색만) 타일로 표시.
- 뽑은 타일의 숫자는 이번 턴 추측의 사적 힌트가 됨(내가 흑7을 뽑았으면 상대 뒷면 흑 타일은 7이 아님) — 원작 그대로.
- 페이즈 제한 15초, 타임아웃 시 잔량 많은 색(동률이면 랜덤) 자동 드로우.

### 6.2. guess — 추측 선언 (의무)

- 폰 상/좌/우에 상대 타일판 노출(§11.3). **탭 가능 대상 = 생존 상대의 뒷면 타일 전부.** 탭 불가: 이미 공개된 타일(앞면), 내 타일, 탈락자의 타일(전부 앞면이므로 자동 충족), 뽑은 타일.
- 같은 타일 재추측 제한은 없음 — 오답이면 어차피 턴이 끝나므로 "이번 턴에 이미 시도한 타일" 상태는 존재하지 않고, 다음 내 턴에 같은 타일을 다시 노리는 것은 원작에서도 당연히 허용.
- 뒷면 타일 탭 → 그 타일이 선택 강조되고 **0~11 숫자 패드** 오버레이 표시(§11.3, dim 규칙은 D12). 숫자 탭 → "P2의 왼쪽 3번째 흑 타일 = 7 선언" 확인 바 → 확정 전송. **조커 옵션 켜짐 시** 패드에 **[조커]** 키가 13번째 선택지로 추가되며, 대상이 조커 타일이면 이 키를 선택해야 정답 처리됨(§6.7·§17). 조커가 아닌 타일에 [조커]를 선언하면 오답.
- 호스트는 수신 즉시 `guessMade`(대상·위치·숫자)를 **전원 브로드캐스트**(D11) → TV·전 폰에서 드럼롤 연출(§11.4) → 판정 결과 `guessResult` 브로드캐스트.
- 즉시 거부 조건(호스트, `actionAck { accepted: false }`): 자기 턴 아님 / 턴 페이즈가 guess 아님 / 대상 타일이 없거나 이미 공개됨 / 숫자 범위 밖 / 자기 자신 대상.

### 6.3. 정답 → choose — 계속/멈춤 선택

- 정답이면 대상 타일이 **제자리에서 앞면 공개**(전원 `guessResult { correct: true }` + `boardsUpdate`).
- 공개 직후 호스트가 탈락 판정(§7.1). 대상이 탈락했고 **생존자가 나 혼자면 즉시 게임 종료(내 승리)** — choose 페이즈 없이 종료 시퀀스로.
- 그 외에는 본인 폰에 **[한 번 더 추측] / [여기서 멈춤]** 두 버튼 표시(choose 페이즈). 계속을 고르면 guess 페이즈로 복귀(대상은 아무 생존 상대의 아무 뒷면 타일 — 직전과 다른 사람이어도 됨). 성공하는 한 횟수 무제한.
- 이번 턴 연속 성공 수(combo)는 호스트가 집계해 TV 콤보 연출에 사용(§11.4).

### 6.4. 오답 → insert — 뽑은 타일 공개 삽입

- 오답이면 턴 즉시 종료. **추측당한 타일은 공개되지 않고 뒷면 유지**(원작 그대로 — "아니다"라는 사실만 공용 정보로 남음).
- **이번 턴에 뽑은 타일이 앞면(공개) 상태로 자기판에 자동 삽입**됨. 삽입 위치는 §3 규칙으로 호스트가 계산(자유 배치 옵션 + 동점 보유 시에만 §6.6의 좌/우 선택 후 진행). 전원에게 색·위치·숫자가 공개됨(`tileInserted { revealed: true }`).
- 공개 삽입은 비공개 타일 수를 줄이지 않으므로 이것만으로 탈락하지는 않음.

### 6.5. 더미 소진 시의 오답 — revealOwn (D7)

- 더미가 비어 드로우 없이 시작한 턴에서 오답이 나면, 공개할 "뽑은 타일"이 없으므로 **자기 뒷면 타일 중 1장을 스스로 선택해 공개**함.
- 폰에 자기 타일판의 뒷면 타일들이 선택 모드로 강조 → 탭 + 확인 → 해당 타일 제자리 공개. 15초 미선택 시 뒷면 타일 중 랜덤 자동 공개.
- 이 공개는 비공개 수를 줄이므로 **자기 탈락을 유발할 수 있음**(마지막 비공개 타일을 깠으면 탈락 → 생존자 1명이면 그 사람 승리).

### 6.6. 삽입 시 좌/우 선택 (자유 배치 옵션 전용)

- 옵션이 켜져 있고, 삽입할 타일과 같은 숫자의 반대색 타일을 이미 보유한 경우에만: 본인 폰에 "왼쪽에 둘까, 오른쪽에 둘까?" 2택 프롬프트(두 후보 위치가 자기판 위에 고스트로 표시). 15초 미선택 시 공식 룰 위치(흑좌) 자동.
- 멈춤(비공개 삽입)의 경우 이 선택 결과로 확정된 **위치만** 전원에게 보임(숫자는 여전히 비밀). 오답(공개 삽입)이면 어차피 숫자까지 공개.

### 6.7. 조커 삽입 위치 선택 (조커 옵션 전용, D3)

- 조커 옵션이 켜진 게임에서 조커 타일이 (a) 세팅 분배 중 뽑히거나(§5.3) (b) 턴 중 드로우되어 멈춤/오답으로 판에 삽입되어야 할 때(§6.4, §6.3 멈춤 경로), 그 조커는 **오름차순 자동 정렬 대상에서 제외**되고 소유자가 자기 판의 원하는 위치(맨 왼쪽 ~ 맨 오른쪽 사이 임의 지점, 이미 놓인 타일들의 "틈" 중 하나)를 직접 선택함 — 공식 룰의 "아무 데나 꽂기"를 그대로 구현.
- 폰에 자기 판이 위치 선택 모드로 표시되어 삽입 가능한 틈마다 탭 지점(고스트 슬롯)이 생김. 15초 미선택 시 맨 오른쪽 자동 배치.
- **한 번 세운 조커의 위치는 이후 다시 옮길 수 없음**(공식 룰). 이후 새 숫자 타일이 오름차순으로 삽입될 때 그 조커는 정렬 계산에서 무시되고 제자리에 고정된 채 좌우로 밀려날 뿐임.
- 오답으로 삽입되는 조커는 위치 선택과 동시에 **공개**(앞면, 조커 무늬 노출)됨. 멈춤으로 삽입되는 조커는 위치만 전원에게 공개되고, "이 타일이 조커"라는 사실 자체는 여전히 **비공개**(뒷면 유지 — §6.2의 [조커] 선언으로만 확인 가능).
- 이 선택은 §6.6의 동점 좌/우 선택과 별개 페이즈(`jokerPlace`)임 — 둘 다 필요한 상황은 없음(조커는 숫자가 없어 동점 판정 대상이 아님).

### 6.8. 타이머 (D13)

- guess/choose 페이즈: 로비 설정값(기본 60초, 턴 전체가 아니라 **선언 1회 단위로 리셋** — 연속 성공 중 매 추측마다 새로 60초). draw/revealOwn/좌우선택/조커 위치선택(`jokerPlace`): 15초 고정.
- 남은 시간은 TV 타이머 링 + 현재 플레이어 폰에 표시, 10초 이하 진동·색 경고(플랫폼 공통 패턴).
- guess 타임아웃: 이번 턴 성공 0회면 **오답 취급**(§6.4 또는 §6.5로 분기), 1회 이상이면 **멈춤 취급**(§6.3의 멈춤 경로 = 비공개 삽입). choose 타임아웃: 멈춤 취급. 어느 경우든 원작에 없는 신규 벌칙을 만들지 않음.

## 7. 탈락 · 승리 · 이탈

### 7.1. 탈락

- 판정 시점: 어떤 타일이 공개되는 즉시(추측 성공 공개, §6.5의 자기 공개, 이탈 처리). **비공개 타일 수 == 0**이면 탈락.
- 탈락자는 턴 순서에서 제외되고(현재 턴 진행 중인 추측자의 턴은 계속됨), 이후 추측 대상도 될 수 없음(뒷면 타일이 없으므로 자동). 탈락자의 타일판은 전부 앞면으로 TV·폰에 계속 표시됨(공개된 정보는 남은 플레이어들의 추리 재료).
- 탈락자 폰: 관전 모드 — 자기(전부 공개된) 판 + "TV로 관전하세요" + 탈락 순위 표시. **탈락했어도 타인의 비공개 숫자는 절대 전송하지 않음**(재대결·구두 유출 방지).

### 7.2. 승리

- **생존자(비공개 타일 ≥ 1장 보유)가 1명이 되는 순간 즉시 그 사람 승리.** 2인전이면 상대 전체 공개 순간, 다인전이면 최후 1인 시점. 연속 추측 체인 도중이라도 즉시 종료.
- 종료 시 전원의 전 타일 공개(`gameFinished.revealedBoards`) — 원작에서 게임 끝나고 타일 눕혀 보여주는 관례의 재현. 결과 화면 순위: 승자 1위, 이하 탈락 역순(늦게 탈락 = 상위). 동시 탈락은 구조상 없음(공개는 1장씩 일어남).

### 7.3. 중도 이탈 (D17)

- 플랫폼 공통 유예(재접속 대기 60초). 유예 중 그 사람 턴이 오면: 드로우 페이즈면 자동 드로우 후 대기, guess 타임아웃 규칙(§6.7)으로 자연 처리(성공 0회 오답 취급). 즉 이탈자의 턴은 타이머가 알아서 정리함.
- 유예 만료로 확정 이탈 시: 전 타일 공개 = 탈락 처리(사유 "이탈" 표기). 생존자 1명 남으면 즉시 종료.
- 재접속: 플랫폼 rejoin 흐름 → 호스트가 `stateSync`(§12)로 복원 — **자기 비공개 숫자 포함 전문은 본인 소켓에만**.

## 8. 상태 모델 (호스트 권위 상태)

```
{
  phase: 'lobby' | 'setupPick' | 'playing' | 'finished',
  options: { tieRule: 'official' | 'free', guessTimerSec: 30|60|120|null, includeJokers: boolean },
  pool: { black: [number,...], white: [number,...] },   // 셔플된 숫자 목록. 호스트 메모리에만
  players: {
    [playerId]: {
      nickname, seat,                       // seat: 좌석 배치 계산용 턴 순서 인덱스
      tiles: [ { uid, color, number, joker, revealed }, ... ], // 항상 §3(+조커는 §6.7) 정렬 유지
      eliminated: boolean, eliminatedRank,  // 탈락 순번 (결과 순위용)
      connected: boolean
    }
  },
  turnOrder: [playerId,...], currentTurnIdx,
  turn: {
    phase: 'draw' | 'guess' | 'choose' | 'revealOwn' | 'tiebreak' | 'jokerPlace',
    drawnTile: { uid, color, number, joker } | null,   // 이번 턴 뽑은 타일 (아직 미삽입)
    comboCount: number,                          // 이번 턴 연속 성공 수
    deadlineTs
  },
  setupPickIdx: number                       // setupPick 단계 진행 인덱스
}
```

- **공개 뷰 파생 함수** `publicView(state)`: 위 상태에서 비공개 숫자(`revealed:false`인 타일의 `number`, `pool` 내용, `drawnTile.number`)를 제거한 사본을 만드는 단일 함수. TV 렌더와 브로드캐스트 메시지는 **반드시 이 함수의 출력만** 사용 — 비공개 값 유출을 코드 구조로 차단(리뷰 포인트).
- 루미큐브의 스냅샷/롤백 장치는 불필요 — 이 게임엔 "임시 조작 후 검증"이 없고 모든 행위(뽑기/선언/선택)가 원자적·즉시 확정임. 검증은 §10의 수신 시점 거부만으로 충분.

## 10. 호스트 검증 (수신 시점 즉시 거부 목록)

이 게임은 커밋-검증형이 아니라 행위 즉시 확정형이므로, 검증은 전부 메시지 수신 시점의 가드로 처리함. 거부 시 해당 폰에만 `actionAck { accepted: false, reason }` (한글 사유 문구 코드화 — "지금은 당신 차례가 아니에요", "이미 공개된 타일이에요" 등).

1. 공통: `phase == 'playing'`(또는 setupPick 전용 메시지는 `setupPick`), 발신자 미탈락·연결 상태.
2. `pickTiles`: setupPick 단계 + 현재 선택 차례 본인 + 요청 장수 합 == startTileCount + 색별 재고 이내.
3. `drawTile`: 자기 턴 + `turn.phase=='draw'` + 해당 색 잔량 ≥ 1.
4. `guess`: 자기 턴 + `turn.phase=='guess'` + 대상이 생존 타인 + 해당 인덱스 타일 존재·뒷면 + `number` 0~11 정수 또는(조커 옵션 on) `'joker'`.
5. `turnChoice(continue|stop)`: 자기 턴 + `turn.phase=='choose'`.
6. `revealOwnTile`: 자기 턴 + `turn.phase=='revealOwn'` + 지정 타일이 자기 것·뒷면.
7. `placeTiebreak`: 자기 턴 + `turn.phase=='tiebreak'` + 자유 배치 옵션 on.
8. `placeJoker`: 자기 턴 + `turn.phase=='jokerPlace'` + 조커 옵션 on + `position`이 현재 자기 타일 수(조커 제외/포함 무관, 삽입 전 배열 길이) 이내의 유효 인덱스.
9. 타이머 만료와 클라이언트 메시지의 레이스: 호스트 기준 **먼저 처리된 쪽만 유효**, 늦은 쪽은 페이즈 불일치로 자연 거부(별도 로직 불필요).

추측 판정 자체(`tiles[idx].number === guessedNumber`)와 삽입 위치 계산, 탈락·승리 판정은 전부 `DavinciEngine`의 순수 함수로 두고 단위 테스트 선작성(§16 M1).

## 11. 화면 설계

### 11.1. 호스트 (TV/PC) — `DavinciGame.js` (D10)

- **테이블 뷰**: 화면을 가상 테이블로 보고 플레이어 패널을 4변에 배치(2인=상하, 3인=하+좌상+우상, 4인=4변). 각 패널 = 닉네임 + 타일판(타일은 색 몸체 + 공개면 숫자/뒷면이면 무늬) + 비공개 잔여 수 배지 + 접속 상태. **뒷면 타일에 숫자를 그리지 않는 것은 렌더 계층이 `publicView` 데이터만 받는 구조로 보장**(§8).
- **중앙**: 더미(흑 스택/백 스택, 각 잔량 숫자) + 현재 턴 화살표/스포트라이트 + 타이머 링.
- **추측 무대(중앙 오버레이)**: `guessMade` 수신 시 "🗣 민수 → 지현의 왼쪽 3번째 [흑?] = **7**!" 말풍선 + 해당 타일 하이라이트 → 드럼롤 → 판정 스탬프(O/X). 이 게임의 TV 연출 중심(§11.4).
- **사이드 로그**: 최근 추측 이력 6~8건(누가 누구의 몇 번째를 뭐라고 불렀고 결과) — 실물 게임에서도 전원이 들은 공개 정보의 재표시일 뿐이므로 왜곡 아님. 단 "그 타일이 아닌 숫자 목록" 같은 **가공·요약은 하지 않음**(기억력·추리도 실력의 일부 — 원시 이력만 흘려보냄).
- **콤보 카운터**: 연속 성공 시 중앙에 `COMBO ×N` 배지.
- QR: 플랫폼 표준(로비 컴포넌트) 따름. 게임 중 4코너 QR은 이 게임엔 불필요(중도 난입 불가 게임).

### 11.2. 모바일 — 내 타일판 (하단 고정, 항상 표시)

- 화면 하단 ~30%: 내 타일판. 내 타일은 **항상 숫자가 보임**(앞면 공개된 타일은 "공개됨" 마킹 — 모서리 접힘/밝기 차이로 구분, 상대에게 보이는 상태를 나도 알아야 함). 턴·비턴 무관 상시 노출.
- 그 옆 전용 슬롯: 이번 턴 뽑은 타일(내 턴 중에만, 숫자 포함). "아직 판에 안 꽂힌 타일"임을 부유(floating) 스타일로 구분.
- 정렬은 시스템 자동(§3.1)이므로 정렬 조작 UI 없음 — 루미큐브 D9 같은 로컬 정렬 개념 자체가 없음.

### 11.3. 모바일 — 내 차례 화면 (D8, D9)

내 턴이 시작되면 상단 ~70% 영역에 상대 타일판들이 나타남:

- **좌석 배치**: 4인 = 좌/상/우, 3인 = 좌/우, 2인 = 상단. 내 다음 턴 플레이어부터 시계방향(좌→상→우) 배치. 좌/우 패널의 타일판은 90도 회전 렌더(테이블에 둘러앉은 메타포) 또는 세로 공간이 부족하면 축소 가로 렌더 — 구현 시 실기기에서 판단하되 탭 타깃 최소 40px 확보가 우선.
- **뒷면 타일 탭** → 선택 링 표시 + 화면 중앙에 **0~11 숫자 패드**(4×3 그리드) 슬라이드 업. dim 규칙은 D12(이미 공개된 동일 색·숫자 조합 dim, 선택은 가능). 숫자 선택 → 하단 확인 바("지현의 흑 타일을 7로 선언") → [선언!] 탭으로 전송. 패드 밖 탭이면 선택 취소.
- **choose 페이즈**: 정답 연출 후 [🔥 한 번 더] / [✋ 멈추기] 대형 2버튼 오버레이 + 남은 시간.
- **draw 페이즈**: 흑/백 대형 2버튼(잔량 표기).
- **revealOwn / tiebreak 페이즈**: §6.5 / §6.6의 전용 선택 UI.
- **내 차례가 아닐 때(D9)**: 상대판 영역 숨김 → "○○의 차례 — 전황은 TV에서!" 안내 + 최소 상태(더미 잔량, 내 비공개 수). 단 **추측 선언·판정 브로드캐스트는 비턴 폰에도 토스트/배너로 표시**(내가 추측당하는 순간은 내 폰에서도 드럼롤 + 진동 — 당사자의 긴장 연출, §11.4). 내 타일이 공개당하면 내 타일판에서 즉시 플립.

### 11.4. 모션/연출 설계 (D16 — "액티브한 UI")

다빈치 코드는 조작량이 적은 게임이라(턴당 탭 몇 번) 방치하면 루미큐브보다도 정적으로 보이기 쉬움. 대신 **모든 드라마가 "선언 → 판정" 한 순간에 응축**되므로, 그 순간의 드럼롤·플립·콤보 연출에 예산을 집중함. 기존 게임 이펙트 패턴(`gyf-badge-pop`, `shake-screen`, `flash-pop`/`score-pulse` 등)의 타이밍·이징 재사용.

#### 원칙

- **판정은 즉시 보여주지 않는다.** `guessMade` 수신 → 0.8~1.2초 드럼롤(선언된 타일이 흔들리며 스포트라이트, 배경 dim, 심장박동 pulse) → 판정 공개. 호스트가 `guessResult` 전송 자체를 늦추는 게 아니라, **결과를 함께 보내되 클라이언트가 연출 후 공개**(연출 시간을 상수 `DRUMROLL_MS`로 shared/motion.js에 정의, 전 화면 동기).
- **타일 공개는 반드시 3D 플립.** 제자리에서 Y축 회전 플립(CSS `rotateY` + `backface-visibility`) — 이 게임의 시그니처 모션. 숫자면이 드러나는 순간 `flash-pop` 계열 반짝임.
- **모든 타일 이동은 트윈**(FLIP 기법, 루미큐브 §11.4와 동일 유틸 공유): 분배 딜링, 드로우, 삽입(양옆 타일이 벌어지며 자리를 만들고 새 타일이 날아와 안착).
- **턴 전환은 스포트라이트 스윕**, 타이머는 링 + 색 전이(민트→주황→빨강) — 플랫폼 공통 패턴.

#### 호스트(TV) 연출 목록

| 이벤트 | 연출 |
|---|---|
| 세팅 분배 | 중앙 더미에서 각 패널로 타일이 날아가 꽂히는 딜링(색 구성 선택 확정마다 그 사람 몫 일괄, stagger 30ms) + 자동 정렬로 슬라이드 정돈되는 트윈 |
| 턴 시작 | 현재 패널 스포트라이트 스윕 + 타이머 링 리셋 |
| 드로우 | 더미 스택에서 타일 1장이 패널 옆 슬롯으로 포물선 비행(뒷면 유지) + 더미 잔량 카운트 롤링 |
| 추측 선언(`guessMade`) | 배경 dim + 대상 타일 스포트라이트 + 선언 말풍선 팝(`gyf-badge-pop` 이징) + 드럼롤(타일 미세 진동 + 저음 하트비트) |
| 정답 | 3D 플립 공개 + 초록 `flash-pop` + "정답!" 스탬프 + 콤보 배지 `COMBO ×N` 스케일 팝(N≥2부터, N 커질수록 배지 크기·색 강화) |
| 오답 | 붉은 X 스탬프 + 대상 타일이 고개 젓듯 좌우 셰이크(공개는 안 됨) + 추측자의 뽑은 타일이 자기판으로 날아가 **플립 공개되며** 삽입(양옆 벌어짐 트윈) + 화면 가장자리 붉은 비네트 200ms |
| 멈춤 선택 | 뽑은 타일이 뒷면인 채로 자기판에 스르륵 삽입(오답 삽입과 시각적으로 명확히 대비 — 플립 없음) + "여기까지!" 배지 |
| revealOwn(§6.5) | 해당 플레이어 패널 전체에 경고 pulse → 선택된 자기 타일 플립(오답 플립보다 무겁고 느린 이징 — 자책의 무게감) |
| 비공개 1장 남음 | 그 패널 테두리 경고색 pulse 무한 반복(위기 표시 — 루미큐브 "손패 1장"과 동일 패턴) |
| 탈락 | 패널 전체 grayscale 전이 + 타일들이 일제히 눕는(살짝 기울어지는) 트윈 + "탈락" 리본 |
| 승리 | `shake-screen` 저강도 1회 + 승자 패널 확대 줌 연출 + 컨페티 + 전원 타일 순차 전체 공개(좌→우 도미노 플립, stagger 40ms — 원작의 "다 까 보기" 재현) |

#### 모바일 연출 목록

| 이벤트 | 연출 |
|---|---|
| 시작 타일 수령 | 내 타일들이 아래에서 순차 팝인 + 자동 정렬 슬라이드 |
| 내 차례 시작 | "내 차례!" 배너 드롭 인 + 진동 + 상대판 3면이 바깥에서 슬라이드 인(테이블에 앉는 느낌, stagger) |
| 드로우 확인 | 뽑은 타일이 슬롯에 도착 후 나에게만 플립(숫자 확인) + 반짝임 |
| 뒷면 타일 탭 | 선택 링 + 살짝 확대(들어올림) + 숫자 패드 슬라이드 업(spring) |
| 선언 전송 | 확인 바가 말풍선으로 변형되어 위로 날아감 |
| 드럼롤(전 폰 공통) | 화면 dim + 대상 타일 확대 표시 + 미세 진동 반복. **추측당한 당사자 폰은 강한 진동 패턴**(자기 타일이 지목되는 긴장) |
| 정답/오답 결과 | 정답: 초록 플래시 + 콤보 배지 팝 + [한 번 더/멈추기] 버튼이 튀어 오르며 등장. 오답: 화면 셰이크 + 붉은 플래시 + 내 뽑은 타일이 판으로 이동·플립 공개되는 트윈을 그대로 시청 |
| 내 타일이 공개당함 | 하단 내 판에서 해당 타일 플립 + 붉은 테두리 잔광(내 정보가 새어나간 느낌) |
| 멈춤 삽입 | 뽑은 타일이 뒷면 유지한 채 내 판에 삽입(양옆 벌어짐) + 안도 톤의 짧은 초록 글로우 |
| 탈락 | 화면 grayscale 전이 + "탈락… TV로 관전하세요" 오버레이 |
| 승리 | confetti + "VICTORY" 텍스트 팝(`gyf-badge-pop` 이징) |
| 타이머 10초 이하 | 테두리 붉은 vignette pulse + `vibrate('light')` (기존 haptic 패턴 재사용) |

#### 구현 지침

- 색 전이·펄스·셰이크·스탬프는 순수 CSS. 타일의 경로 이동(딜링/드로우/삽입)은 `shared/motion.js`의 FLIP 트윈 유틸(루미큐브와 동일 기법 — 라이브러리 무의존, `transform`+`transition`).
- 상수 예: `FLIP_MS=450`, `DRUMROLL_MS=1000`, `INSERT_MS=320`, `DEAL_STAGGER_MS=30`, `EASE_POP='cubic-bezier(0.34,1.56,0.64,1)'`. 매직넘버 산발 금지.
- `prefers-reduced-motion` 존중: 드럼롤은 0.3초로 단축(완전 생략하면 판정이 너무 급작스러움), 딜링·도미노 플립은 stagger 없이 일괄 처리.
- 연출은 항상 호스트가 확정한 상태를 향해 재생(연출이 끝나기 전에 다음 메시지가 와도 최종 상태 정합성 유지 — 연출 큐잉이 아니라 "최신 상태로 빨리감기" 방식).

- 연출 트리거(`guessMade`)와 상태 확정(`guessResult`, `boardsUpdate`)을 분리 전송해 드럼롤 타이밍을 클라이언트가 제어(§11.4 원칙 1).

## 13. 인원수 결정 근거 (D1 상세)

**결정: minPlayers 2, maxPlayers 4.**

- 원작 공식 인원이 2~4인이고, 루미큐브 XP 같은 **공식 다인원 확장이 존재하지 않음**. 24장 고정 구성에서 5인을 지원하려면 시작 장수를 2~3장으로 줄이는 창작 변형이 필요한데, 시작 정보량이 급감해 게임성이 다른 게임이 되어버림 → "원작 왜곡 없음" 목표와 정면 충돌.
- 사용자 지정 폰 레이아웃(하단 나 + 상/좌/우 상대)이 최대 4인과 정확히 일치 — 5인부터는 레이아웃 창작도 필요해짐.
- 플랫폼 다른 게임 대비 최대 인원이 작지만(대부분 6~8인), digit-puzzle·trading-battle·give-you-fire도 4인 캡 선례가 있음. 관전 재미(TV 추측 무대)가 있어 나머지 인원이 완전히 소외되지는 않음.
- registry 등록값: `minPlayers: 2, maxPlayers: 4`.

## 14. 데모(봇) 모드 (D15)

플랫폼 관례(유휴 시 자동/수동 데모)에 맞춰 가상 봇 2~4명 플레이 지원. 봇 지능 범위를 명시적으로 한정:

### 구현 (제약 전파 라이트)

1. **후보 집합 계산** (`DavinciEngine.candidates(publicBoards, myKnownTiles, targetPlayerId, tileIndex)`): 대상 뒷면 타일의 가능 숫자 =
   - 그 색에서 이미 **어딘가에 공개된 숫자** 제외, 봇 **자신이 들고 있는 같은 색 타일의 숫자**(뽑은 타일 포함) 제외,
   - ∩ 대상 판에서 그 타일 좌/우로 가장 가까운 **공개 타일의 값 범위** (왼쪽 공개값 L, 오른쪽 공개값 R이면 후보 ∈ [L, R] — 동점 허용 경계는 tieRule을 반영해 엔진이 판정: 공식 룰이면 색 순서로 등호 방향까지 좁힘).
   - 이 함수는 **공용 정보 + 자기 사적 정보만** 입력받음(봇도 치팅 금지 — 호스트가 갖고 있는 진짜 값은 판정에만 사용).
2. **대상 선정**: 생존 상대의 모든 뒷면 타일 중 후보 집합이 가장 작은 타일 선택(동률이면 랜덤). 선언 숫자는 후보 중 균등 랜덤. **조커 옵션 켜짐 시**: 아직 어디서도 공개되지 않은 조커가 남아 있다면 후보 집합에 `'joker'`도 균등하게 포함시켜 함께 뽑힐 수 있게 함(정교한 조커 위치 추론은 하지 않음 — 라이트 버전 범위 밖).
3. **계속/멈춤**: 후보 1개짜리(확정) 타일이 남아 있으면 계속, 아니면 30% 확률로만 계속(70% 멈춤). 원작 유저의 "확신 없으면 접는" 패턴 재현.
4. **기타 선택**: 시작 색 구성·드로우 색은 랜덤, revealOwn은 랜덤. **조커 위치 선택(§6.7)도 랜덤 틈 선택.** 생각하는 연출: 각 행동에 1~3초 랜덤 딜레이.

### 미구현 (명시적 스킵)

- 상대 추측 이력의 역추론(누가 뭘 틀렸는지로 소거), 확률 가중 선택, 상대별 위협도 평가. 라이트 버전만으로도 시연에 충분하고, 여기서 더 똑똑해지면 데모가 아니라 AI 대전 기능이 됨(범위 밖).
- 데모 화면 "DEMO" 워터마크(플랫폼 관례). 봇 로직은 엔진의 후보 계산 함수를 그대로 재사용해 규칙 구현 중복 금지.

## 15. 엣지 케이스 체크리스트 (QA 겸용)

- [ ] 2·3인 시작 4장 / 4인 시작 3장이 정확히 분배되고, 더미 잔량(16/12/12)이 맞는지.
- [ ] 세팅 색 선택에서 앞 사람들이 흑을 소진 → 뒷사람 스테퍼 상한이 잔량으로 제한되는지. 15초 타임아웃 랜덤 배정 동작.
- [ ] 공식 tieRule: 흑5·백5를 모두 갖게 됐을 때 흑이 반드시 왼쪽. 백5 보유 중 흑5를 뽑으면 백5 **왼쪽**에 삽입되는지(경계: 0 두 장, 11 두 장도 동일 검증).
- [ ] 자유 배치 옵션: 동점 반대색 보유 시에만 tiebreak 프롬프트가 뜨고, 미보유 시엔 자동 삽입인지. 15초 타임아웃 시 공식 위치 폴백.
- [ ] 오답 시 추측당한 타일이 **공개되지 않고** 뒷면 유지되는지 (가장 흔한 구현 실수 지점).
- [ ] 오답 공개 삽입이 비공개 수를 줄이지 않아 탈락을 유발하지 않는지.
- [ ] 연속 추측 체인: 정답 → 계속 → 다른 플레이어 대상 전환 가능. 체인 도중 한 명 탈락시켜도 턴 지속. 체인으로 마지막 상대의 마지막 타일을 맞추면 choose 없이 **즉시 승리**.
- [ ] 2인전: 상대 전체 공개 순간 즉시 종료.
- [ ] 더미 흑만 소진: 드로우 버튼 흑 비활성·백만 가능. 양쪽 소진: draw 페이즈 스킵하고 guess부터.
- [ ] 더미 소진 + 오답 → revealOwn 진입. 마지막 비공개 타일을 스스로 공개 → 자기 탈락 → 생존 1인 승리 처리.
- [ ] revealOwn 15초 미선택 → 랜덤 자동 공개.
- [ ] guess 타임아웃: 성공 0회 턴 = 오답 경로(뽑은 타일 공개 삽입 / 더미 소진 시 revealOwn), 성공 ≥1회 턴 = 멈춤 경로(비공개 삽입). choose 타임아웃 = 멈춤.
- [ ] 타임아웃 확정 직후 도착한 `guess`/`turnChoice`가 페이즈 불일치로 조용히 거부되는지(레이스).
- [ ] 숫자 패드 dim: 흑7이 공개된 상태에서 다른 흑 뒷면 타일 추측 시 7이 dim(선택은 가능)인지. 백 타일 추측 시엔 7이 dim 아님(색별 독립).
- [ ] 현재 턴 플레이어 이탈 → 타이머로 턴 자연 정리, 유예 만료 시 전 타일 공개·탈락, 생존 1인이면 종료.
- [ ] 재접속 `stateSync`: 내 숫자·뽑은 타일(내 턴이었다면)·턴 페이즈 복원. **타인 비공개 숫자가 페이로드에 없는지 패킷 레벨 검증**.
- [ ] 탈락자 폰이 관전 모드로 전환되고, 탈락 후에도 타인 비공개 숫자를 받지 않는지.
- [ ] `gameFinished.revealedBoards` 24장 전수 검산(색별 0~11 각 1장, 누락·중복 없음).
- [ ] 브로드캐스트 전 메시지에 대해 §9 매트릭스 자동 테스트: `revealed:false` 타일에 `number` 필드가 실려 나가는 경로가 없는지(직렬화 유닛 테스트로 강제).
- [ ] 드럼롤 연출 중 다음 상태 메시지 도착 시 최종 상태 정합성 유지(연출 빨리감기, §11.4).
- [ ] `prefers-reduced-motion`에서 드럼롤 단축·stagger 생략 폴백 동작.
- [ ] **조커 옵션 켜짐**: 더미가 26장(색별 13)으로 정확히 구성되고, 색 선택 시 조커도 같은 색 풀에서 랜덤으로 섞여 나오는지.
- [ ] 세팅 분배·턴 드로우로 조커를 받으면 자동 정렬 대신 `jokerPlace` 위치 선택이 뜨고, 15초 미선택 시 맨 오른쪽 자동 배치되는지.
- [ ] 한 번 놓인 조커 위치가 이후 숫자 타일 삽입에도 절대 이동하지 않는지(정렬 계산에서 조커 제외 검증).
- [ ] 숫자 패드에 [조커] 키가 추가되고, 조커 타일에 [조커] 선언 시 정답·다른 타일에 [조커] 선언 시 오답 처리되는지.
- [ ] 오답으로 조커가 삽입될 때 즉시 공개(조커 무늬 노출)되고, 멈춤으로 삽입될 때는 위치만 공개되고 조커 여부는 비공개 유지되는지.
- [ ] `gameFinished.revealedBoards` 26장 전수 검산(조커 옵션 시 색별 0~11 각 1장 + 조커 1장씩, 누락·중복 없음).
- [ ] **조커 옵션 꺼짐(기본값)**: 위 모든 조커 관련 페이즈·UI·패드 키가 전혀 노출되지 않고 기존 24장 흐름과 동일하게 동작하는지(회귀 확인).

## 16. 구현 순서 제안 (마일스톤)

1. **M1 — 엔진**: `DavinciEngine.js` (타일 생성/셔플(24장/26장 양쪽), 삽입 위치(tieRule 양쪽 + 조커 자유배치 §6.7), 추측 판정(숫자+조커), 탈락/승리 판정, 봇용 후보 계산(조커 포함)) + 단위 테스트(§15의 규칙 케이스를 테스트로 선작성 — 특히 동점 삽입·조커 삽입·가시성 직렬화). 조커는 옵션 분기일 뿐 별도 모듈이 아니므로 M1부터 함께 구현.
2. **M2 — 호스트 상태 머신**: 세팅 선택 루프 → 턴 페이즈 머신(draw/guess/choose/revealOwn/tiebreak/jokerPlace) → 타이머 → 탈락/종료, §12 프로토콜 송수신, `publicView` 분리. 이 시점에 봇(§14)을 먼저 붙여 모바일 없이 전체 루프 검증(데모 모드가 공짜로 나옴 — 루미큐브 M2와 동일 전략). 조커 옵션 on/off 두 경로 모두 봇으로 검증.
3. **M3 — 호스트 렌더**: 테이블 뷰/추측 무대/드럼롤/콤보/로그/종료 연출.
4. **M4 — 모바일**: 내 타일판 상시 표시 → 좌석 레이아웃(2/3/4인) → 추측 UI(탭+숫자 패드+조커 키) → choose/draw/revealOwn/tiebreak/jokerPlace 페이즈 UI → 연출·진동. 로비에 "조커 포함" 토글 추가.
5. **M5 — 통합 QA**: §15 체크리스트(조커 on/off 양쪽), 2/3/4인 실기기 테스트(특히 좌/우 회전 렌더의 탭 정확도), registry/vite 등록, `docs/games/davinci-code.md` 요약 문서(도블 문서 포맷) 작성.

## 17. 부록 — 조커 타일 공식 사양 (로비 옵션 "조커 포함", v1 구현 대상 — D3)

공식 발매판(국내판 포함)은 흑 조커 1장 + 백 조커 1장(표기 "–")을 포함한 26장 구성이며, 룰은 다음과 같음. 로비 "조커 포함" 옵션이 켜졌을 때의 사양이며, §6.7(삽입 위치)·§6.2(추측 시 [조커] 선언)에서 이미 흐름에 통합해 서술함 — 이 절은 그 근거가 되는 공식 룰 원문 정리:

- **분배·드로우**: 일반 타일과 동일하게 섞여 있고 뽑을 수 있음(색은 보임).
- **배치 자유**: 조커는 숫자가 없으므로 오름차순 제약을 받지 않고, 소유자가 **자기 판의 원하는 임의 위치**에 세울 수 있음. 이미 세워둔 조커의 위치는 이후 이동 불가. (이 "아무 데나 꽂기"가 상대의 위치 기반 추리를 교란하는 공식 장치 — 사용자가 동점 자유 배치에 기대한 역할을 공식 룰에서는 조커가 담당함.)
- **추측**: 상대 뒷면 조커를 지목할 때는 숫자 대신 **"조커"라고 선언**해야 맞음(숫자 패드에 "조커" 키 추가). 반대로 조커가 아닌 타일에 "조커" 선언하면 오답.
- **시작 분배에서 조커를 받은 경우**: 정렬 확정 전 원하는 위치에 끼워 넣음(세팅 단계에 위치 선택 UI 필요).
- 구현 영향 범위 요약(모두 위 각 절에 이미 반영): 엔진 삽입 로직(§6.7, 위치 자유), 숫자 패드(§6.2, +[조커] 키), 봇 후보 계산(§14, 조커 가능성 추가), 정보 가시성 매트릭스(§9, "조커 여부" 행 추가), 상태 모델·프로토콜(§8, §12, `joker` 필드 및 `jokerPlace`/`placeJoker` 페이즈·메시지).
