# Digit Puzzle 평가 및 개선안

- 작성일: 2026-07-06
- 분석 범위: `games/digit-puzzle/host/`, `games/digit-puzzle/mobile/`, `games/digit-puzzle/host/PuzzleDemoSimulator.js`
- 분석 방식: Host/Mobile 소스 코드 정적 분석 중심. 실제 다기기 E2E, 크롬 시각 검증, 실기기 햅틱/오디오 검증은 본 문서 범위에 포함하지 않았다.

---

## 1. 게임 평가

### 1.1 코어 플레이 방식 및 재미 요소 분석

`Digit Puzzle`은 모든 플레이어에게 동일한 4x4 슬라이딩 퍼즐 보드를 배포하고, 각자 모바일에서 먼저 완성하는 사람이 이기는 동시 진행형 퍼즐 레이스다. 호스트는 입력 장치가 아니라 전광판 역할을 맡고, 모바일은 오직 퍼즐 풀이에 집중한다. 이 구조는 "공용 화면으로 서로를 보고, 개인 폰으로 조작한다"는 플랫폼 정체성과 잘 맞는다.

코어 재미의 장점은 분명하다.

- 규칙이 빠르게 이해된다. 슬라이딩 퍼즐은 이미 대중에게 익숙한 형식이라 설명 비용이 낮다.
- 공정성이 높다. 호스트가 하나의 공통 보드를 생성해 모두에게 배포하므로 운빨보다 풀이 속도와 침착함이 승부를 가른다.
- 개인 몰입도가 높다. 각자 자기 폰에서 집중해서 풀기 때문에 순간 몰입은 강하다.
- 관전 기본기는 갖춰져 있다. 호스트가 진행률 바, 미니 보드, 이동 수, 시간까지 보여줘서 누가 앞서는지는 읽을 수 있다.

특히 모바일 조작은 단순한 1칸 이동에 머물지 않고, 빈칸과 같은 행/열에 있는 숫자를 누르면 줄 전체가 밀리도록 설계돼 있다. 이는 초보자에게는 입력 장벽을 낮춰 주고, 숙련자에게는 속도감을 준다.

반면 대중성 관점의 한계도 분명하다.

- 소셜 상호작용이 약하다. 블러핑, 협동, 방해, 심리전 대신 각자 조용히 몰입하는 구조라 파티 게임 특유의 폭발력이 작다.
- 막판 드라마가 약하다. 현재 호스트 화면은 누가 앞서는지는 보여주지만, "지금 끝나기 직전"이라는 감정적 피크를 크게 증폭하지 못한다.
- 진행률 지표가 실제 체감 난이도와 어긋날 수 있다. 현재 `correctCount / 15` 기반 진행률은 퍼즐의 실제 해결 근접도를 완전하게 대변하지 못한다.

정리하면 이 게임의 재미 구조는 다음처럼 평가할 수 있다.

| 항목 | 평가 | 근거 |
| --- | --- | --- |
| 진입 장벽 | 낮음 | 슬라이딩 퍼즐에 대한 대중적 친숙도가 높다. |
| 개인 몰입감 | 높음 | 모바일 단독 퍼즐 풀이가 집중감을 만든다. |
| 공정성 | 높음 | 동일 보드 동시 배포 구조다. |
| 관전성 | 중간 | 대시보드는 있으나 추월전 연출이 약하다. |
| 소셜 파티성 | 중하 | 서로에게 직접 개입하는 요소가 거의 없다. |
| 재대결 유도력 | 중간 이하 | 결과 화면과 리매치 동기가 아직 약하다. |

총평하면 `Digit Puzzle`의 코어는 충분히 설득력 있다. 다만 이 게임은 규칙을 바꾸기보다, 레이스의 긴장과 결과의 감정 잔상을 더 강하게 포장해야 대중적 반응이 커진다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

구조적으로는 프로젝트의 권장 패턴을 대체로 잘 따른다. 호스트는 `HostBaseGame`, 모바일은 `MobileBaseGame`을 상속하고 있고, 세션/플레이어 상태는 플랫폼이 관리하며 게임 로직은 메시지 처리와 UI에 집중한다. 퍼즐 보드 생성, 승자 판정, 진행 집계는 호스트가 authoritative state를 쥐고, 모바일은 입력 및 로컬 렌더링을 맡는다.

좋은 점은 다음과 같다.

| 평가 축 | 관찰 | 판정 |
| --- | --- | --- |
| 플랫폼 패턴 준수 | `setPhase`, `showScreen`, `onReset`, `onPlayerRejoin`, `onRejoin`을 사용한다. | 양호 |
| 상태 권한 분리 | 공용 보드 생성과 승자 판정은 호스트, 입력과 퍼즐 렌더링은 모바일이 담당한다. | 우수 |
| 보드 생성 안정성 | 정답 상태에서 유효 이동 300회를 적용해 항상 풀 수 있는 퍼즐만 생성한다. | 우수 |
| 입력 설계 | 탭과 스와이프를 모두 지원하고, 한 번에 여러 칸을 미는 UX가 빠르다. | 양호 |
| 대시보드 정보량 | 진행률, 미니 보드, 이동 수, 시간을 함께 보여준다. | 양호 |
| 레이아웃 안전성 | 호스트 메인 컨테이너에 `position: relative; z-index: 10;`이 있어 배경 felt 뒤로 숨지 않는다. | 규약 준수 |

다만 실제 완성도는 아직 "좋은 시제품"에 가깝다. 특히 결과 처리, 재접속, 반복 플레이, 데모 모드에서 구조적 빈틈이 눈에 띈다.

#### A. 호스트 결과 페이즈가 사실상 미완성이다

호스트 HTML과 CSS에는 결과 오버레이와 `result-rankings` 영역이 준비돼 있다. 그러나 실제 종료 로직인 `PuzzleGame._renderResult()`는 `setPhase('result')`를 호출하지 않고, `result-rankings` 내용도 채우지 않는다. 현재 구조에서는 결과 오버레이가 열리지 않고, `winner-display`만 대시보드 하단에 노출되는 방식으로 끝난다.

이 상태가 만드는 문제는 아래와 같다.

- `btn-restart-result`는 존재하지만 정상적인 플레이 흐름에서 노출 보장이 약하다.
- 호스트 결과 랭킹 UI가 설계만 있고 실제로 사용되지 않는다.
- `winner-display`를 다시 숨기는 코드가 없어 다음 판 시작 후에도 잔상처럼 남을 수 있다.

즉, 결과 화면은 레이아웃 자산은 갖췄지만 로직 마감이 덜 된 상태다.

#### B. 재접속 복구가 플레이 중에도, 결과 단계에서도 완전하지 않다

재접속 처리의 핵심 문제는 세 가지다.

- `PuzzleGame.onPlayerRejoin()`은 `_gameStarted`가 `true`이면 무조건 `rejoinState: playing`을 보내는데, 우승자가 나온 뒤에도 `_gameStarted`가 내려가지 않는다. 그 결과 결과 단계 재접속 플레이어가 다시 플레이 화면으로 복귀할 수 있다.
- `PuzzleMobile`은 `rejoinState` 수신 시 `moves > 0`이면 `_gameActive = true`로 복구하지만 타이머를 재시작하지 않는다. 이후 다음 이동부터도 `_startTimer()`가 다시 호출되지 않아 시간이 영구 정지될 수 있다.
- 로비 재접속 동기화가 부분적이다. 모바일 `onRejoin()`은 `_sendProfile()`을 다시 호출해 대기 화면으로 보내지만, 호스트는 로비 상태에서 `lobbyState` 같은 복구 패킷을 주지 않는다. 준비 완료 상태나 현재 대기 인원 정보가 완전하게 복구되지 않아 UI와 실제 서버 상태가 어긋날 수 있다.

특히 마지막 항목은 프로젝트 규칙에 적힌 "로비 재연결 프리징 가드"와도 결이 맞닿는다. 지금 구현은 멈추지는 않지만, 로비 준비 상태 복구가 명시적이지 않다.

#### C. 반복 플레이 시 모바일 이벤트 리스너 누적 가능성이 크다

`PuzzleMobile._bindBoardEvents()`는 `gameStarted` 수신 때마다, 그리고 `rejoinState` 수신 때마다 다시 호출된다. 하지만 이전 `click`, `touchstart`, `touchend`, `resize` 리스너를 제거하는 코드가 없다.

이 구조가 위험한 이유는 아래와 같다.

- 리매치가 반복되면 동일 입력이 여러 번 처리될 수 있다.
- 재접속 테스트를 반복할수록 버그가 누적되는 형태라 초반에는 잘 드러나지 않는다.
- 이후 조작 피드백, 이펙트, 사운드를 얹을수록 부작용이 커진다.

이 문제는 콘텐츠 개선보다 먼저 고쳐야 하는 품질 리스크다.

#### D. 플레이어 퇴장/리셋 반영이 호스트 UI에서 즉시 정리되지 않는다

`PuzzleGame.onPlayerLeave()`는 `_profiles`와 `_progress`를 정리하고 `_renderLobby()`만 호출한다. 이 때문에 플레이 중 누군가 완전히 퇴장하면 호스트 대시보드는 즉시 다시 그려지지 않고, 다음 `progressUpdate`나 게임 종료가 오기 전까지 오래된 카드가 남아 있을 수 있다.

리셋 시에도 비슷한 마감 문제가 있다.

- `onReset()`은 `_profiles`를 모두 비우므로, 연결은 유지됐어도 플레이어 이름이 다시 도착하기 전까지 로비가 비어 보일 수 있다.
- `winner-display`를 숨기는 처리가 없어 새 게임과 이전 승자 표시가 겹칠 수 있다.

즉, 상태 데이터는 리셋되지만 UI 정리 순서가 세밀하지 않다.

#### E. 결과 정보의 전달력과 순위 산정 품질이 부족하다

호스트는 `_buildRankings()`에서 랭킹 데이터를 만들고 모바일에 `gameFinished`로 전달한다. 하지만 실제 모바일 결과 화면은 `winner` 텍스트와 내 이동 수/시간 정도만 보여주며, `rankings`는 활용하지 않는다.

또한 랭킹 기준도 보완 여지가 있다.

- 현재 정렬 기준은 `progress` 내림차순, `moves` 오름차순이며 `seconds`는 동률 해소에 반영되지 않는다.
- `progress` 자체가 `correctCount / 15` 기반이라 퍼즐 실질 난전과 어긋날 수 있다.

레이스 장르에서 중요한 것은 "몇 등인지", "얼마나 아깝게 졌는지", "왜 졌는지"인데, 현재 결과 화면은 이 감정을 충분히 살리지 못한다.

#### F. 데모 시뮬레이터는 존재하지만 운영 도구 수준으로는 부족하다

`PuzzleDemoSimulator.js`는 데모 모드의 출발점으로는 의미가 있지만, 운영 및 회귀 검증용 도구로 보기엔 부족하다.

핵심 문제는 다음과 같다.

- 파일명이 프로젝트 규약의 기대치인 `DemoSimulator.js`와 다르다.
- 시작 버튼은 있지만 명시적인 중단 버튼과 상태 배너가 없다.
- 실제 플레이어가 이미 있는 로비에서 데모 시작을 막는 가드가 없다.
- `this.game._profiles`, `this.game.players`, `this.game.sdk._players`, `this.game.sdk._messageHandlers` 같은 내부 구현에 직접 접근한다.
- 봇의 `progressUpdate`는 `board`를 싣지 않기 때문에, 진행이 시작되면 호스트 미니 보드가 비거나 의미 없는 상태가 될 수 있다.

즉, 현재 데모는 "한 번 돌아가는 시연"에는 가깝지만, 운영 안정성과 QA 재현성을 갖춘 Attract Mode는 아니다.

#### G. 규약 준수 측면에서 부분 미흡한 부분이 있다

이 게임은 호스트 메인 컨테이너의 `z-index` 규칙은 잘 지켰다. 다만 `.hidden { display: none !important; }` 형태의 공통 유틸리티 클래스는 로컬 CSS에 명시돼 있지 않고, `.dp-overlay.hidden`, `.dp-screen.hidden`, `.dp-winner-display.hidden`처럼 개별 선택자에 의존한다.

현재 구조에서는 동작하더라도, 이후 UI 요소가 늘어나면 "hidden은 붙었는데 숨지지 않는" 류의 회귀가 생길 여지가 있다.

### 1.3 종합 진단

`Digit Puzzle`의 상태를 한 문장으로 요약하면 다음과 같다.

> 코어 게임성은 충분히 좋지만, 결과 페이즈와 재접속, 반복 플레이, 데모 모드의 마감 품질이 아직 프로덕션 수준까지 올라오지 않은 상태다.

좀 더 실무적으로 표현하면 다음과 같다.

- 게임 아이디어: 좋음
- 플랫폼 적합성: 좋음
- 코드 구조: 대체로 양호
- 상태 복구 안정성: 보완 필요
- 결과 연출/재대결 유도: 미흡
- 데모/운영 툴링: 미흡

## 2. 대중성 강화 요소

### 제안 1. 레이스 쇼맨십 패키지

가장 먼저 보강해야 할 것은 "막판 추월이 보이는 공용 화면"이다. 현재도 선두를 읽을 수는 있지만, 관전자에게 감정적 피크를 만들 정도로 강하지는 않다.

구체적 제안은 다음과 같다.

- 호스트 대시보드에서 선두와 2위를 `TOP 1`, `CHASE` 배지로 강조한다.
- 진행률 80% 이상 또는 해결 직전 추정 구간에 들어가면 카드 외곽 펄스, 미세 줌, 긴장음 같은 마이크로 연출을 넣는다.
- 우승 순간에는 `winner-display`만 노출하지 말고 결과 오버레이로 전환해 1위부터 순차 공개한다.
- 결과 화면에 `몇 수 차`, `몇 초 차`, `선두와의 차이`를 넣어 "아깝게 졌다"는 감정을 남긴다.

이 보강은 규칙 변경 없이도 관전 재미와 재대결 의지를 동시에 끌어올린다.

### 제안 2. 모바일 조작 피드백 패키지

슬라이딩 퍼즐에서 초보자가 가장 빨리 좌절하는 지점은 "무엇이 움직이고, 방금 내가 제대로 입력했는가"를 즉시 체감하지 못할 때다. 따라서 모바일 손맛은 장식이 아니라 이탈률 방어 수단이다.

구체적 제안은 다음과 같다.

- 빈칸과 같은 행/열에 있는 이동 가능 타일에 은은한 하이라이트를 준다.
- 유효 이동에는 짧은 햅틱, 무효 탭에는 아주 짧은 흔들림/탁 피드백을 준다.
- 여러 칸이 한 번에 밀릴 때 이동 경로를 0.15~0.2초 정도 시각적으로 남겨 조작 결과를 명확히 한다.
- `correctCount` 상승 또는 실제 난이도 완화 구간에서 작은 성공 피드백을 넣어 성취감을 강화한다.

이 패키지는 초심자의 체감 난도를 낮추고, 숙련자에게는 손맛을 준다.

### 제안 3. 첫 판 이탈을 줄이는 온보딩 + 라운드 구조 보강

이 게임은 규칙 자체는 간단하지만, "줄 전체가 밀린다", "같은 보드로 동시에 레이스한다", "준비 완료 후 즉시 시작된다"는 핵심을 20초 안에 이해시켜야 한다. 또한 한 판이 끝난 뒤 곧바로 "한 판 더"가 이어질 장치가 필요하다.

구체적 제안은 다음과 같다.

- 호스트 로비에 3컷 튜토리얼을 넣어 `같은 보드 -> 줄 밀기 -> 먼저 완성`을 시각적으로 설명한다.
- 모바일 첫 입장 시 1회성 튜토리얼 애니메이션 또는 2~3수 체험 퍼즐을 제공한다.
- 입문용 `Assist ON` 모드를 두어 첫 경기에서는 이동 가능 줄 강조를 더 강하게 켠다.
- 단판 종료 후 바로 리셋하는 대신 `3전 2선`, `베스트 타임 누적`, `승점 2점제` 같은 짧은 라운드 구조를 옵션으로 검토한다.

핵심은 정규 4x4 모드를 버리는 것이 아니라, 초보자와 반복 플레이어 모두가 다시 들어올 사다리를 만드는 것이다.

## 3. 가상 전문가 회의록 (Decision Making Meeting)

### 3.1 회의 목적

다음 3개 안건의 적용 타당성과 우선순위를 결정한다.

1. 레이스 쇼맨십 패키지
2. 모바일 조작 피드백 패키지
3. 온보딩 + 라운드 구조 보강

### 3.2 참석자별 의견

**PMOrchestrator**

현재 문제는 코어 게임이 약해서가 아니라, 장면 전환과 결과 전달이 약해서 생기는 체감 완성도 부족이라고 판단했다. 공용 화면이 "누가 이기고 왜 아까웠는지"를 더 크게 전달해야 한다.

**GameScout**

슬라이딩 퍼즐은 이미 대중에게 친숙한 장르라 규칙 자체가 바이럴 포인트가 되기는 어렵다. 대신 막판 추월, 1위 교체, 우승 세리머니처럼 멀리서 봐도 눈에 들어오는 순간을 만드는 쪽이 흥행에 더 직접적이라고 보았다.

**KidsBoardGameExpert**

아동과 가족 단위 플레이에서는 허용된 입력을 빨리 알아차리는 것이 가장 중요하다. 첫 판에서 "뭐가 움직이는지 모르겠다"가 오면 바로 이탈한다. 그래서 이동 가능 줄 강조와 무효 입력 피드백은 높은 우선순위를 받아야 한다고 보았다.

**OnlineGameProducer**

지금 구조는 단판 승부형이라 빠르고 간결하지만, 결과 화면이 약하면 재대결 버튼을 누를 이유가 약해진다. 내 등수, 선두와의 차이, 아쉬운 포인트를 보여줘야 리텐션이 생긴다고 판단했다. 짧은 세트전 옵션도 검토 가치가 있다고 봤다.

**UIUXDesigner**

모바일 레이아웃은 깔끔하지만 손가락 피드백은 아직 기능형이다. 유효 이동/무효 이동의 차이를 더 분명히 보여주고, 호스트 결과 화면은 "정보판"이 아니라 "이벤트 화면"처럼 설계해야 감정 밀도가 오른다고 의견을 냈다.

**TechAnalyst**

세 안건 모두 기술적으로 무리한 수준은 아니다. 다만 결과 페이즈 누락, 재접속 타이머 정지, 리스너 누적, 데모의 내부 필드 직접 조작 같은 품질 리스크를 먼저 정리하지 않으면 연출 추가가 회귀 버그를 키울 수 있다고 지적했다.

**SeniorGameDev**

우선순위는 "구조 보정 후 연출 보강"이 맞다고 보았다. 호스트 결과 상태를 명시적으로 만들고, 모바일 입력 리스너를 mount/unmount 가능한 구조로 바꾸면 이후 마이크로 애니메이션, 오디오, 튜토리얼을 올리기 쉬워진다. 데모 시뮬레이터도 공개 메서드 기반으로 재설계하는 편이 안전하다고 판단했다.

### 3.3 핵심 논점

#### 논점 1. 무엇이 가장 빨리 체감 재미를 올리는가

다수 의견은 `레이스 쇼맨십 패키지`였다. 이유는 단순하다. 규칙은 이미 이해 가능한 수준이고, 지금 부족한 것은 "공용 화면에서 반응을 끌어내는 힘"이기 때문이다.

#### 논점 2. 초보자 이탈을 가장 효과적으로 막는 장치는 무엇인가

`온보딩`보다 `조작 피드백`이 먼저라는 의견이 우세했다. 설명을 길게 늘리는 것보다, 첫 입력에서 바로 "아, 이게 움직이는구나"를 느끼게 만드는 편이 효과적이라는 판단이다.

#### 논점 3. 기술 부채와 대중성 기능 중 무엇을 먼저 처리해야 하는가

전원 합의에 가까웠다. 결과 페이즈, 재접속, 리스너 누적, 데모 안정성을 먼저 보정한 뒤 연출과 사운드를 얹는 순서가 맞다. 그렇지 않으면 디버깅 난이도만 커진다.

### 4.3 우선 수정 방향

#### P0. 구조적 결함 먼저 해결

1. 호스트 결과 상태를 명시적으로 완성한다.
2. `winner-display`와 `result-rankings`의 역할을 분리하고, 게임 종료 시 반드시 `setPhase('result')`를 호출한다.
3. 결과 단계 재접속은 `gameFinished`로 복구하고, 플레이 단계 재접속은 타이머까지 재개되도록 수정한다.
4. 모바일 보드 이벤트는 `bind/unbind` 또는 1회 바인딩 구조로 바꿔 누적을 제거한다.
5. 플레이어 퇴장 시 호스트 대시보드를 즉시 다시 렌더링한다.

#### P1. 결과 감정선과 조작 피드백 보강

1. 모바일 결과 화면에서 `rankings`를 실제로 렌더링해 내 순위와 선두와의 차이를 보여준다.
2. 호스트 결과 화면을 우승 세리머니 중심으로 재구성하고, `몇 수 차`, `몇 초 차`를 짧게 요약한다.
3. 이동 가능 타일 하이라이트, 무효 입력 피드백, 짧은 햅틱을 넣어 첫 판 만족도를 높인다.

#### P2. 반복 플레이와 확장성 보강

1. 첫 입장 온보딩 또는 `Assist ON` 옵션을 추가한다.
2. 단판 외에 짧은 세트전 옵션을 검토한다.
3. 진행률 계산 로직을 `correctCount` 단일 지표보다 더 현실적인 근접도 지표로 확장할지 검토한다.

### 4.4 🤖 데모 시뮬레이터 개선점 및 수정 가이드라인

현재 `PuzzleDemoSimulator.js`는 기반은 있지만, 운영 및 QA 관점에서는 다음 방향으로 개편하는 것이 바람직하다.

#### 1. 파일/책임 구조 정리

- 파일명을 프로젝트 규약에 맞춰 `DemoSimulator.js`로 통일하거나, 최소한 `PuzzleDemoSimulator.js`를 `DemoSimulator.js`의 게임별 구현으로 명시하는 브리지 구조를 둔다.
- `startDemo()`, `stopDemo()`, `isDemoActive()`, `canStartDemo()` 같은 공개 API를 제공한다.

#### 2. 내부 필드 직접 조작 제거

- `this.game._profiles`, `this.game.players`, `this.game.sdk._players`를 직접 만지지 말고, `PuzzleGame` 쪽에 데모 전용 공개 메서드를 둔다.
- 예시:
  - `game.enterDemoLobby(bots)`
  - `game.applyDemoProgress(botId, snapshot)`
  - `game.finishDemoRound(botId, result)`
  - `game.exitDemoMode()`

이렇게 해야 실제 게임 상태와 데모 상태가 섞이지 않는다.

#### 3. 실플레이어 가드와 중단 UX 추가

- 실제 플레이어가 1명이라도 있으면 데모 시작을 막거나 강제 확인을 요구한다.
- 로비에 `데모 실행`과 `데모 중단` 버튼을 명확히 분리한다.
- 호스트 상단 앱바나 고정 배너에 `데모 진행 중` 표시를 두고, 누가 봐도 실게임이 아니라는 점을 알 수 있게 한다.

#### 4. 시뮬레이션 데이터 품질 개선

- 봇 `progressUpdate`에도 반드시 `board` 스냅샷을 포함해 호스트 미니 보드가 비지 않게 한다.
- 순수 랜덤 증가 대신 "초반 느림 -> 중반 추월 -> 막판 1위 결정" 같은 시나리오형 곡선을 지원한다.
- QA용 모드에서는 고정 시드 기반으로 매번 같은 결과를 재현할 수 있게 한다.

#### 5. 종료 정리와 회귀 안정성 강화

- 데모 종료 시 타이머, 배너, QR 블러, 봇 상태, 결과 오버레이, 승자 표시를 모두 정리한다.
- `onReset()`과 `stopDemo()`의 책임을 분리해 이중 정리나 누락이 없도록 한다.
- 데모 종료 후 즉시 로비 플레이어 목록과 준비 수가 정상 상태로 돌아와야 한다.

#### 6. 권장 데모 시나리오

가장 운영 친화적인 흐름은 아래와 같다.

1. 로비에서 봇 3명 자동 입장
2. 1.5초 내 준비 완료 연출
3. 동일 보드 배포 후 20초 내외 레이스 진행
4. 중간에 한 번 선두 교체 연출 발생
5. 결과 오버레이와 순위 공개
6. 5~6초 후 자동 리셋 또는 운영자 수동 중단

이 흐름은 관객 시연과 회귀 테스트 모두에 유용하다.

## 결론

`Digit Puzzle`은 기본 골격이 좋은 게임이다. 공정한 공통 보드, 모바일 중심 입력, 호스트 대시보드라는 세 축은 이미 성립돼 있다. 문제는 게임성보다 마감 품질이다. 결과 페이즈, 재접속, 반복 플레이, 데모 모드의 구멍을 먼저 메운 뒤, 레이스 쇼맨십과 조작 피드백을 보강하면 대중성은 꽤 큰 폭으로 올라갈 가능성이 높다.

우선순위는 명확하다. 먼저 구조적 결함을 정리하고, 다음으로 결과 감정선과 손맛을 보강하고, 마지막으로 온보딩과 세트전 같은 확장 요소를 붙이는 순서가 가장 안전하다.
