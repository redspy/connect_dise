# `trivia-vegas` 평가 및 개선안

- 작성일: 2026-07-07
- 분석 범위:
  - `games/trivia-vegas/host/main.js`
  - `games/trivia-vegas/host/DemoSimulator.js`
  - `games/trivia-vegas/host/index.html`
  - `games/trivia-vegas/host/style.css`
  - `games/trivia-vegas/mobile/main.js`
  - `games/trivia-vegas/mobile/index.html`
  - `games/trivia-vegas/mobile/style.css`
  - `tests/trivia-vegas/demo.spec.js`
- 분석 방식: 소스 코드 정적 분석과 빌드 검증 기반 평가. 실기기 다중 접속 QA와 브라우저 시각 검증은 이번 문서 범위에 포함하지 않았다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`trivia-vegas`의 코어 루프는 `숫자 퀴즈 추정 → 제출 답안 정렬 → 정답을 초과하지 않는 가장 가까운 답에 베팅 → 배당 정산`으로 구성된다. 구조 자체는 보드게임 `Wits & Wagers` 계열의 재미를 카지노 감성으로 옮겨온 형태이며, 이 플랫폼의 "TV는 공동 보드, 모바일은 비밀 입력 장치"라는 목적과 궁합이 좋다.

이 게임이 기본적으로 재미있는 이유는 단순한 상식 퀴즈가 아니기 때문이다. 정답을 모르는 플레이어도 다른 사람의 추정치를 읽고 베팅으로 역전할 수 있으므로, 지식 격차가 큰 모임에서도 끝까지 참여할 명분이 생긴다. 즉, 재미가 `정답 맞히기` 하나에만 걸려 있지 않고 `남의 감각 읽기`, `리스크 감수`, `역전 기대감`으로 분산된다.

특히 강점은 다음 네 가지다.

| 평가 축 | 판단 | 코멘트 |
| --- | --- | --- |
| 규칙의 기본 이해도 | 높음 | "숫자를 적고, 정답을 넘지 않는 가장 가까운 답에 칩을 건다"는 한 문장으로 핵심 설명이 가능하다. |
| 플랫폼 적합성 | 높음 | 정렬된 답안판을 TV에서 함께 보고, 각자 폰에서는 비밀리에 추정과 베팅을 입력하는 구조가 자연스럽다. |
| 역전 가능성 | 중상 | 내 추정이 틀려도 베팅으로 복구할 수 있어, 지식 우위 플레이어의 독주를 어느 정도 완화한다. |
| 관전자성 | 중상 | 호스트 화면의 펠트 보드와 칩 시각화가 있어 "누가 어디에 걸었는지"를 같이 보는 맛이 있다. |

반대로 대중성 기준에서 약한 지점도 뚜렷하다.

| 관찰 포인트 | 현재 상태 | 영향 |
| --- | --- | --- |
| 질문 풀 규모 | 기본 질문이 7개뿐이며 모두 숫자 상식형이다. | 2~3판만 반복해도 문제를 외우기 시작해 리플레이성이 빠르게 떨어진다. |
| 룰 학습 보조 | "정답을 초과하지 않는 가장 가까운 값" 규칙을 시각적으로 가르치는 온보딩이 없다. | 첫 판에서 베팅 기준을 직관적으로 못 잡는 플레이어가 생길 수 있다. |
| 템포 제어 | 답안 정렬과 정산이 호스트 수동 버튼에 의존한다. | 리듬이 끊기고, 사회자가 익숙하지 않으면 게임이 늘어진다. |
| 개념 일관성 | 모바일에서 추정값과 슬롯 표기에 `$`가 섞이고 소수점 입력도 허용된다. | 퀴즈 값과 베팅 머니 개념이 혼재되어 초심자 이해를 방해한다. |

종합하면, 코어 아이디어는 분명히 매력적이다. "상식을 잘 몰라도 남의 감을 읽으면 이길 수 있다"는 구조는 파티 게임으로 좋은 방향이다. 다만 현재 구현은 첫 판 체험용 데모로는 충분히 작동하지만, 반복 플레이와 대중적 흥행을 견인할 정도의 콘텐츠 풀과 템포 설계는 아직 부족하다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

호스트 측은 `HostBaseGame`을 상속해 상태를 비교적 명확하게 나누고 있다. `_round`, `_roundPhase`, `_playerEstimates`, `_playerBalances`, `_playerBets`, `_sortedSlots`가 역할별로 분리되어 있어 읽기 쉽고, `lobby → playing → result` 전환도 `setPhase()` 규약을 잘 따른다. `hidden` 클래스와 호스트 메인 컨테이너의 `position: relative; z-index: 10;` 규칙도 지켜져 있어 프로젝트 공통 규약 준수도 양호하다.

호스트 구현의 장점은 다음과 같다.

| 항목 | 평가 | 근거 |
| --- | --- | --- |
| 상태 분리 | 좋음 | 추정, 자산, 베팅, 슬롯, 우승 슬롯이 각각 `Map` 또는 배열로 분리되어 있다. |
| 라운드 흐름 가독성 | 좋음 | `_startGame()`, `_startRound()`, `_sortEstimates()`, `_resolveBets()`, `_endGame()`으로 루프가 선형적으로 읽힌다. |
| 재접속 가드 | 보통 이상 | `onPlayerRejoin()`에서 `lobbyState`와 `rejoinState`를 구분해 보내므로 로비 프리징 위험을 줄였다. |
| 데모 모드 존재 | 좋음 | 별도 `DemoSimulator.js`와 로비 버튼이 있어 시연용 진입점은 확보되어 있다. |

하지만 "상용형 완성도"를 기준으로 보면 리스크도 분명하다.

| 구분 | 관찰 내용 | 영향 |
| --- | --- | --- |
| 모바일 베이스 클래스 미사용 | 모바일 구현은 `MobileSDK`를 직접 다루며 `MobileBaseGame`을 상속하지 않는다. | 프로젝트 권장 패턴에서 벗어나며, `onJoin/onRejoin/onReset/showScreen` 중심의 표준 복구 흐름과 홈 버튼 주입을 활용하지 못한다. |
| 재접속 복원 범위 부족 | `rejoinState`는 라운드 페이즈는 복구하지만, `resolved` 상태에서 개인 당첨금·선택 슬롯·베팅 확정 여부 같은 세부 정보는 복원하지 않는다. | 재접속 플레이어 입장에서는 "왜 자산이 이렇게 됐는지" 맥락이 끊긴다. |
| 중복 추정치 보너스 공정성 | 동일한 숫자를 여러 명이 적었을 때 슬롯은 합쳐지지만, `creatorId`는 1명만 남아 정확 추정 보너스 `+$200`을 독점한다. | 같은 답을 낸 플레이어 간 보상 공정성이 깨진다. |
| 수동 오퍼레이터 의존 | 모든 답안 제출 후에도 자동 정렬되지 않고, 데모 모드조차 `답안 정렬하기` 버튼 입력을 요구한다. | 실제 모임이나 전시 환경에서 템포가 느려지고, 데모가 완전 자동 attract mode가 되지 못한다. |
| 내부 API 의존 데모 | `DemoSimulator`가 `game.players`, `sdk._players`, `sdk._messageHandlers`를 직접 건드린다. | SDK 구현이 바뀌면 데모가 쉽게 깨지고, 실제 메시지 경로를 충분히 대표하지 못한다. |
| 실유저와 데모 충돌 가능성 | 데모 시작 시 현재 플레이어 맵을 비우고 봇만 주입한다. | 사람이 접속한 로비에서 데모를 실행하면 실제 세션 상태를 망가뜨릴 위험이 있다. |

UI 구현 완성도는 "방향은 좋지만 밀도는 낮다" 쪽에 가깝다. 호스트는 카지노 펠트 느낌과 슬롯 칩 배치를 비교적 잘 잡았고, 모바일도 커스텀 숫자 키패드를 사용해 소프트 키보드 충돌을 피한 점이 좋다. 다만 현재 피드백은 `vibrate()`와 간단한 색 변화에 주로 의존하므로, 카지노 테마의 감정 피크를 충분히 살릴 정도로 풍부하지는 않다.

### 1.3 종합 판정

`trivia-vegas`는 기획 방향이 명확하고, Host 쪽 상태 관리도 비교적 정돈되어 있어 "플레이 가능한 시연 빌드"로서는 충분히 설득력이 있다. 특히 공용 화면에 정렬된 답안판이 뜨고, 각자 스마트폰으로 비밀 추정과 베팅을 수행하는 구조는 이 플랫폼의 목적을 잘 살린다.

다만 현재 상태를 냉정하게 분류하면 `출시 직전 상용 빌드`보다는 `완성도 높은 프로토타입 또는 내부 데모 버전`에 가깝다. 이유는 세 가지다.

1. 첫 판 진입 장벽을 낮추는 UX 가이드가 부족하다.
2. 데모 모드와 재접속 복원이 "있다" 수준이지, 완전히 안전하고 자율적이지는 않다.
3. 질문 풀과 연출 밀도가 얕아 반복 플레이의 흥행 지속력이 약하다.

즉, 뼈대는 좋다. 이제 필요한 것은 룰 단순화가 아니라 `연출 강화`, `표준 SDK 패턴 정렬`, `리플레이성 확장`, `데모 자율화`다.

## 2. [대중성 강화 요소]

아래 3가지는 현재 구조 위에서 비교적 자연스럽게 반영 가능하면서, 플레이어 체감 품질을 크게 올릴 가능성이 높은 항목들이다.

### 2.1 제안 1: 카지노 쇼 감성을 살리는 마이크로 애니메이션·사운드 패키지

현재 버전에도 승리 슬롯 글로우와 모바일 진동은 있다. 하지만 `답안 정렬`, `베팅 마감`, `배당 정산`, `최종 순위 발표` 같은 감정 피크가 시청각적으로 충분히 구분되지는 않는다.

권장안은 다음과 같다.

| 적용 지점 | 구체 제안 | 기대 효과 |
| --- | --- | --- |
| 답안 정렬 직전 | 제출 카드가 중앙으로 빨려 들어간 뒤 슬롯 보드가 한 장씩 펼쳐지는 애니메이션 | "이제 퀴즈가 베팅 게임으로 전환된다"는 감정 전환을 명확히 만든다. |
| 베팅 카운트다운 | 마지막 5초에 HUD 점멸, 칩 소리, 짧은 드럼롤 추가 | 현장 긴장감과 집중도가 올라간다. |
| 배당 정산 | 우승 슬롯 금빛 펄스, 패배 슬롯 딤 처리, 칩 수거/증식 모션 | 정산 결과를 말로 설명하지 않아도 직관적으로 이해시킬 수 있다. |
| 모바일 | 슬롯 선택, 베팅 확정, 당첨, 탈락에 서로 다른 햅틱 패턴과 짧은 오디오 큐 제공 | 조작 손맛이 살아나고, 한 손 플레이의 만족도가 높아진다. |
| 최종 결과 | 1등 플레이어 강조, 점수 카운트업, 잭팟성 배경 사운드 | "한 판 끝냈다"는 만족감이 강해진다. |

핵심은 거대한 리디자인이 아니라, 이미 있는 단계 전환에 `짧고 강한 피드백`을 얹는 것이다. 파티 게임은 룰보다 "순간의 반응"이 기억에 남는다.

### 2.2 제안 2: 첫 판 60초 이해를 위한 룰 온보딩·조작 피드백 정리

이 게임에서 가장 헷갈리기 쉬운 부분은 지식이 아니라 규칙 해석이다. `정답을 넘지 않는 가장 가까운 값`이라는 판단 기준을 한 번에 이해시키지 못하면, 첫 판 베팅 단계에서 플레이어가 얼어붙는다.

필수 보강 포인트는 다음과 같다.

| 적용 지점 | 구체 제안 | 기대 효과 |
| --- | --- | --- |
| 모바일 첫 진입 | 2~3장 분량의 초간단 룰 카드 제공. 예: `정답 330`, `320에 베팅 성공`, `350은 초과라 탈락` 같은 시각 예시 | 사회자 설명 부담을 줄이고, 첫 판 오류를 크게 줄인다. |
| 숫자 입력기 | 소수점 키 제거, 추정값 표기의 `$` 제거, 정답 단위만 질문과 함께 명시 | 퀴즈 값과 베팅 머니 개념이 섞이는 문제를 해소한다. |
| 입력 검증 | `alert()` 대신 인라인 경고와 제출 버튼 상태 피드백 사용 | 브라우저 기본 다이얼로그로 몰입이 끊기는 문제를 줄인다. |
| 베팅 상태 | 선택 슬롯, 현재 베팅금, 확정 여부를 더 크게 표시하고 제출 후 "대기 중" 상태를 명확히 구분 | 조작 불안감을 줄이고, 중복 탭 실수를 예방한다. |
| 호스트 보드 | 답안 정렬 후 "초과하면 탈락" 보조 라벨 또는 작은 룰 배지 노출 | TV만 보고 있는 관전자도 현재 승부 원리를 바로 이해할 수 있다. |

이 제안은 화려한 기능 추가보다 비용 대비 효과가 크다. 대중성은 대부분 "첫 라운드가 얼마나 매끄럽게 굴러가느냐"에서 갈린다.

### 2.3 제안 3: 질문 팩 확장과 자동 템포 제어를 결합한 리플레이성 패키지

현재 가장 큰 장기 리스크는 질문 수와 라운드 템포다. 문항 수가 7개뿐이면 기억 게임이 되어버리고, 호스트가 단계마다 수동 클릭해야 하면 반복 플레이 피로가 빨리 온다.

권장안은 아래와 같다.

| 적용 지점 | 구체 제안 | 기대 효과 |
| --- | --- | --- |
| 질문 데이터 | `역사`, `과학`, `일상`, `스포츠`, `K-컬처` 같은 카테고리 팩과 `쉬움/보통/어려움` 난이도 태그 추가 | 모임 성격에 맞춘 플레이가 가능해지고 반복 플레이 수명이 늘어난다. |
| 매치 길이 | `1라운드 체험`, `3라운드 기본`, `5라운드 확장` 프리셋 제공 | 행사장/가족 모임/스트리밍 등 다양한 상황에 대응하기 쉬워진다. |
| 자동 진행 | 전원 제출 후 1.5초 뒤 자동 정렬, 베팅 종료 후 자동 정산, 라운드 결과 후 자동 다음 라운드 대기 카운트 제공 | 사회자 의존도를 줄이고 게임 리듬을 안정화한다. |
| 룰 명확화 | 동일 추정치 보너스 분배 규칙을 명문화하고 UI에도 표시 | 분쟁 포인트를 줄이고 공정성 인식을 높인다. |

이 제안은 단순히 콘텐츠를 늘리는 것이 아니라 `계속 틀어도 질리지 않는 게임`으로 만드는 작업이다. 대중적 흥행을 원하면, 질문 풀과 라운드 템포를 반드시 함께 다뤄야 한다.

### 4.3 `DemoSimulator.js`의 현재 한계

`DemoSimulator.js`는 존재 자체는 긍정적이지만, 현재 구현은 "현장 시연의 초안"에 가깝고 "회귀 검증 가능한 완전한 데모 드라이버"라고 보기는 어렵다.

| 개선 포인트 | 현재 상태 | 문제점 |
| --- | --- | --- |
| 자율 진행성 | 봇 추정 제출과 봇 베팅은 자동이지만, 답안 정렬은 호스트 버튼 클릭이 필요하다. | attract mode가 완전 자동으로 1판을 완주하지 못한다. |
| 상태 주입 방식 | `players`, `sdk._players`, `_playerNicknames`를 직접 수정한다. | 실제 세션 이벤트를 통과하지 않아 운영 경로와 테스트 경로가 다르다. |
| 내부 핸들러 호출 | `sdk._messageHandlers.get(...)`를 직접 사용한다. | SDK 내부 구조 변경에 취약하고 캡슐화가 깨진다. |
| 실유저 충돌 가드 | 데모 시작 전에 실제 접속 플레이어 존재 여부를 검사하지 않는다. | 라이브 로비에서 데모 실행 시 사람 플레이어 상태를 덮어쓸 수 있다. |
| 시나리오 다양성 | 정상 제출/베팅 흐름 위주이며, `Banker` 승리·동점 추정·재접속·무응답 분기가 없다. | 예외 상황 회귀 검증력이 낮다. |
| 정리 루틴 | `setTimeout`만 추적하고, 실제 플레이어 상태 스냅샷 복구 개념이 없다. | 중단 후 원상 복구 신뢰도가 낮다. |

### 4.4 `DemoSimulator.js` 수정 가이드라인

안전하고 활용도 높은 데모로 바꾸려면 아래 순서가 적절하다.

1. **Attract Demo와 Regression Demo를 분리한다.**
   - `AttractDemo`는 화면이 계속 살아 움직이고 빠르게 재미를 보여주는 데 집중한다.
   - `RegressionDemo`는 동일 시나리오를 결정론적으로 재현하는 테스트 드라이버에 집중한다.

2. **실제 플레이어 상태를 스냅샷하고, 실유저가 있으면 데모 실행을 차단하거나 별도 샌드박스 세션을 만든다.**
   - 현재처럼 `players.clear()`로 시작하면 라이브 로비를 망가뜨릴 수 있다.
   - 최소한 `this.game.players.size > 0`일 때 데모 버튼을 비활성화하거나 경고 배너를 띄워야 한다.

3. **호스트 액션까지 포함한 자동 진행 스케줄러를 추가한다.**
   - 봇 추정 제출 후 전원 제출이 끝나면 `queueHostSort()`가 자동 실행되어야 한다.
   - 베팅 종료 후에는 `queueHostResolve()`, 결과 후에는 `queueNextRound()`까지 이어져야 진짜 attract mode가 된다.

4. **내부 `_messageHandlers` 직접 호출 대신 공용 진입점 또는 데모 전용 어댑터를 둔다.**
   - 예: `submitEstimateForPlayer(id, value)` 같은 게임 레벨 메서드를 만들고, 실제 메시지 핸들러와 데모가 같은 로직을 공유하게 한다.
   - 이렇게 해야 SDK 내부 구조가 바뀌어도 데모가 덜 깨진다.

5. **예외 시나리오를 최소 4종 이상 준비한다.**
   - 정상 우승 시나리오
   - `Banker` 승리 시나리오
   - 동일 추정치 발생 시나리오
   - 재접속 또는 타임아웃 시나리오
   - 이 정도는 있어야 정산, 복원, 보너스, 예외 분기를 한 번에 검증할 수 있다.

6. **타이머와 인터벌을 공통 스케줄러로 관리한다.**
   - `scheduleTimeout`, `scheduleInterval`, `clearAllSchedules` 같은 래퍼를 두고, `stopDemo()`와 `onReset()`에서 같은 해제 루틴을 사용해야 한다.
   - 호스트 본 게임의 베팅 타이머와 데모 스케줄을 따로 놀게 두면 중단 직후 레이스 컨디션이 생길 수 있다.

7. **호스트 화면에 데모 상태 배지와 시나리오 이름을 노출한다.**
   - 예: `DEMO / ROUND 2 / BANKER WIN SCENARIO`
   - 브라우저 검증과 현장 시연 모두에서 현재 데모가 어떤 분기를 보여주는지 즉시 이해할 수 있다.

### 4.5 우선 수정 방향 요약

가장 먼저 손봐야 할 항목은 아래 다섯 가지다.

1. 모바일 구현을 `MobileBaseGame` 기반 클래스로 재정렬해 표준 라이프사이클과 재접속 흐름을 맞춘다.
2. 동일 추정치 보너스 규칙을 명확히 정의하고, 구현도 공정하게 수정한다.
3. 데모 모드를 완전 자동 진행형으로 바꾸고, 실유저 세션 오염을 막는다.
4. 숫자 입력기와 베팅 UI에서 `$` 표기와 소수점 입력을 제거해 의미 계층을 정리한다.
5. 질문 팩 확장과 자동 정렬/정산으로 반복 플레이 템포를 끌어올린다.

이 다섯 가지가 정리되면 `trivia-vegas`는 "아이디어가 좋은 데모"에서 한 단계 올라가, 대중 앞에서 반복 플레이해도 설명이 쉽고 템포가 살아 있는 파티 게임으로 발전할 가능성이 크다.
