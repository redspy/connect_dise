# 그림 릴레이 평가 및 개선안

- 작성일: 2026-07-06
- 분석 대상: `games/relay-drawing/host/`, `games/relay-drawing/mobile/`, `games/relay-drawing/shared/AudioManager.js`, `games/relay-drawing/host/RelayDemoSimulator.js`
- 참고 문서: `docs/games/relay-drawing/spec2.0.md`, `AGENTS.md`, `docs/agents/roles.md`
- 분석 방식: 소스 코드 정적 분석 기반 평가. 실제 다기기 E2E 플레이, 브라우저 UI 시각 검증, 오디오 체감 QA는 이번 문서 범위에 포함하지 않았다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`그림 릴레이`는 전형적인 텔레스트레이션 계열 파티 게임을 `Host TV + N Mobile` 구조에 잘 옮긴 작품이다. 각 플레이어는 스마트폰에서 제시어를 그림으로 그리거나, 이전 플레이어의 그림을 보고 단어로 추측한다. 이 과정이 체인 단위로 이어지고, 마지막에 호스트가 시작 제시어부터 최종 결과까지 순서대로 공개한다. 따라서 이 게임의 핵심 재미는 정답 경쟁보다 **오해가 연쇄적으로 증폭되는 과정**과 **결과 발표에서 터지는 집단 리액션**에 있다.

이 구조가 플랫폼과 잘 맞는 이유는 공용 화면과 개인 화면의 책임이 명확하게 분리되기 때문이다.

- 모바일은 비밀 입력 장치다. 플레이어는 자신의 턴에 필요한 정보만 보고 조용히 수행한다.
- 호스트 화면은 관전 장치다. 실시간 스트로크 복원, 제출 상태, 결과 발표가 같은 공간의 웃음 포인트를 만든다.
- 최종 결과는 모두가 같은 TV를 보며 동시에 확인하므로, 같은 테이블에 둘러앉아 보드게임을 하는 감각이 살아난다.

코어 재미를 구성하는 축은 아래와 같다.

| 축 | 분석 |
| --- | --- |
| 실시간 구경 재미 | 모바일이 `strokeStart`, `strokeMove`, `strokeEnd`를 보내고 호스트가 플레이어별 미니 캔버스로 즉시 복원해, 대기 시간이 단순 공백으로 남지 않는다. |
| 오해의 증폭 | 그림과 단어가 번갈아 이어지므로 정보 손실이 설계 의도 자체다. 그림 실력, 추측 실수, 엉뚱한 제시어가 누적될수록 웃음 포인트가 커진다. |
| 결과 발표의 서사성 | `storyChains`를 따라 시작 단어부터 마지막 결과까지 단계적으로 공개하는 구조가 "오해의 역사"를 보여 주는 데 적합하다. |
| 같은 공간의 반응 | 플레이어는 자기 폰에서 과제를 수행하지만, 재미의 정점은 TV 앞에서 서로 반응을 확인하는 순간에 온다. 플랫폼 목적과 부합한다. |

현재 구현은 코어 자체는 이미 강하다. 특히 제시어 풀도 충분히 엉뚱하고, 그림과 단어를 번갈아 받는 흐름이 명확해서 첫 설명만 이해하면 누구나 금방 참여할 수 있다. 다만 대중성 관점에서는 몇 가지 마찰점이 보인다.

- 호스트 기본 설정이 `2인 시작 가능`, `그림 제한 시간 = 제한 없음`이라 첫 판 템포가 쉽게 늘어진다.
- 결과 발표 구조는 좋지만, 공개 순간의 사운드와 카드 등장 리듬이 아직 "쇼" 수준까지는 올라가지 않았다.
- 아동/가족 관점의 진입 장벽을 낮추기 위한 이모지 보조 입력은 좋지만, "이 게임은 잘 그리는 게임이 아니라 오해가 커질수록 웃긴 게임"이라는 핵심 메시지를 로비 단계에서 더 빨리 전달할 필요가 있다.

정리하면 `그림 릴레이`는 **기획 코어가 이미 살아 있는 파티 게임**이다. 구조를 갈아엎을 이유는 없고, 웃음이 터지는 장면을 더 빨리, 더 크게 보이게 만드는 연출과 운영 품질 보강이 핵심 과제다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

아키텍처는 전반적으로 건전하다. 호스트는 `HostBaseGame`, 모바일은 `MobileBaseGame`을 상속하며, authoritative state를 호스트가 보유하는 구조가 분명하다. 게임 고유 상태는 호스트의 `_storyChains`, `_currentRound`, `_timeLimitDraw`, `_timeLimitText`, `_currentStoryIndex`에 집중되어 있고, 모바일은 프로필 입력, 그림 입력, 단어 입력, 공유 액션 같은 사용자 인터랙션에 집중한다.

구현 강점은 다음과 같다.

- **플랫폼 SDK 규약 준수**
  - 호스트는 `setPhase()`, 모바일은 `showScreen()`을 중심으로 화면 전환 규약을 잘 지킨다.
  - `onSetup`, `onPlayerJoin`, `onPlayerRejoin`, `onReset`, `onRejoin` 훅을 전반적으로 올바르게 사용한다.

- **실시간 드로잉 동기화 품질**
  - 모바일은 좌표를 0~1 정규화해 전송하고, 호스트는 800x600 논리 캔버스로 복원한다.
  - 호스트는 `seqBuffer`와 `nextSeq`를 사용해 `strokeMove` 패킷 역전 수신을 보정한다.
  - P2P 우선 전송 구조와도 잘 맞는 데이터 형식이다.

- **모바일 플레이 흐름의 완성도**
  - `setup -> waiting -> draw/word -> standby -> spectate` 흐름이 단순하고 이해하기 쉽다.
  - 프로필을 손그림 아바타로 만드는 요소, 4:3 캔버스 잠금, 이모지 보조 입력, 최종 Web Share 연결은 상품성이 있다.

- **결과 카드 파이프라인**
  - 호스트가 체인 전체를 합성한 뒤 WebP 이미지로 압축하고, 모바일이 이를 네이티브 공유 또는 다운로드로 이어받는 구조는 확장성이 좋다.
  - 파티 게임이 끝난 뒤 "작품"을 남기는 장치가 있어 재방문보다 외부 확산에 유리하다.

아키텍처 평가를 표로 정리하면 다음과 같다.

| 평가 축 | 관찰 | 평가 |
| --- | --- | --- |
| 플랫폼 SDK 준수 | Host/Mobile 모두 베이스 클래스 패턴과 phase/screen 전환 규약을 비교적 충실히 따른다. | 우수 |
| 상태 권한 분리 | 라운드, 제출 여부, 타이머, 결과 발표, 공유 카드 생성이 호스트 기준으로 일원화되어 있다. | 우수 |
| 실시간 드로잉 동기화 | 정규화 좌표 + 시퀀스 버퍼 방식으로 패킷 꼬임에 방어적이다. | 우수 |
| 모바일 UX 기반 기능 | 4:3 캔버스, 이모지 입력, 제출 대기, 결과 공유까지 구현돼 있다. | 양호 |
| 재접속 복구 | 인게임 재접속은 대응하지만 `final` 단계의 공유 카드 복구가 비어 있다. | 보완 필요 |
| 이탈 복원력 | 플레이어 이탈 시 체인 무결성과 작성자 정보 보존이 약하다. | 보완 필요 |
| 프로필 지속성 | 닉네임만 `localStorage`에 저장되고, 아바타는 새로고침 시 보존되지 않는다. | 보완 필요 |
| 데모 시뮬레이터 | 존재 자체는 좋고 `HostBaseGame`의 idle auto-demo 훅과도 연결되지만, 운영 가능한 Attract Mode 수준은 아니다. | 미완성 |
| 사운드 안정성 | 외부 URL 의존형 사운드는 행사장/폐쇄망에서 지연 리스크가 있다. | 보완 필요 |

현재 코드에서 반드시 짚어야 할 구조적 공백은 아래와 같다.

#### 1. 중도 퇴장 시 체인 무결성이 깨질 수 있다

호스트 `onPlayerLeave()`는 `_profiles.delete(playerId)`와 로비 갱신만 수행하고, 진행 중인 `storyChains` 자체는 보정하지 않는다. 그런데 다음 라운드 소유권 전환은 `_rotateStoryChains()`가 `currentHolderId`의 `indexOf` 결과를 기반으로 계산한다. 이때 현재 홀더가 이미 나간 플레이어라면 `indexOf`가 `-1`이 되고, 결과적으로 체인이 첫 번째 플레이어 쪽으로 비정상 회전할 수 있다.

영향은 다음과 같다.

- 체인별 할당이 왜곡될 수 있다.
- 중간 단계가 비어도 결과 발표는 계속 진행돼 "왜 갑자기 이 사람이 두 번 연속 했지?" 같은 어색한 결과가 생길 수 있다.
- 자동 제출 fallback과 조합되면 빈 그림 또는 빈 단어가 의도치 않게 삽입될 수 있다.

#### 2. 결과 히스토리용 작성자 정보가 휘발된다

호스트는 라이브 프로필 정보를 `_profiles`에만 들고 있다. 그런데 퇴장 시 바로 삭제해 버리므로, 이미 제출이 끝난 그림이나 단어라도 결과 발표 시 작성자가 `?`로 바뀔 수 있다. 공유 카드 생성도 동일한 맵을 참조하므로, "누가 이렇게 그렸는가"라는 파티 게임의 중요한 웃음 정보가 사라질 수 있다.

이는 단순 UI 문제가 아니라 결과 서사의 일부 손실이다. `storyChains.steps`에는 `authorId`만 있고 작성 시점의 `nickname`, `avatar`, `color` 스냅샷이 없기 때문에 생기는 문제다.

#### 3. 재접속 시 아바타가 유지되지 않는다

모바일은 닉네임만 `localStorage`에 저장하고, `onRejoin()`에서는 현재 `profileCanvas`를 다시 `toDataURL()`로 읽어 호스트에 보낸다. 하지만 새로고침 후 프로필 캔버스는 기본 흰색 상태로 다시 초기화되므로, 기존에 그린 손그림 아바타가 복구되지 않고 빈 이미지가 재전송될 가능성이 높다.

즉, 현재 재접속은 "닉네임 복구"에는 성공하지만 "프로필 정체성 복구"에는 실패할 수 있다. 가족/아동 파티 게임에서 손그림 아바타는 작지만 중요한 몰입 요소이므로, 이 부분은 생각보다 체감 손실이 크다.

#### 4. `final` 단계 공유 카드의 재접속 복구가 비어 있다

호스트 `onPlayerRejoin()`은 `result`와 `final` 단계에서 모두 `showResults`만 다시 보내고 종료한다. 반면 최종 공유 카드 이미지는 `_autoBroadcastShareImage()`에서 `showFinalShareCard`를 한 번 브로드캐스트할 뿐, 캐시하거나 재송신하지 않는다. 따라서 `final` 단계에서 재접속한 모바일은 관전 화면에는 돌아와도 결과 카드 이미지는 받지 못한다.

여기에 추가로, 전역 CSS에는 `body.mobile-controller:not(.rd-mobile-share-active) .orientation-guard` 예외가 이미 준비돼 있지만, 실제 게임 코드에서는 공유 카드가 열릴 때 `body`에 `rd-mobile-share-active` 클래스를 붙이지 않는다. 즉, 공유 카드가 보이는 순간 가로 모드 예외를 풀어 줄 준비는 되어 있으나, 실제 연결 코드가 빠져 있다.

#### 5. 데모 시뮬레이터가 Attract Mode 요구사항에 못 미친다

장점부터 말하면, `RelayDemoSimulator`가 존재하고 `RelayDrawingGame`이 `_demoSimulator`를 보유하므로 `HostBaseGame`의 idle auto-demo 훅과 연결될 수 있다는 점은 좋다. 즉, 플랫폼 차원에서 요구한 데모 플레이 통합 방향은 맞다.

문제는 생명주기 관리다.

- `RelayDemoSimulator.startDemo()`는 봇 주입과 QR 블러 오버레이는 수행하지만, 수동 중단 버튼이나 진행 배너 상태를 완결하지 않는다.
- `simulateDrawing()`는 `setInterval()`을 생성하지만 `stopDemo()`에서 이 인터벌을 정리하지 않는다.
- 데모용 그림/단어 제출 스케줄 일부는 `RelayDrawingGame._startRound()` 내부의 `setTimeout()`에서 직접 생성되어 DemoSimulator가 취소권을 갖지 못한다.
- `startDemo()` 주석은 "3초 카운트다운 없이 바로 시작"이라고 되어 있지만 실제로는 `_startGame()`을 호출하므로 인트로 카운트다운을 그대로 탄다.
- 데모 종료 후 자동 로비 복귀와 봇 상태 정리가 명시적으로 보장되지 않는다.

즉, "데모 시작 기능"은 있지만 "무인 시연이 가능한 운영 도구"는 아직 아니다.

#### 6. `spec2.0.md`와 실제 구현 사이에 간극이 있다

다음은 구현 완료에 가깝다.

- 실시간 스트로크 복원
- 4:3 종횡비 고정 캔버스
- 이모지 보조 입력
- 모바일 Web Share 연동

반면 아래 항목은 축소되었거나 미완성이다.

- `15초 내` 완주형 데모 시나리오
- 로비부터 강하게 보이는 attract UI
- 데모의 중단/복구 생명주기
- 인트로의 강한 캐릭터성 연출

문서와 구현의 차이를 방치하면 이후 QA와 운영팀 기대치가 엇갈릴 수 있다.

### 1.3 종합 평가

| 항목 | 평가 | 코멘트 |
| --- | --- | --- |
| 게임 코어 | 강함 | 오해가 누적되는 파티 게임 구조가 분명하고 재플레이성이 높다. |
| 플랫폼 적합성 | 매우 높음 | 공용 화면과 개인 모바일의 역할 분리가 자연스럽다. |
| 아키텍처 건전성 | 높음 | 호스트 권한형 상태 관리와 스트로크 동기화 구조가 좋다. |
| UX 완성도 | 중상 | 플레이 흐름은 좋지만 결과 쇼맨십과 모바일 손맛은 더 키울 수 있다. |
| 운영 안정성 | 중 | 재접속, 이탈, 데모 생명주기에서 몇 가지 중요한 공백이 있다. |
| 문서 정합성 | 보완 필요 | `spec2.0.md`의 데모/연출 기대치를 현재 구현이 완전히 충족하지는 못한다. |

결론은 명확하다. `그림 릴레이`는 **재미 구조를 다시 설계할 게임이 아니라, 안정성 결함을 먼저 막고 그 위에 연출과 손맛을 얹어야 할 게임**이다.

## 2. [대중성 강화 요소]

### 제안 1. 결과 발표를 "TV 쇼"로 만드는 마이크로 연출 패키지

이 게임의 하이라이트는 결과 발표다. 따라서 가장 높은 투자 우선순위는 발표 구간의 감정 곡선을 키우는 것이다.

권장 보강안:

- 이야기 공개 직전 `0.8~1.2초`의 짧은 정적 구간과 "이번엔 어디까지 틀어졌을까?" 같은 서스펜스 카피 추가
- `story-item`을 단순 페이드가 아니라 `카드 등장 -> 살짝 확대 -> 정착` 리듬으로 노출
- 시작 단어, 그림, 추측 단어가 바뀔 때마다 다른 효과음을 사용해 단계감을 강화
- 실시간 드로잉 중 현재 붓을 움직이는 플레이어 카드에 이름 펄스, 테두리 점멸, "Alice가 그리고 있어요" 상태 카피 추가
- 마지막 공유 카드 생성 시 호스트와 모바일 모두에 피날레 카피와 저장 유도 CTA 추가

이 제안의 장점은 룰 변경 없이도 구경하는 재미를 크게 키운다는 점이다. 행사장이나 가족 모임에서는 TV에서 "재밌어 보이는가"가 플레이 유입을 좌우하므로, ROI가 가장 높은 개선안이다.

### 제안 2. 모바일 조작의 손맛과 제출 확신을 강화

현재 모바일은 기능적으로 충분하지만 감각적으로는 아직 기본형에 가깝다. 플레이어가 "내가 잘 그리고 있다", "방금 확실히 제출됐다"를 손끝에서 느끼게 만들 필요가 있다.

권장 보강안:

- 색상 선택, 지우개 전환, 이모지 탭, 제출 완료 시 짧은 햅틱과 버튼 반응 애니메이션 추가
- 지우개 전환 시 툴바 전체에 짧은 반전 플래시나 "지우개 모드" 배지 표시
- `초기화`를 브라우저 `confirm()` 대신 길게 누르기 또는 2단계 버튼으로 바꿔 실수 삭제 방지
- 그림 제출 후 `standby` 화면에 내가 제출한 썸네일 미리보기 표시
- 단어 입력 화면에서 이모지 탭 시 입력창 하단에 조합 미리보기 칩을 띄워 아동/가족 플레이의 즐거움을 증폭

이 제안은 대규모 시스템 변경 없이도 "잘 만든 게임"이라는 인상을 강하게 준다. 특히 아동이나 비게이머는 룰보다 버튼 반응과 모드 피드백에서 품질을 먼저 체감한다.

### 제안 3. 첫 판 이해를 빠르게 만드는 퀵 스타트 운영 모드

이 게임은 룰이 어려운 편이 아니지만, 첫 판에서 웃기기까지 시간이 길어지면 이탈이 생긴다. 대중성을 키우려면 설명을 늘리기보다 "첫 판 결과가 빨리 나오는 구조"를 제공해야 한다.

권장 보강안:

- 로비 설명을 텍스트 문단 대신 3컷 인포그래픽으로 단순화
  - `제시어 받기`
  - `그림 또는 단어 제출`
  - `마지막에 얼마나 틀어졌는지 같이 보기`
- 기본값을 `45초 + 3스테이지` 퀵 모드로 두고, 긴 모드는 옵션으로 내리기
- 로비에 `3명 이상 추천` 문구를 추가해 대표 재미가 더 잘 드러나는 인원 구성을 유도
- 첫 판에서는 더 쉬운 사물/동물 제시어 비중을 높이고, 이후 엉뚱한 주제를 섞는 방식으로 난이도 곡선 조정
- 호스트 대기 화면에 운영자용 한 줄 설명 카피 제공
  - 예: "이 게임은 잘 그리는 게임이 아니라, 오해가 커질수록 웃긴 게임입니다."

이 제안은 룰을 바꾸지 않으면서도 첫 판 성공률을 높인다. 특히 행사장 회전율과 가족 플레이 적응 속도에 직접적인 영향을 준다.

### 3.3 핵심 논점

#### 논점 A. 룰을 더 단순화해야 하는가

회의 결론은 "아니다"였다. 현재 룰은 충분히 직관적이다. 문제는 룰이 어려운 것이 아니라, **왜 웃긴지 체감되기 전에 첫 판이 끝나지 않을 수 있다는 점**이다. 따라서 룰 재설계보다 퀵 스타트와 결과 발표 연출 강화가 우선이다.

#### 논점 B. 가장 큰 체감 개선은 어디에서 오는가

전원 일치로 `결과 발표 마이크로 연출 패키지`가 최우선으로 선정됐다. 이 게임의 대표 장면은 결과 공개이며, 이 장면이 강해질수록 플레이어와 구경꾼 모두가 즉시 재미를 이해한다.

#### 논점 C. 모바일 개선은 기능보다 감각을 우선해야 하는가

찬성 의견이 우세했다. 현재 기능은 충분하다. 따라서 다음 단계는 "툴이 잘 동작한다"가 아니라 "손에 남는 게임 같다"를 만드는 것이다. 햅틱, 버튼 반응, 제출 확신 피드백이 그 핵심이다.

#### 논점 D. 흥행 보강 전에 반드시 손봐야 할 기술적 선결 과제는 무엇인가

합의된 선결 과제는 아래 네 가지다.

1. 플레이어 이탈 시 체인 무결성 보정
2. 결과 히스토리용 작성자 정보 스냅샷 보존
3. `final` 단계 공유 카드 재접속 복구
4. DemoSimulator 생명주기 정리

## 4. [테스트 결과 및 수정 방향]

### 4.1 검증 전제

아래 "테스트 결과"는 실제 기기 실험 결과가 아니라, 현재 소스 코드를 기준으로 한 정적 분석 판정이다. 따라서 합격/불합격 최종 판정이라기보다, 수동 QA 전에 반드시 확인해야 할 검증 포인트와 예상 리스크를 정리한 문서로 보는 것이 맞다.

### 4.2 정적 분석 기준 테스트 결과 요약

| 항목 | 판정 | 근거 |
| --- | --- | --- |
| 로비 -> 준비 -> 게임 -> 결과 기본 루프 | 양호 | 프로필 설정, 준비, 라운드 배정, 결과 발표, 리셋 흐름이 모두 구현돼 있다. |
| 실시간 스트로크 관전성 | 우수 | 정규화 좌표와 시퀀스 버퍼 기반 복원 로직이 갖춰져 있다. |
| 모바일 플레이 흐름 | 양호 | 4:3 캔버스, 이모지 입력, 제출 후 대기, 결과 공유까지 연결돼 있다. |
| 재접속 복구 | 보완 필요 | 진행 중 재접속은 고려했지만 `final` 단계 공유 카드 복구가 없다. |
| 프로필 지속성 | 보완 필요 | 새로고침 후 닉네임만 남고 손그림 아바타는 유지되지 않는다. |
| 중도 퇴장 복원력 | 보완 필요 | 체인 회전과 작성자 스냅샷 보존이 충분하지 않다. |
| 데모 시뮬레이터 | 보완 필요 | 시작은 가능하지만 중단, 자동 복구, 타이머 정리, 15초 시연 시나리오는 미완성이다. |
| 문서-구현 정합성 | 보완 필요 | `spec2.0.md`의 데모/연출 기대치 일부가 현재 구현과 다르다. |

| ID | 시나리오 | 절차 | 기대 결과 |
| --- | --- | --- | --- |

| T06 | 단어 추측 + 이모지 입력 | 이전 그림을 보고 텍스트와 이모지를 섞어 제출 | 입력값이 그대로 `storyChains`에 반영되고 다음 라운드에 정확히 전달된다. |
| T07 | 제출 후 재접속 | 그림 또는 단어를 제출한 뒤 브라우저 새로고침 | 제출 완료 플레이어는 `standby` 화면으로 복구되고 중복 제출이 허용되지 않는다. |
| T08 | 진행 중 재접속 | 제출 전에 새로고침 | 현재 턴 타입, 제시어 또는 이전 그림, 제한 시간이 적절한 화면으로 복구된다. |
| T09 | 프로필 아바타 재접속 복구 | 손그림 아바타 생성 후 새로고침 또는 재접속 | 수정 전에는 아바타가 빈 캔버스로 덮일 가능성이 있으므로, 수정 후에는 기존 아바타가 유지되어야 한다. |
| T10 | 결과 발표 중 재접속 | `result` 단계에서 새로고침 | 최소한 결과 관람 화면은 끊김 없이 복구되어야 한다. |
| T11 | 최종 공유 카드 재접속 | `final` 단계에서 새로고침 | 수정 후에는 `showResults`뿐 아니라 공유 카드 이미지도 다시 받아야 한다. |
| T12 | 공유 카드 가로 모드 검증 | 공유 카드 노출 상태에서 모바일 기기를 가로 회전 | `rd-mobile-share-active`가 적용돼 orientation guard가 공유 카드를 가리지 않아야 한다. |
| T13 | 플레이어 중도 퇴장 | 게임 도중 현재 홀더 1명이 이탈 | 체인이 깨지지 않고 다음 유효 플레이어로 소유권이 자연스럽게 넘어가야 한다. |
| T14 | 결과 직전 이탈 | 이미 제출을 마친 플레이어가 결과 발표 전에 이탈 | 결과 발표와 공유 카드에서 닉네임/아바타/색상 스냅샷이 유지되어야 한다. |
| T15 | 데모 모드 1회 완주 | 로비에서 데모 시작 후 완주까지 관찰 | 봇 입장, 실시간 드로잉, 단어 제출, 결과 발표, 최종 공유, 로비 복귀가 지정 시간 내 끊김 없이 완료돼야 한다. |
| T16 | 데모 모드 중단 | 데모 도중 수동 중단 | 인터벌, 타이머, QR 오버레이, 봇 상태가 모두 정리되고 로비가 정상 복구되어야 한다. |
| T17 | idle auto-demo | 일정 시간 유휴 상태 유지 | 자동 데모가 시작되더라도 실제 플레이어 접속 흐름과 충돌 없이 안전하게 실행되어야 한다. |

### 4.4 우선 수정 방향

#### P0. 안정성 선행 보강

1. **이탈 시 체인 보정 로직 추가**
   - 현재 홀더 이탈 시 다음 유효 플레이어를 찾는 전용 헬퍼를 두고, `_rotateStoryChains()`가 `indexOf === -1` 케이스를 허용하지 않게 해야 한다.
   - 필요하다면 `steps`에 `system` 타입 보정 스텝을 넣어 결과 서사를 끊기지 않게 유지한다.

2. **작성자 정보 스냅샷 분리**
   - `storyChains.steps` 또는 별도 `authorSnapshotMap`에 `nickname`, `avatar`, `color`를 기록해 `_profiles`와 분리해야 한다.
   - 그래야 이탈 이후에도 결과 발표와 공유 카드의 작성자 정보가 유지된다.

3. **아바타 지속성 복구**
   - 최소 구현은 `localStorage`에 아바타 Data URL을 함께 저장하는 것이다.
   - 더 안전한 구현은 호스트가 마지막 프로필 스냅샷을 유지하고, 재접속 시 모바일이 아바타를 재전송하지 못해도 호스트가 기존 값을 유지하도록 하는 것이다.

4. **최종 공유 카드 재접속 복구**
   - 호스트는 마지막으로 생성한 공유 카드 Data URL을 캐시하고, `final` 단계 재접속 시 `showFinalShareCard`를 재송신해야 한다.
   - 모바일은 공유 카드가 열릴 때 `body.classList.add('rd-mobile-share-active')`, 닫히거나 다음 라운드로 돌아갈 때 제거하는 방식으로 orientation guard 예외를 실제 연결해야 한다.

5. **데모 시뮬레이터 생명주기 정리**
   - 아래 `4.5`의 가이드대로 DemoSimulator가 타이머, 인터벌, 봇 상태, UI 오버레이를 전부 소유하도록 재설계해야 한다.

#### P1. 대중성 강화 수정

1. **결과 발표 연출 패키지 적용**
   - 스텝별 등장 모션, 사운드, 현재 스텝 강조, 피날레 카피를 추가한다.

2. **모바일 손맛 강화**
   - 색상/이모지/제출/지우개 전환에 햅틱과 짧은 애니메이션을 붙인다.

3. **퀵 스타트 운영 모드 추가**
   - 기본값을 짧은 모드로 두고, 긴 모드는 선택형 옵션으로 내려 첫 판 회전율을 높인다.

4. **사운드 자산 로컬화 검토**
   - 현재 외부 URL에 걸린 BGM/SFX를 게임 에셋으로 흡수하거나 preload 전략을 추가해 현장 네트워크 품질 의존성을 줄인다.

### 4.5 🤖 `RelayDemoSimulator.js` 개선점 및 수정 가이드라인

현재 `RelayDemoSimulator.js`는 "봇 3명을 넣고, 몇 가지 드로잉 패턴을 재생한다"는 최소 기능은 갖췄다. 하지만 프로젝트 요구사항의 **Attract Mode**로 쓰려면 구조 재설계가 필요하다.

#### 1. 데모 상태를 명시적인 상태 머신으로 분리

권장 상태:

- `idle`
- `booting`
- `round-running`
- `presenting`
- `cleanup`

지금은 `_isDemo` 불리언 하나로 처리해 중간 종료, 재시작, 자동 반복, 실패 복구를 예측 가능하게 통제하기 어렵다. 특히 `HostBaseGame`이 idle 상태에서 `startDemo()`를 자동 호출할 수 있으므로, 무인 시연을 버틸 수 있는 안정성이 필요하다.

#### 2. 모든 예약 작업의 소유권을 DemoSimulator로 집중

현재 문제:

- `simulateDrawing()`가 만든 `setInterval()`이 `stopDemo()`에서 정리되지 않는다.
- `RelayDrawingGame._startRound()`가 데모용 `setTimeout()`을 직접 생성해 DemoSimulator가 취소권을 갖지 못한다.
- `demoTimeouts` 배열은 존재하지만 실제 예약 작업을 완전히 커버하지 못한다.

권장 수정:

- `trackTimeout(fn, ms)`와 `trackInterval(fn, ms)` 헬퍼를 만들고, 데모 중 생성되는 모든 예약 작업을 이 경로로만 생성한다.
- `stopDemo()`는 등록된 모든 타이머와 인터벌을 비우고, 이후 지연 실행이 남지 않도록 해야 한다.
- 호스트는 `_startRound()` 안에 데모 전용 `setTimeout()`을 두지 말고, DemoSimulator가 `onRoundStarted(roundInfo)` 같은 훅을 통해 봇 행동을 스케줄하도록 바꾸는 편이 안전하다.

#### 3. DemoSimulator가 호스트 내부 구현 세부사항을 직접 만지지 않게 정리

지금은 DemoSimulator가 `_profiles`, `players`, `_activeStrokes`, `_handlePlayerSubmission()`에 직접 접근한다. 빠르게 만들기에는 편하지만, 유지보수성은 낮다.

권장 방향:

- 호스트에 `addDemoPlayers()`, `removeDemoPlayers()`, `submitDemoTurn()`, `beginDemoStroke()`, `appendDemoStroke()`, `endDemoStroke()` 같은 얇은 공개 메서드를 둔다.
- DemoSimulator는 그 공개 메서드만 호출하고, 내부 `Map` 구조를 직접 수정하지 않는다.

이렇게 해야 나중에 스트로크 렌더링 방식이나 제출 구조가 바뀌어도 데모 코드가 덜 깨진다.

#### 4. 15초 내 완주형 고정 시나리오를 별도로 설계

`spec2.0.md`의 acceptance criteria는 "데모가 15초 내에 막힘 없이 한 번 완주"하는 것이다. 현재 구현은 인트로 카운트다운, 5초 드로잉, 3.5초 단어 제출, 결과 발표 지연까지 포함하면 길이가 늘어나기 쉽다.

권장 데모 타임라인 예시:

1. 0.0s: 봇 입장, QR 잠금, "데모 진행 중" 배너 표시
2. 0.5s: 인트로 생략, 1라운드 즉시 시작
3. 0.5s~4.0s: 드로잉 3.5초
4. 4.0s~6.0s: 단어 추측 2초
5. 6.0s~10.5s: 결과 발표 4.5초
6. 10.5s~13.0s: 공유 카드 피날레
7. 13.0s~15.0s: 자동 정리 및 로비 복귀

실제 운영에서는 `1회 완주`와 `자동 반복` 옵션을 분리하는 편이 좋다.

#### 5. 데모 UI를 시작/중단/상태 표시까지 완결

필수 보강안:

- 로비 버튼을 `실행`/`중단` 토글로 바꾼다.
- QR 영역 또는 상단에 현재 단계와 남은 시간을 보여 주는 상시 배너를 둔다.
- 데모 중 신규 접속은 실제 게임 플레이어로 편입하지 말고, "데모 종료 후 다시 참여" 안내만 보여 준다.
- 데모 완주 또는 수동 중단 시 버튼, 배너, QR 블러, 내부 플래그, 봇 상태를 한 번에 정리한다.

현재 `onPlayerJoin()`에서 데모 중 난입을 UI 차원에서 무시하고 있지만, 내부 플레이어 상태는 이미 추가된 뒤일 수 있으므로 정책을 더 명시적으로 다뤄야 한다.

#### 6. 정리 루틴을 자동 복구 기준으로 설계

`stopDemo()`가 끝났을 때 보장돼야 할 상태는 아래와 같다.

- 남아 있는 타이머/인터벌이 없다.
- `_activeStrokes`가 비워져 있다.
- QR 블러와 오버레이가 제거돼 있다.
- 봇 플레이어가 세션 상태에서 제거돼 있다.
- `_isDemo`가 `false`다.
- 호스트 phase가 `lobby`로 복구돼 있다.
- 공유 카드나 결과 발표 잔여 UI가 없다.

현재 구조에서는 이 정리가 `resetSession()` 경로에 간접 의존하는 부분이 많아, 수동 중단 시나리오에 취약하다.

#### 7. 구현 우선순위 제안

1. DemoSimulator의 타이머/인터벌 추적 일원화
2. `RelayDrawingGame._startRound()`의 데모 전용 스케줄 제거
3. 자동 복구가 보장되는 `stopDemo()` 완성
4. 15초 내 완주형 데모 스크립트 설계
5. 진행 배너와 시작/중단 토글 UI 추가
6. 자동 반복 옵션과 무인 attract mode 검증

이 순서로 가야 DemoSimulator가 장식용 기능이 아니라, 개발 중 검증 도구이자 행사장 운영 도구로 모두 쓸 수 있다.
