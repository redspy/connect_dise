## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`hidden-agent`는 "각자의 스마트폰은 개인 비밀 카드, TV는 공동 추리 보드"라는 플랫폼 강점을 가장 직접적으로 활용한 게임이다. 시민과 스파이가 서로 다른 단어를 받고, 각자 한 단어 힌트를 내고, 이를 근거로 토론과 투표를 진행하는 구조는 규칙이 단순하면서도 시선 교환, 표정 읽기, 말의 뉘앙스 해석 같은 오프라인 보드게임 특유의 재미를 잘 살린다.

특히 재미의 중심은 다음 세 지점에서 강하게 발생한다.

| 항목 | 평가 |
| --- | --- |
| 비대칭 정보 구조 | 역할과 제시어를 모바일 개별 패킷으로만 전달하므로, "누가 무엇을 봤는지"가 분리되어 심리전의 기본 토대가 탄탄하다. |
| TV 중심의 집단 주목 | 힌트가 TV에 떠오르는 구조 덕분에 모든 플레이어가 같은 화면을 보며 서로의 반응을 읽게 된다. 플랫폼 목적과 매우 잘 맞는다. |
| 짧은 의사결정 루프 | 입력은 닉네임 설정, 카드 뒤집기, 힌트 1회, 투표 1회로 끝난다. 모바일 조작량이 적어 입문 장벽이 낮다. |

반면 현재 버전은 "첫 판 체험"은 좋지만 "연속 플레이" 관점에서는 몇 가지 약점이 보인다.

| 관찰 포인트 | 평가 |
| --- | --- |
| 제시어 풀 규모 | 단어 쌍이 12개로 적어 반복 플레이 시 빠르게 패턴이 학습된다. 리플레이성이 급격히 떨어질 가능성이 높다. |
| 한 라운드 구조 | 실제 구현은 힌트 제출 1회 후 바로 투표로 넘어간다. 심리전의 깊이는 살아 있으나, 역전 서사나 추가 추리 기회는 부족하다. |
| 연출 밀도 | 카드 뒤집기와 플로팅 버블은 좋지만, 입장-정체 확인-투표 마감-결과 공개까지의 감정선이 한 단계 더 증폭될 여지가 크다. |

종합하면, 코어 플레이는 충분히 매력적이며 플랫폼 적합성도 높다. 다만 현재 상태는 "잘 만든 프로토타입과 플레이어블 알파" 사이에 가깝고, 대중적 흥행을 위해서는 연출 밀도, 학습 보조, 리플레이성 강화가 필요하다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

구조적으로는 `HostBaseGame`과 `MobileBaseGame`을 적절히 상속받아 페이즈 전환과 메시지 흐름을 명확히 분리한 점이 장점이다. 호스트는 `Map` 기반으로 프로필, 역할, 힌트, 투표를 개별 관리하고, 모바일은 `assignRole`, `phaseChange`, `lobbyState`를 기준으로 화면을 전환한다. 역할 배정이 `broadcast`가 아닌 `sendToPlayer` 유니캐스트로 처리되는 점도 게임 특성상 정확한 설계다.

아키텍처 관점의 강점은 다음과 같다.

| 항목 | 평가 |
| --- | --- |
| 상태 분리 | `profiles`, `assignedRoles`, `assignedWords`, `playerHints`, `playerVotes`가 분리되어 있어 디버깅과 리셋이 비교적 쉽다. |
| 재접속 복원 | 호스트의 `onPlayerRejoin`과 모바일의 `_restoreRejoinPhase`가 맞물려 로비/토론/투표/결과 단계 복원을 모두 고려하고 있다. |
| 플랫폼 컨벤션 준수 | 호스트는 `setPhase`, 모바일은 `showScreen` 중심으로 UI를 전환하고 있어 프로젝트 표준과 일치한다. |
| 데모 모드 존재 | 로비에서 데모를 즉시 실행할 수 있어 현장 시연성과 내부 검증 편의성이 좋다. |

반면 구현 완성도 측면에서는 아래의 구조적 보완 포인트가 분명하다.

| 구분 | 관찰 내용 | 영향 |
| --- | --- | --- |
| 스펙 싱크 불일치 | `spec.md`는 힌트 제출 단계가 사실상 2라운드형으로 읽히지만, 실제 구현은 1회 제출 후 즉시 투표로 종료된다. | 문서와 플레이 경험의 괴리가 생기고, 확장 설계의 기준점이 흐려진다. |
| 투표 비밀성 손상 | 현재 호스트는 투표 중 실시간 득표 수와 게이지를 각 플레이어 카드에 갱신한다. 이는 "누가 투표했는지만 보이고 누구에게 몰리는지는 비공개"라는 설계 의도와 충돌한다. | 후행 투표자의 선택이 왜곡될 수 있고, 심리전의 공정성이 약해진다. |
| 타이머 정리 미흡 | 실제 게임의 Setup 카운트다운과 데모 시뮬레이터의 Setup 가속 카운트다운이 공통 정리 루틴에 묶여 있지 않다. | 중도 리셋/데모 중단 시 잔존 타이머가 다음 페이즈를 늦게 밀어 올릴 위험이 있다. |
| 입력 검증 얕음 | 모바일 UI에서는 닉네임/힌트를 검증하지만, 호스트 메시지 수신부는 악의적 혹은 비정상 패킷에 대해 방어가 얕다. | 실서비스에서 예상치 못한 빈 문자열, 비정상 타겟, 오염된 텍스트가 상태에 남을 수 있다. |
| 브라우저 기본 다이얼로그 의존 | `alert`와 `confirm`이 핵심 순간에 사용된다. | 몰입감이 끊기고, 모바일 브라우저별 UX 편차가 커진다. |

### 1.3 종합 판정

`hidden-agent`는 플랫폼 목적과 게임 장르가 잘 맞물린 좋은 사례다. 코어 루프의 방향성은 명확하고, Host/Mobile 분리와 재접속 처리도 생각보다 탄탄하다. 다만 "대중적 상용 완성도"라는 기준으로 보면 다음 세 축이 아직 부족하다.

1. 감정선을 올려주는 시청각 피드백
2. 규칙을 더 빠르게 이해시키는 UX
3. 재플레이 욕구를 유지할 콘텐츠 확장성

정리하면, 현재 상태는 "출시 가능한 내부 시연용 빌드" 수준이며, 대중적 흥행을 노리려면 연출과 UX를 우선 보강하고, 이후 리플레이성 확장을 붙이는 순서가 적절하다.

## 2. [대중성 강화 요소]

아래 3가지는 단순 아이디어가 아니라, 현재 코드 구조에 비교적 자연스럽게 얹을 수 있고 체감 개선 효과가 큰 항목들이다.

### 2.1 제안 1: 시네마틱 피드백 패키지

핵심은 각 페이즈의 감정 변화를 시청각적으로 명확히 구분하는 것이다.

| 적용 항목 | 구체 제안 | 기대 효과 |
| --- | --- | --- |
| 역할 공개 | 카드 플립 시 짧은 글로우, 스파이/시민별 컬러 차별 효과, 0.5초 내 짧은 사운드 큐 | 첫 인상 강화, 역할 공개 순간의 긴장감 상승 |
| 힌트 제출 | 버블 생성 시 팝 애니메이션, 제출 완료 수가 찰 때 미세한 카운터 반응 | TV를 보는 재미 강화, 관전자 몰입 증가 |
| 투표 마감 | 마지막 5초 드럼롤형 UI, 마감 직전 게이지 점멸 | 현장 긴장감 상승 |
| 결과 공개 | 스포트라이트, 탈락자 강조, 시민/스파이 승리별 다른 배경 연출 | "한 판 끝났다"는 만족감 강화 |

현재 UI는 이미 다크 네온 톤과 플립 카드 기반이므로, 구조를 갈아엎지 않고도 애니메이션 클래스와 짧은 오디오 큐만 더해 체감 완성도를 크게 올릴 수 있다.

### 2.2 제안 2: 규칙 이해 및 조작 UX 간소화 패키지

대중성의 핵심은 "설명을 듣지 않아도 첫 판이 돌아가는가"에 있다. 현재 버전은 룰 자체는 단순하지만, 브라우저 기본 다이얼로그와 일부 정보 노출 방식 때문에 몰입과 가독성이 끊긴다.

필수 보강 포인트는 다음과 같다.

| 적용 항목 | 구체 제안 | 기대 효과 |
| --- | --- | --- |
| 온보딩 | 모바일 첫 진입 시 2~3장의 초간단 룰 카드 또는 20초 내 튜토리얼 오버레이 제공 | 사회자 설명 부담 감소 |
| 힌트 입력 | "예: 달콤함 / 붉다 / 여름" 같은 예시 칩 제공, 공백/중복/금칙어를 인라인 경고로 처리 | 입력 실수 감소 |
| 투표 UX | `confirm()` 대신 커스텀 바텀시트로 최종 확인, 버튼 탭 후 즉시 촉각 피드백 제공 | 브라우저 의존성 감소, 조작감 향상 |
| 비밀 유지 | 힌트 입력 화면에서 제시어를 항상 크게 보여주기보다 "길게 눌러 다시 보기" 방식으로 전환 | 옆 사람에게 정보가 새는 위험 감소 |
| 공정성 | 투표 중에는 현재처럼 개별 득표수를 공개하지 않고, "몇 명이 투표 완료했는지"만 보여주도록 변경 | 후행 투표 편향 방지 |

이 패키지는 게임의 본질을 바꾸지 않으면서도, 이해 속도와 몰입감을 동시에 개선하는 가장 효율적인 개편안이다.

### 2.3 제안 3: 리플레이성 강화 패키지

현재 가장 큰 장기 리스크는 "재미는 있는데 여러 판 하다 보면 금방 읽히는 게임"이 될 수 있다는 점이다. 이를 막으려면 단어 풀과 매치 구조를 함께 확장해야 한다.

| 적용 항목 | 구체 제안 | 기대 효과 |
| --- | --- | --- |
| 제시어 덱 확장 | 일상/음식/여행/학교/직업 등 테마 덱 추가, 쉬움/보통/어려움 난이도 분리 | 반복 플레이 피로 감소 |
| 단어 품질 관리 | 너무 멀거나 너무 가까운 단어 쌍을 정리하고, 헷갈리되 설명 가능한 쌍으로 큐레이션 | 추리 밸런스 안정화 |
| 매치 구조 | 단판 외에 2라운드 또는 3라운드 누적 점수 모드 추가 | 모임/방송 환경에서 체류 시간 증가 |
| 결과 리포트 | 결과 화면에 "누가 어떤 힌트를 냈는지" 복기 보드를 추가 | 한 판의 서사를 다시 즐길 수 있음 |

단, 다라운드 구조는 현재 코드와 문서의 싱크를 먼저 맞춘 뒤 도입하는 편이 안전하다. 우선순위는 "단어 덱 확장"이 먼저고, "매치 구조 확장"은 그 다음이다.

## 3. [가상 전문가 회의록 (Decision Making Meeting)]

### 3.1 회의 개요

- 안건:
  - 제안 1 `시네마틱 피드백 패키지`
  - 제안 2 `규칙 이해 및 조작 UX 간소화 패키지`
  - 제안 3 `리플레이성 강화 패키지`
- 참석자:
  - PMOrchestrator
  - GameScout
  - KidsBoardGameExpert
  - OnlineGameProducer
  - UIUXDesigner
  - TechAnalyst
  - SeniorGameDev

### 3.2 전문가 발언 시뮬레이션

| 전문가 | 발언 요지 |
| --- | --- |
| PMOrchestrator | "`hidden-agent`의 방향은 맞다. 다만 지금은 첫 판 만족도가 핵심이고, 반복 플레이와 관전 만족도는 아직 한 단계 부족하다. 즉시 체감되는 개선과 구조 변경이 큰 개선을 분리해서 결정해야 한다." |
| GameScout | "이 장르는 추리보다 반응 보는 재미가 중요하다. TV 화면에서 버블이 떠오르는 장점은 이미 있으니, 결과 공개와 투표 마감 연출을 강화하면 파티 게임다운 기억점이 생긴다." |
| KidsBoardGameExpert | "60초 안에 이해 가능한가가 중요하다. 규칙 설명을 길게 하지 말고, 모바일 첫 화면에서 예시 중심으로 알려줘야 한다. 힌트 입력 실패를 `alert`로 막는 방식은 학습 친화적이지 않다." |
| OnlineGameProducer | "현재 실시간 득표수 공개는 심리전의 공정성을 해친다. 투표가 닫히기 전에는 진행률만 보여주고, 결과는 한 번에 터뜨리는 편이 훨씬 재미있다. 이것은 연출이 아니라 핵심 룰 품질 문제다." |
| UIUXDesigner | "모바일은 한 손 조작과 비밀 유지가 중요하다. 단어를 큰 텍스트로 계속 노출하기보다 필요할 때만 다시 보는 패턴이 좋다. `confirm()`은 반드시 커스텀 UI로 교체해야 한다." |
| TechAnalyst | "데모 시뮬레이터가 내부 `Map`을 직접 건드리는 구조는 실제 메시지 경로와 다르다. 연출 개선 이전에 데모가 실제 동작을 얼마나 잘 대표하는지 높여야 품질 검증 가치가 생긴다." |
| SeniorGameDev | "제안 1과 2는 지금 구조에서도 빠르게 반영 가능하다. 제안 3 중 단어 덱 확장은 즉시 가능하지만, 다라운드 누적 점수는 상태 머신과 문서 업데이트가 동반되어야 하므로 2차 작업으로 두는 게 맞다." |

### 3.3 최종 의사결정

회의 결과, 세 개선안은 아래와 같이 결정되었다.

| 항목 | 결정 | 사유 |
| --- | --- | --- |
| 제안 1 시네마틱 피드백 패키지 | 즉시 반영 | 코드 구조 변경이 작고, 체감 완성도 향상 폭이 가장 크다. |
| 제안 2 규칙 이해 및 조작 UX 간소화 패키지 | 즉시 반영 | 첫 판 진입 장벽을 낮추고, 몰입 저해 요소를 직접 제거한다. |
| 제안 3 리플레이성 강화 패키지 | 단계 반영 | 단어 덱 확장은 우선 반영, 다라운드/누적 점수는 구조와 문서 싱크 정비 후 반영한다. |

최종 우선순위는 다음과 같이 정리되었다.

1. 투표 비밀성 수정, 커스텀 UX 피드백, 온보딩 추가
2. 역할 공개/투표 마감/결과 발표 연출 강화
3. 단어 덱 확장과 난이도 관리
4. 다라운드 구조 및 누적 점수 모드

즉, "룰 품질과 첫 판 경험"을 먼저 고치고, "콘텐츠 수명"은 그 다음 단계에서 키우는 방향으로 합의되었다.

## 4. [테스트 결과 및 수정 방향]

### 4.1 현재 품질 판단

기존 `test-report.md`는 PASS로 기록되어 있으며, 로비-역할 배정-힌트 제출-투표-결과-리셋의 기본 루프는 성립해 있다. 다만 코드 정적 분석 기준으로는 타이머 정리, 투표 비밀성, 데모 시뮬레이터 대표성 측면의 보완이 필요하다. 따라서 아래 회귀 시나리오를 기준으로 다시 검증하는 것이 바람직하다.

### 4.3 `DemoSimulator.js`의 개선점

현재 데모 시뮬레이터는 "시연용"으로는 유용하지만, "실제 코드 경로를 검증하는 시뮬레이터"로 보기에는 아쉬움이 있다.

| 개선 포인트 | 현재 상태 | 문제점 |
| --- | --- | --- |
| 상태 주입 방식 | `players`, `_profiles`, `_assignedRoles`, `_assignedWords` 등을 직접 수정 | 실제 SDK 이벤트/메시지 경로를 통과하지 않아 회귀 검증력이 낮다. |
| 타이머 관리 | `setTimeout`만 배열에 넣고, `setInterval`은 공통 정리 대상이 아님 | 중단 후 잔존 카운트다운이 다음 페이즈를 밀 수 있다. |
| 리셋 경로 | `stop()`이 `game.onReset()`을 직접 호출 | SDK 리셋 루프와 분리되어 있어 실제 복구 흐름과 어긋난다. |
| 시나리오 폭 | 정상 진행 1종만 표현 | 타임아웃, 동률 투표, 재접속, 무응답 플레이어 같은 예외를 검증하지 못한다. |
| 관측성 | 콘솔 로그 위주 | 어느 단계에서 무엇이 실패했는지 UI 기준으로 판단하기 어렵다. |

### 4.4 `DemoSimulator.js` 수정 가이드라인

아래 순서로 정리하는 것이 가장 안전하다.

1. **타이머 스케줄러를 공통화한다.**
   - `setTimeout`, `setInterval`을 각각 등록/해제하는 래퍼를 만들고, `stop()`과 `onReset()`에서 모두 같은 해제 루틴을 사용한다.
   - 실제 게임의 Setup 카운트다운도 별도 핸들로 저장해 중도 리셋 시 반드시 끊어야 한다.

2. **직접 상태 주입 대신 "데모 드라이버" 계층을 둔다.**
   - 가능하면 `DemoSimulator`가 `game._wireMessages()` 내부의 실제 수신 경로와 비슷한 단계를 밟도록 구성한다.
   - 최소한 봇 입장, 준비 완료, 힌트 제출, 투표 제출을 각각 전용 메서드로 감싸고, 내부 `Map` 직접 수정은 한 곳에만 몰아 관리한다.

3. **실제 페이즈 전환 함수와 데모 페이즈 전환을 통합한다.**
   - Setup, Discussion, Voting, Result 전환 로직을 분산 복제하지 말고, 공용 메서드 또는 라운드 컨트롤러로 묶는다.
   - 현재처럼 데모가 자체적으로 `_simulateDiscussionPhase`, `_simulateVotingPhase`를 별도 구현하면 실제 게임과 점점 다른 흐름으로 드리프트할 수 있다.

4. **데모 시나리오를 최소 3종으로 늘린다.**
   - 정상 검거 시나리오
   - 힌트 또는 투표 타임아웃 시나리오
   - 동률 투표 또는 오검거 시나리오
   - 이렇게 해야 결과 화면, 타임아웃 처리, 예외 분기를 한 번에 검증할 수 있다.

5. **UI 검증용 상태 배지를 추가한다.**
   - 호스트 화면 상단 또는 배너에 `LOBBY > SETUP > DISCUSSION > VOTING > RESULT` 진행 상태를 소형 텍스트로 노출하면, 브라우저 기반 검증 시 데모가 어느 단계에 있는지 즉시 파악할 수 있다.

6. **문서와 데모의 목표를 분리해 정의한다.**
   - "현장 시연용 attract demo"와 "회귀 검증용 deterministic demo"를 같은 스크립트 하나가 모두 맡지 않도록 역할을 구분하는 편이 좋다.
   - 전자는 연출 우선, 후자는 재현성과 분기 커버리지가 우선이다.

### 4.5 우선 수정 방향 요약

가장 먼저 손봐야 할 항목은 아래 네 가지다.

1. 투표 중 실시간 득표수 노출 제거
2. Host Setup 타이머와 DemoSimulator 가속 타이머의 정리 루틴 통합
3. 모바일 `alert`/`confirm` 제거 및 인라인/커스텀 UI 전환
4. 단어 덱 확장 전, 현재 규칙이 단판 구조인지 다라운드 구조인지 문서와 구현을 먼저 일치시킴

이 네 가지를 정리하면 `hidden-agent`는 단순히 "동작하는 게임"을 넘어, 대중 앞에서 반복 플레이해도 설득력 있는 파티 게임으로 올라갈 수 있다.
