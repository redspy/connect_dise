## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`리듬 잼`의 코어 루프는 매우 간결하다.

1. 호스트가 로비에서 곡을 선택한다.
2. 플레이어는 모바일로 입장해 준비를 완료한다.
3. 게임이 시작되면 각자 하나의 악기 역할을 부여받는다.
4. 호스트 화면의 3개 레인에 흘러오는 노트를 보고, 모바일의 거대한 패드를 타이밍에 맞춰 두드린다.
5. `대박! / 나이스! / 앗!` 판정에 따라 팀 점수와 콤보가 누적되고, 결과 등급을 확인한다.

이 구조는 공용 스크린과 개인 모바일을 함께 쓰는 플랫폼의 장점과 잘 맞는다. TV에는 모두가 같이 보는 박자선과 점수, 모바일에는 오직 "지금 두드리면 된다"는 단순한 입력만 남겨 두었기 때문이다. 특히 아래 요소는 첫 판 몰입을 빠르게 만든다.

| 항목 | 평가 | 근거 |
| --- | --- | --- |
| 입력 규칙의 즉시성 | 높음 | 모바일은 사실상 한 개의 대형 패드만 누르면 되므로 설명 부담이 작다. |
| 공용 화면 관전성 | 높음 | 3레인 컨베이어, 판정 스탬프, 콤보 HUD가 같은 공간의 리액션을 잘 유도한다. |
| 오디오-비주얼 결합 | 높음 | 호스트의 Web Audio 합성 드럼음과 네온 리플 이펙트가 타격 순간을 확실하게 강조한다. |
| 짧은 세션 호흡 | 높음 | 기본 곡 길이가 20초라 한 판 회전이 빠르다. |
| 트랙 재플레이성 | 중상 | 구현상 10개 패턴을 제공해 반복 시 체감 차이를 준다. |

재미의 본질은 "같은 박자를 여러 사람이 나눠 연주한다"는 협동 감각이다. 이 게임은 경쟁보다 합주와 호응에 초점이 있으므로, 가족/지인 모임에서 분위기를 띄우는 용도로 잠재력이 크다.

다만 현재 코어 설계는 몇 가지 치명적인 마찰을 안고 있다.

#### 강점

- **첫 인상이 좋다.**
  - 호스트의 캔버스 무대와 모바일의 네온 패드는 진입 즉시 "리듬 게임"이라는 장르를 이해시킨다.
- **설명보다 체험이 빠르다.**
  - 패드를 두드리는 행위 자체가 직관적이라 비게이머도 바로 참여할 수 있다.
- **오디오 에셋 의존도가 낮다.**
  - 짧은 합성 사운드만으로도 게임 분위기를 일정 수준 확보한다.

#### 약점

- **현재 악보 구조는 사실상 3인 플레이를 전제로 한다.**
  - `games/registry.js`상 `minPlayers: 1`, `maxPlayers: 8`이지만, 실제 호스트 로직은 3레인 고정이고 플레이어는 `idx % 3`으로만 악기를 배정한다.
  - 1인 플레이는 베이스만, 2인 플레이는 베이스/스네어만 담당하므로 남는 레인의 노트는 자동으로 `MISS`가 된다.
  - 반대로 4인 이상은 동일 악기를 중복 배정받아 역할 고유성이 급격히 약해진다.
- **합주 감각보다 '타이밍 타격기'에 가깝다.**
  - 기준이 되는 백킹 비트, 카운트인, 메트로놈, 오토 반주가 없어, 플레이어가 음향적으로 곡을 따라간다는 감각이 약하다.
  - 현재는 "노트가 보이면 두드린다"는 시각 의존도가 지나치게 높다.
- **과타(무의미한 연타)에 대한 억제 장치가 없다.**
  - `tapNote` 수신 시 먼저 악기 사운드를 재생하고, 근처 노트가 없으면 불이익도 거의 없다.
  - 결과적으로 고난도 구간에서 정확히 맞추는 것보다 "근처에서 자주 두드리는" 플레이가 손해가 적다.

즉, `리듬 잼`은 **첫 판 체험의 임팩트는 강하지만, 리듬 게임으로서의 공정성과 인원 확장성은 아직 상품 수준으로 다듬어지지 않았다**고 볼 수 있다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

#### 호스트 구조 평가

호스트는 `HostBaseGame`을 올바르게 상속하고 있으며, 상태와 렌더링 책임도 비교적 읽기 쉽게 모여 있다.

- `onSetup()`에서 캔버스, 곡 선택, 데모 버튼을 초기화한다.
- `_startGame()`이 점수 초기화, 트랙 로드, 악기 배정, 렌더 루프 시작을 담당한다.
- `_updateGame()`이 노트 스폰, 이동, MISS 판정, 파티클 업데이트, 종료 조건을 처리한다.
- `_drawCanvas()`가 시각화 전담 함수로 분리되어 있다.
- `_triggerJudge()`가 점수/콤보/HUD 브로드캐스트를 한곳에서 관리한다.

이 구조는 작은 규모의 액션 게임으로는 충분히 실용적이다. 특히 캔버스 드로잉과 판정 로직이 같은 파일 안에 있어도 함수 경계가 분명해, 현재 규모에서는 유지보수성이 아주 나쁘지 않다.

#### 모바일 구조 평가

모바일은 동작 자체는 단순하고 빠르지만, 플랫폼 권장 패턴 준수도와 복구 완성도는 낮다.

- `MobileBaseGame`을 상속하지만 `onJoin`, `onRejoin`, `onAllReady`를 사실상 활용하지 않는다.
- 실제 화면 전환은 `assignInstrument`, `gameFinished` 같은 커스텀 메시지에 많이 의존한다.
- 호스트가 보내는 `lobbyState`는 모바일에서 처리하지 않으므로 로비 재접속 동기화가 끊겨 있다.
- HUD는 팀 점수와 콤보만 보여주고, 내 타이밍 정확도나 내 역할 기여도는 거의 보여주지 않는다.

#### 구현 완성도 평가 표

| 평가 축 | 관찰 | 평가 |
| --- | --- | --- |
| 코어 루프 전달력 | 패드 하나로 두드리는 구조가 직관적이다. | 우수 |
| 호스트 베이스 클래스 활용 | `HostBaseGame`의 phase, lobby, reset 루프를 대체로 잘 활용한다. | 양호 |
| 모바일 베이스 클래스 활용 | 상속은 했지만 `onRejoin`, 로비 복구, 상태 머신 활용이 얕다. | 보완 필요 |
| 판정 공정성 | 고정 픽셀 윈도우 기반이며 레이턴시 보정이 없다. | 취약 |
| 인원 수 확장성 | 3레인 고정 구조라 1~2인/4인 이상에서 재미 품질이 크게 흔들린다. | 취약 |
| 시각 연출 | 네온 레인, 리플, 피버 플래시는 첫인상이 좋다. | 우수 |
| 오디오 설계 | 에셋 없는 합성음은 장점이지만, 합주를 끌고 가는 기준 비트가 없다. | 보통 |
| 재접속/운영 안정성 | 로비 재접속, 영구 이탈, 데모 양도 정책이 불완전하다. | 취약 |
| 데모 시뮬레이터 품질 | 존재 자체는 장점이지만 내부 결합도가 과도하다. | 미완성 |

#### 핵심 구현 이슈

##### 1. `1~2인` 플레이가 사실상 정상 난이도로 성립하지 않는다

현재 `_assignInstruments()`는 플레이어 순서대로 `Bass / Snare / Hihat`를 순환 배정하고, `_getTrackNotes()`는 항상 3레인을 기준으로 악보를 만든다. 이 설계는 정확히 3명이 모였을 때만 온전하다.

- 1인: 두 레인에서 지속적으로 `MISS` 발생
- 2인: 남은 한 레인의 노트가 무조건 실패
- 4~8인: 추가 플레이어가 동일 악기를 공유하므로 내 역할의 고유성이 사라짐

이 문제는 단순 밸런스 조정이 아니라, **현재 상품 설명(`1~8명`)과 실제 플레이 가능 조건이 어긋나는 구조적 결함**이다.

##### 2. 재접속 처리가 로비와 인게임 모두 완전하지 않다

호스트는 `onPlayerRejoin()`에서 인게임 중 플레이어에게 `assignInstrument`를 다시 보내므로, 최소한의 역할 복구는 된다. 그러나 로비 단계에서는 `lobbyState`를 보내는 것 외에 추가 조치를 하지 않고, 모바일은 그 메시지를 듣지 않는다.

그 결과:

- 로비에서 새로고침한 모바일이 원래 대기 화면으로 복구되지 않을 수 있다.
- 준비 완료 상태와 닉네임 흐름이 사용자에게 일관되게 보장되지 않는다.

또한 일시 끊김은 `playerDisconnect` 이벤트로 먼저 들어오는데, `리듬 잼` 호스트는 이를 활용하지 않고 `playerLeave` 이후에야 게임을 멈춘다. 즉, **잠깐 끊겼을 때는 즉시 보호하지 못하고, 완전히 나간 뒤에는 오히려 게임이 멈추는 역전된 흐름**이다.

##### 3. 판정 로직이 대중성보다 원시 구현에 가깝다

현재 판정은 `note.x`와 판정선 `x = 130` 사이의 거리만 본다.

- `PERFECT`: 오차 25px 이하
- `GOOD`: 오차 55px 이하
- 그 외는 노트가 지나가며 나중에 `MISS`

문제는 다음과 같다.

- 네트워크 왕복 지연이나 P2P/소켓 폴백 차이를 고려한 동적 보정이 없다.
- 모바일 입력 시점과 호스트 화면 표시 시점의 차이를 플레이어가 체감 그대로 보상받지 못한다.
- 잘못된 타이밍으로 계속 두드려도 즉시 감점이나 오버히트 패널티가 없어, 정확성보다 연타가 손해가 적다.

즉, 파티 게임으로서 쉽고 즐거워야 하는데, 실제로는 **실력 차는 애매하고 억울함은 남을 수 있는 판정 구조**다.

##### 4. `DemoSimulator.js`는 운영 도구가 아니라 내부 해킹에 가깝다

현재 데모 시뮬레이터는 다음 내부 상태를 직접 건드린다.

- `game.players.clear()`
- `game.sdk._players`
- `game._playerNicknames`
- `game.sdk._messageHandlers`

이 방식은 단기적으로는 동작하더라도, 플랫폼 표준 Attract Mode로 보기 어렵다. 특히 아래 리스크가 크다.

- 실사용자가 데모 중간에 입장했을 때 안전한 양도 경로가 없다.
- `stopDemo()`가 실제 SDK 플레이어 맵까지 비워 버릴 수 있다.
- 호스트 공개 API가 아니라 내부 구현 세부사항에 기대므로 리팩터링에 극도로 취약하다.
- 로비의 "데모 중" 상태를 분명하게 보여주는 배너와 중단 UX가 없다.

##### 5. 세부 구현에도 몇 가지 품질 누수가 보인다

- `techno` 악보 생성 분기에 `b % 4 === 3.5`처럼 실제로 도달할 수 없는 조건이 있다.
- 모바일 CSS는 `.role-name`에 색상 테마를 주는데, 실제 HTML은 `id="role-name"`과 `class="role-val"`을 쓴다. 역할 텍스트 스타일링이 의도대로 적용되지 않을 가능성이 크다.
- `MISS` 발생 시 모든 모바일에 동일 경고를 브로드캐스트하므로, 누구의 실수였는지보다 전체 벌칙처럼 느껴질 수 있다.

## 2. [대중성 강화 요소]

### 제안 1. 인원 적응형 악보와 역할 설계로 `1~8명` 약속을 실제 게임성으로 바꾸기

현재 가장 시급한 과제다. 게임 설명은 1~8명을 허용하지만, 실제 재미 품질은 사실상 3명에 맞춰져 있다. 대중성 강화를 위해서는 "사람이 몇 명이 와도 한 판이 성립한다"는 신뢰를 먼저 만들어야 한다.

구체 제안:

- 1인: 베이스/스네어/하이햇을 한 패드에 통합한 솔로 악보 또는 자동 반주 지원
- 2인: 두 명이 각각 메인 레인을 맡고, 남는 레인은 오토 플레이 또는 박수/클랩 샘플로 보조
- 3인: 현재 구조 유지
- 4~8인: 중복 악기만 주지 말고 `클랩`, `필인`, `피버 트리거`, `리듬 쉴드` 같은 서브 역할을 추가
- 로비에 `추천 인원: 3명` 또는 `인원 수에 따라 편곡 자동 조정` 문구를 명시

기대 효과:

- 실제 행사장과 가족 모임에서 "지금 모인 인원"으로 바로 돌릴 수 있다.
- 3명 미만에서 억울한 `MISS`가 쌓이는 구조를 제거할 수 있다.
- 4명 이상이 들어와도 "남는 사람"이 아니라 "추가 역할"을 가진다.

### 제안 2. 합주 감각을 키우는 타이밍 피드백 패키지

지금의 `리듬 잼`은 시각적으로는 리듬 게임인데, 청각적으로는 기준 비트가 약하고, 판정은 네트워크 영향을 그대로 받는다. 대중성을 높이려면 플레이어가 "내가 박자 안으로 들어갔다"는 확신을 몸으로 느껴야 한다.

구체 제안:

- 게임 시작 전 `3-2-1`이 아니라 실제 BPM 기준 `2마디 카운트인` 제공
- 호스트에 아주 얇은 메트로놈/백킹 루프를 깔아 합주 기준점을 제공
- `HostSDK` 또는 별도 헬퍼를 통해 평균 핑을 측정하고, 판정 윈도우를 플레이어별 또는 세션별로 미세 이동
- `Perfect / Good / Miss`에 서로 다른 햅틱 강도와 패드 애니메이션 적용
- 과타 시 즉시 `Overhit` 또는 `Offbeat` 피드백을 주어 연타 메타를 억제
- 10콤보 이상 피버 구간에서는 모바일도 BPM에 맞춰 패드 외곽이 박동하도록 확장

기대 효과:

- 억울한 실패보다 "내가 왜 틀렸는지"가 분명해진다.
- 단순 터치 패드인데도 리듬 게임다운 손맛이 생긴다.
- 초보자는 카운트인과 메트로놈 덕분에 빨리 적응하고, 숙련자는 정확도를 올릴 이유가 생긴다.

### 제안 3. TV 쇼형 결과 연출과 기여도 피드백으로 "한 판 더"를 만들기

현재 결과 화면은 최종 점수와 등급만 보여준다. 하지만 이 게임의 진짜 흥행 포인트는 "누가 합주를 살렸는지", "이번 곡이 얼마나 잘 맞았는지", "다음 곡도 해 보자"는 감정선을 남기는 데 있다.

구체 제안:

- 호스트 플레이 화면에 각 레인 담당자 이름 또는 컬러 배지 노출
- 결과 화면에 `최고 정확도 플레이어`, `콤보 세이버`, `피버 메이커` 같은 기여도 카드 추가
- 곡 종료 직후 2초짜리 `하이라이트 리플레이` 또는 판정 요약 바 노출
- 등급 공개 시 짧은 팬파레, 관객 환호, 리벤지 CTA(`다음 곡 도전`, `한 단계 빠르게`) 추가
- 모바일 결과 화면에도 내 역할 기여도 한 줄 피드백 표시

기대 효과:

- 협동 게임인데도 개인의 존재감이 분명해진다.
- 승패보다 리액션과 칭찬 포인트가 생겨 재시도가 쉬워진다.
- 영상/사진으로 찍었을 때 더 "행사장용 콘텐츠"처럼 보인다.

### 4.2 `DemoSimulator.js` 개선점 및 수정 가이드라인

`games/rhythm-jam/host/DemoSimulator.js`는 파일 분리 자체는 잘 되어 있다. 문제는 "어떻게 데모를 돌리느냐"다. 현재 구현은 호스트 내부 맵과 SDK 비공개 속성을 직접 조작하므로, 유지보수성과 실운영 안정성이 낮다.

#### 개선 목표

- 데모 모드가 실제 플레이어 세션 상태를 오염시키지 않아야 한다.
- 실사용자가 입장하면 데모에서 자연스럽게 인간 플레이로 양도할 수 있어야 한다.
- 호스트가 `resetSession()` 없이도 데모 시작/중단/복구를 예측 가능하게 제어할 수 있어야 한다.

#### 수정 가이드라인

1. **공개 데모 API를 호스트에 추가한다**
   - `RhythmJamHost`에 `enterDemoMode()`, `exitDemoMode()`, `spawnDemoPlayer()`, `simulateDemoTap()` 같은 공개 메서드를 만든다.
   - `DemoSimulator.js`는 더 이상 `sdk._players`, `_messageHandlers`에 직접 접근하지 않는다.

2. **실제 세션 상태와 데모 상태를 분리 저장한다**
   - 데모 시작 전 실제 플레이어 목록, 닉네임, 선택 곡, ready 상태를 별도 스냅샷으로 보관한다.
   - 데모 중단 시 스냅샷을 기반으로 로비 상태를 정확히 복원한다.
   - 절대로 `game.players.clear()`나 `game.sdk._players.clear()`로 실세션을 직접 비우지 않는다.

3. **중단 배너와 인간 플레이 양도 UX를 추가한다**
   - 로비에서 "🤖 데모 플레이 실행" 버튼을 누르면 별도 `데모 재생 중` 배너와 `중단` 버튼이 떠야 한다.
   - 실제 사용자가 입장하면 `데모를 종료하고 실제 플레이로 전환할까요?` 같은 명확한 양도 절차를 둔다.
   - 자동 데모(`HostBaseGame`의 idle timer)로 시작된 경우에도 같은 배너 정책을 공유한다.

4. **인원 수별 데모 프로파일을 만든다**
   - 1인/2인/3인/4인+ 구성에서 각각 어떤 자동 편곡이 재생되는지 데모가 보여 주도록 한다.
   - 그래야 로비를 보는 사용자도 "이 게임은 사람이 적어도 된다"는 메시지를 직관적으로 이해한다.

5. **정확도 모델과 휴먼라이즈를 분리한다**
   - 현재처럼 무작위 0~40ms 지터를 주는 것은 괜찮지만, 이를 `accuracyProfile`과 `timingJitterMs` 설정으로 분리해 튜닝 가능하게 만든다.
   - `Perfect 70% / Good 25% / Miss 5%` 같은 프로파일을 곡별로 다르게 줄 수 있어야 결과 화면 다양성이 생긴다.

6. **타이머 생명주기를 중앙 관리한다**
   - `timeouts` 배열 외에 현재 데모 상태(`idle`, `starting`, `playing`, `stopping`)를 명시한다.
   - `onReset()`, `onPlayerJoin()`, `onPlayerDisconnect()`에서 어떤 조건에 데모를 중지할지 표준화한다.
   - 가능하면 `AbortController` 또는 전용 `dispose()` 패턴으로 모든 예약 작업을 한 번에 끊을 수 있게 만든다.

#### 우선 수정 대상 파일

- `games/rhythm-jam/host/main.js`
  - `onPlayerDisconnect`, `onPlayerLeave`, `onPlayerRejoin`, `_assignInstruments`, `_startGame`
- `games/rhythm-jam/mobile/main.js`
  - `onJoin`, `onRejoin`, `lobbyState` 처리, 대기/복구 화면 분기
- `games/rhythm-jam/host/DemoSimulator.js`
  - 내부 SDK 직접 접근 제거, 공개 API 기반 데모 생명주기 재작성

#### 권장 수정 순서

1. 인원 적응형 편곡과 역할 재설계
2. 로비/인게임 재접속 복구 정리
3. `DemoSimulator.js` 공개 API 기반 리팩터링
4. 타이밍 보정과 과타 억제 추가

> `리듬 잼`은 이미 데모에서 눈길을 끌 수 있는 외형을 갖췄다. 하지만 플랫폼 대표작으로 키우려면, 먼저 "몇 명이 와도 성립하는가", "끊겨도 복구되는가", "데모가 실제 세션을 망치지 않는가"를 해결해야 한다. 그 위에 손맛과 결과 쇼를 얹는 것이 가장 안전한 확장 경로다.
