# 루미큐브 (Rummikub) 기획 및 개발 규약 문서

원작 보드게임 Rummikub(공식 룰 기준)을 Connect Dise 플랫폼(TV/PC 호스트 보드 + 스마트폰 컨트롤러, Socket.IO)에 충실하게 이식하기 위한 설계 문서. 구현 담당 엔지니어가 이 문서만으로 개발 가능한 수준을 목표로 함.

---

## 0. 이 문서에서 확정한 결정 사항 (요약)

| # | 항목 | 결정 | 근거 요약 |
|---|------|------|-----------|
| D1 | 인원수 | **minPlayers: 2, maxPlayers: 6**. 2~4인은 원작 표준(106장), 5~6인은 공식 확장판 Rummikub XP 사양(타일 3세트 156장 + 조커 4장 = 160장) 자동 적용 | 원작 충실도와 파티게임 다인원을 모두 만족. XP는 임의 변형이 아닌 **공식 발매 사양**이므로 "원작 왜곡 없음" 조건 충족 (→ §13) |
| D2 | 초기 착수 기준점 | **로비에서 10 / 20 / 30점 중 선택(기본 30점 = 원작 그대로)**. 어느 값을 골라도 규칙 로직은 동일 — "오직 이번 턴에 자기 손패에서 낸 타일만으로" 합계가 그 기준점 이상이어야 함. 보드 기존 타일 재활용 불가는 기준점과 무관하게 항상 적용. 초기 착수 전에는 보드 조작 자체를 클라이언트/호스트 양쪽에서 차단 | 30점은 원작 표준. 10/20점은 공식 룰은 아니지만 실제로 널리 쓰이는 하우스룰(입문자·아이 동반·짧은 판)이라 파티게임 성격에 맞게 옵션으로 열어둠 — 기본값을 30으로 둬 "원작 왜곡 없음" 기본 경험은 그대로 유지 (→ §5) |
| D3 | 초기 착수 턴의 보드 조작 | 초기 착수를 **한 그 턴에도** 기존 보드 재배치·타일 추가 불가. 다음 턴부터 허용 | 원작 공식 룰 ("may not use tiles already on the table during initial meld") (→ §5) |
| D4 | 조커 회수 | 원작 그대로 적용. 조커가 대신하던 것과 **같은 숫자·색의 실물 타일**(손패 또는 보드 출처 모두 허용)로 그 자리를 메꿔야 회수 가능. 회수한 조커는 **같은 턴 안에 반드시 보드의 새/기존 세트에 다시 사용**해야 하며, 조커를 손에 쥔 채 턴 종료 불가. 초기 착수 전 플레이어는 회수 불가 | 원작 공식 룰 (→ §7) |
| D5 | 조커 세트 제한 | 한 세트에 조커 복수 허용(원작 허용). 단 **세트당 실물 타일 최소 1장** 필요(조커만으로 세트 불가) | 원작 룰. 5~6인 모드(조커 4장)에서 실질 의미 발생 (→ §7) |
| D6 | 보드 재배치 UX | **드래그 앤 드롭이 기본**, 보조로 "탭-탭(타일 선택 → 목적지 슬롯 선택)" 병행 지원. 조작 단위는 원자적 `moveTile` 연산 1종으로 통일하고, 분할/병합/새 세트 생성은 모두 이 연산의 목적지 표현으로 파생 | 폰 화면에서 가장 직관적이면서 프로토콜을 단순하게 유지 (→ §11) |
| D7 | 턴 검증 방식 | **턴 시작 시 스냅샷 저장 → 턴 중 자유 조작(임시 상태) → "턴 종료" 버튼 시 호스트가 보드 전체 검증 → 실패 시 스냅샷 롤백 + 강제 1장 드로우** | 원작의 "만지작거리다 되돌리기"를 그대로 재현하며 구현이 단순 (→ §6, §10) |
| D8 | 턴 중 보드 실시간 중계 | 조작 중인 임시 보드를 호스트 TV 화면에 **실시간 반영**(다른 플레이어 폰에는 미반영, TV에만) | "고민하는 모습"이 보이는 관전 재미. 폰까지 중계하면 트래픽·혼란 대비 이득 없음 (→ §9) |
| D9 | 손패 정렬 | **순수 클라이언트 로컬 처리**(서버 미동기화). 정렬 순서는 localStorage에 저장해 재접속 시 복원 | 손패 순서는 게임 상태에 무영향. 메시지 트래픽 절감 (→ §11.2) |
| D10 | 턴 타이머 | 기본 **60초**(호스트 로비에서 30/60/120초/무제한 선택). 타임아웃 시 = 검증 실패와 동일 처리(롤백 + 강제 드로우 + 턴 종료) | 원작 권장 룰(1~2분 제한)에 부합 + 파티게임 템포 유지 (→ §6.4) |
| D11 | 교착(스테일메이트) 판정 | "더 이상 수가 없음"의 완전 탐색은 계산상 비현실적이므로, **더미 소진 이후 전원이 연속 1바퀴 아무 변경 없이 턴을 넘기면** 교착으로 간주하고 원작 교착 점수 규칙 적용 | 원작 교착 룰의 실용적 디지털 번역 (→ §8.2) |
| D12 | 데모(봇) 모드 | **휴리스틱 v1 구현**: 손패 내 세트 탐색 + 기존 세트에 1장 붙이기까지. 보드 전면 해체·재조합과 조커 회수는 봇에서 **미구현(스킵)** | 그럴듯한 시연에 충분하며, 완전 탐색 AI는 투자 대비 효과 낮음 (→ §14) |
| D13 | 라운드 수 | 1라운드 단판 기본. 누적 점수제(여러 라운드)는 문서화만 하고 v1 미구현 | 파티 플랫폼의 다른 게임들과 세션 길이 일관성 |
| D14 | 모션/연출 강도 | **"움직임이 많은 액티브한 UI"를 명시적 목표로 설정** — 타일 하나하나의 이동·배치·검증 결과·턴 전환마다 애니메이션을 붙인다(정적인 보드 게임 느낌을 피함). 기존 게임들의 이펙트 패턴(`gyf-badge-pop`, `gyf-shake-card`, `shake-screen`, `flash-pop`/`score-pulse` 등)과 타이밍·이징을 그대로 재사용해 플랫폼 전체의 시각적 일관성 유지 | 사용자 요청. 루미큐브는 원래 정적인 타일 게임이라 방치하면 밋밋해지기 쉬움 — 모든 상태 변화를 시각적 피드백으로 드러내 파티게임다운 텐션을 만듦 (→ §11.4) |
| D15 | 폰 화면의 보드 노출 시점 + 제출 게이트 | **보드는 "내 차례"일 때만 폰에 노출**(그 외/제출 직후엔 TV로만 확인). **제출 버튼은 (a)보드 전체 유효 + (b)이번 턴 손패에서 최소 1장 이상 놓았을 때만** 활성화(클라이언트에서 `validateBoard()` 재사용 + `_placedFromHandThisTurn` 추적으로 판정, 서버와 동일 로직). 이번 턴에 손패에서 놓은 타일은 보드 위에서 시각적으로 강조 | 사용자 요청. 원래 초안(§11.3, 아래)의 "턴 아닌 폰도 커밋된 보드 상시 표시"를 대체 — 폰은 "내 조작 콘솔", TV는 "관전용 진실 공급원"으로 역할을 명확히 분리 (→ §11.3) |

## 1. 개요 및 파일 구조

- 경로: `games/rummikub/`
- CSS 접두사: `rk-`
- 인원: 2~6명 (registry: `minPlayers: 2, maxPlayers: 6`)
- 썸네일: 🀄 (또는 전용 PNG)

```
games/rummikub/
├── shared/
│   ├── RummikubEngine.js    # 타일 생성/셔플, 세트 유효성 검사, 조커 값 해석,
│   │                        # 초기착수 기준점(가변) 계산, 점수 계산 (host/mobile/bot 공유)
│   ├── TileRenderer.js      # 타일 1장 DOM/캔버스 렌더 유틸 (색·숫자·조커 얼굴)
│   └── motion.js            # 모션 상수(SNAP_MS 등) + FLIP 트윈 유틸 (§11.4, host/mobile 공유)
├── host/
│   ├── index.html
│   ├── main.js
│   ├── RummikubGame.js      # HostBaseGame 상속, 게임 상태의 단일 권위(authority)
│   └── style.css
└── mobile/
    ├── index.html
    ├── main.js
    ├── RummikubMobile.js    # MobileBaseGame 상속
    └── style.css
```

- 로비는 `<game-lobby>` 컴포넌트 재사용. 로비 옵션: 턴 타이머(30/60/120/∞), 초기 착수 기준점(10/20/30점, 기본 30).
- 상태 권위는 다른 게임과 동일하게 **호스트 브라우저의 게임 인스턴스**. 서버(Socket.IO)는 릴레이만 담당. 이하 "호스트 검증"이 곧 이 프로젝트 문맥의 "서버 검증"임.
- `vite.config.js`에 host/mobile 엔트리 추가 필요.

## 2. 구성물 (타일)

### 2.1. 표준 구성 (2~4인)

- 색상 4종: 빨강(red) · 파랑(blue) · 노랑(yellow) · 검정(black) — 원작 기준 색상.
- 숫자 1~13 × 4색 × **2세트** = 104장 + 조커 **2장** = **총 106장**.

### 2.2. 확장 구성 (5~6인, Rummikub XP 사양)

- 숫자 1~13 × 4색 × **3세트** = 156장 + 조커 **4장** = **총 160장**.
- 게임 시작 시 로비 인원수를 보고 호스트가 자동 선택. 별도 옵션 노출 안 함.

### 2.3. 타일 ID 체계

모든 타일은 게임 시작 시 고유 ID를 부여받고, 이후 모든 메시지·상태에서 이 ID로만 참조함.

- 일반 타일: `{색1글자}{숫자2자리}{사본}` — 예: `r07a`(빨강 7 첫 사본), `k13c`(검정 13 세 번째 사본, 5~6인 모드에서만 존재). 색 코드: `r`(빨강) `b`(파랑) `y`(노랑) `k`(검정). 사본: `a`/`b`(/`c`).
- 조커: `j1`, `j2`(, `j3`, `j4`).

ID에 색·숫자가 인코딩돼 있으므로 검증 로직이 별도 조회 테이블 없이 파싱 가능. 단, **모바일에는 자기 손패와 보드에 공개된 타일의 ID만 전달**(더미 내용·타인 손패는 절대 전송 금지 — 클라이언트 메모리 스니핑 방지).

## 3. 세트(조합) 규칙 — 검증 사양

보드는 "세트(meld)"의 목록이며, 각 세트는 **순서 있는 타일 배열**임. 세트는 아래 둘 중 하나로 유효해야 함.

### 3.1. Group (그룹)

- 같은 숫자, 서로 다른 색, **3장 또는 4장**. (5~6인 모드에서도 색이 4종이므로 최대 4장 불변. 같은 색 중복 불가.)
- 예: `빨7·파7·노7` (유효), `빨7·빨7·파7` (무효 — 색 중복).

### 3.2. Run (런)

- 같은 색, 연속 숫자, **3장 이상**(이론상 최대 13장).
- **1이 최저, 13이 최고. 13→1 순환(wrap-around) 없음.** `파12·파13·파1`은 무효.
- 세트 배열은 왼쪽→오른쪽 오름차순으로 저장·표시함(조커 값 해석의 기준이 됨).

### 3.3. 조커 값 해석 (validation 시 확정 알고리즘)

조커는 어떤 타일이든 대신하지만, 세트가 유효하려면 조커가 대신하는 **숫자·색이 논리적으로 확정 가능**해야 함. 세트 배열이 순서를 가지므로 해석은 결정적임:

- **런 내 조커**: 배열 내 위치로 값 확정. 예: `[파5, J, 파7]` → J=파6. `[J, 파12, 파13]` → J=파11. 양끝 조커가 0 이하 또는 14 이상이 되면 그 세트는 **무효**. 예: `[파12, 파13, J]` → J=파14 → 무효 (클라이언트 UI는 배치 시점에 즉시 경고하되, 최종 판정은 커밋 검증에서).
- **그룹 내 조커**: 숫자는 그룹의 숫자로 확정. 색은 "그룹에 아직 없는 색 중 하나"로, 후보가 여럿 남는 경우(3장 그룹) **색 미확정 상태를 허용** — 점수 계산에는 숫자만 필요하고, 조커 회수 시에는 후보 색 중 아무 색이나 인정(원작과 동일, §7.2).
- **세트 타입 판별**: 실물 타일들의 패턴으로 결정. 실물 숫자가 모두 같고 색이 다르면 그룹 후보, 실물이 한 색이면 런 후보. 둘 다 해석 가능한 극단 케이스(예: 실물 1장 + 조커 2장, `[J, 노8, J]`)는 **어느 쪽으로든 유효 해석이 하나라도 존재하면 유효**로 판정하고, 점수·조커 회수용 값은 "런 해석"을 우선 채택(노7·노9로 확정되는 쪽이 회수 조건이 더 명확). 이 우선순위는 엔진에 상수로 명시할 것.
- **세트당 실물 타일 최소 1장** (D5). 조커 개수 ≥ 세트 크기인 세트는 무효.

### 3.4. 세트 점수 (초기 착수 합산·감점 계산 공용)

- 일반 타일 = 액면 숫자.
- 조커 = **세트 안에서는** 대신하는 숫자의 값(§3.3 해석 결과). **손패에 남았을 때는** 30점 감점(§8.1).

## 4. 게임 흐름 총괄

```
로비(<game-lobby>) → 시작
  ↓
[분배] 타일 셔플 → 각자 14장 → 나머지는 더미(pool, 비공개 스택)
  ↓
[턴 순서 결정] 원작은 타일 뽑기로 선 결정 → 디지털에선 랜덤 셔플로 대체하고
               호스트 화면에 순서 공개 (연출: "타일 뽑기" 애니메이션은 선택 사항)
  ↓
[턴 루프] 현재 플레이어만 조작 가능 (§6)
  ├─ 초기 착수 미완료자: 손패→새 세트만 가능, 기준점 검증 (§5)
  ├─ 초기 착수 완료자: 추가/재배치/새 세트 자유 (§6.2)
  ├─ 커밋 시 전체 보드 검증 → 실패 시 롤백+드로우 (§10)
  └─ 자발적 패스 → 더미에서 1장 드로우 (더미 비었으면 그냥 턴 종료)
  ↓
[종료] 누군가 손패 0장 → 즉시 종료 (§8.1)
       또는 교착 판정 (§8.2)
  ↓
[점수 정산 → 결과 화면 → 다시하기/로비 복귀]
```

## 5. 초기 착수 (Initial Meld) — ⚠️ 최다 오해 규칙, 구현·UI 양쪽에서 강제

> **핵심: 초기 착수 기준점(기본 30점)은 "이번 턴에 자기 손패에서 낸 타일"만으로 채워야 한다. 보드에 이미 깔린 타일(남의 세트)을 재배치하거나 거기에 붙여서 채우는 것은 절대 불가.** 초보자가 가장 자주 틀리는 지점이므로, 규칙 텍스트로만 안내하지 말고 아래처럼 시스템으로 차단할 것.

### 5.0. 기준점 옵션 (D2)

- 로비에서 호스트가 **10 / 20 / 30점** 중 선택, 기본값 **30점(원작 표준)**. `<game-lobby>`에 턴 타이머(D10)와 같은 자리에 라디오 옵션으로 노출.
- 선택값은 `gameStarted` 메시지의 `initialMeldThreshold` 필드로 전 클라이언트에 전파(§12) — 이후 모든 검증·UI 표시는 하드코딩된 30이 아니라 이 값을 참조. 게임 시작 후에는 변경 불가(라운드 도중 기준이 바뀌면 이미 착수한 사람과 불공평).
- 10/20점은 원작 공식 룰이 아닌 널리 쓰이는 하우스룰(입문자·아이 동반·빠른 판 진행용)이므로, 호스트 로비 UI에 "10/20점은 하우스룰, 원작 그대로 하려면 30점" 정도의 짧은 안내 문구를 둘 것. 아래 §5.1~5.2의 "30점"은 모두 이 선택값을 가리키는 것으로 읽는다.

### 5.1. 규칙

- 첫 착수는 **하나 이상의 유효한 세트**, 그 세트들의 **합계가 선택된 기준점(기본 30점) 이상**. 여러 세트로 나눠 합산 가능 (30점 기준 예: 그룹 10·10·10 = 30 한 방, 또는 런 3·4·5(12점) + 그룹 6·6·6(18점) = 30. 10점/20점을 고른 경우도 동일한 방식으로, 더 적은 세트로도 기준을 채울 수 있음).
- 조커 포함 시 조커는 대신하는 값으로 합산 (예: `노10·J·빨10` 그룹 = 30점, J=10).
- 초기 착수 턴에는 **기존 보드 타일 사용·재배치 일절 불가** (D3). 착수에 성공한 그 턴에도 마찬가지 — 재배치는 다음 자기 턴부터.
- 초기 착수를 안 하거나 못 하면(기준점 미달 포함): 그 턴의 임시 배치를 전부 되돌리고 더미에서 1장 드로우 후 턴 종료.

### 5.2. 시스템 강제 방법

- **모바일 UI**: `initialMeldDone == false`인 플레이어의 턴에는 기존 보드 세트를 전부 **비활성(회색 잠금) 표시** — 드래그 대상도, 드롭 목적지도 될 수 없음. 유일하게 가능한 조작은 "손패 → 새 세트 존" 및 "이번 턴에 자기가 만든 새 세트들 사이의 이동". 화면 상단에 실시간 합계 배지: `이번 착수 합계 17/{기준점}점`(기준점은 로비 선택값을 그대로 표시).
- **호스트 검증**: 커밋 시 이번 턴 op 로그를 검사해 출처가 손패가 아닌 타일이 하나라도 개입했으면 즉시 실패 처리(클라이언트 버그/조작 대비 이중 방어). 새로 만든 세트들의 합계가 `initialMeldThreshold` 미만이면 실패.
- 실패 시 처리(§10)는 일반 검증 실패와 동일: 롤백 + 강제 드로우.

## 6. 턴 진행 상세

### 6.1. 턴의 라이프사이클 (D7 스냅샷 방식)

1. **턴 시작**: 호스트가 `{ board, 현재 플레이어 손패 }` 스냅샷 저장. `turnStarted` 브로드캐스트(현재 플레이어 ID, 마감 시각).
2. **조작 단계**: 현재 플레이어의 폰만 조작 활성화. 다른 폰은 관전 상태(자기 손패 정렬만 가능). 조작은 원자 연산(op) 단위로 호스트에 전송되고, 호스트는 임시 상태에 적용 후 TV 화면에 즉시 반영(D8). 플레이어는 턴 안에서 **횟수 제한 없이** 재배치·되돌리기 가능. "처음부터 다시" 버튼은 스냅샷 상태로 임시 상태를 리셋함(턴은 유지).
3. **종료 선택지** (셋 중 하나로 반드시 끝남):
   - **확정(턴 종료) 버튼**: 호스트가 §10 검증 수행. 성공 → 임시 상태를 정식 상태로 커밋, 드로우 없음. 실패 → 롤백 + 강제 1장 드로우.
   - **패스(뽑기) 버튼**: 임시 변경이 있으면 자동 롤백 후, 더미에서 1장 드로우. 더미가 비어 있으면 드로우 없이 턴만 종료.
   - **타임아웃**: 검증 실패와 동일 처리(롤백 + 강제 드로우; 더미 비면 드로우 생략).
4. 손패 0장 커밋 성공 시 즉시 게임 종료(§8.1). 아니면 다음 플레이어로.

주의: **변경을 하나라도 커밋에 성공한 턴에는 드로우하지 않음**(원작 — 내거나 뽑거나 둘 중 하나). 드로우한 타일은 그 턴에 낼 수 없음(어차피 드로우 즉시 턴이 끝나는 구조라 자연 충족).

### 6.2. 허용되는 조작 (초기 착수 완료자)

원작의 (a)(b)(c)를 모두 지원하며, 전부 `moveTile` op 하나로 표현됨(§9.2):

- (a) 손패 타일을 기존 세트의 임의 위치에 추가 (런의 양끝/중간 삽입, 그룹의 4번째 색).
- (b) 보드 위 임의 타일들의 자유 재배열 — **남이 낸 세트라도 완전히 해체·재조합 가능.** 세트 분할(런 가운데서 쪼개기), 병합, 타일 순회 이동 전부 허용. 턴 중간에는 보드가 무효 상태(2장짜리 조각 등)여도 무방 — **유효성은 오직 커밋 시점의 최종 상태**에 대해서만 검사.
- (c) 손패 타일로 새 세트 생성.
- 조커 회수(§7.2) — moveTile 조합으로 표현되나 UI는 전용 플로우 제공.
- 보드 타일을 손패로 가져오는 것은 **조커 회수 외에는 불가** — op 수신 시점에 호스트가 즉시 거부(임시 상태에도 반영 안 함). 자기 손패에서 이번 턴에 임시로 내려놓은 타일을 다시 손패로 회수하는 것은 가능(아직 커밋 전이므로).

### 6.3. op 시점 즉시 거부 vs 커밋 시점 검증의 분담

- **즉시 거부(호스트가 op 수신 시)**: 자기 턴 아님 / 존재하지 않는 타일 ID / 소유하지 않은 손패 타일 / "보드→손패" 이동(조커 및 이번 턴에 내려놓은 타일 제외) / 초기 착수 미완료자의 보드 터치. → `opAck { accepted: false }` 응답, 임시 상태 무변경.
- **커밋 시점 검증**: 세트 유효성, 초기 착수 기준점, 조커 회수 완결성 등 "최종 상태" 규칙 전부 (§10). 턴 중간의 무효 배치는 자유이므로 여기서만 본다.

### 6.4. 타이머 (D10)

- 로비 옵션: 30/60/120초/무제한, 기본 60초.
- 남은 시간은 호스트 화면 + 현재 플레이어 폰에 표시. 10초 남으면 폰 진동/색 경고.
- 타임아웃 처리는 §6.1-3 참조.

## 7. 조커 상세 규칙

### 7.1. 사용

- 어느 세트에서든 임의 타일 대체 가능. 한 세트에 조커 복수 허용, 단 실물 최소 1장(D5).
- 초기 착수에 사용 가능하며 대신하는 값으로 착수 합계에 계산(§5.1).

### 7.2. 회수 (D4 — 원작 공식 룰 그대로)

보드 위 세트의 조커를 손패로 가져오는 조건, 전부 **같은 턴 안에서** 충족돼야 함:

1. 조커가 현재 대신하는 것과 **동일한 숫자·색의 실물 타일**로 그 자리를 채운다. 색 미확정 그룹(3장, §3.3)의 조커는 "그룹에 없는 색 중 아무 색"의 해당 숫자 타일로 대체 가능. 대체 타일의 출처는 **손패든 보드 위 다른 세트든 무방**(원작 룰 — 보드에서 가져올 경우 그쪽 세트도 커밋 시점에 유효해야 함은 물론임).
2. 회수한 조커는 **그 턴이 끝나기 전에 반드시 보드 위 세트(새 세트 또는 기존 세트)에 다시 사용**돼야 함. **조커를 손에 쥔 채로 턴을 커밋할 수 없음.** (커밋 검증 항목: "턴 시작 시 보드에 있던 조커는 턴 종료 시에도 보드에 있어야 한다" — 이 한 줄로 회수·재사용 의무가 모두 검증됨.)
3. 초기 착수를 마치지 않은 플레이어는 조커 회수 불가(보드 조작 자체가 잠겨 있으므로 자동 충족되나, 호스트 검증에도 명시적 가드 둘 것).

### 7.3. UX 처리

- 조커 회수를 순수 드래그로만 하게 하면 순서 실수(조커 먼저 빼기)가 잦으므로, **보드 위 조커 롱프레스 → "조커 회수" 모드 → 대체할 실물 타일 선택(손패/보드에서 후보 타일 하이라이트) → 스왑 실행**의 전용 플로우 제공. 내부적으로는 moveTile 2건(대체 타일→조커 자리, 조커→손패)으로 기록됨.
- 후보 하이라이트: 엔진의 조커 값 해석(§3.3)으로 "지금 이 조커를 대체할 수 있는 타일"을 계산해 표시. 후보가 전무하면 회수 모드 진입 자체를 막고 사유 토스트.

### 7.4. 감점

- 게임 종료 시 손패에 남은 조커는 **30점 감점**.

## 8. 게임 종료와 점수

### 8.1. 정상 종료 (Rummikub!)

- 누군가 커밋 성공으로 손패 0장이 되면 **즉시 종료**. 호스트 화면에 "Rummikub!" 연출.
- 점수(원작 그대로):
  - 패자들: 각자 손에 남은 타일 액면 합계만큼 **감점**(음수 기록). 조커는 30점.
  - 승자: **패자 전원의 감점 합계**만큼 득점(양수). (검산: 전원 점수 합 = 0.)
- 결과 화면: 순위(승자 → 감점 적은 순), 각자 남은 타일 공개.

### 8.2. 교착 종료 (D11)

- 전제: 더미 소진(0장) 상태.
- 판정: 더미 소진 이후, **모든 생존 플레이어가 연속으로 한 바퀴(N명 N턴) 동안 보드에 아무 변경도 커밋하지 못하고 턴을 넘기면** 교착으로 종료. (검증 실패로 인한 롤백 턴도 "변경 없음"으로 집계. 커밋 성공이 하나라도 나오면 카운터 리셋.)
- 점수(원작 교착 룰): 손패 합계가 **가장 적은** 플레이어가 승자. 패자들은 각자 자기 손패 합만큼 감점, 승자는 **(패자 감점 합계 − 자기 손패 합계)** 만큼 득점. 최소 합계 동률이면 공동 승자로 하고 패자 감점 합계를 균등 분배(원작에 명시 없는 부분의 최소 보완).
- 호스트 화면에 "교착 카운트" 표시(더미 소진 후: `무변경 3/4턴`) — 플레이어가 종료 임박을 인지하게.

### 8.3. 중도 이탈 처리 (플랫폼 공통 이슈)

- 이탈자의 손패는 **더미에 섞지 않고 게임에서 제거**(재분배·더미 환원 모두 정보 왜곡 발생. 제거가 가장 중립적). 이탈자가 보드에 이미 낸 타일은 보드에 남음.
- 남은 인원이 2명 미만이 되면 게임 종료 → 남은 1인 승리 처리.
- 이탈자 점수는 이탈 시점 손패로 감점 계산해 결과 화면에 "(이탈)" 표기.
- 재접속: 플랫폼의 rejoin 흐름을 따르고, 호스트가 `stateSync`(§12)로 전체 상태 복원. 이탈 판정 유예(예: 60초)는 플랫폼 공통 정책 준수.

## 9. 상태 모델 (호스트 권위 상태)

### 9.1. 게임 상태

```
{
  phase: 'lobby' | 'playing' | 'finished',
  tileSetMode: 'standard' | 'xp',          // 인원수로 자동 결정 (§2)
  initialMeldThreshold: 10 | 20 | 30,      // 로비 선택값, 기본 30 (§5.0)
  pool: [tileId, ...],                     // 셔플된 더미 (비공개, 호스트 메모리에만)
  players: {
    [playerId]: {
      nickname, hand: [tileId, ...],       // 호스트만 전체 보유. 각 폰엔 자기 것만
      initialMeldDone: boolean,
      score: number,                       // 결과 정산 시 기록
      connected: boolean
    }
  },
  turnOrder: [playerId, ...],
  currentTurnIdx, turnDeadlineTs,
  board: [ { meldId, tiles: [tileId, ...] }, ... ],   // 순서 있는 세트 배열 (§3)
  // 턴 임시 영역
  snapshot: { board, hand } | null,        // 턴 시작 시 저장 (§6.1)
  provisional: { board, hand },            // 턴 중 조작이 반영되는 작업본
  opLog: [op, ...],                        // 이번 턴 op 기록 (검증·리플레이용)
  stalemateCounter: number                 // §8.2
}
```

- `meldId`는 호스트가 발급하는 증가 정수. 재배치로 빈 세트(`tiles.length === 0`)가 되면 즉시 제거, 새 세트 생성 시 새 ID 발급.
- 커밋 성공 시 `provisional` → 정식 상태로 승격, 실패 시 `snapshot` 복원.

### 9.2. 조작 연산(op) — 단일 원자 연산

```
moveTile {
  tileId,
  from: { zone: 'hand' | 'meld', meldId?, index? },
  to:   { zone: 'hand' | 'meld' | 'newMeld', meldId?, index }
}
```

- `to.zone === 'newMeld'` → 호스트가 새 meldId 발급 후 결과를 에코.
- `to.zone === 'hand'`는 "이번 턴에 내가 손패에서 내려놓은 타일 회수" 또는 "조커 회수"(§7.2)일 때만 합법 — 그 외 즉시 거부(§6.3).
- 세트 분할 UX(§11.3)는 클라이언트가 moveTile 여러 건으로 풀어서 전송(예: 런 6장을 3+3으로 쪼개기 = 뒤 3장을 newMeld로 옮기는 op 3건). 프로토콜은 끝까지 1종 유지.
- 각 op에 클라이언트 증가 `seq` 부여 → 호스트 에코에 같은 seq 포함 → 폰의 낙관적(optimistic) 로컬 적용과 어긋나면 폰이 호스트 전문 기준으로 재동기화.

## 10. 커밋 시점 검증 파이프라인 (호스트, 순서대로 전부 통과해야 성공)

1. **타일 보존 검사**: `provisional.board ∪ provisional.hand` = `snapshot.board ∪ snapshot.hand` (타일 집합이 정확히 일치 — 증발·복제 없음).
2. **세트 유효성**: 보드의 모든 세트가 §3의 그룹 또는 런으로 유효(조커 해석 포함, 실물 ≥1장).
3. **변경 존재 검사**: 스냅샷과 완전히 동일하면 "확정"이 아니라 패스로 간주 → 드로우 처리로 분기(확정 버튼 오터치 안전망).
4. **초기 착수 검사** (`initialMeldDone == false`인 경우): opLog에 보드 기존 타일 개입 없음 + 새 세트 합계 ≥ `initialMeldThreshold` (§5.2). 통과 시 `initialMeldDone = true`.
5. **조커 완결성**: 턴 시작 시 보드에 있던 모든 조커가 턴 종료 시에도 보드에 있음 (§7.2-2).
6. **결과 반영**: 성공 → 커밋 + `boardCommitted` 브로드캐스트 + 손패 0장이면 종료 시퀀스. 실패 → `snapshot` 복원 + 강제 드로우 + `turnResult { accepted: false, reason }` (reason은 폰에 한글 문구로 표시: "노랑 세트가 2장뿐이에요", "초기 착수 합계가 24점으로 30점 미달이에요" 등 — 검증 단계별 사유 코드 정의 필수).

검증 실패는 "벌칙"이 아니라 원작의 원상복구 룰이므로, 폰 문구 톤은 안내형으로.

## 11. 화면 설계

### 11.1. 호스트 (TV/PC) — `RummikubGame.js`

- **중앙 대부분 = 공용 보드**: 세트들을 그리드 흐름(flow) 레이아웃으로 배치, 세트 내 타일은 가로로 붙여 표시. 세트 수가 늘면 타일 크기 자동 축소(2~3단계 스케일). 턴 중 임시 조작을 실시간 반영(D8)하되, 임시 상태임을 알리는 표시(이동 중 타일 하이라이트).
- **상단 바**: 현재 턴 플레이어(강조 + 타이머 링), 턴 순서 목록, 더미 남은 장수(🂠 × N).
- **플레이어 패널**(측면 또는 하단): 각자 닉네임 + **손패 장수만**(내용 비공개) + 초기 착수 완료 뱃지 + 접속 상태.
- **연출**: 커밋 성공 시 변경된 세트 플래시, 검증 실패 시 "되돌아가는" 애니메이션 + 드로우 연출, 손패 1장 남으면 해당 플레이어 패널 경고 강조, 종료 시 "Rummikub!" 풀스크린.
- QR: 플랫폼 표준(로비 컴포넌트) 따름.

### 11.2. 모바일 — 자기 손패

- 화면 하단 40~45%를 손패 트레이(2단 랙 — 원작의 타일 거치대 메타포). 가로 스크롤 허용.
- **정렬**: 드래그로 자유 재배치 + 보조 버튼 "색순 정렬"/"숫자순 정렬"(원작 유저의 양대 정리법: 런 준비 vs 그룹 준비). 전부 로컬 처리(D9), 순서는 localStorage 보존.
- 새로 받은(드로우/분배) 타일은 반짝임 표시.

### 11.3. 모바일 — 보드 조작 UX (D6)

화면 상단 55~60%가 보드 뷰(호스트 보드와 동일 데이터, 핀치 줌 + 팬 스크롤 가능).

- **기본: 드래그 앤 드롭.** 손패/보드의 타일을 집어 끌면:
  - 각 세트의 **양끝과 타일 사이사이에 드롭 슬롯**이 벌어지며 표시됨(삽입 위치 시각화).
  - 보드 빈 영역에 상시 노출되는 **[+ 새 세트]** 드롭 존.
  - 드롭 시 낙관적 로컬 반영 + `boardOp` 전송(§9.2).
- **보조: 탭-탭 모드.** 타일 탭(선택 상태) → 목적지 슬롯 탭. 드래그가 어려운 상황(작은 화면, 접근성) 대비. 설정 토글 없이 두 입력을 항상 동시 지원(탭만으로도 완결 가능하게).
- **세트 분할**: 런의 타일 사이 경계를 롱프레스 → "가위" 표시 → 확인 탭으로 분할(뒤쪽 타일들이 새 세트로). 내부적으로 moveTile 다건(§9.2).
- **조커 회수**: §7.3 전용 플로우.
- **하단 고정 버튼 3개**: `처음부터`(스냅샷 리셋) / `뽑기(패스)` / `제출`(구현 시 "턴 종료"에서 "제출"로 명칭 확정, 사용자 지시). 확정 버튼에는 확인 다이얼로그 1회(오터치로 롤백+강제드로우 당하는 사고 방지). 자기 턴이 아닐 때는 세 버튼 모두 숨기고 보드는 열람 전용.
- **제출 버튼 클라이언트 사이드 게이트(사용자 추가 지시, 2026-08-23)**: 아래 두 조건을 모두 만족해야 활성화 — 만족 못 하면 버튼 자체가 비활성(disabled) 처리돼 눌러도 반응 없음(서버가 거부하고서야 아는 게 아니라 애초에 못 누르게):
  1. 현재 작업 중인 보드(workBoard)의 모든 세트가 §3 기준으로 유효(그룹/런). `shared/RummikubEngine.js`의 `validateBoard()`를 호스트와 동일하게 클라이언트에서도 재사용해 판정 불일치를 방지.
  2. 이번 턴에 **내 손패에서 보드로 최소 1장 이상**을 실제로 놓았어야 함(보드만 재배치하고 손패는 하나도 안 낸 채로는 제출 불가). 호스트의 `_placedFromHandThisTurn` 추적과 동일한 로직을 클라이언트에도 두어 판정.
- **이번 턴에 새로 놓은 내 타일 강조 표시(사용자 지시)**: 위 `_placedFromHandThisTurn`에 포함된 타일은 보드 위에서 시각적으로 구분(테두리 글로우 등)돼, 재구성 중에 "이번 턴에 내가 뭘 냈는지"를 한눈에 볼 수 있게 함.
- **보드는 "내 차례"일 때만 폰 화면에 노출(사용자 지시로 변경 — 원래 초안은 "턴이 아닌 폰도 커밋된 보드는 상시 표시"였으나, 사용자가 명시적으로 "제출하고 나면 플레이어 화면에는 타일 구성이 사라지고 보드판(TV)에서만 확인 가능"으로 확정함)**: 내 턴이 시작되면 보드(현재 커밋된 상태)가 폰 화면에 나타나 재구성을 시작할 수 있고, 제출(또는 뽑기/타임아웃)로 턴이 끝나는 순간 폰에서 보드 영역이 다시 숨겨지고 "보드는 TV 화면에서 확인하세요" 안내로 대체됨. 손패 트레이는 턴과 무관하게 항상 노출(자기 타일은 언제든 볼 수 있어야 하므로).

### 11.4. 모션/연출 설계 (D14 — "액티브한 UI")

루미큐브는 원작 자체가 정적인 타일 나열 게임이라, 디지털로 그대로 옮기면 "숫자판 붙이기"처럼 밋밋해지기 쉽다. 이 프로젝트의 다른 게임들(give-you-fire의 공격 배지 팝업·흔들림, dobble의 정답 플래시, dice의 화면 흔들림 등)과 동일한 밀도로 **상태가 바뀌는 모든 순간에 애니메이션을 건다**. 정적인 것은 "아직 확정되지 않은 것"뿐이어야 하고, 나머지는 전부 움직인다.

#### 원칙

- **모든 타일 이동은 트윈된다.** 손패↔보드, 보드 내 슬롯 이동, 드로우 등 어떤 경로로 타일이 옮겨가든 순간이동(즉시 위치 변경) 없이 이동 애니메이션을 거친다. 다수 타일이 한 번에 움직일 때(예: 세트 분할, 롤백)는 각 타일에 짧은 stagger(순차 지연, 20~40ms 간격)를 줘서 "와르르" 느낌을 낸다.
- **검증 결과는 몸으로 티가 난다.** 성공은 상승감(스케일 업 + 반짝임), 실패는 원작처럼 "손이 튕겨 나오는" 되돌림(급가속 후 감속하는 이징으로 원위치 복귀) + 화면 가장자리 붉은 플래시.
- **턴 전환은 조명이 옮겨가는 느낌으로.** 순간적으로 바뀌지 않고, 이전 플레이어 패널이 dim되며 다음 플레이어 패널로 스포트라이트(글로우 테두리)가 스윕한다.
- **타이머는 숫자만 바뀌지 않는다.** 원형 타이머 링이 실시간으로 줄어들고, 10초 이하부터는 pulse(맥박) 애니메이션 + 색상 전이(민트→주황→빨강)로 긴박감을 준다.

#### 구현 지침

- 순수 CSS `transition`/`@keyframes`로 충분한 것(색 전이, 펄스, 흔들림, 배지 스케일)은 CSS로. **타일이 슬롯 사이를 실제 경로로 이동하는 애니메이션**(드래그 릴리즈 후 스냅, 롤백 되돌림)은 좌표 트윈이 필요하므로 `TileRenderer.js`에 소형 트윈 유틸(FLIP 기법 — First/Last/Invert/Play, 별도 라이브러리 의존성 없이 `transform`+`transition`만으로 구현 가능) 하나를 두고 host/mobile이 공유한다.
- 애니메이션 지속시간·이징은 상수로 모아 `shared/motion.js`(신규)에 정의하고 매직넘버 산발 금지: 예) `SNAP_MS=180`, `ROLLBACK_MS=420`, `STAGGER_MS=28`, `EASE_SNAP='cubic-bezier(0.34,1.56,0.64,1)'`(overshoot), `EASE_ROLLBACK='cubic-bezier(0.6,0,0.4,1)'`.
- 저사양 기기 대비: 동시 이동 타일이 많은 롤백/딜링 시퀀스는 `prefers-reduced-motion` 미디어쿼리를 존중해 stagger 없이 즉시 처리하는 폴백 경로를 둔다(접근성 + 저사양 기기 프레임드랍 방지).
- §15 엣지 케이스 체크리스트에 "대량 롤백 시(세트 여러 개 재조합 실패) 애니메이션이 겹쳐도 최종 위치가 정확한지" 항목 추가할 것(연출이 상태 정합성을 깨면 안 됨 — 애니메이션은 항상 이미 확정된 최종 좌표를 향해 재생되고, 좌표 자체의 소스는 항상 §10 검증 후의 정식 상태).

## 12. 메시지 프로토콜

닉네임 설정 등 로비 단계는 플랫폼 공통(`setProfile` 등, `<game-lobby>` 처리) 재사용. 아래는 루미큐브 전용.

### Mobile → Host

| type | payload | 시점 / 비고 |
|------|---------|------------|
| `boardOp` | `{ seq, op: moveTile{...} }` (§9.2) | 턴 중 조작 1건마다. 즉시 거부 조건은 §6.3 |
| `resetTurn` | `{}` | "처음부터" 버튼. 임시 상태를 스냅샷으로 리셋 |
| `endTurn` | `{}` | "턴 종료(확정)". 호스트가 §10 검증 실행 |
| `drawAndPass` | `{}` | "뽑기(패스)". 임시 변경 자동 롤백 후 드로우 |
| `requestState` | `{}` | 재접속/포그라운드 복귀 시 전체 상태 요청 |
| `requestRematch` | `{}` | 결과 화면에서 다시하기 |

### Host → Mobile / All

| 방향 | type | payload | 시점 |
|------|------|---------|------|
| H→All | `gameStarted` | `{ turnOrder, tileSetMode, poolCount, turnTimerSec, initialMeldThreshold }` | 시작 직후 |
| H→Player | `handDealt` | `{ tiles: [tileId×14] }` | 분배 시 (각자에게 개별 전송 — 절대 브로드캐스트 금지) |
| H→All | `turnStarted` | `{ playerId, turnNo, deadlineTs, poolCount }` | 매 턴 시작 |
| H→Player | `opAck` | `{ seq, accepted, reason?, newMeldId? }` | boardOp 응답. 거부 시 폰은 로컬 낙관 반영 롤백 |
| H→All | `boardPreview` | `{ board }` | 턴 중 임시 상태 변경 시. **호스트 화면 렌더용**. 비턴 플레이어 폰은 무시 (D8) |
| H→Player | `turnResult` | `{ accepted, reason?, drawnTile?, hand }` | endTurn/drawAndPass/타임아웃 처리 결과. 실패·패스 시 드로우 타일 포함. `hand`는 권위 손패 전문(全文) 재동기화용 |
| H→All | `boardCommitted` | `{ board, poolCount, handCounts: {playerId: n}, initialMeldFlags }` | 커밋 성공/롤백 확정 후 (양쪽 모두 이 메시지로 정식 상태 확정) |
| H→All | `jokerRetrieved` | `{ playerId }` | 커밋에 조커 회수가 포함됐을 때 연출용 (선택) |
| H→Player | `stateSync` | `{ board, hand, poolCount, turnInfo, handCounts, initialMeldFlags, phase }` | requestState 응답 / 재접속 복구 |
| H→All | `stalemateWarning` | `{ passStreak, needed }` | 더미 소진 후 무변경 턴 누적 시 (§8.2) |
| H→All | `gameFinished` | `{ endType: 'rummikub'\|'stalemate'\|'forfeit', winnerIds, scores: {playerId: n}, revealedHands: {playerId: [tileId]} }` | 종료. 전원 손패 공개 |

설계 원칙 정리:

- **손패 내용은 오직 그 소유자에게만** 송신 (`handDealt`, `turnResult.hand`, `stateSync.hand`). 타인에겐 항상 장수만.
- 손패 **정렬은 메시지 없음** (D9 — 순수 로컬).
- 보드 전송은 diff가 아닌 **전문 스냅샷**(`board` 배열 통짜) — 세트 수십 개 수준이라 트래픽 부담 없고, 폰·TV의 상태 어긋남을 원천 차단.
- 폰은 자기 op를 낙관 반영하되, `opAck` 거부·`boardCommitted`·`stateSync` 수신 시 무조건 호스트 전문으로 덮어씀.

## 13. 인원수 결정 근거 (D1 상세)

**결정: minPlayers 2, maxPlayers 6. 5인 이상 시 타일만 XP 사양(160장)으로 자동 확장, 규칙은 전 인원 동일.**

- 트레이드오프: ① 원작 표준은 2~4인 — 4인 초과를 지원하려면 무언가는 표준에서 벗어난다. ② 이 플랫폼의 다른 게임들은 대부분 6~8인 지원 — 4인 캡은 파티 상황에서 "두 명은 구경만"을 만든다.
- 해소: 제작사가 직접 발매한 **Rummikub XP(6인용, 타일 3세트 156장 + 조커 4장)** 사양을 그대로 쓰면 "임의 변형 없이" 6인까지 커버 가능. 규칙(30점 착수, 조커, 점수)은 표준과 완전 동일하고 타일 수만 다르므로 엔진 분기가 `tileSetMode` 상수 하나로 끝난다.
- 7~8인 미지원 사유: 공식 사양이 존재하지 않아 색 추가/4세트 등 순수 창작 변형이 필요 → "원작 왜곡 없음" 목표와 충돌. 또한 턴제 특성상 7~8인은 자기 차례까지 대기가 6분 이상(턴 60초 기준)이라 파티게임 체감도 나쁘다. 6인 캡이 규칙 충실도·템포 양쪽의 균형점.
- 2인 하한: 원작이 2인 공식 지원.
- registry 등록값: `minPlayers: 2, maxPlayers: 6`.

## 14. 데모(봇) 모드 (D12)

플랫폼 관례(유휴 시 자동/수동 데모)에 맞춰 가상 봇 2~4명이 플레이하는 데모 지원. 루미큐브는 상태가 복잡하므로 **봇 지능의 범위를 명시적으로 한정**함:

### 구현 (휴리스틱 v1)

1. **손패 내 세트 탐색**: 손패에서 만들 수 있는 그룹/런 후보를 그리디 열거(숫자별 색 모으기 + 색별 연속 구간 스캔, 조커는 가장 점수 높은 후보의 빈칸에 투입). 초기 착수 전이면 후보 조합 합계 ≥ `initialMeldThreshold`일 때만 착수, 미달이면 드로우.
2. **기존 세트에 1장 붙이기**: 초기 착수 후, 손패 각 타일에 대해 "어느 런의 끝에 연결 가능한가 / 어느 3장 그룹의 4번째 색인가"를 검사해 가능하면 냄. (붙이기는 기존 세트를 깨지 않으므로 검증 실패 위험이 사실상 0.)
3. **낼 게 없으면 드로우**. 생각하는 연출: 턴마다 2~4초 랜덤 딜레이 + 타일을 한 장씩 옮기는 애니메이션(op를 시간차로 나눠 적용해 사람처럼 보이게).

### 미구현 (명시적 스킵)

- 보드 전면 해체·재조합(재배치 탐색은 조합 폭발 — 제대로 하려면 백트래킹/정수계획 솔버가 필요하며 데모 목적 대비 과투자).
- 조커 회수.
- 이로 인해 봇 게임은 사람 게임보다 교착이 다소 잦을 수 있으나, §8.2 교착 룰로 자연 종료되므로 문제 없음. 데모 화면에는 "DEMO" 워터마크(플랫폼 관례).

봇 로직은 `shared/RummikubEngine.js`의 검증 함수를 그대로 재사용해 규칙 구현 중복을 만들지 말 것.

## 15. 엣지 케이스 체크리스트 (QA 겸용)

- [ ] 초기 착수: 기준점(기본 30점) 정확히 충족 시 통과, 1점 미달 시 실패(30/20/10 세 기준점 모두 경계값 테스트).
- [ ] 로비에서 기준점 10점 또는 20점 선택 후 게임 시작 → `gameStarted.initialMeldThreshold` 값이 실제로 반영되고, 모바일 UI 배지("이번 착수 합계 N/{기준점}점")와 검증 로직이 30이 아닌 그 값을 기준으로 동작.
- [ ] 초기 착수 턴에 보드 기존 세트로 드래그 시도 → 드롭 불가 + op 즉시 거부.
- [ ] `[파12, 파13, J]` 배치 후 커밋 → J=14 해석 불가로 실패·롤백.
- [ ] 런 wrap-around `[13, 1, 2]` 커밋 실패.
- [ ] 그룹 5장 / 같은 색 중복 그룹 커밋 실패.
- [ ] 남의 세트 완전 해체 후 전부 유효하게 재조합 → 커밋 성공.
- [ ] 재조합하다 2장짜리 조각 남긴 채 커밋 → 실패·롤백·강제 드로우, 손패·보드가 스냅샷과 동일하게 복원.
- [ ] 조커 회수 후 재사용 없이 커밋 → 실패. 회수+새 세트에 사용 → 성공.
- [ ] 조커 2장 + 실물 1장 세트 → 성공. 실물 0장 → 실패.
- [ ] 색 미확정 그룹(3장)의 조커를 두 후보 색 중 어느 쪽 타일로도 회수 가능.
- [ ] 더미 0장에서 패스 → 드로우 없이 턴 종료. 이후 전원 1바퀴 무변경 → 교착 종료·점수 정산 검증.
- [ ] 마지막 타일 커밋과 동시에 전체 검증 통과 → Rummikub 종료, 점수 합계 = 0 검산.
- [ ] 턴 타임아웃 순간에 endTurn 도착(레이스) → 호스트는 먼저 처리된 쪽만 유효, 나머지 무시.
- [ ] 현재 턴 플레이어 이탈 → 유예 후 롤백+드로우 취급으로 턴 강제 종료, §8.3 처리.
- [ ] 재접속 → `stateSync`로 보드/손패/턴 정보 복원, 손패 로컬 정렬 순서 복원.
- [ ] 5인 시작 → 160장 모드 확인(조커 4장, 사본 `c` 타일 존재).
- [ ] 대량 롤백(세트 여러 개를 재조합하다 실패) 시 여러 타일의 되돌림 애니메이션이 동시/순차로 겹쳐도, 애니메이션 종료 후 모든 타일이 정확히 스냅샷 좌표에 위치하는지(연출이 상태 정합성을 깨지 않는지, §11.4).
- [ ] `prefers-reduced-motion` 환경에서 stagger 없는 즉시 처리 폴백이 실제로 적용되는지.

## 16. 구현 순서 제안 (마일스톤)

1. **M1 — 엔진**: `RummikubEngine.js` (타일 생성, 세트 검증, 조커 해석, 30점 계산, 점수) + 단위 테스트(§15 케이스를 테스트로 선작성 권장).
2. **M2 — 호스트 상태 머신**: 분배/턴 루프/스냅샷·커밋·롤백/타이머/종료·교착, §12 프로토콜 송수신. 이 시점에 봇(§14)을 먼저 붙이면 모바일 없이 전체 루프 검증 가능(데모 모드가 공짜로 나옴).
3. **M3 — 호스트 렌더**: 보드/패널/연출.
4. **M4 — 모바일**: 손패 트레이·정렬 → 드래그/탭-탭 조작 → 조커 회수 플로우 → 버튼·검증 결과 표시.
5. **M5 — 통합 QA**: §15 체크리스트, 다인원 실기기 테스트, registry/vite 등록, `docs/games/rummikub.md` 요약 문서(도블 문서 포맷) 작성.
