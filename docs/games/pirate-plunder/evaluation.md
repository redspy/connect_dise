## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`pirate-plunder`의 코어 루프는 매우 이해하기 쉽다. 모든 플레이어는 같은 TV를 보며 파트너와 협상하고, 각자 스마트폰에서는 비밀리에 `나누기(Split)` 또는 `훔치기(Steal)`를 선택한다. 둘 다 나누면 50/50, 한쪽만 훔치면 100/0, 둘 다 훔치면 0/0이라는 구조는 설명이 짧고 결과가 즉시 납득된다. 여기에 홀수 인원일 때 `망보기(Lookout)`를 둬 20 금화를 지급하는 규칙을 더해, 플랫폼 특성상 자주 생길 수 있는 홀수 매칭 문제를 자연스럽게 처리한다.

이 게임의 재미는 단순히 "배신 버튼을 누른다"에서 나오지 않는다. 실제로는 다음 세 층위가 겹치면서 파티 게임다운 긴장감이 만들어진다.

| 평가 축 | 판단 | 코멘트 |
| --- | --- | --- |
| 즉시 이해도 | 높음 | 죄수의 딜레마를 해적 테마로 단순화해 30초 내 설명이 가능하다. |
| 공용 화면 적합성 | 높음 | 파트너 매칭, 협상 상태, 결과 공개를 TV가 책임져 "같은 화면을 보며 심리전을 한다"는 목적에 잘 맞는다. |
| 사회적 상호작용 | 높음 | 선택 자체보다 협상, 표정 읽기, 말투 해석에서 재미가 발생한다. |
| 짧은 의사결정 루프 | 높음 | `setup → negotiation → reveal` 흐름이 명확해 한 라운드 감정선이 빠르게 완결된다. |
| 리플레이성 | 중상 | 매 라운드 파트너와 망보기 배치가 달라져 대화 양상이 바뀐다. 다만 보상 구조가 고정이라 장기 반복 시 패턴화 위험이 있다. |
| 관전자 재미 | 중상 | TV 결과 연출은 충분히 읽기 쉽지만, 라운드마다 기억점이 강하게 남는 시청각 피크는 아직 약하다. |

현재 버전이 잘하는 지점은 "서로 얼굴을 보고 속이거나 믿게 만드는 구조"다. 모바일은 사적인 결정 장치이고, TV는 모두가 동시에 바라보는 협상 무대이기 때문에 플랫폼 컨셉과의 궁합이 좋다. `Split/Steal` 구조상 매 라운드마다 짧은 토론과 추론이 발생하고, 누가 방금 배신했는지를 TV가 즉시 공개하므로 같은 공간에서의 반응이 커진다.

특히 홀수 인원 대응으로 넣은 `Lookout`은 기획적으로 의미가 있다. 단순히 한 명을 쉬게 하지 않고, "이번 라운드는 밖에서 지켜보며 안정적으로 20 금화를 얻는 사람"이라는 서사를 붙여 탈락감보다는 역할감으로 포장했다. 이 덕분에 3인 플레이에서도 게임이 성립하고, 5인 이상에서는 "누가 이번에 쉬운 돈을 가져가느냐"라는 작은 감정선도 추가된다.

다만 현재 상태는 "짧게 체험하면 재밌는 게임"에 가깝고, "계속 붙잡는 흥행형 콘텐츠"로 가려면 다음 약점이 보인다.

| 관찰 포인트 | 현재 상태 | 영향 |
| --- | --- | --- |
| 보상 메타 고정 | 모든 라운드가 `100 금화`, 망보기 `20 금화`로 고정 | 몇 판 반복하면 수학적으로 안전한 선택 논리가 고착될 수 있다. |
| 망보기 체감 | 수동 대기 후 정액 보상 | 홀수 인원 플레이에서 일부 사용자는 참여감이 떨어질 수 있다. |
| 감정 피크 연출 | 결과는 보이지만 라운드별 인상적인 사운드/모션 피크는 약함 | 첫 판 기억점과 관전자 반응성이 조금 아쉽다. |
| 길이 조절성 | 현재는 5라운드 고정 | 캐주얼 현장에서는 "짧게 한 판" 옵션이 없으면 진입이 무거워질 수 있다. |

종합하면, 코어 플레이 자체는 강하다. "배신"이라는 감정 자극이 매우 직관적이고, 개인 모바일의 비밀성과 공용 TV의 공개성이 자연스럽게 결합되어 있다. 다만 대중적 흥행까지 보려면, 지금의 명료한 뼈대 위에 `연출 밀도`, `초심자 친화성`, `망보기 참여감`을 더 얹어야 한다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

구조적으로는 프로젝트 권장 패턴을 비교적 잘 따르고 있다. 호스트는 `HostBaseGame`을 상속해 `lobby`, `setup`, `negotiation`, `reveal`, `result` 페이즈를 분리했고, 모바일은 `MobileBaseGame`을 상속해 `setup-profile`, `waiting`, `role-reveal`, `negotiation`, `reveal` 화면을 분리했다. 즉, 상태 머신의 골격은 명확하다.

호스트의 상태 분리도 읽기 쉽다.

| 상태 변수 | 역할 | 평가 |
| --- | --- | --- |
| `_profiles` | 닉네임/아바타 보관 | 로비, 재접속, 결과 렌더링에 일관되게 활용된다. |
| `scores` | 누적 금화 | 라운드 누적과 최종 리더보드 계산이 단순하다. |
| `lookoutHistory` | 망보기 로테이션 추적 | 홀수 인원 밸런스 제어에 유효하다. |
| `currentPairs` | 현재 라운드 짝 정보 | 협상/정산의 중심 축이 분명하다. |
| `decisions` | 개별 선택 저장 | 동시 선택 구조를 단순하게 유지한다. |
| `lastPayouts` | 직전 라운드 결과 | 모바일 재연결 복구와 결과 화면 렌더링에 도움이 된다. |

구현 완성도 측면의 강점은 다음과 같다.

#### 장점

##### 1. 페이즈 기반 흐름이 선명하다

호스트는 `_startRound()`, `_startNegotiation()`, `_resolveResult()`, `_endGame()`으로 라운드 루프를 분리했고, 모바일도 `roundStart`, `phaseChange`, `revealResult`, `rejoinState`, `lobbyState`를 기준으로 화면을 전환한다. 읽는 사람 입장에서 "언제 무엇이 일어나는지"가 비교적 분명하다.

##### 2. 재접속 복구를 실제 서비스 관점에서 챙겼다

이 게임은 `onPlayerRejoin()`에서 로비와 인게임을 나눠 복구한다. 로비에서는 `lobbyState`, 인게임에서는 `rejoinState`를 보내고, 모바일은 이를 받아 역할/파트너/제출 여부/결과 화면까지 복구한다. 단순 프로토타입에서 자주 빠지는 부분인데, 이 게임은 그 부분이 이미 들어가 있다.

##### 3. AFK 방어가 있다

협상 30초 내 미제출 시 자동으로 `split` 처리하는 가드는 실전 운영에 유용하다. 이 한 줄 덕분에 게임이 한 명의 무응답 플레이어 때문에 멈추지 않는다.

##### 4. 데모 모드가 기본 탑재돼 있다

로비에서 `🤖 데모 플레이 실행` 버튼을 누르면 즉시 보드가 살아나는 구조는 현장 시연 측면에서 분명한 장점이다. 이 프로젝트의 필수 규칙을 충실히 따른 사례다.

반면 "코드 품질"과 "상용 완성도" 기준으로 보면 개선이 필요한 지점도 분명하다.

#### 구조적 약점

##### 1. 중도 이탈 처리 기준이 너무 느슨하다

현재 호스트는 게임 도중 플레이어가 완전히 퇴장해도 `playerCount < 3`일 때만 세션을 리셋한다. 이 조건은 최소 인원만 본다. 예를 들어 4인 게임에서 1명이 나가 3명이 되거나, 6인 게임에서 1명이 나가 5명이 되면 게임은 계속 진행된다. 하지만 `currentPairs`와 `currentLookout`은 이미 라운드 시작 시점 기준으로 고정돼 있으므로, 퇴장한 플레이어가 포함된 짝 정보가 남아 제출 대기, 정산, 재접속 복구가 꼬일 수 있다.

즉, 현재 구현은 "최소 인원 유지 여부"는 보지만 "현재 라운드 구조의 무결성"은 충분히 보지 않는다. 이 부분은 아키텍처 완성도에서 가장 큰 리스크다.

##### 2. 닉네임 렌더링이 `innerHTML` 기반이라 안전성과 유지보수성이 낮다

호스트는 파트너 카드, 결과 카드, 리더보드 대부분을 `innerHTML` 문자열로 조립한다. 닉네임은 모바일 입력값에서 오므로, 악의적 마크업이 들어올 경우 DOM 오염 가능성이 있다. 현재 플랫폼이 폐쇄적 사용 시나리오를 주로 상정하더라도, 게임 컨텐츠 레이어에서 최소한의 escape 정책이 없는 것은 품질 상 약점이다.

##### 3. 모바일 조작 안내 문구와 실제 슬라이더 방향이 어긋난다

모바일 협상 화면의 기본 문구는 `위로 슬라이드하여 훔치기 잠금 해제`인데, 실제 구현은 가로 방향으로 오른쪽까지 끌어야 unlock 된다. `_resetSlider()`는 다시 `오른쪽으로 슬라이드하여 훔치기 잠금 해제`라는 문구로 바꾼다. 즉, 첫 진입 문구와 실제 제스처가 불일치한다. 이는 작은 문구 문제처럼 보이지만, 첫 판 UX에서는 매우 치명적이다.

##### 4. 결과 연출 CSS에 완성도 저하 요소가 있다

호스트 CSS의 `@keyframes breakChest` 마지막 키프레임은 `transform`과 `opacity` 선언이 한 줄에서 잘못 결합돼 있다. 이 때문에 "둘 다 훔쳐 상자가 깨지는" 시나리오의 파괴 연출이 의도대로 재생되지 않을 가능성이 높다. 바로 눈에 띄는 결함은 아니지만, 게임의 감정 피크가 가장 필요한 장면에서 연출 품질을 떨어뜨린다.

##### 5. `DemoSimulator.js`는 시연용으로는 유용하지만 검증 도구로는 얕다

현재 데모 시뮬레이터는 다음 특징을 가진다.

| 항목 | 현재 구현 | 한계 |
| --- | --- | --- |
| 봇 구성 | 3명 고정 | 4인/5인/6인 이상의 짝 구성과 홀짝 분기를 검증하지 못한다. |
| 라운드 수 | 2라운드 후 종료 | 실제 게임의 5라운드 루프를 대표하지 못한다. |
| 상태 반영 방식 | `players`, `_profiles`, `scores`, `decisions` 직접 수정 | 실제 SDK 이벤트/메시지 경로를 거치지 않아 회귀 검증력이 낮다. |
| 타이머 정리 | `setTimeout` 중심 큐 정리, 일부 `setInterval`은 개별 clear | 중단 타이밍에 따라 잔존 타이머가 남을 수 있다. |
| 예외 분기 커버 | `split/steal`, `split/split` 정도만 시연 | `steal/steal`, 타임아웃, 재접속, 플레이어 이탈 등 핵심 분기를 보여주지 못한다. |

#### 종합 평가

아키텍처 골격은 좋다. 상태 분리, 페이즈 전환, 재접속 복구, AFK 가드는 이미 들어가 있어 "플레이 가능한 내부 시연 빌드"로서의 완성도는 충분하다. 그러나 대중적 서비스 품질을 기준으로 보면 아직 다음 세 축이 부족하다.

1. 이탈/예외 상황까지 포함한 상태 무결성
2. 첫 판 조작 혼란이 없는 UX 정합성
3. 데모 시뮬레이터의 대표성과 회귀 검증력

정리하면, 현재 `pirate-plunder`는 "재미있는 프로토타입을 넘어선 안정형 알파" 수준이다. 다만 상용형 파티 콘텐츠로 올리려면 운영 리스크와 연출 디테일을 한 번 더 다듬어야 한다.

### 1.3 종합 판정

`pirate-plunder`는 플랫폼 적합성이 높고, 코어 루프가 명료하며, 현장 반응을 끌어낼 잠재력이 충분한 게임이다. 특히 `TV에서 협상하고 폰에서 배신한다`는 문장 하나로 기억될 수 있는 점이 강하다.

반면 현재 버전은 "한 번 해보면 재밌다"는 수준에서 멈출 위험도 있다. 이유는 단순하다.

1. 결과 연출과 사운드가 아직 약해 라운드별 기억점이 크지 않다.
2. 망보기 역할이 안전하지만 수동적이라 일부 인원은 심리전의 중심에서 밀려난다.
3. 데모 모드가 실제 콘텐츠 품질을 충분히 대표하지 못한다.

따라서 이 게임의 다음 목표는 룰 변경보다도, `체험 밀도`와 `운영 안정성`을 높이는 것이다.

## 2. [대중성 강화 요소]

아래 3가지는 현재 코드 구조 위에서 비교적 자연스럽게 붙일 수 있으면서, 실제 체감 품질을 크게 끌어올릴 가능성이 높은 항목들이다.

### 2.1 제안 1: 라운드 감정선을 살리는 마이크로 애니메이션 + 사운드 패키지

현재도 화면 구성은 나쁘지 않지만, 각 라운드의 감정 피크가 시청각적으로 강하게 찍히지는 않는다. 특히 이 게임은 `배신 성공`, `상호 파멸`, `공동 분배`가 모두 다른 감정을 주는 만큼, 결과별 연출 차등이 중요하다.

권장안:

| 적용 지점 | 구체 제안 | 기대 효과 |
| --- | --- | --- |
| `setup` | 파트너 매칭 카드가 한 장씩 뒤집히며 등장, 망보기 카드에는 망원경/등대 효과 추가 | 첫 인상 강화, 관전자 몰입 상승 |
| `negotiation` | 마지막 5초 타이머 점멸, 상자 흔들림, 북소리형 효과음 | 선택 직전 긴장감 강화 |
| `reveal` | `split/split`, `split/steal`, `steal/steal`별로 색/모션/사운드 차등화 | 결과 기억점 강화 |
| 모바일 | `split` 탭, 슬라이더 unlock, `steal` 확정, 결과 공개에 각기 다른 짧은 햅틱/오디오 큐 추가 | 조작 손맛 상승 |
| `result` | 1등 행 등장 시 금화 샤워, 왕관 스케일업, 점수 카운트업 | 최종 만족감 상승 |

우선순위는 `reveal` 연출 강화가 가장 높다. 이 게임은 한 라운드의 결말이 곧 밈 포인트이기 때문이다. "둘 다 훔쳤다"가 터질 때 TV가 더 크게 반응해야, 같은 공간에 있는 사람들이 함께 웃는다.

### 2.2 제안 2: 초심자 기준의 규칙/조작 UX 정합성 개선

이 게임은 룰이 단순해 보이지만, 실제 첫 판 이탈 포인트는 룰 그 자체보다 `조작 오해`에서 생길 가능성이 높다. 현재 가장 대표적인 사례가 훔치기 슬라이더 문구와 실제 제스처 방향의 불일치다.

권장안:

| 적용 지점 | 구체 제안 | 기대 효과 |
| --- | --- | --- |
| 모바일 첫 진입 | `3장 이내`의 초간단 룰 카드 또는 `15초 온보딩` 제공 | 사회자 설명 부담 감소 |
| 훔치기 슬라이더 | 문구/애니메이션/손잡이 이동 방향 완전 일치, 잠금 해제 후 버튼에 즉시 광택 피드백 | 첫 판 혼란 제거 |
| 제출 후 상태 | `내 선택은 이미 전달됨`, `상대 대기 중`, `남은 총 제출 인원`을 더 선명하게 표현 | 불안 감소 |
| 망보기 화면 | 단순 대기 대신 "이번 라운드 감시 중" 상태 배지와 결과 예측 힌트 표시 | 수동 대기 체감 완화 |
| 리셋/재시작 | `alert`에 의존한 차단 대신 커스텀 배너/토스트로 설명 | 몰입 유지 |

이 제안의 핵심은 "설명을 덜 해도 첫 판이 돌아가게 만든다"는 것이다. 파티 게임은 룰이 어려워서 망하는 경우보다, 조작이 헷갈려 첫 라운드 감정선이 끊겨서 망하는 경우가 더 많다.

### 2.3 제안 3: 망보기 역할의 참여감 강화와 짧은 리플레이 변주

현재 `Lookout`은 홀수 인원 처리용 구조로는 합리적이지만, 플레이 감정으로 보면 다소 수동적이다. 그냥 20 금화를 받는 역할은 공정성은 있으나 "내가 이번 라운드에 뭘 했다"는 손맛이 약하다.

권장안:

| 적용 지점 | 구체 제안 | 기대 효과 |
| --- | --- | --- |
| 망보기 역할 | 협상 시작 전에 `이번 짝이 서로 믿을까?`를 예측하는 1탭 선택 추가 | 대기 시간을 참여 시간으로 전환 |
| 보상 구조 | 예측 성공 시 추가 `+10`, 실패 시 기본 `+20` 유지 또는 `+15`로 조정 | 과도한 패널티 없이 참여감 확보 |
| 라운드 변주 | 기본 5라운드 외에 `3라운드 퀵 모드` 제공 | 캐주얼 체험 회전율 향상 |
| 후반 긴장 장치 | 마지막 라운드만 상자 가치 `120` 또는 `망보기 10`으로 변경하는 이벤트 라운드 옵션 | 반복 플레이 시 패턴 고착 완화 |

중요한 점은 룰을 무겁게 만들지 않는 것이다. 망보기에게 복잡한 방해 기능을 주면 오히려 본래 장점인 간결함이 깨진다. 가장 좋은 방향은 `예측`처럼 한 번 눌러 참여하되, 전체 룰 설명 길이를 거의 늘리지 않는 방식이다.

## 4. [테스트 결과 및 수정 방향]

### 4.1 현재 품질 판단

기존 `test-report.md` 기준으로는 빌드와 E2E 시나리오가 통과되어 기본 플레이 루프는 이미 성립한다. 다만 정적 분석 관점에서 보면 다음 항목은 여전히 회귀 테스트 대상으로 관리해야 한다.

1. 홀수/짝수 인원에 따른 짝 배정 및 망보기 로테이션
2. 협상 미제출 자동 `split` 처리
3. 로비 및 인게임 재접속 복구
4. 플레이어 중도 퇴장 시 세션 정합성
5. 데모 모드 시작/중단 후 잔존 타이머와 상태 초기화

즉, 현재 품질은 "행복 경로는 좋다"에 가깝고, "운영 중 예외 경로도 안전하다"까지는 아직 확인이 더 필요하다.

### 4.2 게임 전체 동작 검증 시나리오

아래 시나리오는 실제 QA와 회귀 확인에 모두 사용할 수 있는 기준안이다.

| ID | 검증 시나리오 | 절차 | 기대 결과 |
| --- | --- | --- | --- |
| T01 | 최소 인원 제한 | 플레이어 2명만 접속 후 시작 버튼 클릭 | 게임 시작이 차단되고 로비 안내 문구가 유지된다. |
| T02 | 기본 3인 루프 | 3명 접속, 프로필 입력, Ready, 게임 시작 | 1명은 망보기, 2명은 해적으로 배정되며 `setup → negotiation → reveal`이 정상 진행된다. |
| T03 | 짝수 인원 짝 배정 | 4명 또는 6명 접속 후 시작 | 망보기 없이 모든 인원이 2인 1조로 배정된다. |
| T04 | 망보기 로테이션 | 5라운드 진행하며 홀수 인원 유지 | 특정 플레이어가 연속으로 망보기만 되는 현상이 없고, `lookoutHistory`가 의도대로 순환한다. |
| T05 | 제출 완료 경로 | 모든 해적이 제한 시간 내 선택 제출 | 타이머가 즉시 중단되고 결과 정산으로 넘어간다. |
| T06 | AFK 자동 처리 | 한 명 이상이 30초 내 선택하지 않음 | 미제출자에게 자동 `split`이 적용되고 게임이 멈추지 않는다. |
| T07 | `split/split` 결과 | 양쪽 모두 `split` 제출 | 각자 `+50`, 호스트 결과 카드가 공동 분배 연출로 표시된다. |
| T08 | `split/steal` 결과 | 한쪽 `split`, 한쪽 `steal` | 배신자 `+100`, 상대 `+0`, 모바일 결과 설명과 진동이 올바르게 표시된다. |
| T09 | `steal/steal` 결과 | 양쪽 모두 `steal` | 둘 다 `+0`, 파괴 연출과 결과 텍스트가 맞게 노출된다. |
| T10 | 로비 재접속 | 닉네임 설정 후 모바일 새로고침 | 호스트가 `lobbyState`를 보내고 모바일이 프로필/대기 화면으로 복구된다. |
| T11 | 협상 중 재접속 | 협상 단계에서 모바일 새로고침 | 파트너 정보, 내 금화, 제출 여부가 복구되고 중복 제출이 발생하지 않는다. |
| T12 | 결과 단계 재접속 | `reveal` 단계에서 모바일 새로고침 | 직전 선택과 지급 금화 정보가 재구성되어 결과 화면으로 복구된다. |
| T13 | 중도 이탈 예외 | 4인 이상 게임 도중 1명 완전 퇴장 | 세션이 안전하게 리셋되거나 남은 인원 기준으로 라운드 구조가 재정렬되어, 유령 짝이 남지 않는다. |
| T14 | 리셋 경로 | 최종 결과 후 다시 하기 실행 | 호스트/모바일/타이머/점수/결정/망보기 이력이 모두 초기화된다. |
| T15 | 데모 시작 가드 | 실제 플레이어가 1명 이상 접속한 로비에서 데모 시작 시도 | 데모가 차단되고 기존 플레이를 침범하지 않는다. |
| T16 | 데모 중단 정리 | 데모 진행 중 임의 시점에서 중단 | 모든 타이머와 봇 상태가 정리되고 로비가 정상 복원된다. |
| T17 | 라이브 플레이어 혼입 | 데모 진행 중 실제 모바일 접속 시도 | 접속 차단 또는 대기 안내가 명확해야 하며, 데모 상태가 오염되지 않아야 한다. |
| T18 | 연속 세션 반복 | 게임 종료 후 3회 이상 연속 재시작 | 점수, 프로필 참조, 망보기 이력, 제출 상태가 세션 간 누수되지 않는다. |

### 4.3 `DemoSimulator.js`의 현재 한계

현재 데모 시뮬레이터는 "현장 attract mode"로는 기능하지만, "게임 전체의 대표 시뮬레이터"라고 보기에는 범위가 좁다.

| 개선 포인트 | 현재 상태 | 문제점 |
| --- | --- | --- |
| 시나리오 폭 | 3봇, 2라운드, 거의 정상 진행 중심 | 실제 5라운드 게임과 예외 분기를 대표하지 못한다. |
| 상태 주입 방식 | 내부 `players`, `_profiles`, `scores`, `decisions` 직접 수정 | 실전 메시지 경로와 달라 회귀 검증력이 낮다. |
| 타이머 관리 | `setTimeout` 큐는 있으나 `setInterval` 정리가 분산돼 있음 | 중단/리셋 타이밍에 따라 잔존 interval이 남을 수 있다. |
| 결과 커버리지 | `split/steal`, `split/split` 위주 | `steal/steal`, 시간 초과, 이탈, 재접속은 검증하지 못한다. |
| 실사용자 공존성 | 데모 시작 전 플레이어 수만 검사 | 데모 도중 실제 사용자가 들어오면 상태 오염 여지가 있다. |
| 리셋 경로 | `stop()`이 `game.onReset()`을 직접 호출 | 실제 SDK 세션 리셋 흐름과 분리되어 있다. |

### 4.4 `DemoSimulator.js` 개선 가이드라인

아래 방향으로 정리하면 데모가 단순 시연 도구를 넘어 "운영 검증에 도움 되는 보조 엔진"으로 올라갈 수 있다.

#### 1. `Attract Demo`와 `QA Demo`를 분리한다

지금은 하나의 스크립트가 "보여주기"와 "검증하기"를 동시에 맡고 있다. 이 둘은 목적이 다르다.

- `Attract Demo`:
  - 로비에서 빠르게 시선을 끄는 목적
  - 결과 연출, 금화 증가, 배신 장면을 짧게 보여주면 된다
- `QA Demo`:
  - 결정적 시나리오 재현 목적
  - 타임아웃, `steal/steal`, 홀수/짝수 인원, 재시작, 중단 복구를 일정하게 돌릴 수 있어야 한다

같은 파일 한 개로 두 목적을 다 해결하려고 하면 시나리오가 계속 뒤섞인다. 문서와 코드 모두에서 역할을 먼저 분리하는 편이 좋다.

#### 2. 타이머 등록/해제를 공통 스케줄러로 통일한다

현재는 일부 `setTimeout`만 `_timerQueue`에 넣고, `setupInterval`, `timerInterval`은 각 함수 안에서만 관리한다. 가장 안전한 방향은 `registerTimeout(fn, ms)`와 `registerInterval(fn, ms)` 같은 래퍼를 두고, `stop()`에서 전부 같은 루틴으로 해제하는 것이다.

권장 원칙:

1. 모든 타이머 핸들은 한 컬렉션에 등록한다.
2. `stop()`, `onReset()`, 데모 완료 시점 모두 같은 정리 함수를 사용한다.
3. `setup`, `negotiation`, `reveal`, `end` 전환마다 이전 타이머가 남아 있지 않음을 보장한다.

#### 3. 게임 로직 복제보다 공용 라운드 컨트롤러 호출을 우선한다

현재 데모는 실제 게임 루프를 재사용하기보다, 자체 `_simulateRoundStart()`, `_simulateNegotiation()`, `_simulateResolveResult()`에서 유사 로직을 별도로 구현한다. 이 방식은 시간이 갈수록 실게임과 데모가 드리프트하기 쉽다.

더 나은 방향은 다음 둘 중 하나다.

1. 데모가 실제 호스트 메서드 `_startRound()`, `_startNegotiation()`, `_resolveResult()`를 최대한 재사용하고, 입력만 봇으로 주입한다.
2. 아니면 라운드 제어 로직을 별도 컨트롤러로 추출해, 실게임과 데모가 같은 상태 전환 함수를 쓰게 만든다.

핵심은 "데모도 같은 엔진 위에서 움직여야 한다"는 점이다.

#### 4. 봇 시나리오를 최소 4종으로 늘린다

현재 데모는 한두 가지 결말만 보여준다. 아래 네 가지는 최소 커버리지로 권장된다.

| 시나리오 | 목적 |
| --- | --- |
| `split/split` | 우호적 협상 결과 연출 검증 |
| `split/steal` | 배신 연출과 모바일 결과 피드백 검증 |
| `steal/steal` | 상자 파괴 연출, 0점 처리, CSS/사운드 검증 |
| `timeout -> auto split` | AFK 가드와 타이머 정리 검증 |

여기에 3인, 4인, 5인 구성까지 섞어야 진짜 대표성이 생긴다.

#### 5. 데모 중 실제 사용자 유입 정책을 명확히 한다

지금은 데모 시작 전에만 `playerCount > 0`을 검사한다. 하지만 데모 도중 실제 사용자가 입장하는 경우도 고려해야 한다.

권장안:

- 데모 활성 중에는 QR 접속을 아예 비활성 배너로 명확히 잠그기
- 또는 실제 사용자가 입장하면 데모를 즉시 종료하고 로비로 복귀하기
- 최소한 "데모 재생 중에는 실제 접속을 받지 않음"이라는 정책을 코드와 UI 양쪽에 명시하기

#### 6. 데모 상단에 현재 시나리오와 페이즈를 표시한다

현장 데모와 내부 QA 모두에서 "지금 무슨 장면을 보여주는지"가 바로 보여야 한다. 배너에 아래 정도는 표시하는 편이 좋다.

- 현재 페이즈: `LOBBY`, `SETUP`, `NEGOTIATION`, `REVEAL`, `RESULT`
- 현재 시나리오: `배신 예시`, `상호 파멸`, `AFK 자동 처리`
- 남은 라운드 또는 현재 봇 수

이 정보가 있으면 영상 캡처나 회귀 확인도 훨씬 쉬워진다.

### 4.5 우선 수정 방향 요약

가장 먼저 보강해야 할 항목은 아래 순서가 적절하다.

1. 모바일 슬라이더 문구/제스처/피드백 정합성 수정
2. 게임 도중 플레이어 완전 퇴장 시 라운드 구조 무결성 보강
3. `DemoSimulator.js` 타이머 정리 통합과 시나리오 확장
4. 결과 공개 중심의 시청각 연출 강화
5. 망보기 예측 1탭과 3라운드 퀵 모드 검토

최종적으로 `pirate-plunder`는 룰을 크게 바꾸지 않아도 훨씬 좋아질 수 있다. 지금 필요한 것은 새 아이디어를 무한히 추가하는 것이 아니라, 이미 좋은 코어 루프를 `더 명확하게 느끼게 하고`, `예외 상황에서도 안전하게 돌게 만드는` 정교화 작업이다.
