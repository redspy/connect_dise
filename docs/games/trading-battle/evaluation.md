# 천하제일단타대회 평가 및 개선안

- 작성일: 2026-07-07
- 분석 대상: `games/trading-battle/host/`, `games/trading-battle/mobile/`, `games/trading-battle/host/TradingDemoSimulator.js`
- 참고 문서: `docs/games/trading-battle/trading_battle_game_design.md`, `docs/games/trading-battle/trading_battle_wireframes.md`
- 분석 방식: 소스 코드 정적 분석 기반 평가. 실제 다기기 E2E 플레이, 브라우저 시각 검증, 오디오 체감 QA는 이번 문서 범위에 포함하지 않았다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`천하제일단타대회`의 현재 구현은 "정교한 금융 시뮬레이터"보다는 **공용 차트를 함께 보며 짧은 주기로 상승/하락에 베팅하는 멀티플레이 추세 예측 배틀**에 가깝다. 이 방향 자체는 나쁘지 않다. 오히려 `Host TV + N Mobile` 구조와 잘 맞는다. 모두가 같은 차트를 공유하고, 각자는 모바일에서 빠르게 포지션을 잡고, 결과는 공용 화면 순위 변동으로 확인하는 구조이기 때문이다.

핵심 재미는 아래 네 축에서 발생한다.

| 축 | 현재 구현에서의 작동 방식 | 평가 |
| --- | --- | --- |
| 공유된 정보, 분리된 입력 | 모두가 동일한 차트를 보고 각자 모바일에서 비밀리에 판단한다. | 플랫폼 적합성이 높다. |
| 짧은 의사결정 주기 | `3초` 간격 기본 캔들 공개로 판단과 결과가 자주 반복된다. | 리듬감이 좋다. |
| 레버리지 기반 드라마 | `롱/숏/2배 롱/2배 숏/현금` 전환이 순위 변동 폭을 크게 만든다. | 역전과 과감한 선택의 맛이 있다. |
| 공용 화면 경쟁 노출 | 호스트 화면에서 1위, 수익률, 플레이어 마커가 실시간으로 보인다. | 관전자 재미를 만들 수 있다. |

특히 호스트 차트 위에 플레이어 진입 마커가 찍히고, 하단 패널이 수익률 순으로 재정렬되는 구조는 "누가 지금 잘하고 있는가"를 빠르게 읽게 해 준다. 이 덕분에 플레이어는 자기 판단뿐 아니라 상대의 과감한 선택도 함께 의식하게 된다.

다만 현재 구현이 주는 재미는 기획서의 방향과는 다소 다르다.

- 기획서는 "실제 과거 주식 데이터를 기반으로 한 경쟁"을 전면에 내세우지만, 실제 코드는 `generateStockData()`로 생성한 랜덤형 OHLCV 데이터를 사용한다.
- 기획서는 RSI, MACD, Bollinger Band 등 다층 지표를 말하지만, 실제 구현은 이동평균선과 거래량 정도에 머문다.
- 기획서에는 "다음 캔들 공개 시 체결"이 적혀 있지만, 실제 코드는 현재 캔들 종가 기준 즉시 포지션을 바꾸고 다음 캔들까지 재주문만 잠근다.

그래서 현재 게임의 본질은 "진짜 차트 분석 대회"보다 **짧은 주기의 파티형 방향성 베팅 게임**으로 이해하는 편이 정확하다. 이건 단점만은 아니다. 오히려 대중성을 생각하면 진입 장벽이 낮아질 수 있다. 문제는 제목과 설명이 하드코어 금융 게임처럼 보이는데, 실제 플레이는 훨씬 캐주얼하다는 점이다. 이 간극이 첫 경험에서 혼란을 줄 수 있다.

현재 기준 재미 요소와 저해 요소를 함께 정리하면 아래와 같다.

| 구분 | 관찰 |
| --- | --- |
| 강점 | 같은 화면을 보며 동시에 판단하는 구조가 명확하고, 레버리지 선택이 즉각적인 드라마를 만든다. |
| 강점 | 플레이어 패널, 1위 배지, 차트 마커 덕분에 "누가 앞서는지"가 빠르게 읽힌다. |
| 강점 | 모바일 입력은 버튼 수가 적고 한 손 조작이 쉬워 행사장 운영에 유리하다. |
| 약점 | `롱/숏/레버리지` 용어가 익숙하지 않은 대중에게는 첫 판 이해 비용이 높다. |
| 약점 | 모바일의 `chart_analysis` 화면은 실제 분석 도구 없이 10초 카운트다운만 보여줘 체감 공백이 있다. |
| 약점 | 데이터가 랜덤 생성이라 잘 읽었다는 실력감보다 운과 모멘텀 추종의 인상이 강해질 수 있다. |

종합하면, 코어는 분명히 있다. 다만 그것을 "주식 차트 전략 게임"으로 포장할지, "같이 보는 방향성 심리 배틀"로 정리할지 기획 톤을 명확히 맞출 필요가 있다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

구조 자체는 비교적 건강하다. 호스트는 `TradingBattleGame`, 모바일은 `TradingMobile`에 게임별 책임을 모으고 있으며, 각각 `HostBaseGame`, `MobileBaseGame` 규약을 이용해 phase/screen 전환을 구현한다. 권한 있는 상태는 호스트가 들고, 모바일은 입력과 표시 역할에 집중하는 구조도 적절하다.

핵심 구조 평가는 다음과 같다.

| 평가 축 | 관찰 | 평가 |
| --- | --- | --- |
| 상태 권한 분리 | `_profiles`, `_positions`, `_pendingOrders`, 타이머, 랭킹 계산을 호스트가 단일 권한으로 관리한다. | 우수 |
| 플랫폼 SDK 활용 | `setPhase()`, `showScreen()`, `onPlayerRejoin()`, `onReset()` 등 베이스 클래스 흐름을 잘 활용한다. | 우수 |
| 메시지 프로토콜 | `setProfile`, `placeOrder`, `gameStarted`, `candleRevealed`, `rejoinState`, `gameFinished` 등 이벤트가 비교적 선명하다. | 양호 |
| 화면 역할 분리 | 호스트는 차트와 경쟁 상황, 모바일은 개인 포지션과 입력에 집중한다. | 우수 |
| 재접속 복구 | 로비와 트레이딩 중 복구는 어느 정도 되어 있다. | 부분 우수 |
| 데모/운영 도구 | 데모 파일이 존재하고 로비 버튼도 있다. | 존재는 긍정적이나 완성도는 낮음 |

반면 구현 완성도를 떨어뜨리는 핵심 갭은 분명하다.

#### 1. 기획 문서와 실제 구현 사이의 스펙 괴리가 크다

기획서와 와이어프레임에서 강조한 아래 요소들이 현재 UI/로직에는 충분히 반영되지 않았다.

- 설정 단계 UI
- 실제 과거 데이터 사용
- RSI, MACD, Bollinger Band
- 최대 4명 정책의 명시적 강제
- "다음 캔들 체결" 규칙

호스트 코드에는 설정 관련 상태와 이벤트 바인딩이 남아 있지만, 실제 `host/index.html`에는 해당 버튼과 토글 UI가 없다. 즉, 설정 시스템이 **설계 중간 단계에 머문 흔적**으로 보인다. 이런 상태는 유지보수자에게 "이미 지원되는 기능인지, 폐기된 기능인지"를 헷갈리게 만든다.

#### 2. 게임 규칙의 핵심 문구와 실제 체결 로직이 어긋난다

기획 문서는 주문이 "다음 캔들 공개 시점에 체결"된다고 설명하지만, 실제 호스트의 `_handleOrder()`는 현재 가격으로 즉시 포지션을 바꾸고, `_settleOrders()`는 다음 캔들에서 잠금만 해제한다. 모바일도 `orderAccepted` 수신 즉시 포지션을 바꾸고 `체결` 오버레이를 띄운다.

이 차이는 단순 문구 문제가 아니다.

- 초보자는 "지금 체결된 것인지, 다음 캔들에 반영되는 것인지"를 헷갈릴 수 있다.
- 실력감의 기준이 달라진다. 현재 구조는 추세 반응 속도 게임에 가깝고, 다음 캔들 체결 구조는 예측 게임에 더 가깝다.
- 튜토리얼과 데모 설명을 만들 때 규칙 서술이 계속 어긋난다.

즉, 이 게임은 **규칙 자체보다 규칙 표현의 정합성**부터 먼저 정리해야 한다.

#### 3. 재연결과 리셋 복구는 "대체로 가능"하지만 끝단 품질은 불안하다

좋은 점은 있다.

- 호스트가 `rejoinState`를 보내고, 모바일이 이를 받아 트레이딩 화면으로 복구한다.
- 닉네임과 아바타는 로컬 저장소를 이용해 다시 제출할 수 있다.

하지만 끝단에서 빈틈이 보인다.

- `game_result` 단계 재접속 시 호스트는 랭킹을 별도로 다시 보내지 않는다. 모바일도 `phase === 'game_result'`일 때 결과를 직접 복원하지 않는다.
- 호스트의 `_priceHistory`는 리셋 시 초기화되지 않아 다음 판 가격 변동률 기준점이 누적될 여지가 있다.
- 모바일의 `chart_analysis` 카운트다운은 `setTimeout()` 재귀인데 추적 핸들이 없다. 리셋이나 비정상 종료 시 이전 타이머가 살아남을 가능성이 있다.
- 호스트의 10초 분석 대기와 카운트다운 역시 별도 추적 없이 예약된다.

즉, 평시 흐름은 동작하더라도 **세션 중단, 재접속, 반복 플레이**에서 운영 품질이 흔들릴 수 있다.

#### 4. 데모 시뮬레이터는 출발점은 있지만 Attract Mode 품질에는 도달하지 못했다

`TradingDemoSimulator.js`가 별도 파일로 존재하는 것은 장점이다. 하지만 현재 구조는 "행사장 운영용 데모"보다 "개발자가 빠르게 한 판 흉내 내는 스크립트"에 가깝다.

핵심 문제는 다음과 같다.

- 파일명이 프로젝트 규약형 `DemoSimulator.js`가 아니라 `TradingDemoSimulator.js`다.
- 호스트는 `onPhaseChange()`에서 `this._isDemo`를 검사하지만, 이 값은 설정되지 않아 실제 데모 AI 루프가 연결되지 않는다.
- 데모 봇이 `players`, `sdk._players`, `_profiles`, `_positions` 같은 내부 맵을 직접 수정한다.
- 봇 행동 주기가 `3000ms` 하드코딩이라 설정값과 동기화되지 않는다.
- 진행 중 상시 배너와 `데모 중단` 버튼이 없다.

즉, 버튼은 있지만 **완결된 생명주기를 가진 데모 모드**라고 보기는 어렵다.

#### 5. 게임 내부 자산과 상태 책임이 일부 느슨하다

세부적으로는 다음 같은 결합도도 보인다.

- 아바타 이미지를 `trading-battle` 전용 assets가 아니라 `nunchi-ten` 경로에서 참조한다.
- 모바일은 `_otherPlayers` 목록을 계속 수신하지만 실제 UI 소비는 거의 없다.
- 호스트 CSS는 `.hidden` 공통 클래스를 광범위하게 재사용하기보다 특정 요소별 `.hidden` 규칙에 의존한다.

치명적인 문제는 아니지만, 장기적으로는 "게임 단위 독립성"과 "컴포넌트 재사용성"을 떨어뜨리는 방향이다.

### 1.3 종합 평가

| 항목 | 평가 | 코멘트 |
| --- | --- | --- |
| 코어 플레이 잠재력 | 높음 | 차트를 함께 보고 짧게 베팅하는 리듬은 분명히 재미가 있다. |
| 플랫폼 적합성 | 매우 높음 | 공용 화면과 개인 모바일의 역할 분리가 자연스럽다. |
| 대중성 즉시성 | 중 | 금융 용어와 설명 톤이 첫 판 장벽을 만든다. |
| 구현 안정성 | 중상 | 정상 루프는 잘 보이지만, 반복 플레이와 예외 흐름의 마감이 약하다. |
| 문서-구현 정합성 | 보완 필요 | 기획서와 현재 로직의 간극이 꽤 크다. |
| 운영 친화성 | 중 | 데모 버튼은 있으나 운영형 attract mode로는 미완이다. |

한 줄로 정리하면 이 게임은 **코어는 살아 있으나, 규칙 표현과 운영 완성도가 아직 코어의 매력을 충분히 밀어 올리지 못하는 상태**다.

## 2. [대중성 강화 요소]

### 제안 1. 체결 순간의 손맛을 키우는 "주문 타격감 패키지"

현재 모바일은 주문 버튼 자체는 크고 명확하지만, 누르는 순간의 감정 보상이 약하다. `orderAccepted`가 와도 화면상 변화는 포지션 텍스트, 체결 오버레이, 잠금 상태 정도에 머문다. 대중성 강화를 위해서는 "내가 방금 과감한 선택을 했다"는 감각이 더 크게 와야 한다.

구체 제안:

- 모바일 `orderAccepted` 시 짧은 햅틱(`light` 또는 `medium`)과 버튼 축소/복귀 애니메이션 추가
- 주문 종류별 체결 컬러 차별화: `롱 = 초록`, `숏 = 붉은색`, `2배 = 금색 보조광`
- 호스트 차트 마커가 찍힐 때 짧은 플래시와 사운드 큐 추가
- 1위 변경 시 상단 `top-player` 배지가 순간 확대되며 "선두 교체"를 보여주는 마이크로 연출 추가

이 개선은 기존 메시지 구조만으로도 붙일 수 있다. `orderAccepted`, `playerOrderPending`, `candleRevealed` 이벤트가 이미 존재하므로 로직을 크게 흔들지 않고 체감 품질을 높이기 좋다.

기대 효과:

- 모바일 조작 만족도 상승
- 첫 판에서도 "버튼 누르는 재미"가 즉시 전달
- 관전자도 누가 과감하게 진입했는지 더 빨리 인지

### 제안 2. 초보자 친화 온보딩과 용어 간소화

이 게임의 가장 큰 대중성 장벽은 규칙의 복잡성보다 **용어의 인상**이다. `롱`, `숏`, `레버리지`, `현금 전환`은 금융에 익숙하지 않은 사람에게 위압적으로 보일 수 있다. 첫 경험은 더 단순하게 정리하는 편이 좋다.

구체 제안:

- 버튼 라벨을 이중 표기로 구성: `상승 베팅 (롱)`, `하락 베팅 (숏)`, `정리 (현금)`
- 모바일 `chart_analysis` 화면을 단순 카운트다운에서 "이번 게임은 오를지/내릴지 맞히는 배틀" 식의 30초 튜토리얼 카드로 변경
- 호스트 로비 설명을 텍스트 나열보다 "1. 차트 본다 2. 상승/하락 누른다 3. 자산 높은 사람이 승리" 구조로 압축
- 첫 판용 `퀵 모드`를 두어 3분 또는 90초 버전을 노출

이 개선은 게임 로직을 바꾸지 않는다. 대신 **규칙을 대중이 받아들이는 언어를 바꾸는 일**이다. 흥행성 측면에서는 오히려 ROI가 높다.

기대 효과:

- 비금융권 사용자 진입 장벽 완화
- 행사장 첫 판 이탈률 감소
- "차트를 읽어야만 하는 어려운 게임"이라는 인상을 줄임

### 제안 3. 관전자 드라마를 키우는 "라이벌리 스펙터클 패키지"

이 게임은 TV 앞에서 구경하는 재미가 커질수록 가치가 올라간다. 현재도 순위와 마커는 있지만, 더 넓은 대중을 끌어들이려면 "누가 누구를 역전했는지", "누가 지금 가장 위험한 선택을 했는지"가 더 극적으로 보여야 한다.

구체 제안:

- 호스트 하단 패널에 `연승`, `고위험 2배`, `방금 청산` 같은 짧은 상태 태그 추가
- 선두 교체, 최하위의 급반등, 2배 포지션 진입 같은 장면에 짧은 배너 콜아웃 추가
- 게임 종료 직전 마지막 30초에는 상단 타이머를 붉게 바꾸고 "라스트 스퍼트" 연출 적용
- 최종 결과 화면에 단순 순위 외에 `최고 리스크`, `가장 안정적`, `최대 낙폭 후 회복` 같은 보조 타이틀 제공

이 패키지는 게임 룰을 복잡하게 만들지 않으면서도 관람 가치를 높인다. 특히 행사장, 방송형 콘텐츠, 사내 이벤트 환경에서 회전율과 주목도를 끌어올리기 좋다.

기대 효과:

- 플레이어 외 주변 관전자도 스코어보드에 감정 이입
- "보는 맛"이 커져 재도전과 구경 유입이 증가
- 결과 화면이 단순 정산이 아니라 회고 장면으로 바뀜

`천하제일단타대회`의 코어를 유지한 채, 대중성 강화 요소 3가지의 적용 우선순위와 실제 반영 타당성을 검토한다. 동시에 현재 코드베이스가 이를 안전하게 수용할 수 있는지도 함께 판단한다.

### 3.3 쟁점 토론

#### 쟁점 A. 더 많은 지표와 실제 시장 데이터를 먼저 넣어야 하는가

회의 다수는 "지금은 아니다"라고 판단했다. 이유는 명확하다.

- 현재 게임의 강점은 정밀한 금융 분석보다 **짧은 리듬과 공개 경쟁**에 있다.
- 지표와 데이터 현실성을 먼저 늘리면 초보자 장벽이 더 높아질 수 있다.
- 대중성 강화 과제는 규칙 심화보다 "보이는 재미"와 "즉시 이해" 쪽이 더 급하다.

결론: 실제 데이터/보조지표 확대는 장기 과제로 두되, 이번 우선순위에서는 제외한다.

#### 쟁점 B. 가장 먼저 넣어야 할 대중성 요소는 무엇인가

전문가 대부분이 `주문 타격감 패키지`를 최우선으로 봤다. 이 게임은 결국 플레이어가 모바일에서 결단을 내리는 순간과, 공용 화면에서 순위가 출렁이는 순간이 핵심이다. 이 두 장면의 감정 곡선을 먼저 키우는 것이 가장 빠른 효과를 낸다는 의견이 모였다.

#### 쟁점 C. 초보자 친화화가 코어의 매력을 약하게 만들 위험은 없는가

논의 결과, 룰을 단순화하자는 것이 아니라 **표현을 단순화하자**는 방향으로 정리됐다.

- 내부 로직은 유지
- 외부 용어와 튜토리얼은 더 쉽게
- 금융 느낌은 유지하되 첫 판은 "오를까/내릴까" 수준으로 이해시키기

즉, 전문성을 줄이기보다 진입 언어를 바꾸는 방향이 타당하다고 결론났다.

### 3.5 회의 결론

회의의 결론은 다음 한 문장으로 정리된다.

> `천하제일단타대회`는 더 어려워질 필요가 아니라, 더 잘 읽히고 더 크게 느껴질 필요가 있다.

실행 순서는 아래가 적절하다.

1. 규칙 문구와 체결 로직 정합성부터 맞춘다.
2. 주문 타격감과 선두 교체 연출을 보강한다.
3. 초보자용 온보딩과 쉬운 언어를 넣는다.
4. 그 위에서 관전자 드라마와 결과 회고 연출을 확대한다.
5. 데모 시뮬레이터를 운영형 attract mode로 올린다.

### 4.4 우선 수정 방향

#### P0. 안정성과 정합성을 먼저 맞추는 수정

1. 체결 규칙을 문서와 맞추거나, 현재 즉시 체결 규칙을 기준으로 UI/설명문을 전면 수정
2. `game_result` 재접속 시 랭킹을 다시 전송하고 모바일이 직접 결과 화면을 복원하도록 보강
3. `onReset()`에서 `_priceHistory`, 카운트다운 `setTimeout()`, `requestAnimationFrame()` 등 모든 일시 상태를 확실히 회수
4. 데모 모드의 phase 연동 버그와 stop UI 부재를 해결
5. 설정 UI를 실제로 제공할지, 미사용 코드로 정리할지 결정

#### P1. 대중성과 운영성을 끌어올리는 수정

1. 용어 간소화와 첫 판 튜토리얼 보강
2. 3분 또는 90초 퀵 모드 추가 검토
3. 선두 교체, 2배 진입, 마지막 30초 연출 등 관전자 드라마 강화
4. 최대 4명 정책 강제 및 로비 카피 정리

#### P2. 장기 차별화 과제

1. 랜덤 생성 데이터 대신 큐레이션된 실데이터 리플레이 도입
2. RSI/MACD/Bollinger Band 추가 여부 재검토
3. 게임별 전용 assets로 의존성 분리

### 4.5 🤖 데모 시뮬레이터(`DemoSimulator.js`)의 개선점 및 수정 가이드라인

현재 구현 파일은 `games/trading-battle/host/TradingDemoSimulator.js`다. 기능상 최소한의 출발점은 맞지만, 프로젝트가 요구하는 **운영형 Attract Mode + 핵심 루프 검증 도구** 수준으로 보려면 아래 방향으로 재설계하는 편이 적절하다.

#### 1. 파일 진입점과 상태 소유권을 표준화

- 권장안: `games/trading-battle/host/DemoSimulator.js`를 표준 진입점으로 두고, 기존 구현을 옮기거나 브리지 export를 둔다.
- 데모 상태는 `TradingBattleGame`의 불분명한 `_isDemo`가 아니라 `DemoSimulator`의 명시적 상태 머신으로 소유한다.

권장 상태:

- `idle`
- `booting`
- `running`
- `finishing`
- `cleanup`

현재는 `TradingBattleGame.onPhaseChange()`가 `_isDemo`를 보고 simulator 훅을 호출하도록 되어 있으나, 이 플래그가 실제로 세팅되지 않아 데모 AI가 돌지 않는다. 이 문제부터 우선 수정해야 한다.

#### 2. 모든 예약 작업을 DemoSimulator가 직접 추적

현재 데모는 `demoInterval`, `demoTimeouts`만 일부 추적한다. 그러나 실제 게임 진입 타이밍, 분석 대기, 카운트다운, 자동 재시작은 호스트 본체의 `setTimeout()` 체인에도 영향을 받는다. 데모를 안정적으로 중단하려면 예약 작업의 소유권이 명확해야 한다.

수정 가이드:

- `scheduleTimeout(fn, delay)`와 `scheduleInterval(fn, delay)` 헬퍼를 두고 등록/해제 일원화
- `stopDemo()`에서 등록된 타이머, 인터벌, RAF, DOM 오버레이를 모두 정리
- 데모용 봇 행동은 `candleInterval`과 동기화하고, `3000ms` 하드코딩 제거

#### 3. 내부 구현 세부사항 직접 접근을 줄이기

현재 구현은 아래 내부 구조를 직접 만진다.

- `game.players`
- `game.sdk._players`
- `game._profiles`
- `game._positions`
- `game.sdk._messageHandlers`

빠르게 만들기에는 편하지만, 유지보수성과 안전성은 낮다. 권장 방향은 다음과 같다.

- 호스트에 `addDemoBot(profile)`, `removeDemoBots()`, `simulatePlayerMessage(playerId, type, payload)` 같은 공개 메서드 제공
- DemoSimulator는 공개 메서드만 호출
- SDK 내부 맵과 핸들러 레지스트리를 직접 건드리지 않음

이렇게 해야 SDK 내부 구현 변경이 생겨도 데모가 함께 깨지는 일을 줄일 수 있다.

#### 4. "랜덤 자동 플레이"보다 "보여주기 좋은 시나리오형 데모"로 바꾸기

현재 봇 로직은 확률적으로 포지션을 바꾸는 구조라, 시연 품질이 운에 좌우된다. 운영형 데모는 게임의 핵심 장면을 안정적으로 보여줘야 한다.

권장 시퀀스 예시:

1. 봇 3명 순차 입장
2. 1초 간격으로 준비 완료
3. 분석 화면 10초
4. 첫 3캔들은 서로 다른 포지션을 고르게 배치
5. 중반부 한 번은 2배 포지션 역전 장면을 의도적으로 발생
6. 마지막 30초에는 1위 경쟁이 붙는 방향으로 주문 스크립트 조정
7. 종료 후 결과 5초 노출, 자동 로비 복귀

이렇게 해야 데모가 QA 도구이면서도 행사장 attract mode 역할을 동시에 할 수 있다.

#### 5. 진행 중 상시 배너와 즉시 중단 버튼 추가

현재는 QR을 블러 처리하는 오버레이만 있고, 운영자가 데모 상태를 명확히 제어할 수 있는 상시 UI가 없다. 요구사항에 맞게 아래 요소를 넣는 편이 맞다.

- 고정 배너: `🤖 데모 플레이 진행 중`
- 버튼: `데모 중단`
- 보조 문구: `실제 참가를 원하면 데모를 중단하세요`

추가 정책도 필요하다.

- 실제 플레이어가 입장하면 데모를 자동 중단할지
- 실제 플레이어가 있으면 데모 시작을 막을지
- 데모 중 접속 시 "다음 실제 게임에서 참여 가능" 안내를 띄울지

#### 6. 데모 시작 전 스냅샷, 종료 시 완전 복구

현재 `stopDemo()`는 내부 맵을 비우는 방향에 가깝다. 하지만 데모는 "항상 로비 원상복구"가 보장되어야 한다.

권장 복구 절차:

1. 시작 전 `players`, `_profiles`, `_positions`, `_pendingOrders`, `phase`, `_timeLeft` 스냅샷 저장
2. 데모 봇 및 오버레이 생성
3. 데모 종료 시 타이머/오버레이/봇 제거
4. 스냅샷 복원
5. 로비 UI와 QR 상태 재렌더

핵심은 `데모 종료 후 남는 흔적이 없어야 한다`는 점이다.

#### 7. 데모 시뮬레이터 개선 우선순위

1. `_isDemo` 연동 버그 수정과 상태 머신 도입
2. `DemoSimulator.js` 표준 진입점 정리
3. 타이머/인터벌/오버레이 정리 권한 일원화
4. 내부 맵 직접 접근 제거
5. 스크립트형 봇 시나리오 도입
6. 상시 배너 및 수동 중단 UI 추가
7. 실제 플레이어 합류 정책까지 문서화

이 순서로 가야 데모 모드가 장식용 버튼이 아니라, **행사장 운영 도구이자 반복 검증 도구**로 승격될 수 있다.
