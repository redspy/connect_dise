# Give You Fire 평가 및 개선안

- 작성일: 2026-07-06
- 분석 대상: `games/give-you-fire/host/`, `games/give-you-fire/mobile/`, `games/give-you-fire/shared/`
- 참고 문서: `docs/games/give-you-fire.md`, `docs/archive/game-plans/give-you-fire-plan.md`, `docs/agents/roles.md`
- 분석 방식: 정적 코드 리뷰 + `npm run build` 검증
- 검증 한계: 실제 다기기 플레이, 브라우저 시각 QA, P2P 로그 검증은 이번 문서 범위에 포함하지 않았다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`Give You Fire`의 코어 루프는 매우 명확하다. 각 플레이어는 개인 모바일에서 테트리스를 생존형으로 플레이하고, 공용 호스트 화면은 모든 플레이어의 미니 보드와 속도 레벨을 동시에 보여준다. 여기서 핵심 재미를 만드는 규칙은 하나다.

> 내가 라인을 지우면 내 점수가 직접 오르는 대신, 다른 플레이어들의 속도가 올라간다.

이 규칙 덕분에 혼자 퍼즐을 푸는 감각이 곧바로 파티형 대전 감각으로 바뀐다. 플레이어는 자기 보드만 보면서도 다른 사람의 패배를 유발할 수 있고, 호스트 화면을 보는 사람은 누가 누구를 압박하는지 실시간으로 읽을 수 있다. 플랫폼의 목표인 "공용 화면을 통해 서로 시선을 교환하며 즐기는 보드게임적 효과"와도 잘 맞는다.

재미 요소를 세분화하면 다음과 같다.

| 항목 | 현재 구현의 강점 |
| --- | --- |
| 진입 장벽 | 테트리스라는 익숙한 규칙을 사용해 설명 비용이 낮다. |
| 사회적 긴장감 | 라인 클리어가 곧 상대 가속 공격이므로, 개인 퍼즐이 즉시 경쟁 이벤트가 된다. |
| 관전성 | 호스트가 모든 미니 보드와 레벨 막대를 동시에 보여줘 "누가 위험한지"가 빠르게 읽힌다. |
| 난이도 구조 | 자동 레벨 상승 + 상대 공격 누적으로 후반부 긴장감이 살아난다. |
| 모드 확장성 | 1인 플레이와 1~4인 멀티가 모두 성립해 콘텐츠 소비 폭이 넓다. |

특히 호스트 쪽 대시보드 구조는 좋은 출발점이다. 카드 단위로 닉네임, 색상, 레벨, 보드, 생존 상태를 묶어 보여 주기 때문에 행사장이나 거실 TV 환경에서 이해가 쉽다. 모바일도 풀스크린 제스처 조작으로 물리 버튼 UI 없이 몰입감을 유지한다.

다만 "재미의 구조"와 "재미가 보이는 방식"은 아직 차이가 있다. 규칙 자체는 재미있지만, 대중적으로 더 강하게 먹히려면 다음 부족분이 있다.

- 공격 성공의 쾌감이 시각적으로 약하다.
- 첫 판 학습이 제스처 경험에 의존한다.
- 솔로 클리어와 탈락의 순간 연출이 짧고 결과 화면에 바로 덮인다.
- 호스트 미니보드가 체감상 완전 실시간으로 따라오지 않아 관전성이 잠재력보다 약하다.

정리하면 `Give You Fire`는 **코어 루프는 강하고, 패키징과 운영 완성도가 아직 그 잠재력을 다 끌어내지 못한 게임**이다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

전반적인 구조는 플랫폼 철학과 잘 맞는다. `TetrisEngine`과 `BoardRenderer`를 `shared/`로 분리했고, 호스트는 `HostBaseGame`, 모바일은 `MobileBaseGame`을 상속한다. 게임 로직과 플랫폼 인프라의 경계도 비교적 분명하다.

#### 잘된 점

1. `shared/TetrisEngine.js`
   - DOM 비의존 순수 로직으로 분리되어 있어 재사용성과 테스트 가능성이 높다.
   - 7-bag 랜덤, 고스트 피스, 단순 wall kick, 스냅샷 렌더링용 API까지 기본기가 좋다.

2. `shared/BoardRenderer.js`
   - 호스트 미니보드와 모바일 메인 보드가 같은 렌더러를 공유해 시각 언어가 일관된다.
   - 고스트 피스, 탈락 오버레이, next-piece 렌더링까지 한 모듈에 정리되어 있다.

3. `host/TetrisGame.js`
   - 로비, 플레이, 결과의 페이즈 전환이 깔끔하다.
   - 플레이어별 카드 렌더링 구조가 직관적이라 공용 화면 역할에 충실하다.
   - `setProfile`, `boardUpdate`, `linesCleared`, `gameOver`, `soloClear` 등 메시지 흐름이 단순하고 이해하기 쉽다.

4. `mobile/TetrisMobile.js`
   - 탭 회전, 수평 드래그, 소프트 드롭, 하드 드롭을 하나의 제스처 체계 안에서 풀었다.
   - 방향 잠금(`gestureMode`)으로 입력 충돌을 줄인 점이 좋다.
   - `next-piece` 표시 토글, 진동 피드백, 세로 모드 가드 등 모바일 UX 기본기는 갖춰져 있다.

#### 구조적 약점 및 완성도 리스크

아래 항목들은 단순한 아이디어 수준이 아니라, 현재 코드상 실제로 보이는 리스크다.

##### A. 관전용 보드 동기화가 "실시간"에 못 미친다

모바일은 `boardUpdate`를 100ms 스로틀로 보내는 것처럼 주석이 적혀 있지만, 실제 전송은 `dropTick()`에서 아래로 한 칸 이동했을 때와 `lock` 직후에만 일어난다. 즉 다음 입력은 즉시 호스트에 반영되지 않는다.

- 수평 드래그 이동
- 회전
- 소프트 드롭 중간 프레임

이 세 가지는 호스트 미니보드에 즉시 반영되지 않는다. 따라서 호스트 대시보드는 "플레이어 상태의 대략적 요약"으로는 괜찮지만, 엄밀한 실시간 관전 화면으로는 부족하다. 이 게임이 파티형 콘텐츠라는 점을 생각하면, 이는 UX 품질보다 한 단계 위의 핵심 상품성 이슈다.

##### B. 재접속 복구가 부분 상태만 복원한다

호스트의 `onPlayerRejoin()`은 `showNextPiece`, `level`, `lines`만 보내고, 모바일은 새 `TetrisEngine`을 만든 뒤 피스를 다시 스폰한다. 이 방식은 아래 상태를 복원하지 못한다.

- 기존 보드 스택
- 현재 낙하 중인 피스
- 다음 피스
- bag 랜덤 상태
- 현재 위치와 회전 상태

즉, 현재의 재접속은 "게임 복구"가 아니라 "비슷한 숫자를 가진 새 판 시작"에 가깝다. 형식적으로는 `rejoinState`가 존재하지만, 실제 공정성 기준으로는 미완성이다.

##### C. 탈락자 재접속 처리 의미가 어긋난다

호스트는 게임이 아직 끝나지 않았더라도 `alive === false`인 재접속자에게 `gameFinished`를 내려 보낸다. 그 결과 탈락자는 남은 생존자 경기가 계속되는 동안에도 최종 결과 화면으로 들어갈 수 있다. 이때 순위도 아직 확정되지 않은 플레이어가 `rank ?? 1`로 처리될 여지가 있어 의미가 흔들린다.

보다 자연스러운 흐름은 다음 중 하나다.

- `eliminatedState`를 따로 보내 탈락 화면으로 복귀시킨다.
- 관전 전용 대기 화면으로 복귀시킨다.
- 결과 화면은 실제 경기 종료 후에만 보낸다.

##### D. `playerEliminated` 프로토콜이 정의만 있고 실사용이 약하다

호스트는 `playerEliminated`를 브로드캐스트하지만, 모바일 쪽에는 이를 처리하는 핸들러가 없다. 결과적으로 제거 이벤트는 프로토콜상 존재하지만, 실제로는 플레이 중 다른 플레이어들의 탈락 상황을 모바일 UX에서 소비하지 않는다.

이 메시지는 다음 용도로 확장 가치가 높다.

- 탈락자에게 "남은 인원 수" 표시
- 생존자에게 "누가 떨어졌는지" 짧은 토스트 표시
- 결과 직전 긴장감 연출

현재는 설계는 있는데 연출 소비가 비어 있는 상태다.

##### E. `solo-clear`와 `eliminated` 화면이 연출 화면으로 거의 기능하지 못한다

모바일은 `_onSoloClear()`에서 `solo-clear` 화면을 띄우고, `_onGameOver()`에서 `eliminated` 화면을 띄운다. 그러나 호스트는 곧바로 `gameFinished`를 브로드캐스트하고 모바일은 즉시 결과 화면으로 넘어간다. 네트워크 왕복이 짧으면 전용 화면이 사실상 플래시 수준으로만 보일 수 있다.

즉, 화면은 존재하지만 연출 체류 시간 설계가 없다. 완성도 관점에서는 "구현은 되었으나 사용 경험은 덜 마무리된 상태"다.

##### F. 데모 시뮬레이터가 운영 도구 수준에 도달하지 못했다

`host/FireDemoSimulator.js`는 다음 문제를 가진다.

- 파일명이 프로젝트 규약형 `DemoSimulator.js`와 다르다.
- `this.game._isDemo`를 세우지 않아 `onPhaseChange()`와 연결이 끊겨 있다.
- `sdk._players`, `sdk._messageHandlers`, `game._players` 등 private 필드를 직접 만진다.
- 실행 버튼은 있지만 수동 중단 버튼과 명시적 데모 상태 UI가 없다.
- 시작 시 기존 세션 상태 스냅샷을 보관하지 않아 원상 복구 보장이 약하다.

특히 가장 치명적인 점은 `startDemo()`가 게임을 시작해도 `TetrisGame.onPhaseChange()`는 `this._isDemo`를 기준으로 동작한다는 점이다. 즉 현재 구조만 보면 봇 자동 플레이 루프가 의도대로 이어지지 않을 가능성이 높다.

##### G. 운영성 측면의 소소하지만 실제적인 품질 부채가 있다

- `window.addEventListener('resize', ...)`가 게임 시작 때마다 누적된다.
- 호스트 스타일은 `.hidden` 규약은 지키지만, 호스트 오버레이에 명시적 `z-index` 방어가 없어 공용 `host-board` 배경 레이어 규약과 완전히 맞지는 않는다.
- 호스트가 인게임 중 `playerLeave`를 받을 때 `_aliveCount`와 순위 정리를 즉시 갱신하지 않아 운영 정책이 불분명하다.

#### 종합 평가

| 평가 축 | 판정 | 코멘트 |
| --- | --- | --- |
| 코어 게임성 | 우수 | 규칙이 짧고 경쟁 구조가 즉시 이해된다. |
| 플랫폼 적합성 | 우수 | 모바일 개인 조작 + 호스트 관전 구도가 잘 맞는다. |
| 공용 로직 분리 | 우수 | 엔진과 렌더러 분리가 좋다. |
| 모바일 조작 설계 | 양호 | 제스처 체계는 좋지만 초심자 피드백이 부족하다. |
| 관전 완성도 | 보완 필요 | 보드 업데이트 빈도와 공격 연출이 약하다. |
| 재접속 안정성 | 미흡 | 부분 복구만 가능하다. |
| 데모 모드 | 미완성 | 규약 및 생명주기 설계 보강이 필요하다. |
| 운영 품질 | 보완 필요 | 중도 퇴장, 상태 복원, 결과 연출 체류 시간이 약하다. |

한 줄로 요약하면 다음과 같다.

> `Give You Fire`는 재미의 뼈대는 강하지만, 관전 동기화·재접속·데모 운영·첫 판 친화성까지 포함한 "상품화 완성도"는 아직 한 단계 더 올려야 한다.

## 2. [대중성 강화 요소]

아래 3가지는 단순 아이디어가 아니라, 현재 코드와 게임 구조를 기준으로 실제 흥행 체감을 가장 빠르게 끌어올릴 가능성이 높은 보완점이다.

### 제안 1. 공격/피격 연출 패키지 강화

현재 공격 결과는 본질적으로 재미있지만, 보이는 방식이 약하다. 라인을 지웠을 때 "불을 줬다"는 감각이 레벨 숫자와 막대 너비 증가에 너무 의존한다.

구체적 제안:

- 호스트 카드에 `FIRE!`, `DOUBLE FIRE`, `TETRIS FIRE` 배지 추가
- 공격 성공 플레이어 카드 외곽에 300~500ms 불꽃 플래시 적용
- 피격 플레이어 카드에 짧은 흔들림과 화염 펄스 오버레이 적용
- 모바일 `levelUp` 수신 시 화면 가장자리 불꽃 프레임 + 차등 진동 패턴 제공
- 2줄 이상 클리어에는 짧은 사운드 큐를 붙여 시청각 피드백 강화

기대 효과:

- 호스트 앞에 모인 사람이 공격 관계를 즉시 이해할 수 있다.
- "내가 라인을 지웠다"가 아니라 "내가 상대를 압박했다"는 감정이 선명해진다.
- 행사/로비 시연에서 구경꾼이 상황을 더 빨리 읽는다.

### 제안 2. 초심자 친화형 조작 피드백과 보조 모드 추가

제스처 기반 조작은 이 게임의 개성이다. 다만 대중성은 "좋은 입력 설계"만으로 오르지 않고, 첫 판에서 실패 이유를 몸으로 이해시키느냐에 달려 있다.

구체적 제안:

- 현재 3초 고정 힌트를 "애니메이션 예시 힌트"로 강화
- 회전 성공/실패를 진동 패턴 또는 짧은 색상 변화로 구분
- 좌우 이동 성공 시 셀 스냅 이펙트와 약한 햅틱 부여
- 초보자 옵션으로 `회전 버튼만 보이기` 또는 `하드 드롭 버튼만 보이기` 제공
- 첫 게임 기본값은 `next-piece ON`으로 고정하고 숙련자 설정에서만 OFF 허용

기대 효과:

- 가족층, 아동층, 테트리스 비숙련자도 첫 판에서 덜 당황한다.
- 현재 제스처 UX의 장점을 유지하면서 이탈률을 줄일 수 있다.
- 규칙을 늘리지 않고도 체감 난이도를 낮출 수 있다.

### 제안 3. 퀵 스타트 규칙과 결과 리벤지 루프 보강

현재 100레벨 목표 구조는 클래식하게는 타당하지만, 파티 게임 운영에서는 첫 판이 다소 길게 느껴질 수 있다. 짧은 회전감이 대중성에 유리하다.

구체적 제안:

- `Quick Fire` 모드 추가
  - 시작 레벨 5
  - `next-piece ON`
  - 목표 레벨 40 또는 제한 시간 기반 승부
- `Classic Fire` 모드는 현재 규칙 유지
- 게임 시작 전 3초 카운트다운 추가
- 결과 화면에 1위 하이라이트, "즉시 리벤지" 문구, 다시하기 CTA 강화
- 탈락자 화면에 남은 인원 수와 현재 1위 플레이어를 표시해 이탈을 줄임

기대 효과:

- 행사장, 매장 시연, 친구 모임에서 한 판 회전이 빨라진다.
- 첫 플레이의 몰입 진입이 쉬워진다.
- 결과에서 재도전 버튼으로 자연스럽게 이어진다.

### 3.3 쟁점별 토론

#### 쟁점 1. 가장 먼저 손댈 대중성 강화 요소는 무엇인가

회의는 거의 만장일치로 안건 A를 1순위로 봤다. 이유는 간단하다. 지금도 규칙은 재미있지만, 호스트 앞에 모인 사람이 그 재미를 3초 안에 읽기 어렵기 때문이다. 공격/피격 연출만 강화해도 "왜 이 게임이 시끄럽고 재밌는지"를 바로 이해시킬 수 있다.

#### 쟁점 2. 제스처 조작을 유지할 것인가

완전한 버튼 회귀는 기각되었다. 현재 게임의 개성은 보드 전체를 쓰는 직관적 제스처에 있고, 버튼을 과하게 넣으면 화면이 다시 복잡해진다. 다만 초심자용 보조 옵션은 필요하다는 데 의견이 모였다. 결론은 다음과 같다.

- 기본 철학: 제스처 유지
- 보완책: 애니메이션 힌트 + 실패 피드백 + 선택형 보조 버튼

#### 쟁점 3. 100레벨 구조를 유지할 것인가

`Classic Fire`는 유지하되, 대중적 추천 기본값은 더 짧은 `Quick Fire`로 가는 쪽이 합리적이라는 결론이 나왔다. 파티 게임에서는 "한 판이 약간 짧다"가 "한 판이 약간 길다"보다 훨씬 안전하다.

### 3.4 최종 의사결정

| 안건 | 결정 | 우선순위 | 적용 조건 |
| --- | --- | --- | --- |
| 공격/피격 연출 패키지 | 채택 | P0 | 호스트 카드 플래시, 모바일 피격 오버레이, 사운드/진동 포함 |
| 초심자 친화형 조작 피드백 | 채택 | P0 | 제스처 유지, 보조 설명 및 피드백 강화 중심 |
| 퀵 스타트 규칙 도입 | 채택 | P1 | `Quick Fire` 추천 모드, `Classic Fire` 유지 |
| 전면 버튼형 조작 회귀 | 기각 | - | 현재 게임의 장점을 해칠 가능성이 큼 |
| 기반 리스크 무시 후 연출만 선적용 | 기각 | - | 재접속/데모/관전 동기화가 받쳐줘야 효과가 난다 |

### 3.5 회의 결론

가상 전문가 회의의 최종 결론은 다음과 같다.

> `Give You Fire`의 대중성 문제는 룰이 약해서가 아니라,  
> **공격이 덜 보이고, 첫 판이 덜 친절하며, 운영 안정성이 아직 상품 수준에 덜 도달했기 때문**이다.

따라서 다음 개발 사이클의 우선순위는 아래 순서가 적절하다.

1. 관전/재접속/데모의 기반 안정화
2. 공격/피격 연출 패키지 강화
3. 초심자 피드백 보강
4. `Quick Fire` 모드 추가

## 4. [테스트 결과 및 수정 방향]

### 4.1 현재 검증 결과 요약

이번 분석에서 실제 수행한 검증과 정적 판정은 다음과 같다.

| 항목 | 결과 | 비고 |
| --- | --- | --- |
| 소스 정적 리뷰 | 완료 | Host/Mobile/Shared 전 파일 구조 검토 |
| 프로덕션 빌드 | 통과 | `npm run build` 성공 |
| 다기기 수동 플레이 | 미실행 | 실제 호스트 1대 + 모바일 N대 환경 검증 필요 |
| 브라우저 시각 QA | 미실행 | `browser_subagent` 기반 UI 입증은 이번 요청 범위 밖 |
| P2P 직접 연결 로그 확인 | 미실행 | 콘솔 기반 확인 필요 |

즉, 현재 문서의 "테스트 결과"는 빌드 통과와 정적 코드 분석에 근거한다. 실제 체감 품질은 아래 시나리오로 추가 검증해야 한다.

### 4.2 전체적인 동작 검증 시나리오

#### A. 기본 게임 루프

1. 호스트 로비 진입 후 QR 및 세션 생성 확인
2. 모바일 1대 입장, 닉네임 입력, 준비 완료, 게임 시작
3. 솔로 플레이에서 레벨 상승, 보드 렌더링, 결과 전환 확인
4. 모바일 2~4대 입장 후 멀티 플레이에서 전원 준비, 시작, 탈락, 결과 확인

기대 결과:

- 로비, 플레이, 결과의 화면 전환이 정상이어야 한다.
- 닉네임, 색상, 준비 수치가 호스트와 모바일 양쪽에서 일관되어야 한다.

#### B. 공격 및 관전성

1. 플레이어 A가 1줄, 2줄, 4줄 클리어를 각각 수행
2. 플레이어 B/C가 `levelUp`을 수신하는지 확인
3. 호스트 미니보드가 이동/회전/소프트 드롭 중 얼마나 따라오는지 확인

기대 결과:

- 피격자의 레벨이 정확히 상승해야 한다.
- 공격 순간이 공용 화면에서 읽혀야 한다.
- 현재 구현 기준으로는 수평 이동/회전/소프트 드롭의 관전 반영이 늦을 수 있으므로, 이를 실제로 계측해 개선 전 기준선으로 삼아야 한다.

#### C. 재접속 및 이탈

1. 로비 대기 중 모바일 새로고침 후 복귀
2. 플레이 중 모바일 새로고침 후 복귀
3. 탈락 후 새로고침 후 복귀
4. 플레이 중 모바일 강제 종료 후 leave 처리

기대 결과:

- 로비 복귀는 매끄러워야 한다.
- 인게임 복귀는 기존 보드 상태가 그대로 살아 있어야 한다.
- 탈락자는 결과 화면이 아니라 관전/탈락 상태로 복귀해야 자연스럽다.
- leave 정책은 "즉시 패배" 또는 "유예 후 패배" 중 하나로 명확해야 한다.

#### D. 모바일 UX

1. 탭 회전, 좌우 드래그, 소프트 드롭, 하드 드롭 반복 수행
2. 세로/가로 전환 시 orientation guard 확인
3. 결과 화면, 솔로 클리어 화면, 탈락 화면의 체류 시간 확인

기대 결과:

- 제스처가 의도대로 일관되게 동작해야 한다.
- 현재 구현은 `solo-clear`와 `eliminated`가 결과 패킷에 빠르게 덮일 수 있으므로, 실제 체류 시간이 충분한지 확인해야 한다.

#### E. 데모 모드

1. 로비에서 데모 시작 버튼 클릭
2. 봇 입장, 자동 진행, 결과, 자동 복귀 확인
3. 데모 중 실제 유저 입장 시 정책 확인
4. 데모 중단 버튼 동작 확인

기대 결과:

- Attract Mode가 실제 운영 도구처럼 작동해야 한다.
- 시작, 진행, 종료, 중단, 원상 복구가 모두 명확해야 한다.
- 현재 구현은 생명주기와 공개 API 경계가 약하므로, 실패 시나리오까지 포함한 검증이 필요하다.

### 4.3 우선 수정 방향

#### P0. 기반 안정화

1. `rejoinState`를 전체 스냅샷 기반 복구로 재설계
   - `board`, `current`, `nextType`, `bag`, `level`, `lines`, `alive`, `phase`를 명시적으로 직렬화
   - `playingState`, `eliminatedState`, `resultState`, `lobbyState`를 분리

2. `boardUpdate` 전송 정책 개선
   - 회전, 좌우 이동, 소프트 드롭 중간 프레임까지 100ms 스로틀로 반영
   - 호스트 미니보드가 "실시간 관전 장치" 역할을 하도록 개선

3. 퇴장 정책 명문화
   - `playerLeave`를 즉시 패배로 볼지, reconnect grace 후 패배로 볼지 결정
   - `_aliveCount`, `rank`, 결과 계산, 브로드캐스트 메시지를 한 번에 정리

4. 결과 전용 연출 체류 시간 확보
   - `solo-clear`, `eliminated` 화면에 최소 체류 시간이나 짧은 전용 연출 시퀀스 도입

#### P1. 대중성 강화

1. 공격/피격 연출 패키지 추가
2. 초심자 힌트와 보조 입력 옵션 추가
3. `Quick Fire` 모드 도입

#### P2. 규약 및 문서 정합성

1. `FireDemoSimulator.js`를 `DemoSimulator.js` 규약에 맞추거나 표준 브리지 추가
2. 현재 구현된 제스처 조작 기준으로 `docs/games/give-you-fire.md` 업데이트
3. 시작 카운트다운, 결과 흐름, 데모 정책을 문서와 실제 구현에 일치시킴

### 4.4 🤖 데모 시뮬레이터(`DemoSimulator.js`)의 개선점 및 수정 가이드라인

현재 구현 파일은 `host/FireDemoSimulator.js`다. 기능 자체는 "가상 봇을 넣고 한 판 흉내 낸다" 수준까지는 도달했지만, 프로젝트가 요구하는 데모 시뮬레이터 표준에는 부족하다. 개선 방향은 아래와 같다.

#### 1. 파일명과 진입 규약 정리

- 권장안: `games/give-you-fire/host/DemoSimulator.js`로 표준화
- 대안: `DemoSimulator.js`를 만들고 내부에서 `FireDemoSimulator`를 export 하도록 브리지 구성

이유:

- 프로젝트 전반에서 데모 시뮬레이터를 공통 도구처럼 다룰 때 진입점이 통일되어야 한다.
- 문서와 코드, 운영 습관 사이의 마찰이 줄어든다.

#### 2. 데모 생명주기를 상태 머신으로 분리

권장 상태:

- `idle`
- `booting`
- `running`
- `finishing`
- `cleanup`

현재는 `isDemo` 불리언과 인터벌/타임아웃 목록만으로 관리한다. 이 구조는 중도 중단, 결과 연출 체류, 실제 유저 난입 처리, 로비 복귀를 안전하게 조율하기 어렵다.

#### 3. `game._isDemo`와 페이즈 훅을 실제로 연결

최소 요구사항:

- `startDemo()` 시작 시 `game._isDemo = true`
- `stopDemo()` 종료 시 `game._isDemo = false`
- `TetrisGame.onPhaseChange()`는 `_isDemo`와 시뮬레이터의 내부 상태를 일관된 기준으로 참조

현재 구조에서는 `startDemo()`는 돌아도 `onPhaseChange()`가 데모 러닝 루프를 이어 받지 못할 가능성이 높다. 이는 품질 이슈가 아니라 동작 성립 이슈다.

#### 4. private SDK 접근 제거

현재 직접 접근하는 내부 필드:

- `sdk._players`
- `sdk._messageHandlers`
- `game._players`

권장 구조:

- `TetrisGame.injectDemoPlayer()`
- `TetrisGame.removeDemoPlayers()`
- `TetrisGame.dispatchDemoMessage()`
- 또는 플랫폼 공용 데모 훅 제공

핵심은 데모가 SDK 내부 구현에 잠기지 않게 만드는 것이다.

#### 5. 랜덤 시뮬레이션보다 "보여주기 좋은 스크립트" 우선

운영용 데모는 난수가 아니라 연출 시나리오가 중요하다. 예시:

1. 0~4초: 봇 3명 입장, 닉네임 공개, 준비 완료
2. 4~10초: 카운트다운, 시작
3. 10~25초: 안정 플레이, 레벨 상승, 공격 1회
4. 25~40초: 2줄 이상 클리어 2~3회, 카드 플래시 연출 강조
5. 40~50초: 1명 탈락
6. 50~60초: 승자 확정, 결과 노출
7. 이후 자동 리셋 및 로비 복귀

이렇게 해야 데모가 QA 도구이면서 동시에 전시용 Attract Mode가 된다.

#### 6. 수동 중단 UI와 실제 유저 난입 정책 추가

필수 항목:

- 로비 또는 상단 헤더에 `데모 중단` 버튼
- 데모 중 배너 상시 표시
- 실제 유저 입장 시 정책 명확화
  - 정책 A: 즉시 데모 중단 후 로비 복귀
  - 정책 B: 데모 종료 전까지 신규 입장 차단

현재는 "진행 중" 문구는 있으나 운영자 제어 UI가 부족하다.

#### 7. 시작 전 상태 스냅샷과 종료 후 복원

데모 시작 전에 최소 아래 상태를 저장해야 한다.

- `players`
- `profiles`
- `playerData`
- `readyCount`
- `phase`
- QR 영역 blur/overlay 상태

종료 시에는 무조건 `clear()`가 아니라, 시작 전 상태로 복구해야 한다. 그래야 실제 운영 도중 데모 실행과 실유저 참여가 섞여도 상태가 덜 꼬인다.

#### 8. QA용 결정론 모드 분리

추천 모드:

- `scripted`: 행사/시연용
- `random`: 자유 데모용
- `rejoin-test`: 재접속 복구 검증용

이렇게 분리하면 데모가 단순 쇼케이스가 아니라 회귀 테스트 도구로도 쓸 수 있다.

### 4.5 최종 정리

`Give You Fire`는 이미 코어 재미가 살아 있는 게임이다. 따라서 다음 단계에서 필요한 것은 룰 재발명이 아니라, 아래 네 가지를 한 번에 밀어 올리는 일이다.

1. 관전 보드 동기화 정확도
2. 재접속과 퇴장 처리의 운영 안정성
3. 공격/피격이 보이는 연출 패키지
4. 데모 시뮬레이터의 표준화와 운영 도구화

최종 권고는 다음 한 문장으로 정리된다.

> **재접속·데모·관전 동기화의 기반을 먼저 고치고, 그 위에 공격 연출과 초심자 친화성을 얹는 것이 `Give You Fire`를 대중적으로 가장 빠르게 강하게 만드는 길이다.**
