## 1. 게임 평가

### 1.1 코어 플레이 방식 및 재미 요소 분석

`단어 폭탄`은 "한 명만 비밀 제시어를 보고, 같은 공간의 나머지 플레이어는 그 설명을 듣고 정답을 외친다"는 비대칭 구조를 사용한다. 이 구조는 공용 화면과 개인 모바일을 함께 쓰는 connect-dise 플랫폼과 궁합이 매우 좋다. 호스트 화면은 시간 압박과 관전자 몰입을 담당하고, 모바일은 오직 "내 차례인가 아닌가"와 "정답이 나왔을 때 즉시 넘길 수 있는가"만 담당한다.

현재 구현의 핵심 루프는 명확하다.

1. 호스트가 카테고리를 선택하고 로비를 연다.
2. 모바일 플레이어는 닉네임을 입력하고 준비 완료를 누른다.
3. 게임 시작 후 현재 차례 플레이어의 모바일에만 제시어가 보인다.
4. 방 안 사람들은 소리 내어 정답을 맞히고, 설명자는 `정답!` 버튼으로 턴을 넘긴다.
5. 무작위 타이머가 끝나는 순간 폭탄을 들고 있던 플레이어가 패배한다.

이 구조가 주는 재미는 다음과 같다.

- 학습 비용이 매우 낮다. 모바일 입력이 사실상 버튼 1개라서 처음 보는 사람도 즉시 참여할 수 있다.
- 웃음 포인트가 자연스럽다. 설명이 꼬이거나 엉뚱한 오답이 나오는 순간이 곧 콘텐츠가 된다.
- 비대칭 정보가 선명하다. 제시어는 설명자만 보고, 나머지는 공용 화면과 음성 커뮤니케이션에 집중한다.
- 시간 압박이 잘 작동한다. 호스트의 폭탄 캔버스, 째깍 비프음, 10초 이하 가속 구간은 파티 게임다운 긴장감을 만든다.

다만 장기 흥행 관점에서는 한계도 분명하다.

- 한 판이 "폭발 1회 = 종료" 구조라서 회차 누적 동기와 리턴 매치 동기가 약하다.
- 제시어 풀이 작고 재사용 방지 장치가 약해, 같은 세션에서 중복 체감이 빨리 올 수 있다.
- 설명자가 하는 조작이 사실상 `submitCorrect` 하나뿐이라 숙련도 차이가 표현될 여지가 크지 않다.

종합하면, 이 게임은 "처음 붙였을 때 바로 웃기는 힘"은 강하지만, "계속 붙들어 두는 메타 구조"는 아직 약한 상태다.

### 1.2 Host/Mobile 코드베이스 아키텍처 및 구현 완성도 평가

#### 강점

- 플랫폼 컨벤션 준수는 전반적으로 양호하다. 호스트는 `HostBaseGame` + `setPhase()`, 모바일은 `MobileBaseGame` + `showScreen()` 패턴을 그대로 따른다.
- 네트워크 모델이 가볍다. 게임 중 핵심 입력은 사실상 `submitCorrect` 하나이며, 실시간 센서 스트림이 없어 지연과 지터에 강하다.
- 연출 완성도가 생각보다 높다. 호스트는 Canvas 폭탄, Web Audio 비프/폭발음, CSS 흔들림 효과를 결합했고, 모바일은 대형 버튼, 햅틱, 적색 플래시로 역할을 명확히 나눈다.
- 데모 시뮬레이터와 Playwright E2E 스펙이 이미 존재해 "호스트 단독 데모 루프"를 검증할 기반이 있다.

#### 한계와 리스크

1. `games/word-bomb/host/main.js` 한 파일에 상태 관리, 오디오, Canvas 렌더링, 네트워크 메시지, 로비 UI가 모두 몰려 있다. 현재 스펙에는 충분하지만, 라운드제, 점수전, 모드별 규칙, 관전자 UI를 추가하려면 유지보수 난도가 빠르게 올라간다.
2. 재접속 복구는 "인게임 도중"만 부분적으로 구현되어 있다. 호스트의 `onPlayerRejoin()`은 `_gameActive`일 때만 `_syncTurnToMobiles()`를 호출하고, 모바일은 `onRejoin()`을 구현하지 않는다. 따라서 로비 또는 결과 화면에서 새로고침으로 복귀하면 원래 상태가 아니라 기본 `setup` 화면에 남을 가능성이 높다.
3. 로비 준비 상태 표현이 부정확하다. 호스트의 `_renderLobbyGrid()`는 모든 카드를 항상 `player-card ready`로 렌더링하므로, 실제 누가 준비를 눌렀는지 UI에서 구분되지 않는다.
4. 최소 인원 보장이 없다. 서버의 `SessionManager.setReady()`는 `readyCount >= totalCount && totalCount > 0`이면 `allReady`를 발생시키므로, 1명만 들어와 준비해도 게임이 시작될 수 있다. 레지스트리의 `minPlayers: 2`가 실제 런타임 규칙으로 연결되어 있지 않다.
5. 데모 시뮬레이터가 구현 규약을 우회한다. `DemoSimulator.startDemo()`는 `game.players`, `game.sdk._players`, `game._playerNicknames`를 직접 비우고 다시 채우며, 메시지 처리도 `sdk._messageHandlers`를 직접 호출한다. 이 구조는 SDK 내부 구현이 바뀌면 쉽게 깨지고, 실 플레이어가 연결된 로비에서 데모를 시작하면 호스트가 실제 플레이어 상태를 잃어버릴 수 있다.
6. 데모 종료 수명주기가 불완전하다. 자연 종료 후 `DemoSimulator.isDemo`가 명시적으로 `false`로 돌아가지 않아, 로비 복귀 후 자동 데모 재기동 조건과 상태 판정이 꼬일 여지가 있다.

#### 총평

이 게임의 구현 완성도는 "파티 현장에서 바로 써먹을 수 있는 데모 품질"로는 중상급이다. 반면 "실서비스 운영 안정성" 관점에서는 로비 복구, 최소 인원 가드, 준비 상태 시각화, 데모 격리 계층이 아직 부족하다. 즉, 재미의 코어는 이미 살아 있지만 운영용 마감은 덜 된 상태라고 평가하는 편이 정확하다.

## 2. 대중성 강화 요소

### 제안 1. 턴 넘김 마이크로 애니메이션 패키지 강화

현재는 턴이 바뀔 때 텍스트와 카드 강조가 바뀌는 수준이라, 관전자 입장에서 "지금 막 무슨 일이 일어났는가"가 아주 폭발적으로 느껴지진 않는다. 다음을 추가하면 전달력이 크게 올라간다.

- 호스트: 설명자 이름 카드가 좌우로 슬라이드하며 다음 플레이어로 스냅 전환
- 호스트: `정답!` 성공 시 카운터 숫자에 짧은 스케일 업과 파티클 링 연출
- 모바일: 현재 제시어 카드가 뒤집히며 사라지고, 다음 플레이어 폰에서 새 카드가 플립 인
- 모바일: 버튼 탭 성공 직후 120ms 정도의 짧은 색상 플래시와 진동 확인 피드백

이 개선은 룰을 바꾸지 않으면서도 "손에 잡히는 손맛"을 만들어 주는 가장 저비용 고효율 보강안이다.

### 제안 2. 사운드와 햅틱을 상태 중심으로 재구성

현재 호스트는 비프음과 폭발음이 있고 모바일은 단순 진동이 있다. 여기에 상태별 오디오 레이어를 얹으면 현장 반응이 훨씬 좋아진다.

- 턴 시작: 설명자에게만 짧은 "내 차례" 스팅어 + 중간 진동
- 정답 성공: 호스트에 짧은 성공음, 모바일에 가벼운 "딸깍" 계열 햅틱
- 5초 이하: 호스트는 고조되는 심장박동형 저역 펄스, 모바일은 짧은 더블 진동
- 폭발 결과: 패배자와 생존자 햅틱 패턴을 더 강하게 분리
- 옵션: 소리 끄기/낮추기 토글

`word-bomb`은 언어 중심 게임이라 시각보다 청각 신호가 특히 중요하다. 사람들은 화면을 계속 보지 않아도 소리만으로 현재 긴장도를 이해해야 한다.

### 제안 3. 패밀리 모드 중심의 콘텐츠 확장과 규칙 패키징

지금 구조는 첫 판 진입은 쉽지만 반복 플레이 이유가 약하다. 대중성을 키우려면 "누구와 하느냐"에 따라 덱과 규칙을 다르게 묶어줄 필요가 있다.

- 덱 확장: `키즈`, `패밀리`, `밈/인터넷`, `성인 파티` 식으로 단어팩 분리
- 난이도 태그: 쉬움/보통/어려움 표시
- 입문 규칙 카드: 모바일 대기 화면에 3줄 튜토리얼 고정
- 파티 모드: 3라운드 누적 패배 점수 또는 생존 점수
- 패밀리 모드: 현재의 단일 폭발 구조 유지, 대신 단어 풀과 시각 가이드를 더 친절하게 제공

핵심은 규칙을 복잡하게 만드는 것이 아니라, 사용자가 "우리 모임에 맞는 버전"을 즉시 고를 수 있게 패키징하는 것이다.

## 3. 가상 전문가 회의록 (Decision Making Meeting)

### 회의 안건

- 안건 A: 턴 넘김 마이크로 애니메이션 패키지
- 안건 B: 상태 중심 사운드/햅틱 강화
- 안건 C: 패밀리 모드 중심 콘텐츠 확장 및 규칙 패키징

### 발언 요약

**PMOrchestrator**

현재 `word-bomb`은 코어 재미가 이미 검증된 만큼, 이번 개선의 목표는 "처음 보는 손님이 10초 안에 끌리는가"와 "한 번 끝난 뒤 다시 하자고 말하게 만드는가" 두 가지로 잡아야 한다. 따라서 A와 B는 현장 반응 증폭용, C는 반복 플레이용 가치로 판단한다.

**GameScout**

이 장르는 짧은 쇼츠 클립으로도 퍼질 수 있는 유형이다. 그래서 A가 가장 중요하다. 지금도 구조는 재밌지만, 성공 패스 순간의 시각적 보상이 약해서 구경하는 사람의 감탄이 조금 덜하다. C도 중요하다. 특히 밈/인터넷 단어팩은 젊은 층 확장에 직접적이다.

**KidsBoardGameExpert**

A는 찬성하지만 과도한 이펙트는 아동에게 정보 과부하가 될 수 있으므로 0.2초 내외의 짧은 전환으로 제한해야 한다. C는 사실상 필수다. `키즈`와 `패밀리` 덱이 분리되지 않으면 읽기 난이도와 어휘 편차 때문에 어린 플레이어가 쉽게 위축될 수 있다.

**OnlineGameProducer**

B가 생각보다 중요하다. 파티룸에서는 모두가 항상 화면을 보지 않는다. 턴 시작, 정답 성공, 폭발 임박을 귀로도 알아야 군중 반응이 붙는다. C는 장기 잔존율을 위해 필요하지만, 점수전과 라운드제를 넣으려면 먼저 상태 관리 리팩터링이 선행돼야 한다.

**UIUXDesigner**

A는 즉시 반영 가능한 체감 개선안이다. 현재 모바일 버튼은 충분히 크지만 누른 뒤의 "확실한 성공감"이 약하다. 버튼 성공 플래시, 카드 뒤집힘, 호스트 이름 전광판 스냅 전환은 바로 효용이 있다. B도 찬성하되, 음량 토글이나 무음 대응은 꼭 들어가야 한다.

**TechAnalyst**

A와 B는 현재 구조에서도 비교적 안전하게 얹을 수 있다. 반면 C의 라운드 메타는 지금의 단일 파일 구조와 데모 시뮬레이터 방식으로는 관리가 거칠어진다. 특히 재접속 복구와 데모 봇 흐름까지 함께 고려하면 먼저 호스트 상태를 `lobby / round / result / attract` 수준으로 분리하는 게 맞다.

**SeniorGameDev**

실행 순서는 명확하다. A와 B는 지금 코드에 증분 적용 가능하다. C는 "단어팩 확장 + 입문 튜토리얼"은 바로 넣을 수 있지만, "3라운드 누적 점수"까지 가려면 `host/main.js`의 로직 분해와 `DemoSimulator.js` 재작성부터 해야 한다. 당장 대중성 체감만 노린다면 A, B를 선반영하고 C는 2단계로 쪼개는 게 현실적이다.

### 최종 의사결정

| 안건 | 결정 | 반영 우선순위 | 결정 사유 |
| --- | --- | --- | --- |
| A. 턴 넘김 마이크로 애니메이션 | 즉시 반영 | 1순위 | 룰 변경 없이 체감 재미와 관전자 가독성을 동시에 올릴 수 있음 |
| B. 상태 중심 사운드/햅틱 | 즉시 반영 | 1순위 | 파티 현장에서는 시각보다 청각 피드백의 효과가 큼 |
| C-1. 단어팩 확장 + 입문 규칙 패키지 | 단기 반영 | 2순위 | 대중성 확장 효과가 크고 구조 변경 비용이 비교적 낮음 |
| C-2. 라운드제/누적 점수전 | 구조 리팩터링 후 반영 | 3순위 | 현재 단일 파일 구조와 데모 시뮬레이터로는 운영 리스크가 큼 |

### 회의 결론

이번 평가 기준에서 가장 타당한 방향은 "코어 룰은 유지하고, 전달력과 반복 플레이 동기만 키운다"이다. 따라서 다음 스프린트에서는 A와 B를 먼저 구현하고, C는 단어팩/튜토리얼과 라운드 메타를 분리하여 단계적으로 반영하는 것이 최종 결정으로 정리된다.

## 4. 테스트 결과 및 수정 방향

### 4.1 현재 확인 가능한 테스트 자산 및 해석

현재 저장소에서 직접 확인되는 자동화 테스트는 `tests/word-bomb/demo.spec.js` 1건이다. 이 스펙은 다음을 검증한다.

이 평가는 테스트 파일과 소스 코드를 기준으로 한 정적 분석 결과이며, 이번 문서 작성 과정에서 브라우저 기반 실기동 테스트를 추가 실행한 것은 아니다.

- 호스트 페이지 로딩
- 카테고리 선택
- 데모 버튼으로 게임 시작
- 패스 수 증가
- 결과 화면 진입
- 대기실 복귀

즉, "호스트 단독 데모 루프"는 커버하지만 실제 운영에서 중요한 아래 항목은 자동화 범위 밖이다.

- 실제 모바일 다중 접속
- 준비 상태 시각화
- 재접속 복구
- 인게임 중 플레이어 이탈
- P2P 연결/폴백
- 실 플레이어가 존재하는 상태에서의 데모 기동

따라서 현재 테스트 상태는 "기본 연출 데모는 있음, 실서비스 안정성 검증은 부족함"으로 보는 것이 맞다.

### 4.3 수정 방향

우선순위는 다음 순서가 합리적이다.

1. 최소 인원 가드 추가
2. 로비 준비 상태 시각화 추가
3. 모바일 `onRejoin()` 및 호스트 로비/결과 상태 동기화 패킷 추가
4. 데모 시뮬레이터의 실세션 격리
5. 단어팩 확장 및 라운드 구조 분리

특히 1~4는 재미 개선 이전에 운영 안전성을 위해 먼저 처리해야 하는 항목이다.

### 4.4 `DemoSimulator.js` 개선점 및 수정 가이드라인

현재 `DemoSimulator.js`는 "데모가 돌아가 보이는가"에는 성공했지만, 실제 세션과 분리된 안전한 Attract Mode 설계로는 아직 부족하다. 다음 기준으로 재작성하는 것이 바람직하다.

#### 1. 실제 플레이어 상태를 파괴하지 말 것

현재 구현은 `game.players.clear()`, `game.sdk._players.clear()`, `game._playerNicknames.clear()`를 직접 호출한다. 이 방식은 실 플레이어가 접속 중일 때 호스트의 세션 인식 자체를 망가뜨릴 수 있다.

가이드라인:

- 데모 시작 전 실제 플레이어 스냅샷을 별도 객체로 보존
- 가능하면 실세션과 분리된 `demoPlayers` 컬렉션을 사용
- 호스트 렌더링 함수가 "실플레이어 컬렉션"과 "데모 컬렉션"을 선택적으로 읽도록 분리
- 실 플레이어가 1명 이상 있으면 데모 시작을 막거나 경고 배너를 띄울 것

#### 2. SDK 내부 구현에 직접 의존하지 말 것

현재는 `sdk._messageHandlers`를 직접 꺼내 호출한다. 이는 공개 API가 아니라 내부 구현 디테일이므로 유지보수에 취약하다.

가이드라인:

- 호스트 게임 쪽에 `handleDemoSubmit(playerId)` 같은 공개용 메서드 추가
- 데모는 그 메서드만 호출하고, 실제 메시지 라우팅과 동일한 검증 로직을 재사용
- 장기적으로는 `RoundController` 같은 순수 상태 모듈을 두고, 실플레이와 데모가 같은 상태 전이 함수를 공유하도록 설계

#### 3. 데모 수명주기를 상태 머신으로 분리할 것

현재는 `isDemo`, `game._isDemo`, `game._gameActive`가 느슨하게 엮여 있고, 자연 종료 후 `DemoSimulator.isDemo`가 명확히 해제되지 않는다.

가이드라인:

- `idle -> seeding -> running -> finishing -> restoring` 상태 정의
- 폭발, 수동 중단, 호스트 리셋 각각에서 공통 종료 루틴 실행
- 자연 종료 시에도 `isDemo = false`와 타이머 정리를 보장
- 로비 복귀 후 60초 자동 데모가 다시 정상 동작하는지 테스트 케이스 추가

#### 4. "보여주기용 시나리오"를 의식적으로 설계할 것

현재 봇은 1.5~2.5초마다 `submitCorrect`만 호출한다. 그래서 데모는 돌아가지만 "게임이 왜 재미있는지"를 설명하는 연출 스크립트는 약하다.

가이드라인:

- 첫 2초: 봇 3명 입장 애니메이션
- 다음 2초: 준비 완료 표시
- 이후: 3~5회 정도의 패스 성공 연출
- 막판 5초: 긴박한 가속 효과를 의도적으로 충분히 보여주기
- 종료 후: 결과 화면 2~3초 노출 뒤 자동 로비 복귀

이렇게 해야 전시장, TV 대기화면, 녹화 영상에서 게임의 핵심 루프가 한 번에 이해된다.

#### 5. 테스트와 직접 연결할 것

데모 시뮬레이터는 단순 편의 기능이 아니라 E2E 테스트 드라이버여야 한다.

가이드라인:

- Playwright에서 확인 가능한 상태 텍스트와 배너를 노출
- 현재 패스 수, 현재 봇 차례, 남은 데모 단계 등을 DOM에 표시
- "데모 시작", "데모 중단", "데모 자동 종료"를 각각 테스트 케이스로 분리
- 실 플레이어가 있는 경우 데모가 차단되는지까지 자동 검증

### 4.5 결론

`word-bomb`은 이미 플랫폼 적합성이 높고 현장 반응을 얻기 쉬운 게임이다. 그러나 실서비스 품질로 끌어올리려면 "재접속 복구", "최소 인원 가드", "준비 상태 시각화", "데모 모드 격리"를 먼저 다져야 한다. 그 다음에야 마이크로 애니메이션, 사운드 레이어, 단어팩 확장 같은 대중성 강화안이 가장 큰 효과를 낼 수 있다.
