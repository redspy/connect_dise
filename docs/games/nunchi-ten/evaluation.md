# 눈치 10단 평가 및 개선안

- 작성일: 2026-07-06
- 분석 대상: `games/nunchi-ten/host/`, `games/nunchi-ten/mobile/`, `games/nunchi-ten/host/NunchiDemoSimulator.js`
- 참고 문서: `docs/games/nunchi-ten/nunchi-ten.md`
- 분석 방식: 소스 코드 정적 분석 기반 평가. 실제 다기기 E2E 플레이, 브라우저 시각 검증, 오디오 체감 QA는 이번 문서 범위에 포함하지 않았다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`눈치 10단`의 코어 룰은 매우 명료하다. 모든 플레이어가 라운드마다 `1~10` 카드 중 한 장을 비밀리에 내고, **내가 낸 숫자보다 낮은 숫자를 낸 사람 수만큼 점수**를 얻는다. 여기에 게임당 3회뿐인 `더블`이 붙어, 단순 비교가 아니라 타이밍과 심리전이 핵심이 되도록 설계되어 있다.

이 구조가 좋은 이유는 다음과 같다.

- `10`이 항상 정답이 아니어서, 고점 카드를 언제 아낄지 고민하게 만든다.
- 카드를 한 번씩만 쓰는 구조라 라운드가 쌓일수록 상대의 남은 선택지를 추론하게 된다.
- 더블은 단순 보너스가 아니라, "이번에 정말 먹을 수 있나"를 묻는 리스크 버튼으로 작동한다.
- 모든 선택이 개인 모바일에서 비밀리에 이뤄지고, 결과는 공용 화면에서 동시에 공개되므로 플랫폼 구조와 잘 맞는다.

특히 이 게임은 "같은 공간에서 서로 표정을 읽는 심리전"이 핵심 재미인데, 이는 `Host TV + N Mobile` 구조와 매우 잘 맞는다. 모바일은 비밀 입력 장치, 호스트는 리액션을 만드는 보드 역할을 한다. 룰의 본질이 네트워크 정밀 조작이 아니라 **동시 선택과 공개 연출**에 있기 때문에, 플랫폼 제약도 오히려 장점으로 전환된다.

코어 재미를 구성하는 축은 네 가지다.

| 축 | 분석 |
| --- | --- |
| 숨은 정보 | 각자 모바일에서 카드와 더블 여부를 비공개로 결정하므로 심리전 밀도가 높다. |
| 누적 메타 | 남은 카드가 계속 줄어들어 후반부로 갈수록 "상대가 뭘 아꼈는지"를 읽게 된다. |
| 희소 자원 | `더블 3회` 제한이 있어 한 번의 대박보다 사용 시점의 눈치 싸움이 중요해진다. |
| 공개 순간 | 전원 제출 후 동시 공개 구조라, 파티 게임의 리액션 포인트가 분명하다. |

반면 대중성 관점에서 현재 한계도 뚜렷하다.

- `2인 플레이`는 기술적으로 가능하지만 대표 재미가 약하다. 현재 구현은 `MIN_PLAYERS = 2`와 로비 `min-players="2"`로 시작 가능하지만, 이 게임의 심리전 밀도는 3인 이상에서 훨씬 잘 살아난다.
- 처음 보는 플레이어에게 "왜 큰 숫자만 내면 안 되는가"를 즉시 납득시키는 연출이 아직 부족하다.
- 공개 순간의 쇼맨십이 다소 기능형이다. 룰은 좋은데, 관전자에게 재미가 크게 보이는 장면 설계가 아직 약하다.

종합하면 `눈치 10단`은 **플랫폼 적합성이 높은 심리전 파티 게임**이다. 코어는 충분히 강하고, 반복 플레이의 여지도 있다. 다만 대중적 흥행을 만들려면 룰을 바꾸기보다 `첫 판 이해`, `공개 장면 임팩트`, `입력 손맛`을 강화하는 편이 더 효과적이다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

코드 구조는 전반적으로 안정적이다. 호스트는 `NunchiGame`, 모바일은 `NunchiMobile`에 게임 고유 로직을 모으고, 베이스 클래스의 규약은 잘 지킨다.

- 호스트는 `HostBaseGame`의 `setPhase()`를 사용해 `lobby`, `round_reveal`, `game_result`를 전환한다.
- 모바일은 `MobileBaseGame`의 `showScreen()`을 사용해 `setup -> waiting -> round_input -> waiting_reveal -> round_result -> game_result` 흐름을 분명하게 유지한다.
- authoritative state는 호스트의 `_profiles`, `_data`, `_submissions`가 들고 있고, 모바일은 표시와 입력에 집중한다.
- 재연결은 호스트의 `_sendRejoinState()`와 모바일의 `_applyRejoinState()`로 비교적 세밀하게 복구된다.

구조적 강점은 다음과 같다.

| 평가 축 | 관찰 | 평가 |
| --- | --- | --- |
| 상태 권한 분리 | 점수 계산, 남은 카드, 더블 잔여 수를 호스트가 단일 진실원으로 관리한다. | 우수 |
| 게임 루프 명확성 | `_startGame() -> _startRound() -> _handleSubmission() -> _revealRound() -> _endGame()` 흐름이 단순하고 읽기 쉽다. | 우수 |
| 모바일 화면 설계 | 입력, 제출 대기, 개인 결과, 최종 결과가 분리되어 있어 플레이 흐름이 자연스럽다. | 우수 |
| 재연결 복구 | 로비, 제출 완료 대기, 공개 중, 최종 결과를 상태별로 복구한다. | 우수 |
| QA 도구 | `?dev` 패널로 9/10라운드 점프가 가능해 후반부 UI 점검에 유용하다. | 양호 |
| 운영용 데모 | 시작 버튼은 있으나 생명주기, 복구, 중단 제어가 부족하다. | 미완성 |

구현 완성도를 끌어내리는 포인트는 아래 다섯 가지다.

#### 1. 최소 인원 정책이 PRD와 다르다

- 구현은 `MIN_PLAYERS = 2`, 로비는 `min-players="2"`다.
- PRD는 권장 `4명`, MVP 지원 범위를 `3~6명`으로 잡고 있다.
- 현재 상태로는 첫 경험이 2인전으로 시작될 수 있는데, 이 경우 게임의 대표 재미가 충분히 전달되지 않을 가능성이 높다.

#### 2. 게임 중 신규 합류 정책이 경쟁 게임으로서는 느슨하다

`onPlayerJoin()`은 게임 시작 후 들어온 플레이어에게 `_initPlayerDataForRound()`를 호출해 **임의의 남은 카드 세트**를 부여한다. 즉, 게임 중 늦게 들어온 플레이어가 랜덤 보정 상태로 현재 경기 흐름에 합류할 수 있다.

이 방식의 문제는 다음과 같다.

- 현재 라운드의 심리전 정보가 이미 어느 정도 형성된 뒤에 새 플레이어가 끼어든다.
- 난입 인원으로 `playerCount`가 바뀌면 점수 기대값과 제출 완료 조건이 즉시 변한다.
- 경쟁 게임의 공정성보다 "세션 수용성"을 우선한 설계라서, 운영 정책이 분명하지 않으면 혼란을 낳는다.

이 게임은 중도 합류를 막거나, 최소한 "다음 판부터 참여" 정책으로 바꾸는 편이 더 자연스럽다.

#### 3. 닉네임 충돌과 입력 정책이 약하다

모바일은 닉네임 최대 길이를 `8자`로 제한하지만, 호스트의 `setProfile` 처리에서는 `trim()` 후 바로 저장한다. 따라서 다음이 부족하다.

- 중복 닉네임 방지 또는 안내
- 금칙어/공백-only 외 추가 검증
- 이미 사용 중인 아바타를 피해야 하는지에 대한 정책

오프라인 행사장에서는 같은 닉네임이 자주 나오므로, 지금 구조는 운영자가 플레이어를 식별하기 어렵게 만들 수 있다.

#### 4. 최종 정렬 규칙과 화면 표기 규칙이 어긋난다

호스트의 `_endGame()`은 다음 순서로 정렬한다.

1. `totalScore` 높은 순
2. `doublesLeft` 적은 순
3. `highestRound` 높은 순

하지만 호스트 `_renderGameResult()`와 모바일 `_calcRankMedals()`는 사실상 `totalScore`만 보고 메달과 순위를 표시한다. 즉, 내부적으로는 타이브레이커가 적용되어 순서가 갈렸는데도 화면은 공동 순위처럼 보일 수 있다. 규칙과 UI가 어긋나는 상태다.

#### 5. 데모 모드는 프로젝트 요구 수준의 Attract Mode에 도달하지 못했다

`NunchiDemoSimulator`는 빠르게 시연용 상태를 만들 수 있다는 점은 좋지만, 구현 방식이 운영 도구로는 거칠다.

- 봇을 `this.game.players`, `_profiles`, `_data`에 직접 주입한다.
- `demoTimeouts` 배열은 있지만 실제 라운드 자동 제출 타이머는 `NunchiGame._startRound()`의 `setTimeout()`에서 생성한다.
- 데모 중단 버튼, 상시 상태 배너, 실제 플레이어 합류 정책이 없다.
- 데모 게임 종료 후 자동 로비 복귀가 보장되지 않는다.

즉, "데모 시작 기능"은 있지만 "운영 가능한 데모 생명주기"는 아직 없다.

### 1.3 종합 평가

| 항목 | 평가 | 코멘트 |
| --- | --- | --- |
| 게임 코어 | 강함 | 규칙은 간결하고 심리전은 살아 있다. |
| 플랫폼 적합성 | 매우 높음 | 공용 화면과 개인 모바일의 역할 분리가 자연스럽다. |
| 아키텍처 건전성 | 높음 | 호스트 권한형 상태 관리와 재연결 설계가 안정적이다. |
| UX 완성도 | 중상 | 플레이 흐름은 좋지만 공개 장면과 입력 손맛은 더 강화할 수 있다. |
| 운영 친화성 | 중 | `?dev` 도구는 좋으나 데모/정책 영역이 미완성이다. |
| 문서 정합성 | 보완 필요 | PRD 제목(`High Unique`)과 실제 게임명, 인원 정책, 순위 표기 규칙이 완전히 맞물리지는 않는다. |

이 게임은 "코어를 뜯어고쳐야 하는 상태"가 아니라, **좋은 코어를 더 크게 보이게 만들어야 하는 상태**에 가깝다.

## 2. [대중성 강화 요소]

### 제안 1. 공개 순간을 쇼타임으로 만드는 리빌 연출 패키지

현재 `round_reveal`은 기능적으로 충분하지만 감정 곡선을 크게 밀어주지는 못한다. 이 게임의 대표 장면은 결국 "다 같이 공개되는 순간"이므로, 가장 높은 투자 우선순위는 여기에 두는 것이 맞다.

권장 보강안:

- 전원 제출 직후 `0.8~1.0초` 정적 구간 추가
- 카드 공개를 한 번에 던지지 말고 `0.12~0.18초` 간격의 staggered flip으로 노출
- `더블` 사용 플레이어에게 금색 플래시, 짧은 타격음, `×2` 배지 확대 애니메이션 부여
- 라운드 최고 득점 카드에 spotlight 또는 왕관 모션 추가
- 최종 우승 화면에서는 1위만 별도의 축하 연출과 사운드를 1회 재생

적용 포인트:

- 호스트 `round_reveal` 오버레이 DOM은 이미 갖춰져 있으므로, `reveal-card` 중심으로 CSS 애니메이션과 상태 클래스를 확장하면 된다.
- `REVEAL_DURATION_MS = 6000`은 현재도 충분하므로, 시간을 늘리기보다 기존 6초를 `서스펜스 -> 공개 -> 정산 -> 다음 라운드 예고`로 더 잘 나눠 쓰는 편이 낫다.

기대 효과:

- 플레이어가 "읽었다/읽혔다"는 감정을 더 강하게 느낀다.
- 구경하던 사람도 공개 장면만 보고 룰의 재미를 이해하기 쉬워진다.
- 게임의 하이라이트가 명확해져 행사장/스트리밍 환경에서 재시청성과 회전율이 올라간다.

### 제안 2. 모바일 조작을 기능형 UI에서 손맛형 UI로 끌어올리기

모바일 컨트롤러는 이미 깔끔하지만, 현재 체감은 "잘 동작하는 폼"에 가깝다. 대중성 강화를 위해서는 **선택하는 순간의 손맛과 확신 피드백**이 더 필요하다.

권장 보강안:

- 카드 탭 시 가벼운 확대/흡착 모션과 짧은 햅틱을 같이 준다.
- 선택 카드가 하단 제출 버튼 위에 `미리보기 토큰`처럼 붙는 UI를 추가한다.
- `더블` ON 상태는 텍스트만 바꾸지 말고 버튼 펄스, 금색 글로우, 잔여 개수 강조를 함께 준다.
- 제출 직후 `잠금 완료` 느낌이 들도록 체크 애니메이션과 짧은 효과음을 넣는다.
- 공개 대기 화면에서 "내가 낸 카드"가 더 중심적으로 보이게 만들어 자기 전략의 몰입감을 높인다.

적용 포인트:

- 모바일은 이미 `card-grid`, `btn-double`, `btn-submit`, `waiting_reveal`로 화면 책임이 잘 나뉘어 있다.
- 즉, 로직 구조를 바꾸지 않고도 CSS 애니메이션, 상태 클래스, 햅틱 패턴 확장만으로 체감 품질을 끌어올릴 수 있다.

기대 효과:

- 초보자도 "내 선택이 지금 확정됐다"는 감각을 즉시 얻는다.
- 더블 사용의 희소성이 손가락 감각으로 전달되어 전략 버튼의 존재감이 커진다.
- 같은 룰이어도 훨씬 잘 만든 게임처럼 느껴진다.

### 제안 3. 첫 60초 온보딩과 운영 모드를 더 단순하게 재구성하기

이 게임은 룰이 복잡해서 어렵다기보다, **핵심 재미를 이해하기 전에 판이 시작될 위험**이 있다. 흥행성을 높이려면 설명을 늘리기보다 "첫 60초에 이해되는 구조"로 바꾸는 편이 좋다.

권장 보강안:

- 로비 설명을 텍스트 5줄 대신 `예시 1개 + 핵심 문장 2개` 중심으로 재편
- `추천 인원 3명 이상`을 UI에서 분명하게 표기
- 행사장 회전율을 위한 `7라운드 퀵 모드`와 `10라운드 정규전` 제공
- 첫 라운드 전 호스트에 `예: 10 / 8 / 5 / 2 -> 3 / 2 / 1 / 0점` 같은 1회성 안내 패널 표시
- 중복 닉네임일 경우 즉시 경고하고 수정 유도

적용 포인트:

- `game-lobby` 설명 슬롯과 모바일 `setup` 화면만 보강해도 첫 경험 개선 폭이 크다.
- 규칙 자체는 유지하면서 이해 비용만 낮추는 방식이므로 기존 코드 구조를 크게 흔들지 않는다.

기대 효과:

- "왜 이게 재밌는지 모르겠다"는 첫 판 이탈을 줄인다.
- 운영자는 행사 성격에 따라 짧은 판과 정규 판을 골라 회전율을 조절할 수 있다.
- 대표 재미가 약한 2인전 노출을 줄여, 첫인상 품질을 안정적으로 관리할 수 있다.

### 3.3 쟁점 토론

#### 쟁점 A. 룰을 더 단순하게 바꿔야 하는가

회의 다수 의견은 "아니오"였다. 현재 룰의 핵심 재미는 이미 충분하다. 문제는 룰이 어려운 것이 아니라, **왜 재밌는지가 첫 판에서 크게 보이지 않는 것**이다. 따라서 점수 공식을 뜯어고치기보다 예시 기반 온보딩과 공개 연출을 강화하는 편이 적절하다고 결론났다.

#### 쟁점 B. 가장 먼저 체감 재미를 올리는 개선은 무엇인가

전원 일치로 `공개 순간 연출 패키지`가 최우선이라고 판단했다. 이 게임에서 관전자와 플레이어가 동시에 반응하는 장면은 공개 순간뿐이다. 여기를 강화하면 체감 재미, 구경 재미, 재도전 의지가 동시에 오른다.

#### 쟁점 C. 2인 플레이를 메인 경험으로 유지할 것인가

기술적으로는 가능하지만, 대표 재미를 보여주는 모드는 아니라는 의견이 우세했다. 결론은 다음과 같다.

- 당장 2인전을 삭제할 필요는 없다.
- 그러나 로비 기본 정책은 `3명 이상 권장`으로 바꾸는 것이 낫다.
- 2인전을 유지하려면 별도 듀얼 규칙 또는 퀵 듀얼 패키지를 나중에 설계하는 편이 맞다.

| --- | --- | --- | --- |

### 3.5 회의 결론

회의의 결론은 명확하다.

> `눈치 10단`은 룰이 약한 게임이 아니라, **좋은 룰을 더 잘 보이게 만들어야 하는 게임**이다.

따라서 다음 순서가 가장 합리적이다.

1. 공개 장면을 강화한다.
2. 모바일 조작 피드백을 강화한다.
3. 첫 60초 온보딩과 운영 정책을 정리한다.

### 4.5 🤖 `NunchiDemoSimulator.js` 개선점 및 수정 가이드라인

현재 `games/nunchi-ten/host/NunchiDemoSimulator.js`는 "버튼을 누르면 봇 3명이 들어와 게임을 시작하는 기능"까지는 제공하지만, 프로젝트 요구사항에 있는 **Attract Mode** 수준에는 도달하지 못한다. 아래 방향으로 재설계하는 것이 적절하다.

#### 1. 데모 상태를 명시적인 상태 머신으로 분리

권장 상태:

- `idle`
- `booting`
- `running`
- `finishing`
- `cleanup`

지금은 `this.game._isDemo` 플래그 하나로 데모 여부를 표현한다. 이 구조는 중단, 자동 종료, 플레이어 합류, 로비 복귀를 분기하기 어렵다. 별도 상태 머신으로 올리면 호스트 배너와 타이머, 봇 행동 스크립트를 안정적으로 제어할 수 있다.

#### 2. 모든 데모 타이머를 DemoSimulator가 소유

현재 `demoTimeouts` 배열은 존재하지만, 실제 봇 입력 예약은 `NunchiGame._startRound()` 내부 `setTimeout()`에서 생성된다. 이 구조에서는 `stopDemo()`가 호출돼도 예약된 라운드 행동을 완전히 회수할 수 없다.

수정 가이드:

- `schedule(fn, delay)` 헬퍼를 두고 모든 `setTimeout()`을 여기로 통합
- `NunchiGame`은 "이번 라운드에 데모 입력이 필요하다"는 훅만 호출
- 실제 봇 입력 타이밍과 연출 타이밍은 `NunchiDemoSimulator`가 관리
- `stopDemo()`는 등록된 타이머를 모두 해제

#### 3. 봇 주입 전에 실제 상태 스냅샷 저장, 종료 시 완전 복구

현재는 봇을 `players`, `_profiles`, `_data`에 직접 주입하고, `stopDemo()`는 QR 오버레이만 치운다. 데모 종료 후에도 상태가 남을 수 있는 구조다.

권장 복구 방식:

1. 데모 시작 전 실제 `players`, `_profiles`, `_data`, `_submissions`, `phase`를 스냅샷
2. 데모 종료 시 봇/타이머/오버레이 제거
3. 스냅샷 상태를 그대로 복원
4. 로비 UI와 준비 카운트를 다시 렌더

핵심은 `데모 종료 후 원상 복구가 항상 보장되어야 한다`는 점이다.

#### 4. 호스트에 상시 배너와 즉시 중단 버튼 추가

현재 로비에는 `🤖 데모 플레이 실행` 버튼만 있고, 진행 중 상시 제어 UI가 없다. 요구사항에 맞게 아래 UI를 추가하는 편이 맞다.

- 상단 또는 우측 고정 배너: `🤖 데모 플레이 진행 중`
- 배너 내부 버튼: `데모 중단`
- 보조 문구: `실제 플레이어가 입장하면 데모가 중단됩니다` 또는 `데모 종료 후 참여 가능합니다`

이 UI는 운영자에게 명확한 상태를 주고, 실수로 데모를 계속 틀어두는 문제를 줄인다.

#### 5. 랜덤 봇이 아니라 "보여주기 좋은 스크립트형 데모"로 전환

현재 봇 로직은 남은 카드 중 랜덤 선택, 더블 20% 확률 사용이다. 이는 구현은 쉽지만, 게임의 핵심 재미를 보여주기에는 운에 너무 의존한다.

권장 시퀀스 예시:

1. 봇 3~4명 순차 입장
2. 준비 완료 연출
3. 초반 라운드에서 쉬운 점수 구조 1회 시연
4. 중반 라운드에서 동점 장면 1회 시연
5. 후반 라운드에서 더블 역전 장면 1회 시연
6. 최종 우승 발표 후 3초 정지
7. 자동 로비 복귀

이렇게 해야 지나가는 사람도 15초 안에 "아, 큰 숫자만 내는 게임이 아니구나"를 이해한다.

#### 6. 실제 플레이어 합류 정책을 명시

데모 중 실제 플레이어가 들어왔을 때의 정책이 필요하다. 추천안은 다음과 같다.

- 정책 A: 실제 플레이어가 입장하면 즉시 데모 중단 후 실제 로비로 전환
- 정책 B: 데모 중에는 입장을 막고 종료 후 참여를 유도

운영 전환율 관점에서는 `정책 A`가 더 낫다. 참여 의지가 생긴 순간을 놓치지 않고 실제 게임으로 넘어갈 수 있기 때문이다.

#### 7. 데모 종료 조건을 명확히 하고 자동 로비 복귀를 필수화

Attract Mode의 핵심은 "끝난 뒤 다시 사람을 받을 준비가 되어 있는 상태"다. 따라서 다음 다섯 가지는 종료 시 반드시 보장돼야 한다.

- 봇 플레이어 제거
- QR 블러 및 오버레이 제거
- 준비 카운트/플레이어 목록 복구
- 로비 페이즈 복귀
- 데모 버튼과 시작 버튼 재활성화

이 다섯 가지가 자동으로 보장되어야 데모를 운영용 도구라고 부를 수 있다.

### 4.6 결론적 수정 방향

가장 효율적인 보강 순서는 아래와 같다.

1. 공개 장면과 모바일 피드백을 강화해 체감 재미를 즉시 끌어올린다.
2. 인원 정책, 신규 합류 정책, 최종 순위 표기 규칙을 정리해 운영 혼선을 없앤다.
3. 데모 시뮬레이터를 상태 복구 가능한 Attract Mode로 재설계한다.
4. 로비 온보딩과 퀵 모드로 첫 판 진입 장벽을 낮춘다.

이 방향이면 `눈치 10단`은 "재미가 있는 프로토타입"을 넘어, **행사장과 가족/파티 환경에서 반복 플레이를 부르는 상용형 콘텐츠**로 한 단계 올라갈 수 있다.
