# `dimension-weaver` 평가 및 개선안

- 작성일: 2026-07-07
- 분석 대상:
  - `games/dimension-weaver/host/main.js`
  - `games/dimension-weaver/host/DemoSimulator.js`
  - `games/dimension-weaver/host/index.html`
  - `games/dimension-weaver/host/style.css`
  - `games/dimension-weaver/mobile/main.js`
  - `games/dimension-weaver/mobile/index.html`
  - `games/dimension-weaver/mobile/style.css`
  - `tests/dimension-weaver/demo.spec.js`
  - `docs/agents/roles.md`
- 분석 방식: 정적 코드 리뷰 + `npm run build` 검증
- 검증 한계:
  - 실제 다기기 동시 접속, P2P 직결 로그 확인, 브라우저 시각 QA는 이번 문서 범위에 포함하지 않았다.
  - Playwright 테스트 파일은 검토했지만 이번 작업에서는 실행하지 않았다.

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`디멘션 위버`의 코어 루프는 매우 명확하다. 호스트 화면에서는 자동 전진하는 러너가 시공간 트랙을 달리고, 모바일 플레이어는 각자 다른 차원의 정보를 받아 협동으로 장애물을 제거한다.

1. `차원 알파`는 끊어진 발판을 복구한다.
2. `차원 베타`는 가시 함정을 소거한다.
3. `차원 감마`는 같은 색의 레이저 게이트를 해제한다.

이 구조는 공용 화면과 개인 모바일을 함께 쓰는 플랫폼 목적과 잘 맞는다. 핵심 재미는 "누가 무엇을 봤는지 서로 다르다"는 비대칭 정보 구조에서 나온다. 한 사람은 구멍을 먼저 보고, 다른 사람은 함정을 먼저 보며, 감마 역할은 호스트의 장면을 읽고 색을 맞춰야 한다. 따라서 자연스럽게 목소리 기반 협업, 긴급 콜아웃, 실시간 역할 분담이 발생한다.

현재 구현에서 강점으로 보이는 지점은 아래와 같다.

| 항목 | 평가 |
| --- | --- |
| 플랫폼 적합성 | TV의 관전성과 모바일의 개인 정보 분할을 모두 활용한다. |
| 규칙 학습 비용 | "각자 다른 위험을 본다, 빨리 말하고 눌러라"로 요약 가능한 편이라 첫 판 진입이 빠르다. |
| 관전성 | 호스트 캔버스가 러너, 트랙, 스파이크, 레이저 게이트를 즉시 보여 주어 외부 관전자도 위기 상황을 읽기 쉽다. |
| 협동 압박감 | 자동 전진, 20% 단위 선체 피해, 게이트 정지 메커니즘 덕분에 느슨하지 않은 실시간 긴장이 유지된다. |
| 역할 개성 | 알파는 공간 인지, 베타는 즉각 반응, 감마는 색 매칭과 타이밍을 담당해 역할 감각이 분명하다. |

특히 호스트 쪽 캔버스 연출은 단순한 규칙을 보기 좋게 감싼다. 별 배경, 스크롤 그리드, 충돌 파티클, 흔들림 효과가 들어가 있어 "우주 러너를 실시간으로 구한다"는 감정선이 잘 살아 있다. 이 게임은 로직보다 장면성이 중요한데, 그 기본 토대는 이미 갖춰져 있다.

반면 현재 구현만 놓고 보면 대중적으로 오래 붙잡는 힘은 아직 약하다.

| 관찰 포인트 | 평가 |
| --- | --- |
| 장애물 패턴 | 장애물이 `4칸 간격`으로 반복 생성되어 몇 판 지나면 리듬이 읽히기 쉽다. |
| 역할 체감 편차 | 알파는 발판을 적극적으로 만지지만, 감마는 세 색 버튼만 반복 탭하는 구조라 장면 대비 조작 손맛이 상대적으로 얇다. |
| 2인 플레이 부담 | 2인일 때 한 플레이어가 `beta + gamma`를 동시에 맡아 인지 부하가 급격히 커진다. |
| 리플레이 수명 | 100m 완주 / 선체 파괴라는 단일 승패 구조만 있어 중장기 변주와 회고 포인트가 적다. |
| 역할 가치 선명도 | 러너가 인접 행으로 자동 회피하는 로직이 있어 알파가 메운 발판의 기여가 체감상 흐려질 때가 있다. |

종합하면 `디멘션 위버`는 "비대칭 협동 러너"라는 코어 아이디어가 분명히 살아 있다. 재미의 씨앗은 좋다. 다만 현재 버전은 아이디어가 대중에게 크게 폭발하도록 밀어주는 온보딩, 피드백, 역할 밸런싱, 라운드 변주가 아직 충분하지 않다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

호스트 구현은 프로젝트 규약과 비교적 잘 맞는다.

- `HostBaseGame`를 상속하고 `setPhase('lobby' | 'playing' | 'result')`로 화면 단계를 분리했다.
- 호스트 CSS는 `.hidden` 규약과 `position: relative; z-index: 10;` 규약을 충족한다.
- `DemoSimulator.js`가 별도 파일로 존재하고 로비 버튼도 구현되어 있어 최소한의 Attract Mode 구조는 있다.
- 캔버스 렌더링, 역할 배정, 결과 화면, 리셋 흐름이 한 파일 안에서 읽히는 편이라 입문 난도는 낮다.

하지만 모바일 구조와 운영 품질은 한 단계 덜 정리되어 있다.

- 모바일은 `MobileBaseGame`를 상속하지 않고 `MobileSDK`를 직접 조합한다.
- 화면 전환, 연결 상태, 준비 버튼, 재접속 복구, 역할 패널 토글이 모두 `mobile/main.js` 단일 파일에 수동 결합되어 있다.
- `destabilized-alert` UI가 존재하지만 실제로 이를 활성화하는 메시지 경로가 없다.

구현 완성도를 축별로 정리하면 아래와 같다.

| 평가 축 | 판정 | 근거 |
| --- | --- | --- |
| 코어 컨셉 적합성 | 높음 | 비대칭 역할, 자동 전진, 공용 화면 관전성이 플랫폼 구조와 잘 맞는다. |
| 호스트 상태 관리 | 중상 | 페이즈, 맵, 선체, 러너 위치, 역할 배정이 비교적 단순한 상태 모델로 유지된다. |
| 모바일 상태 관리 | 보통 이하 | 직접 DOM 제어 중심이라 재접속, 보조 UI, 튜토리얼 추가 시 빠르게 복잡해질 가능성이 높다. |
| 재접속 복구 | 미흡 | 진행 중 상태 일부만 복구하며, 일시 끊김 정지와 결과 단계 복원은 빠져 있다. |
| 액션 판정 신뢰성 | 보통 이하 | 역할 검사는 있으나 좌표 범위와 타이밍 제약이 넓어 실제 플레이 감각을 흐릴 수 있다. |
| 데모 모드 완성도 | 취약 | 시연은 가능하지만 실제 세션 상태를 오염시킬 수 있는 구조다. |
| 테스트 대표성 | 낮음 | 기존 E2E는 호스트 데모 완주만 검증하며 실제 모바일 협동 경로를 증명하지 못한다. |

현재 코드에서 중요하게 봐야 할 리스크는 아래 여섯 가지다.

#### 1. 일시 연결 끊김 시 게임 정지가 발동하지 않는다

서버와 `HostSDK`는 `platform:playerDisconnected`를 별도 이벤트로 내보낸다. 그러나 `dimension-weaver/host/main.js`는 `onPlayerDisconnect()`를 구현하지 않고 `onPlayerLeave()`에서만 `_pauseGameForRejoin()`을 호출한다.

이 구조의 문제는 명확하다.

1. 모바일 플레이어가 새로고침하거나 잠깐 네트워크가 흔들려도 서버는 즉시 `playerLeft`를 보내지 않는다.
2. 유예 기간 동안 호스트는 플레이어가 "복구 가능 상태"라는 것만 알게 된다.
3. 그런데 게임 쪽은 그 신호를 받아 정지하지 않기 때문에, 실제 플레이 중 동료 한 명이 사라져도 러너는 계속 전진한다.

즉, 현재 구현은 프로젝트 문서가 강조한 "재연결 복구 중 정지" 경험을 실질적으로 보장하지 못한다.

#### 2. 모바일이 공통 베이스 클래스 패턴을 쓰지 않아 복구와 확장이 약하다

모바일은 `MobileBaseGame`의 `onJoin`, `onRejoin`, `onAllReady`, `onReset`, `showScreen()` 패턴을 재사용하지 않는다. 직접 구현 자체가 틀렸다는 뜻은 아니지만, 현재 구조는 다음 한계를 만든다.

- 공통 홈 버튼과 라이프사이클 훅 활용이 빠져 있다.
- 재접속 시 어떤 화면을 유지하고 어떤 화면을 재구성할지 정책이 코드에 흩어져 있다.
- 로비, 플레이, 결과, 복구 대기 상태를 늘릴수록 단일 파일 제어가 빠르게 비대해질 수 있다.

지금 규모에서는 작동하지만, 향후 튜토리얼, 옵션, 역할별 미션 설명, 실시간 토스트를 붙이면 유지보수성이 급격히 떨어질 가능성이 높다.

#### 3. 역할별 액션 허용 범위가 너무 넓어 정밀한 협동성이 약해진다

현재 메시지 핸들러는 역할 자체는 확인하지만, 액션 범위를 좁게 제한하지 않는다.

- `buildPath`는 맵 전체 좌표에 대해 발판을 미리 복구할 수 있다.
- `disableTrap`도 시야 밖의 좌표까지 제거할 수 있다.
- `unlockGate`는 현재 위치부터 10칸 이내의 같은 색 게이트를 한 번에 모두 비활성화한다.

이 설계는 구현을 단순하게 만들지만, 반대로 플레이 감각을 흐린다. 이상적인 협동 게임이라면 "지금 바로 앞의 위협을 누가 정확히 읽고 대응했는가"가 손맛이 되어야 한다. 하지만 현 구조에서는 숙련자가 미래 구간을 미리 정리하거나, 감마가 색 한 번 눌러 여러 게이트를 쓸어버리는 상황이 가능하다.

#### 4. 재접속 시 상태 동기화가 단계별로 완결되어 있지 않다

`onPlayerRejoin()`은 진행 중이면 `assignRole`과 일부 수치만 다시 보내고, 그 외에는 `lobbyState`만 보낸다. 이 때문에 다음 문제가 생긴다.

- 결과 화면에 재접속한 플레이어도 `result`가 아니라 `lobby`로 안내될 수 있다.
- 진행 중 복귀 시 `distance`, `hull`은 받지만 `upcoming` 스냅샷은 즉시 받지 못해 다음 틱까지 역할 패널이 비어 있을 수 있다.
- 일시 정지 상태인지, 정상 진행 상태인지, 이미 승패가 났는지에 대한 명시적 phase 동기화가 부족하다.
- 모바일에 존재하는 `destabilized-alert`는 실제로 어떤 상황에서도 표시되지 않는다.

즉, "복구는 되긴 하지만 정확한 현재 장면으로 복귀한다"는 수준까지는 아직 도달하지 못했다.

#### 5. `DemoSimulator.js`가 실제 세션 상태를 오염시킬 수 있다

현재 데모 시뮬레이터는 `game.players`, `sdk._players`, `_playerNicknames`를 직접 비우고 봇 객체를 강제로 주입한다. 이 방식은 데모를 빨리 구현하기에는 편하지만 운영 안전성은 낮다.

문제점은 아래와 같다.

1. 실제 플레이어가 이미 연결된 세션에서 데모를 누르면 호스트 내부 플레이어 맵이 봇으로 교체된다.
2. 데모 중지 시 이 내부 맵을 다시 비워 버려, 서버 세션에는 남아 있는 실제 플레이어와 호스트 UI 상태가 어긋날 수 있다.
3. 데모 종료 후 자동 로비 복귀가 아니라 결과 화면에서 수동 리셋을 기다리므로 진정한 Attract Loop가 아니다.
4. 데모 활성 상태를 알리는 별도 배너나 안전 잠금이 없어 운영자가 실수로 실제 세션 위에서 데모를 돌릴 위험이 있다.

프로젝트 요구사항의 "호스트 단독 핵심 루프 검증용 데모 모드"는 충족하지만, "실운영에서 안전한 데모 모드"라고 부르기에는 부족하다.

#### 6. 닉네임 렌더링이 `innerHTML` 기반이라 입력 안전성이 약하다

호스트의 `_renderRolesBoard()`는 플레이어 닉네임을 문자열 템플릿으로 조합해 `innerHTML`에 삽입한다. 모바일 닉네임은 길이만 제한할 뿐 별도 이스케이프를 하지 않는다.

공용 화면 기반 서비스에서는 사용자 입력이 그대로 메인 디스플레이에 노출되므로, 최소한 HTML 이스케이프나 text node 기반 렌더링으로 바꾸는 것이 안전하다. 이것은 게임성 문제는 아니지만, 운영 품질과 코드 완성도 평가에서는 감점 요소다.

### 1.3 종합 평가

`디멘션 위버`는 컨셉 점수가 높은 게임이다. 비대칭 협동, 짧은 규칙, 호스트의 우주 러너 연출, 모바일 역할 분담은 모두 좋다. 문제는 현재 버전이 그 재미를 서비스 품질로 끝까지 끌고 가지 못한다는 데 있다. 특히 재접속 정지, 모바일 상태 복구, 액션 판정 폭, 데모 모드 안전성이 발목을 잡는다.

점수로 요약하면 아래와 같다.

| 항목 | 점수(10점 만점) | 코멘트 |
| --- | --- | --- |
| 코어 게임성 | 8.4 | 비대칭 협동 구조와 공용 화면 관전성이 강하다. |
| 첫 판 직관성 | 7.4 | 기본 규칙은 이해되지만 역할별 우선순위와 2인 부담 설명이 더 필요하다. |
| 관전성 | 8.2 | 호스트 캔버스 연출이 좋고, 외부 관람도 비교적 쉽다. |
| Host 구현 완성도 | 7.3 | 루프와 렌더링은 좋지만 재접속/데모 세부 설계가 약하다. |
| Mobile 구현 완성도 | 5.8 | 동작은 되나 공통 패턴과 복구 설계 활용이 부족하다. |
| Demo/Test 신뢰성 | 4.4 | 데모가 실세션을 오염시킬 수 있고 기존 E2E 범위도 좁다. |
| 상품화 잠재력 | 8.1 | 피드백과 운영 품질만 보강하면 대중성이 빠르게 올라갈 여지가 크다. |

한 줄 총평:

> `디멘션 위버`는 이미 재미의 방향은 맞지만, 현재 상태는 "강한 플레이어블 프로토타입"에 가깝고, 대중적 흥행을 노릴 상용형 협동 게임으로 가려면 피드백 밀도와 운영 안전성을 한 단계 더 끌어올려야 한다.

## 2. [대중성 강화 요소]

대중적으로 더 크게 흥행시키려면 새 규칙을 과하게 늘리기보다, 지금 있는 코어를 더 잘 보이게 하고 더 쉽게 이해시키고 더 기억에 남게 만들어야 한다. 우선순위가 높은 세 가지는 아래와 같다.

### 2.1 제안 1: 위기 연출 패키지 강화

현재도 호스트에는 충돌 흔들림과 파티클이 있지만, 실제 플레이어가 "우리가 방금 살렸다" 혹은 "지금 진짜 위험하다"를 체감하는 연출은 더 밀어붙일 수 있다.

구체 제안:

- 게이트 등장 시 호스트에 색상 경고 링과 짧은 경보음을 추가한다.
- 발판 복구, 함정 제거, 게이트 해제 성공 시 호스트와 해당 모바일에 동기화된 플래시/햅틱을 준다.
- 선체 30% 이하일 때 모바일 HUD 전체를 단계별로 경고 색으로 전환한다.
- 일시 정지 시 모바일 `destabilized-alert`를 실제로 띄우고, 복구 시 "동기화 재개" 짧은 성공 연출을 넣는다.
- 결과 화면에 "무피해 통과 수", "위기 구조 횟수", "가장 많이 구한 역할" 같은 간단한 후일담 지표를 추가한다.

기대 효과:

- 관전자도 현재 위험도와 구출 순간을 더 빨리 읽는다.
- 플레이어가 자기 행동의 효력을 즉시 느끼므로 손맛이 올라간다.
- 짧은 성공/실패 연출이 반복 플레이의 기억점을 만든다.

### 2.2 제안 2: 역할별 온보딩과 조작 보조 UI 강화

`디멘션 위버`의 장점은 역할이 다르다는 점이지만, 첫 판에서는 그 차이가 곧 혼란이 되기 쉽다. 특히 감마와 2인 플레이의 복합 역할은 설명 보강이 필요하다.

구체 제안:

- 로비에 20초 내 이해 가능한 역할별 튜토리얼 카드 3장을 넣는다.
- 2인 플레이에서는 `beta + gamma` 복합 플레이어에게 현재 우선 위험을 보여 주는 작은 큐를 제공한다.
- 감마 화면에 "현재 차단 색" 텍스트 혹은 호스트와 동기화된 미니 신호등을 제공해, 단순 버튼 3개보다 명확한 판단 보조를 준다.
- 알파는 러너 현재 행이나 위험 예상 행을 약하게 표시해, 어떤 발판을 우선 메워야 하는지 직관을 강화한다.
- 베타는 이미 소거된 함정을 즉시 시각적으로 정리하고, 남은 위협 개수를 상단에 표시해 우선순위를 선명하게 만든다.

기대 효과:

- 첫 판에서 "내가 뭘 봐야 하지?"라는 혼란을 줄일 수 있다.
- 2인 모드의 인지 과부하를 줄여 소규모 모임에서도 접근성이 올라간다.
- 역할별 기여가 더 분명해져 협업 대화가 선명해진다.

### 2.3 제안 3: 구간형 진행과 리플레이 보상 구조 추가

현재 게임은 100m 완주 또는 선체 파괴의 단일 루프라서, 한두 판 뒤에는 패턴이 고정적으로 느껴질 수 있다. 대중성 확대를 위해서는 "한 판이 끝난 뒤 다시 한 판을 누르게 만드는 장치"가 필요하다.

구체 제안:

- 100m를 `3개 구간`으로 나누고 중간마다 테마 장애물을 바꾼다.
- 구간 클리어 때 역할을 순환 배정하거나 보조 역할을 교체해 플레이 감각을 바꾼다.
- `완주`, `무피해`, `초고속`, `위기관리` 같은 메달을 결과 화면에 부여한다.
- 연속 무사 통과 시 콤보 보너스나 특별 연출을 부여해 완주 품질을 경쟁하게 만든다.
- 데모 모드와 실제 플레이 모두에서 사용 가능한 시드 기반 맵 난이도 프리셋을 제공해 "쉬움 / 표준 / 혼돈" 식으로 선택 가능하게 한다.

기대 효과:

- 같은 규칙 안에서도 한 판의 리듬이 더 풍부해진다.
- 플레이 후 회고와 재도전 동기가 생긴다.
- 스트리밍, 행사, 가족 모임에서 "이번엔 더 잘하자"라는 반복 플레이 동력이 커진다.

### 3.3 핵심 쟁점 토론

#### 쟁점 1. 대중성 강화보다 선행해야 할 기술 수정이 있는가

회의 결론은 "그렇다"였다. 특히 아래 세 가지는 선행 조건으로 정리됐다.

1. `onPlayerDisconnect()`를 구현해 일시 끊김 시 즉시 일시정지 및 모바일 공지 브로드캐스트를 넣는다.
2. 재접속 시 `lobby`, `playing`, `paused`, `result`의 현재 phase와 필요한 스냅샷을 모두 동기화한다.
3. `DemoSimulator.js`가 실제 플레이어 맵을 직접 갈아끼우지 않도록 구조를 분리한다.

이 세 가지가 해결되지 않으면, 화려한 연출을 올려도 실제 운영 상황에서 신뢰도가 떨어진다.

#### 쟁점 2. 세 가지 대중성 강화 요소의 우선순위는 무엇인가

전문가 다수 의견은 `B -> A -> C` 순이었다.

- `B`는 첫 판 이탈률과 2인 접근성을 직접 낮춘다.
- `A`는 같은 코어를 더 강하게 체감시키므로 관전성과 바이럴을 키운다.
- `C`는 상품 수명을 늘리는 요소라 중요하지만, 현재 기반 안정화 이후 붙이는 것이 효율적이다.

#### 쟁점 3. 2인 플레이를 어떻게 다뤄야 하는가

결론은 "허용하되 추천 경험으로 밀어서는 안 된다"였다.

- 현재 2인 구조는 한 플레이어에게 복합 역할을 몰아 인지 피로를 크게 만든다.
- 기본 홍보 포인트는 3인 이상 협동 경험으로 잡고, 2인은 보조 모드로 안내하는 편이 더 낫다.
- 2인을 유지하려면 우선순위 큐와 자동 보조 UI가 필요하다.

### 3.4 최종 의사결정

회의는 다음과 같이 결론지었다.

1. 즉시 반영 우선순위는 `역할 온보딩/보조 UI`와 `재접속/데모 안정화`다.
2. 그 다음 단계에서 `위기 연출 패키지`를 호스트와 모바일 양쪽에 동기화해 넣는다.
3. 마지막으로 `구간형 진행과 리플레이 보상 구조`를 붙여 한 판의 수명과 재도전 동기를 늘린다.

최종 메모:

> `디멘션 위버`의 흥행 포인트는 "각자 다른 차원을 보고 같은 위기를 넘기는 장면"이다. 따라서 규칙을 복잡하게 키우기보다, 그 장면을 더 쉽게 이해시키고 더 세게 느끼게 하며 더 안전하게 반복 시연할 수 있게 만드는 것이 맞는 방향이다.

### 4.3 `DemoSimulator.js` 개선점 및 수정 가이드라인

현재 데모는 존재 자체는 유효하지만, 운영 안정성과 재사용성 면에서 보강이 필요하다. 수정 방향은 아래처럼 잡는 것이 좋다.

#### 개선 방향 1. 실제 세션 플레이어 상태와 데모 상태를 분리한다

- `game.players`와 `sdk._players`를 직접 비우거나 덮어쓰지 않는다.
- 데모 전용 `demoPlayers` 스냅샷 계층을 두고, 렌더링과 역할 배정 시에만 이를 참조하도록 구조를 분리한다.
- 실제 세션에 플레이어가 한 명이라도 있으면 데모 실행을 차단하거나 "데모 시작 시 실제 세션이 초기화됩니다" 같은 명시적 확인 절차를 둔다.

#### 개선 방향 2. 데모도 실제 게임 시작 경로를 최대한 재사용한다

- `_startGame()`를 바로 때리는 대신, 공개형 `beginDemoSession()` 같은 메서드를 만들고 이 안에서 로비 표현, 봇 프로필 등록, 준비 완료, 시작 카운트다운을 순서대로 수행한다.
- 봇 액션도 `sdk._messageHandlers`에 직접 접근하는 대신, 호스트에 `handleBuildPath(playerId, payload)`, `handleDisableTrap(playerId, payload)`, `handleUnlockGate(playerId, payload)` 같은 공개 액션 메서드를 두고 이를 재사용하는 편이 안전하다.
- 이렇게 해야 실플레이와 데모 판정 규칙이 갈라지지 않는다.

#### 개선 방향 3. 데모 수명주기를 완전한 Attract Loop로 만든다

- `startDemo()` 후 자동으로 결과까지 진행한 뒤 일정 시간 후 로비로 복귀하도록 한다.
- 데모 실행 중에는 호스트에 `DEMO MODE` 배너를 띄우고, 언제든 중단 가능한 별도 버튼 상태를 유지한다.
- 결과 화면에서 사람이 직접 `restart`를 누르지 않아도 자동 원복되도록 해야 "전시장 시연 모드"로 쓸 수 있다.

#### 개선 방향 4. 재현 가능한 시드와 난이도 프리셋을 넣는다

- 현재는 `Math.random()`만 사용하므로 데모 결과가 매번 달라진다.
- `seed`, `difficultyPreset`, `forcedObstaclePattern`을 넣어 QA 시에 동일 상황을 반복 검증할 수 있게 만드는 것이 좋다.
- 예를 들어 "알파 검증용 구멍 집중 코스", "감마 검증용 게이트 집중 코스", "혼합 위기 코스"를 따로 둘 수 있다.

#### 개선 방향 5. 데모도 재접속/일시정지 경로를 검증하게 만든다

- 데모 중간에 봇 한 명을 의도적으로 이탈시켜 호스트 정지 배너와 모바일 복구 상태가 잘 작동하는지 보여 주는 시나리오를 넣을 수 있다.
- 이 기능은 단순 시연을 넘어 회귀 테스트용 데모로도 가치가 있다.

#### 개선 방향 6. 테스트 범위를 호스트 단독 데모에서 실제 협동 경로로 넓힌다

- 기존 `tests/dimension-weaver/demo.spec.js`는 유지하되, 최소 2개 이상의 모바일 컨텍스트를 띄워 역할별 입력을 실제로 보내는 E2E를 추가한다.
- 적어도 아래 세 가지는 자동화 범위에 들어가야 한다.
  - 3인 역할 배정과 각 역할 입력 성공
  - 게임 중 새로고침 후 재접속 복귀
  - 데모 실행 차단 또는 자동 원복 검증

### 4.4 우선 수정 순서 제안

실제 수정은 아래 순서를 권장한다.

1. `onPlayerDisconnect()` 구현과 phase 동기화 패킷 설계를 먼저 고친다.
2. 모바일을 `MobileBaseGame` 패턴으로 정리하거나 최소한 라이프사이클 책임을 분리한다.
3. 역할별 액션 허용 범위를 현재 시야/현재 위협 기준으로 좁힌다.
4. `DemoSimulator.js`를 세션 비오염 구조로 재작성한다.
5. 마지막으로 위기 연출, 튜토리얼, 결과 보상 구조를 붙여 대중성을 끌어올린다.

이 순서를 따르는 편이 기술 리스크를 줄이면서도, 플레이어가 체감하는 완성도를 가장 빠르게 올릴 수 있다.
