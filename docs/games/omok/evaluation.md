# 오목 평가 및 개선안

- 작성일: 2026-07-07
- 분석 대상: `games/omok/host/`, `games/omok/mobile/`, `games/omok/host/DemoSimulator.js`, `games/omok/host/ai.js`
- 분석 방식: 소스 코드 정적 분석 기반 평가. 실제 다기기 E2E 플레이, 브라우저 시각 검증, 사운드 체감 QA는 이번 문서 범위에 포함하지 않았다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

현재 `omok`은 전통적인 오목을 `Host TV + 2 Mobile` 구조에 맞게 단순화한 **1:1 공개 정보 전략 대결**이다. 공용 화면에는 전체 바둑판과 현재 턴이 크게 노출되고, 각 플레이어는 개인 모바일에서만 착수 좌표를 고른 뒤 확정 버튼을 누른다. 이 구조는 같은 판을 함께 바라보면서도 입력은 각자 손에 쥐고 있게 만들어, "같은 공간에서 심리전을 벌이는 보드게임 감각"을 잘 살린다.

재미의 핵심은 아래 세 지점에서 발생한다.

| 재미 축 | 현재 구현 방식 | 평가 |
| --- | --- | --- |
| 같은 판을 함께 보는 긴장감 | 호스트가 13x13 전체 보드를 보여주고, 마지막 수와 현재 턴을 강조한다. | 플랫폼 적합성이 높다. |
| 비밀 입력, 공개 결과 | 모바일에서 좌표를 고르고 호스트 화면에 돌이 즉시 등장한다. | 같은 공간에서의 눈치싸움이 자연스럽다. |
| 짧은 규칙 학습 | "5개 연결"이라는 규칙만 알면 바로 플레이 가능하다. | 행사장/체험형 환경에 유리하다. |

특히 `13x13` 보드 선택은 `15x15`보다 판이 짧게 끝날 가능성이 높아, 회전율이 중요한 공용 기기 환경에 잘 맞는다. 모바일도 드래그나 제스처가 아니라 "셀 선택 → 착수 버튼" 2단계이므로 오조작을 줄이기 쉽다. 마지막 착수 위치를 강조하는 `last-move` 마커도 관전자와 플레이어 모두에게 현재 국면을 읽기 쉽게 만든다.

다만 현재 구현이 주는 재미는 "기본기"는 갖췄지만, 감정 곡선과 대중적 몰입 장치는 아직 약하다.

- 턴 제한 시간이 없어 장고가 길어지면 공용 화면의 긴장감이 처질 수 있다.
- 승부 연출이 담백하다. 돌이 놓일 때의 애니메이션은 있으나, 위기 상황이나 승리 순간의 드라마는 크지 않다.
- 오목 숙련자에게는 금수/장목 같은 정통 룰 정보가 없고, 초심자에게는 현재 규칙 세트가 "캐주얼 오목"인지 "정통 오목"인지 명시되지 않는다.
- 2인 전용 전략 게임인 만큼 관전자 연출이 약하면 TV 앞 분위기가 조용해질 수 있다.

즉, 코어 플레이는 명확하고 안정적이지만, 흥행 측면에서는 **"재미의 뼈대는 충분하나 현장 체감 연출이 아직 덜 붙은 상태"**로 평가할 수 있다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

구조적으로는 호스트가 권위(authority)를 갖고, 모바일은 컨트롤러에 집중하는 분리가 명확하다. 보드 상태, 턴, 승패 판정은 모두 호스트가 가진다. 모바일은 좌표 선택과 착수 요청만 보내므로, 실시간 멀티 보드게임에서 가장 중요한 상태 충돌 위험을 낮춘다.

핵심 구조 평가는 다음과 같다.

| 평가 축 | 관찰 | 평가 |
| --- | --- | --- |
| 상태 권한 분리 | 호스트가 `_board`, `_currentPlayerColor`, `_gameActive`를 단독 관리한다. | 우수 |
| 메시지 명확성 | `makeMove`, `roleAssign`, `turnUpdate`, `rejoinState`, `gameFinished`로 프로토콜이 단순하다. | 우수 |
| 재접속 복구 | 진행 중 재접속 시 보드와 턴을 다시 내려준다. | 양호 |
| 데모 모드 존재 | `DemoSimulator.js` 분리와 AI 기반 자동 착수 루프가 있다. | 긍정적이나 운영 완성도는 보완 필요 |
| 플랫폼 규약 준수 | 호스트는 `HostBaseGame`을 잘 활용하지만 모바일은 `MobileBaseGame`을 사용하지 않는다. | 부분 준수 |
| 문서-코드 정합성 | 기존 `docs/games/omok.md`는 여전히 "솔로 / 로컬 AI / Socket 없음"으로 설명한다. | 불일치 |

구체적으로 좋은 점은 아래와 같다.

1. **호스트 권위형 턴 처리**
   - 호스트의 `_wireGameMessages()`는 턴 위반, 보드 범위 초과, 이미 놓인 자리 착수를 모두 차단한다.
   - 승패 판정도 호스트의 `OmokAI.checkWin()`을 사용하므로 클라이언트 간 판정 차이가 없다.

2. **재접속 시 최소 복구 정보가 명확함**
   - `onPlayerRejoin()`에서 `color`, `opponentNickname`, `board`, `currentTurn`을 묶어 `rejoinState`로 보내기 때문에, 진행 중 경기 복구 방향은 올바르다.

3. **데모 시뮬레이터가 별도 파일로 분리됨**
   - 호스트 메인 파일이 데모 세부 구현으로 과도하게 비대해지지 않았다.
   - `OmokAI`를 재사용해 두 봇의 자동 대전을 구성한 점은 구현 효율이 좋다.

반면 완성도를 깎는 결함과 부채도 분명하다.

#### 1. 모바일 결과 화면은 현재 코드상 런타임 오류 가능성이 높다

모바일 `main.js`는 `gameFinished` 수신 시 `result-title` ID를 찾지만, 실제 HTML에는 `id="result-text"`만 있다. 이 경우 결과 수신 순간 `null.textContent` 오류가 발생해 결과 화면 전환이 깨질 가능성이 높다. 단순한 UI 오타처럼 보이지만, 실제 플레이에서는 **승패 피드백 전체를 무너뜨리는 P0급 결함**이다.

#### 2. 모바일 구현이 `MobileBaseGame` 패턴을 따르지 않는다

현재 모바일은 `MobileSDK` 위에 직접 이벤트를 매달아 화면 전환과 생명주기를 수동 처리한다. 동작 자체는 가능하지만, 프로젝트의 권장 패턴인 `MobileBaseGame` 기반 구조를 쓰지 않아서 아래 문제가 생긴다.

- `showScreen()`과 라이프사이클 관리가 게임마다 중복될 가능성
- 재연결/리셋 대응 방식의 일관성 저하
- 코드가 커질수록 재사용성과 검증성이 떨어짐

즉, 지금 크기에서는 버티지만 장기 유지보수 관점에서는 비정형이다.

#### 3. 로비 품질이 기대보다 약하다

소스 기준으로는 `game-lobby` 컴포넌트가 제공하는 참가자 카드 렌더링 API(`renderLobbyPlayers`)를 `omok` 호스트가 호출하지 않는다. 따라서 실제 로비에서는 플레이어 목록이 비어 있거나 최소한의 준비 카운트만 보일 가능성이 있다. 또한 `onPlayerJoin()`에서는 시작 버튼 클릭 핸들러를 등록하지만, `onAllReady()`에서 이미 즉시 `_startGame()`을 호출하기 때문에 "호스트가 시작 버튼을 누르는 로비"와 "모두 준비되면 자동 시작되는 로비"가 섞여 있다. 현재 구조는 기능이 완전히 깨진 것은 아니지만, **로비 UX 설계가 흔들리는 상태**다.

#### 4. 로비 재접속 동기화가 부족하다

진행 중 재접속은 `rejoinState`로 복구하지만, 로비 상태에서는 별도 동기화 패킷이 없다. 모바일의 `rejoin` 핸들러도 연결 표시만 바꾸고, 준비 상태나 상대 대기 상태를 다시 맞추지 않는다. 이 때문에 로비에서 새로고침 후 복귀할 경우 사용자가 이미 준비 완료였는지, 다시 버튼을 눌러야 하는지, 현재 누구를 기다리는지 UI가 불명확해질 수 있다.

#### 5. 데모 시뮬레이터는 존재하지만 운영형 Attract Mode로는 미완이다

`DemoSimulator.js` 파일이 있는 점은 좋다. 하지만 현재 구현은 "행사장 데모 모드"보다는 "개발용 자동 대국 스크립트"에 가깝다.

- `players`, `sdk._players` 같은 내부 맵을 직접 수정한다.
- 자동 데모 시작 시 버튼 텍스트나 상시 배너가 함께 갱신되지 않는다.
- 실플레이어 입장 시 데모를 자연스럽게 중단하고 로비를 복원하는 정책이 없다.
- QR 블러 처리 대상이 DOM 구조에 강하게 결합돼 있어 레이아웃 변경에 취약하다.

즉, 데모가 "있다"는 점은 통과지만, 프로젝트 요구사항인 운영 친화적 데모 모드 관점에서는 추가 설계가 필요하다.

#### 6. 문서 싱크가 어긋나 있다

현재 저장소의 `docs/games/omok.md`는 이 게임을 여전히 "솔로(로컬 AI), Socket/SDK 없음"으로 설명한다. 그러나 실제 구현은 `HostSDK`와 `MobileSDK`를 사용한 2인 멀티 게임이다. 코드와 문서의 방향이 어긋난 상태이므로, 신규 팀원이 문서만 보고 이해하면 잘못된 전제를 가질 가능성이 높다.

### 1.3 종합 평가

| 항목 | 평가 | 코멘트 |
| --- | --- | --- |
| 코어 플레이 적합성 | 높음 | 공유 화면 전략 대결이라는 플랫폼 방향과 잘 맞는다. |
| 첫 판 이해도 | 높음 | 규칙은 단순하다. 다만 룰 세트 명시는 더 필요하다. |
| 관전자 재미 | 중 | 지금도 읽히지만, 연출과 템포 장치가 약하다. |
| 코드 구조 건전성 | 중상 | 호스트 권위 구조는 좋지만 모바일 패턴 일관성과 로비/데모 품질이 약하다. |
| 구현 완성도 | 중 | 기본 루프는 보이지만 결과 화면 버그와 로비/재접속 갭이 남아 있다. |
| 운영 친화성 | 중하 | 데모 모드는 있으나 자동 데모, 중단 UX, 상태 정리가 미완이다. |

한 줄로 정리하면 현재 `omok`은 **플랫폼 적합한 전략 게임의 뼈대는 잘 세워졌지만, 로비 품질·결과 피드백·데모 운영성에서 아직 마감이 덜 된 상태**다.

## 2. [대중성 강화 요소]

### 제안 1. 착수 손맛 패키지

현재 모바일은 셀 선택과 착수 버튼 구조가 명확하지만, "내가 방금 중요한 수를 뒀다"는 감각은 약하다. 대중성 강화의 첫 번째 포인트는 **착수 순간의 감정 보상**을 키우는 것이다.

구체 제안:

- 모바일에서 좌표 선택 시 선택 셀에 짧은 파동 애니메이션과 가벼운 햅틱 추가
- `착수하기` 버튼 누름 직후 버튼 압축/복귀 애니메이션과 짧은 사운드 큐 추가
- 호스트에서 돌이 놓일 때 마지막 수 링 펄스, 상대 턴 전환 사운드, 근접 승리 시 경고 톤 추가
- 승리 시 결과 패널에 승자 돌 색상 기반 글로우와 보드 전체 디밍 연출 추가

효과:

- 초보자도 "입력했다"는 확신을 즉시 느낀다.
- 관전자는 현재 무슨 일이 일어났는지 더 빨리 이해한다.
- 조용한 전략 게임이더라도 TV 앞 분위기가 덜 밋밋해진다.

### 제안 2. 템포 부스트 패키지

오목은 생각 시간이 길어질수록 현장 몰입이 급격히 떨어질 수 있다. 공용 화면 게임에서는 실력보다도 **템포 유지**가 중요하다. 따라서 캐주얼 흥행을 위해서는 턴 리듬을 설계해야 한다.

구체 제안:

- 기본 모드에 턴 타이머(예: 12초 또는 15초) 도입
- 타이머 3초 이하에서 모바일과 호스트에 경고 색상 전환 및 짧은 진동 제공
- 연속 장고 방지를 위한 "자동 패스/랜덤 착수" 대신, 시간 초과 시 패배 또는 경고 누적 같은 명확한 규칙 선택
- 로비에서 `퀵 매치(빠른 턴)`와 `클래식 매치(여유 턴)` 2개 프리셋 제공
- 4목 완성 직전에는 해당 라인 주변 셀을 미세하게 강조하여 관전자도 위기 상황을 읽게 만들기

효과:

- 한 판 길이가 안정되어 행사 운영이 쉬워진다.
- 긴 침묵 구간이 줄고 긴장감이 꾸준히 유지된다.
- 실력 차가 있더라도 판이 늘어지지 않아 재도전률이 높아진다.

### 제안 3. 초심자 온보딩 및 룰 명료화

오목은 대중적인 게임이지만, 막상 행사장에서 처음 플레이하는 사람은 "금수 있나?", "5개 넘게 이어도 되나?", "모바일에서 어디를 누르면 되는가?" 같은 질문을 한다. 현재는 이 부분이 텍스트 몇 줄 수준이라, 더 직관적인 온보딩이 필요하다.

구체 제안:

- 로비 설명을 "1. 좌표 선택 2. 착수 버튼 3. 5개 먼저 연결"의 3단계 카드형 안내로 재구성
- 현재 룰 세트를 명시: 예) `캐주얼 오목 - 장목 허용 / 금수 없음`
- 모바일 첫 턴 전에 1회성 미니 튜토리얼 오버레이 제공
- 모바일 보드에 좌표 라벨(A-M, 1-13) 토글 옵션 제공
- 결과 화면에 "방금 승리한 라인"을 간단히 표시해 복기 가능하게 만들기

효과:

- 첫 판 진입 장벽이 낮아진다.
- 숙련자와 초심자 모두 룰 혼선을 덜 겪는다.
- 플레이 후 "왜 졌는지"가 더 쉽게 이해돼 리매치 전환이 빨라진다.

## 3. [가상 전문가 회의록 (Decision Making Meeting)]

### 3.1 회의 목적

`omok`의 현재 코어를 유지하되, 대중성 강화 요소 3가지의 적용 타당성과 우선순위를 검토한다. 동시에 코드베이스가 해당 개선을 안전하게 수용할 수 있는지 논의한다.

### 3.2 7인 가상 전문가 발언 요약

| 전문가 | 핵심 발언 | 판단 |
| --- | --- | --- |
| PMOrchestrator | 지금 단계의 병목은 규칙 부족이 아니라 체감 품질 부족이다. 먼저 결과 버그와 로비/데모 운영성을 정리한 뒤 대중성 요소를 얹어야 한다. | 구조 안정화 선행 |

### 3.3 쟁점 토론

#### 쟁점 A. 정통 오목 룰 확장이 우선인가, 캐주얼 마감이 우선인가

회의 다수는 **캐주얼 마감 우선** 의견을 냈다.

- 현재 플랫폼은 행사형/체험형에 가깝다.
- 금수, 장목, 스왑 규칙까지 늘리면 설명량이 급증한다.
- 지금 부족한 것은 룰 깊이보다 "보는 맛"과 "기다리지 않는 템포"다.

결론: 정통 룰 확장은 장기 과제로 두고, 단기적으로는 현재 룰 세트를 명확히 선언하는 방향이 타당하다.

#### 쟁점 B. 가장 먼저 넣어야 할 대중성 요소는 무엇인가

가장 많은 지지를 받은 것은 **제안 1. 착수 손맛 패키지**였다.

- 구현 비용 대비 체감 향상 폭이 크다.
- 기존 메시지 구조를 거의 바꾸지 않아도 된다.
- 전략 게임 특유의 정적 화면을 깨는 데 즉효가 있다.

#### 쟁점 C. 턴 타이머는 너무 빡빡하지 않은가

`KidsBoardGameExpert`와 `OnlineGameProducer` 의견이 갈렸지만, 최종적으로는 **프리셋 방식**으로 합의됐다.

- 초보자 체험 환경에서는 `클래식 매치`
- 행사 회전율이 중요한 환경에서는 `퀵 매치`

즉, 강제 단일 규칙보다 운영자가 선택 가능한 템포 옵션이 더 적절하다는 결론이다.

### 3.4 최종 의사결정

| 안건 | 결정 | 우선순위 | 이유 |
| --- | --- | --- | --- |
| 모바일 결과 화면 버그 수정 | 채택 | P0 | 현재는 게임 종료 피드백이 깨질 가능성이 높아 가장 먼저 고쳐야 한다. |
| 로비 상태/재접속 동기화 보강 | 채택 | P0 | 준비 상태 혼선과 로비 복구 불안정은 실플레이 품질을 직접 해친다. |
| 데모 시뮬레이터 수명주기 정리 | 채택 | P0 | 운영형 Attract Mode 요구사항을 충족하려면 내부 상태 직접 수정 구조를 정리해야 한다. |
| 제안 1. 착수 손맛 패키지 | 채택 | P0 | 가장 작은 비용으로 대중 체감 품질을 크게 올릴 수 있다. |
| 제안 2. 템포 부스트 패키지 | 채택 | P1 | 흥행 효과가 크지만, 우선 기본 안정화 뒤 붙이는 편이 안전하다. |
| 제안 3. 초심자 온보딩 및 룰 명료화 | 채택 | P0 | 첫 판 이탈을 줄이는 핵심 장치다. |
| 정통 오목 규칙 확장 | 보류 | P2 | 깊이는 늘지만 대중성 병목을 즉시 해결하지는 않는다. |

### 3.5 회의 결론

`omok`은 코어 플레이를 갈아엎을 필요가 없다. 대신 **결과 화면 안정화, 로비/재접속 정리, 데모 운영성 보강**을 먼저 끝내고, 그 위에 **착수 손맛 + 초심자 온보딩 + 템포 옵션**을 얹는 것이 가장 현실적이고 효과적인 개선 순서라는 데 의견이 모였다.

### 4.3 수정 방향

실제 보강은 아래 순서로 진행하는 것이 가장 안전하다.

1. **P0 안정화**
   - 모바일 결과 화면 ID 불일치를 수정해 `gameFinished` 흐름을 먼저 복구한다.
   - 로비에서 참가자 렌더링과 준비 상태 표시를 일관되게 맞춘다.
   - 로비 재접속 시 `lobbyState` 성격의 동기화 패킷을 추가해 준비 여부와 대기 문구를 복원한다.

2. **패턴 정리**
   - 모바일을 `MobileBaseGame` 상속 구조로 옮겨 `showScreen()`, `onJoin()`, `onRejoin()`, `onReset()` 책임을 표준화한다.
   - 호스트도 데모 UI 상태 변경을 `OmokGame` 내부 메서드로 묶어 버튼 텍스트와 배너를 단일 진실 원천으로 관리한다.

3. **연출/흥행 보강**
   - 착수 손맛, 승리 연출, 턴 타이머, 온보딩 카드를 추가한다.
   - 이 단계에서야 비로소 관전자용 콜아웃과 사운드 큐를 붙이는 편이 안전하다.

### 4.4 `DemoSimulator.js` 개선점 및 수정 가이드라인

현재 `DemoSimulator.js`는 기본 동작은 하지만, 운영형 Attract Mode 품질을 위해 아래 보강이 필요하다.

#### 개선점 1. 데모 상태 전환 책임을 `OmokGame`으로 끌어올릴 것

현재는 `DemoSimulator`가 `game._isDemo`, `game._blackPlayer`, `game._whitePlayer` 등을 직접 만진다. 이는 결합도가 높다. 이상적인 구조는 아래와 같다.

- `OmokGame.setDemoMode(enabled)`
- `OmokGame.beginDemoMatch(botProfiles)`
- `OmokGame.endDemoMatch({ resetToLobby: true })`
- `DemoSimulator`는 "언제 시작/언제 수를 둘지"만 결정

이렇게 해야 버튼 텍스트, 배너, phase 전환, 플레이어 정리를 한 곳에서 통제할 수 있다.

#### 개선점 2. `sdk._players` 직접 수정 제거

지금 방식은 `DemoSimulator`가 SDK 내부 맵을 직접 바꾼다. 이는 외부 구현 변경에 취약하다. 호스트 데모는 네트워크 세션 참여자가 아니므로, 아래 둘 중 하나로 바꾸는 편이 좋다.

- 데모 전용 플레이어 배열을 `OmokGame` 내부에서만 관리
- 또는 HostBaseGame의 공개 API 수준에서만 렌더링 보조 상태를 주입

핵심은 데모 봇이 **실플레이어 세션 상태와 같은 자료구조를 함부로 공유하지 않도록 하는 것**이다.

#### 개선점 3. 수동/자동 데모 UI를 완전히 동기화할 것

현재는 버튼 클릭으로 시작한 데모만 텍스트가 바뀌고, 유휴 60초 후 자동 시작된 데모는 버튼 문구가 동기화되지 않는다. 다음 항목을 반드시 맞춰야 한다.

- 로비 버튼 라벨
- 상단 또는 하단의 `데모 플레이 중` 배너
- 중단 버튼
- QR 비활성/블러 상태

사용자는 "지금이 실제 대기인지 데모 재생 중인지"를 즉시 알아야 한다.

#### 개선점 4. 실플레이어 입장 시 데모 자동 중단 규칙 추가

데모는 로비 유휴 상태를 메우기 위한 기능이므로, 실제 플레이어가 입장하면 아래 순서로 안전하게 종료해야 한다.

1. 모든 데모 타이머 해제
2. 데모 보드와 가상 플레이어 정리
3. UI를 로비 상태로 복원
4. 실제 플레이어 목록만 기준으로 로비 다시 렌더링

이 규칙이 없으면 행사 현장에서 "데모 중인데 실제 유저가 들어와 버리는" 어색한 상태가 생긴다.

#### 개선점 5. 봇 수읽기보다 "보기 좋은 대국"을 우선할 것

현재 AI는 즉시 승리/즉시 방어/휴리스틱 평가 구조라 데모용으로는 충분하다. 다만 운영 데모에서는 "너무 빨리 끝나거나", "초반이 너무 기계적으로 보이는" 문제가 생길 수 있다. 따라서 아래와 같은 연출적 제어가 유용하다.

- 첫 4수는 중앙 근처 우선
- 착수 딜레이를 `0.8초 ~ 1.4초` 범위로 랜덤화
- 가끔은 최적해 대신 준최적해 선택
- 근접 승리 직전에는 약간의 텀을 줘 관전자 인지 시간을 확보

즉, 데모 AI는 강한 AI보다 **보기 좋은 AI**가 더 중요하다.

#### 개선점 6. 테스트 훅을 추가할 것

향후 브라우저 자동화나 수동 QA를 쉽게 하려면 아래 인터페이스를 두는 것이 좋다.

- `isDemoActive`
- `getDemoStateSnapshot()`
- `forceDemoMove()`
- `clearDemoTimeouts()`

이런 훅이 있으면 데모 시작 여부, 보드 초기화, 자동 재시작 여부를 더 쉽게 검증할 수 있다.
