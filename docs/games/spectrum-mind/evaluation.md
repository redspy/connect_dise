# 스펙트럼 마인드 평가 및 개선안

- 작성일: 2026-07-07
- 분석 대상: `games/spectrum-mind/host/`, `games/spectrum-mind/mobile/`
- 검토 범위: `main.js`, `index.html`, `style.css`, `DemoSimulator.js`, `tests/spectrum-mind/demo.spec.js`
- 검증 메모: `npm run build`는 성공했다. 반면 현재 샌드박스 환경에서는 `npm run dev` 실행 시 `0.0.0.0:3000`, `0.0.0.0:5173` 포트 바인딩이 `EPERM`으로 차단되어 실기반 Playwright E2E는 실행하지 못했다.

## 1. 게임 평가

### 1.1 게임의 코어 플레이 방식 및 재미 요소 분석

`스펙트럼 마인드`는 본질적으로 "양극단 사이의 미묘한 위치를 말 한마디로 맞춘다"는 심리 파티 게임이다. 출제자는 비밀 목표 각도와 개념 카드의 양끝을 보고, 추측자는 제시어만 보고 다이얼을 조정한다. 공용 화면은 긴장감을 만들고, 개인 모바일은 비대칭 정보와 조작 책임을 가져가는 구조라서 이 플랫폼의 장점을 잘 활용하는 편이다.

이 게임의 가장 큰 강점은 규칙 설명이 짧고, 첫 라운드 진입이 빠르며, 결과 공개의 긴장감이 즉시 보상으로 이어진다는 점이다. 호스트 화면의 반원형 다이얼, 모바일의 회전 휠, 공개 시 웨지 영역 노출은 모두 "감으로 맞춘다"는 코어 판타지를 잘 시각화한다. 특히 출제자가 숫자 각도와 웨지 폭을 보고 단어를 고르고, 추측자가 그 단어를 해석해 위치를 찍는 과정은 같은 단어를 두고도 서로 다른 감각을 드러내게 만들어 웃음 포인트가 생긴다.

재미 포인트는 다음 세 가지로 요약된다.

- 공감대 테스트: 같은 단어를 얼마나 비슷한 감각으로 해석하는지 즉시 드러난다.
- 구경 재미: TV에서 바늘이 움직이고, 공개 순간 정답 웨지가 열리며 모두가 함께 결과를 본다.
- 라운드당 몰입 밀도: 준비 시간이 짧고, 한 라운드의 입력과 결과가 명확해 템포가 좋다.

다만 현재 구현은 게임성 포텐셜에 비해 실제 멀티플레이 파티성 구현이 덜 다듬어져 있다. 코드상 등록 정보는 `minPlayers: 2`, `maxPlayers: 8`로 열려 있지만 `games/registry.js` 기준 실제 라운드 운영은 그렇게 확장 가능하게 설계되어 있지 않다. 현재 라운드 수는 3으로 고정되어 있고(`games/spectrum-mind/host/main.js`), 4인 이상에서는 누군가는 출제자 또는 핵심 추측자 역할을 충분히 수행하지 못한다. 즉, 아이디어 자체는 대중성이 높지만, 현재 규칙 운영은 2~3인 플레이에 더 가까운 완성도를 보인다.

종합하면 코어 아이디어와 화면 언어는 좋다. 그러나 멀티플레이 운영 규칙, 상태 동기화, 역할 가시성이 아직 파티 게임 수준으로 안정화되지 않아 "재미의 잠재력은 높고, 서비스 준비도는 중간 이하"라고 평가하는 편이 정확하다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

#### 총평

- 기획 적합성: 높음
- 시각 연출 완성도: 중상
- 상태 동기화 완성도: 낮음
- 재접속/복구 안정성: 낮음
- 데모 운영 완성도: 중하

#### 잘 된 점

- 호스트는 `HostBaseGame`을 상속해 페이즈 전환과 로비 연동을 비교적 깔끔하게 사용하고 있다.
- 호스트/모바일 CSS 모두 `.hidden`을 정의했고, 호스트 메인 컨테이너도 `position: relative; z-index: 10;`을 명시해 공통 규칙을 잘 지켰다.
- 모바일은 휠 조작만 강제하지 않고 슬라이더를 병행 제공해 접근성을 높였다.
- `DemoSimulator.js`와 Playwright 스펙 파일이 이미 존재해, 적어도 "데모 모드와 검증 자동화의 필요성"은 인지하고 있는 구조다.

#### 아키텍처 강점

| 항목 | 평가 | 근거 |
| --- | --- | --- |
| 호스트 페이즈 구조 | 양호 | `clue`, `guess`, `lobby`, `result`로 역할이 선명하고 TV 오버레이 구조가 단순하다. |
| 캔버스 기반 다이얼 연출 | 양호 | 점수 웨지, 비밀 목표선, 활성 바늘이 한 화면에서 설명된다. |
| 모바일 조작 UX | 양호 | 휠 + 슬라이더 + 햅틱 피드백 조합은 초심자 대응력이 있다. |
| 공통 스타일 규칙 준수 | 양호 | `.hidden` 유지, 호스트 z-index 규칙 준수, 모바일 안전영역 패딩 반영이 확인된다. |

#### 구조적 약점과 완성도 이슈

1. 활성 추측자 개념이 설계와 구현에서 분리되어 있다.

호스트는 `activeGuesserId`를 추측자들에게 보내지만 실제 모바일은 이 값을 사용하지 않는다. 모바일 `roleAssign` 처리에서는 `activeGuesserId`를 받지 않고, `clueSubmitted` 이후에는 `isActiveGuesser = true`를 모든 추측자에게 일괄 적용한다. 결과적으로 여러 명이 동시에 조작할 수 있다고 인식하지만, 호스트는 실제로는 `this._activeGuesser.id`만 허용한다. 사용자는 "내 입력이 왜 먹히지 않지?"라는 혼란을 겪게 된다.

2. 추측자 화면의 개념 카드 동기화가 잘못되어 있다.

호스트는 추측자에게도 `concept`를 보내지만, 모바일은 추측자 분기에서 이를 저장하지 않는다. 이후 `clueSubmitted` 시점에 추측자 화면의 좌우 개념을 `giverConceptLeft/Right`에서 복사하는데, 이 값은 출제자 화면용 DOM이며 추측자 기기에서는 해당 라운드 값으로 갱신된 적이 없다. 즉, 추측자 화면에 기본값이 노출될 가능성이 높고, 이는 게임의 핵심 규칙을 직접 훼손하는 치명적 결함이다.

3. 점수 규칙이 "한 명의 추측자" 구조와 맞지 않는다.

현재 점수 정산은 출제자를 제외한 모든 플레이어에게 동일 점수를 더한다. 하지만 UI와 메시지 구조는 한 명의 활성 추측자를 전제한다. 3인 이상에서 비활성 추측자까지 점수를 받게 되면 경쟁 규칙이 흐려지고, 플레이 동기가 왜곡된다.

4. 재접속 복구가 로비와 결과 공개 상태를 커버하지 못한다.

호스트 `onPlayerRejoin`은 게임이 비활성 상태면 즉시 반환한다. 즉, 로비나 로딩 단계에서 재접속한 모바일에게 상태 동기화 패킷을 주지 않는다. 또한 결과 공개가 사실상 `guess` 페이즈 내부 UI 토글로 처리되기 때문에, 해당 순간 재접속한 플레이어는 `guessResolved` 상태를 복구받지 못하고 중간 화면으로 떨어질 가능성이 높다. 프로젝트 공통 규칙의 "로비 재연결 프리징 가드"를 충족하지 못하는 구현이다.

5. `maxPlayers: 8`과 실제 라운드 구조가 불일치한다.

게임 등록 정보는 8인까지 허용하지만, 라운드 수는 3으로 고정이고 출제자/활성 추측자 순환도 그에 맞춰 단순 순번만 돈다. 4인 이상에서는 공평한 차례 분배가 불가능하다. 현재 규칙은 사실상 2~3인을 기준으로 설계된 것으로 보는 편이 맞다.

6. 데모 시뮬레이터가 플랫폼 계층과 너무 강하게 결합되어 있다.

`DemoSimulator.js`는 `game.players`, `game.sdk._players`, `game._playerNicknames` 같은 내부 구조를 직접 수정한다. 이 방식은 빠르지만, 실제 세션 흐름을 재현하지 못하고 유지보수 리스크도 크다. 더 큰 문제는 데모 중지 시 플레이어 맵을 통째로 `clear()`하기 때문에, 실사용 중 사람이 붙어 있는 방에서 데모를 잘못 실행하면 실제 세션 상태까지 깨질 수 있다는 점이다.

7. 테스트 자산은 있으나 검증 범위가 얕다.

기존 Playwright 스펙은 호스트에서 데모 버튼을 누르고, 힌트 노출과 다음 라운드 버튼까지만 확인한다. 즉 "가상 봇 데모의 해피 패스"만 검증하며, 실제 핵심인 모바일 역할 배분, 재접속 복구, 다인 플레이 충돌, 점수 공정성은 전혀 검증하지 않는다.

#### 구현 완성도 결론

현재 `스펙트럼 마인드`는 "보이는 데모는 꽤 그럴듯하지만, 실제 멀티플레이 정합성은 아직 불안정한 상태"다. TV와 모바일의 비대칭 연출은 매력적이지만, 역할 동기화와 규칙 공정성 문제를 그대로 둔 채로 대중적 공개에 들어가면 첫 인상은 좋아도 반복 플레이에서 빠르게 신뢰를 잃을 가능성이 높다.

## 2. 대중성 강화 요소

### 제안 1. 결과 공개 마이크로 애니메이션 패키지

현재 결과 공개는 정답 웨지와 점수 배지만 보여준다. 이것만으로는 "맞췄다"는 손맛이 다소 얇다. 대중성 강화를 위해서는 결과 순간을 더 강하게 연출해야 한다.

- 호스트: 정답선이 스윕되며 열리고, 바늘이 최종 위치에서 짧게 튕긴 뒤 점수 배지가 팝업되도록 한다.
- 모바일: `guessResolved` 수신 시 배경 컬러 플래시, 점수 숫자 카운트업, 햅틱 패턴 차등화로 감정 곡선을 만든다.
- 효과: 관전자도 "이번 라운드가 끝났다"는 감각을 즉시 이해하고, SNS형 짧은 영상 클립에서도 장면 임팩트가 생긴다.

### 제안 2. 사운드 및 조작 피드백 레이어 강화

현재 모바일에는 진동 피드백이 일부 있지만, 역할별 피드백과 라운드 전환 피드백은 약하다. 파티 게임은 규칙을 글로 이해시키기보다 소리와 촉감으로 학습시키는 편이 훨씬 강하다.

- 출제자 힌트 전송 시 짧은 "lock-in" 사운드와 버튼 리플 효과를 준다.
- 활성 추측자에게만 "네 차례" 오디오/햅틱을 주고, 비활성 추측자에게는 "관전 중" 상태 뱃지와 잔잔한 펄스 애니메이션을 준다.
- 10도 단위 햅틱 외에도 4점/3점/2점 권역 접근 시 미세한 톤 변화 또는 틱음을 추가해 조작 손맛을 강화한다.
- 효과: 단순 회전 입력이 장난감 같은 감각을 얻고, 처음 해보는 사람도 조작 상태를 직관적으로 이해한다.

### 제안 3. 규칙 간소화와 관전자 참여 구조 재설계

대중성 측면에서 가장 중요한 부분이다. 현재 코드는 "한 명의 활성 추측자"와 "여러 추측자 동시 접속" 사이에서 규칙이 흔들린다. 이를 명확히 정리해야 한다.

- 선택지 A: 완전 협동형으로 바꿔 모든 비출제자가 공동 점수를 받게 하고, 모바일도 공동 조작 혹은 다수결 투표형으로 전환한다.
- 선택지 B: 완전 경쟁형으로 바꿔 오직 한 명만 활성 추측자로 표시하고, 나머지는 사이드 예측 또는 응원 역할만 수행하게 한다.
- 추가 보강: 2인, 3인, 4인 이상에서 라운드 수를 동적으로 계산하고, 각 인원이 최소 1회 이상 출제자/핵심 추측자를 수행하도록 차례표를 재구성한다.
- 효과: 규칙 설명이 짧아지고, 억울한 점수 분배나 대기 피로가 줄어 반복 플레이 의지가 올라간다.

## 3. 가상 전문가 회의록 (Decision Making Meeting)

### 회의 목적

`스펙트럼 마인드`의 대중성 강화 요소 3가지가 실제로 적용 가치가 있는지, 그리고 무엇을 먼저 반영해야 하는지를 7인 가상 전문가 관점으로 검토한다.

### 참석자별 발언 요약

**PMOrchestrator**

게임의 콘셉트는 이미 시장성이 있다. 문제는 "재밌는 아이디어"가 "누구나 바로 이해하고, 한 판 더 하자고 말하는 제품"으로 아직 전환되지 않았다는 점이다. 이번 결정은 연출 미세개선보다 규칙 명료화와 상태 동기화 안정화에 우선순위를 둬야 한다.

**GameScout**

이 장르는 Wavelength 류의 파티 게임 문법을 잘 가져왔다. 흥행 포인트는 사람들이 결과를 보는 순간의 폭발력인데, 현재는 연출보다 시스템 혼선이 더 크게 느껴진다. 개념 카드 풀을 늘리고 결과 공개의 드라마를 강화하면 대중성은 충분히 올라갈 수 있다.

**KidsBoardGameExpert**

아동 및 가족 플레이 기준으로 보면 현재 규칙 문장은 간단하지만 실제 조작 책임이 불명확하다. "누가 지금 움직여야 하는가"가 한눈에 안 보이면 아이들은 바로 이탈한다. 규칙 간소화와 활성 플레이어 표시 강화는 필수다.

**OnlineGameProducer**

파티 게임의 핵심은 대기 시간을 지루하지 않게 만드는 것이다. 지금 구조는 비활성 추측자가 사실상 화면만 바라보는 시간이 생긴다. 경쟁형을 유지한다면 관전 참여 기능이 필요하고, 협동형을 택한다면 공동 승리 구조를 더욱 명확히 해야 한다.

**UIUXDesigner**

호스트와 모바일의 기본 비주얼은 이미 괜찮다. 다만 결과 공개 순간과 내 턴 피드백이 얇아서 장면 기억력이 떨어진다. 마이크로 애니메이션과 사운드, 활성 플레이어 시각 신호만 잘 넣어도 체감 품질이 크게 올라갈 것이다.

**TechAnalyst**

연출 추가 자체는 저위험이지만, 현재 상태 동기화 결함을 먼저 정리하지 않으면 연출이 버그를 더 눈에 띄게 만들 수 있다. 특히 `activeGuesserId`, `concept`, `guessResolved` 복구, 라운드 수 계산은 우선적으로 정리해야 한다. 데모 시뮬레이터도 실제 메시지 흐름을 재현하도록 리팩터링해야 한다.

**SeniorGameDev**

우선순위는 명확하다. 첫째, 룰 구조와 상태 머신을 정리한다. 둘째, 모바일을 `MobileBaseGame` 패턴으로 옮겨 재접속/화면 전환을 표준화한다. 셋째, 그 위에 연출 패키지를 올린다. 지금 상태에서 사운드나 애니메이션만 추가하는 것은 겉만 꾸미는 대응이다.

### 토론 결과

| 안건 | 논의 결과 | 최종 결정 |
| --- | --- | --- |
| 결과 공개 마이크로 애니메이션 | 효과 대비 구현 비용이 낮고, 관전자 몰입도를 즉시 높인다. | 반영 |
| 사운드/촉각/조작 피드백 | 모바일 체감 품질과 초보자 학습 속도를 크게 개선한다. | 반영 |
| 규칙 간소화 및 관전자 구조 재설계 | 가장 큰 효과가 있으나 코드 수정 범위도 가장 크다. 그래도 선행 과제로 필요하다. | 최우선 반영 |

### 최종 의사결정

회의 결론은 다음과 같다.

1. 가장 먼저 할 일은 연출이 아니라 규칙과 상태 동기화의 일치다.
2. 그 다음 레이어로 결과 공개 애니메이션과 사운드/햅틱을 얹는다.
3. 데모 시뮬레이터는 "보여주기용 자동 재생"을 넘어서, 실제 멀티플레이 상태 머신을 검증하는 개발 도구로 승격해야 한다.

즉, 이번 게임은 "연출 보강형 유지보수"가 아니라 "규칙 명확화 + 체감 품질 상승" 패키지로 접근해야 한다.

## 4. 테스트 결과 및 수정 방향

### 4.1 현재 테스트 결과

#### 실제 실행 확인 결과

- `npm run build`: 성공
- `npm run dev`: 실패
- 실패 사유: 현재 작업 환경에서 로컬 서버 포트 오픈이 차단되어 `0.0.0.0:3000`, `0.0.0.0:5173` 바인딩이 `EPERM`으로 거부됨
- 따라서 `tests/spectrum-mind/demo.spec.js`의 실주행 검증은 이번 세션에서 수행하지 못함

#### 정적 분석 기준으로 확인된 핵심 리스크

- 추측자에게 전달된 `concept`가 추측 화면에 정상 반영되지 않는다.
- `activeGuesserId`가 모바일에서 사용되지 않아 활성 플레이어 UX와 실제 판정이 불일치한다.
- 점수가 출제자를 제외한 전원에게 배분되어, 경쟁 규칙과 점수판 의미가 충돌한다.
- 로비 재접속 및 결과 공개 중 재접속 복구가 불완전하다.
- 데모 모드는 존재하지만 실제 세션 라이프사이클을 충실히 시뮬레이션하지 않는다.

### 4.3 수정 방향

우선순위는 다음 순서가 적절하다.

1. 역할 상태와 점수 규칙을 먼저 정리한다.
2. 재접속 복구와 라운드 공정성을 정리한다.
3. 데모 시뮬레이터를 실제 메시지 흐름 기반으로 리팩터링한다.
4. 마지막으로 연출, 사운드, 마이크로 피드백을 추가한다.

### 4.4 🤖 데모 시뮬레이터(DemoSimulator.js) 개선점 및 수정 가이드라인

현재 데모 시뮬레이터는 "보여주기"는 가능하지만 "검증 가능한 시뮬레이션"으로 보기에는 부족하다. 다음 방향으로 수정하는 것이 바람직하다.

#### 개선점

- 실제 플레이어 데이터 구조를 직접 `clear()`하거나 내부 맵을 직접 수정하는 방식은 위험하다.
- 봇 입장, 준비 완료, 역할 배분, 힌트 제출, 추측, 결과 공개, 다음 라운드, 종료 복구가 모두 실제 게임 메시지 흐름과 동일해야 한다.
- 데모 실행 중임을 명확히 보여주는 상단 배너 또는 오버레이가 필요하다.
- 데모 시작 시 실제 사람이 이미 방에 있는 경우를 명시적으로 차단하거나, 스냅샷 후 복원하는 안전장치가 필요하다.
- 테스트 재현성을 위해 각도, 개념 카드, 힌트 문구를 시드 기반 또는 시나리오 프리셋 기반으로 재생할 수 있어야 한다.

#### 수정 가이드라인

1. 데모 시작 전 현재 세션 상태를 스냅샷한다.  
   플레이어 목록, 닉네임 맵, 준비 상태, 현재 페이즈를 저장해 두고 종료 시 복원한다.

2. 봇을 내부 맵에 직접 꽂지 말고 "가상 세션 어댑터"를 둔다.  
   가능하면 실제 `onPlayerJoin`, `readyUpdate`, `allReady` 흐름을 통과하도록 하여 데모가 상태 머신 검증 역할도 하게 만든다.

3. 데모용 상태 배너를 추가한다.  
   예: `DEMO PLAY RUNNING`, 현재 라운드, 현재 역할, 중단 버튼. 호스트 로비/게임 화면 어디에서든 즉시 인지 가능해야 한다.

4. 시뮬레이션을 단계형 시나리오로 분리한다.  
   `simulateLobby()`, `simulateCluePhase()`, `simulateGuessPhase()`, `simulateRevealPhase()`, `simulateCleanup()`처럼 쪼개면 유지보수와 테스트 작성이 쉬워진다.

5. 휴먼 플레이어 혼입 방지 로직을 추가한다.  
   실제 플레이어가 1명이라도 있으면 데모 시작을 막거나, 명시적 확인 단계를 두어 세션 파괴를 예방한다.

6. `stopDemo()`는 항상 원상복구를 보장해야 한다.  
   타이머 정리 후 상태 스냅샷을 복원하고, `onReset()`과 로비 UI를 일관되게 재호출해야 한다.

7. Playwright 검증 포인트를 데모 구조와 맞춰 확장한다.  
   현재처럼 "다음 라운드 버튼이 보였다" 수준이 아니라, 봇 준비 완료, 역할 배분, 각도 이동, 점수 반영, 종료 복귀까지 모두 단언해야 한다.

### 4.5 최종 판단

`스펙트럼 마인드`는 콘셉트 선택이 좋고 화면 연출도 기본 이상이다. 다만 지금 상태는 "대중성이 없는 게임"이 아니라 "대중성이 있는데 구현 정합성이 아직 그 잠재력을 따라오지 못한 게임"에 가깝다. 먼저 역할/점수/재접속/라운드 공정성을 바로잡고, 그 위에 결과 공개 연출과 피드백 레이어를 얹으면 플랫폼 대표 파티 게임 후보로 충분히 성장할 수 있다.
