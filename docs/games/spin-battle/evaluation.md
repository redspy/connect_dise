# 팽이 배틀(`spin-battle`) 평가 및 개선안

- 작성일: 2026-07-06
- 분석 범위: `games/spin-battle/host/`, `games/spin-battle/mobile/`, `games/spin-battle/host/SpinDemoSimulator.js`
- 검증 방식: 정적 코드 분석 + `npm run build` 빌드 확인
- 전제: 브라우저 실기기 E2E, 센서 감도, 반응성, 햅틱/오디오 체감은 별도 수동 검증이 필요함

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`spin-battle`의 코어 루프는 매우 직관적이다.

1. 모바일로 입장해 준비한다.
2. 런칭 구간에서 폰을 흔들어 RPM을 충전한다.
3. 배틀 구간에서 폰을 기울여 팽이를 조종한다.
4. 충돌, 벽 반사, 아이템 획득을 거쳐 최후의 1인이 승리한다.

이 구조는 공용 스크린과 개인 모바일을 함께 쓰는 플랫폼 성격에 잘 맞는다. 특히 아래 요소가 즉각적인 재미를 만든다.

| 항목 | 평가 | 근거 |
| --- | --- | --- |
| 몸을 쓰는 입력의 즉시성 | 높음 | 흔들기와 기울이기만 이해하면 바로 플레이 가능하다. |
| 공용 화면 관전 재미 | 높음 | 팽이 충돌, 튕김, 낙장 탈락이 큰 스크린에서 명확하게 보인다. |
| 짧은 경기 호흡 | 높음 | 로비 설명만 보고도 첫 판 진입이 빠르다. |
| 역전 변수 | 중상 | `energy`, `shield`, `cogs` 아이템이 짧은 경기 안에 변수를 만든다. |
| 반복 플레이 전략 깊이 | 중간 | 후반 선택지가 `중앙 복귀`, `근접 추격`, `아이템 선점`으로 빨리 수렴한다. |

재미의 본질은 "내 손으로 물리력을 만든 뒤, 모두가 같은 화면에서 충돌을 본다"는 파티성에 있다. 이 점은 이미 강하다. `SpinRenderer`가 만드는 네온 경기장과 충돌 파티클, RPM HUD는 공용 화면용 게임이라는 목적에 잘 맞는다.

다만 현재는 "첫 판 임팩트"에 비해 "둘째 판 이후의 전략 차별화"와 "상태 체감"이 약하다. 이유는 아래와 같다.

- 모바일 전투 화면의 RPM 게이지가 `battleStart` 시점 1회만 초기화되고, 전투 중 감쇠/충돌/아이템 반영값이 다시 내려오지 않는다.
- 아이템 효과는 실제 규칙상 존재하지만 모바일 플레이어 입장에서는 어떤 강화가 들어왔는지 체감이 약하다.
- 입력 안내 문구가 일관되지 않다.
  - 호스트 로비: "좌우로 흔들어"
  - 모바일 런칭: "비틀어서 런칭"
  - 실제 구현: `devicemotion` 기반 흔들기 누적

즉, 이 게임은 "눈으로 보기 좋은 난장판"은 이미 잘 만들었지만, "내가 왜 이기고 왜 졌는지"를 손에 쥐여주는 피드백 층은 아직 얇다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

#### 호스트 구조 평가

호스트는 비교적 건강한 분리 구조를 갖는다.

- `SpinGame.js`: 세션 상태, 메시지 라우팅, 게임 흐름
- `SpinPhysics.js`: 이동, 충돌, 벽 반사, 탈락, 아이템 규칙
- `SpinRenderer.js`: Three.js 장면, 광원, 파티클, HUD 연출
- `DevPanel.js`: 밸런싱과 비주얼 튜닝용 런타임 도구

이 분리는 유지보수성과 튜닝 효율이 모두 좋다. 특히 `SpinPhysics.update()`는 게임 규칙을 한 프레임 루프로 모아두어 읽기 쉽고, `DevPanel`로 물리/조명 값을 조절할 수 있어 쇼케이스와 밸런싱 양쪽에 실용적이다.

#### 모바일 구조 평가

모바일은 기능은 돌아가지만 구조적 완성도는 호스트보다 낮다.

- `mobile/main.js` 한 파일이 세션 이벤트, 센서 권한, 런칭 로직, 배틀 입력, 결과 UI를 모두 담당한다.
- 프로젝트 권장 패턴인 `MobileBaseGame` 기반 상태 머신을 쓰지 않고 직접 DOM 토글과 전역 변수(`currentPhase`, `myRpm`, `latestBeta`, `latestGamma`)에 의존한다.
- 화면이 늘어나거나 재접속 복구 요구가 커질수록 수정 난도가 급격히 올라갈 구조다.

#### 구현 완성도 총평

아래는 상품화 관점에서 본 핵심 강점과 리스크다.

| 항목 | 판정 | 평가 |
| --- | --- | --- |
| 코어 플레이 원형 | 강함 | 몸을 쓰는 멀티 파티게임으로 첫 인상과 관전성이 좋다. |
| 호스트 아키텍처 분리 | 강함 | `Game / Physics / Renderer / DevPanel` 분리가 선명하다. |
| 비주얼 완성도 | 강함 | Three.js 연출과 HUD 구성이 공용 화면용 콘텐츠에 적합하다. |
| 모바일 구조 일관성 | 보통 이하 | 단일 파일 집중 구조라 재접속/상태 확장에 불리하다. |
| 상태 동기화 정확성 | 취약 | 페이즈 이벤트 의미가 섞여 있어 Host/Mobile 해석이 다르다. |
| 세션 복구 안정성 | 취약 | 로비/런칭/결과/탈락 단계 재접속 복구가 비어 있다. |
| 데모 시뮬레이터 완성도 | 중하 | 존재 자체는 장점이나, 내부 결합과 생명주기 제어가 미완성이다. |

#### 핵심 구현 이슈

##### 1. `allReady` 이벤트를 모바일이 "게임 시작 신호"로 오해하고 있다

가장 큰 구조적 문제다.

- 서버의 `platform:allReady`는 "모든 플레이어가 준비를 마쳤다"는 뜻이다.
- 실제 게임 시작은 호스트가 로비의 시작 버튼을 눌러 `SpinGame._startLaunchCountdown()`을 호출할 때다.
- 그런데 모바일은 `mobile.on('allReady')`에서 즉시 런칭 화면으로 들어가 5초 동안 RPM을 모아 버린다.

즉, 호스트가 시작 버튼을 늦게 누르면 모바일은 이미 런칭을 끝내고 기다리는 상태가 된다. 이 구조는 첫 판 UX, 공정성, 페이즈 이해도 모두에 악영향을 준다.

##### 2. `battleStart`가 실제 배틀 시작이 아니라 "배틀 준비"에 가깝다

호스트는 `SpinGame._startBattle()`에서 `battleStart`를 브로드캐스트한 뒤, 다시 3초 카운트다운을 거쳐 `battle` 페이즈로 진입한다. 하지만 모바일은 `battleStart`를 받는 즉시 전투 화면으로 바꾸고 기울기 전송을 시작한다.

결과적으로 아래 문제가 생긴다.

- 모바일은 호스트가 아직 "3, 2, 1, GO"를 보여주는 동안 이미 전투 UI를 보고 있다.
- 재접속 플레이어가 `countdown` 중 복귀하면 즉시 배틀 화면으로 진입한다.
- 전투 개시 시점이 사용자에게 명확하지 않다.

이 문제는 단순 연출 문제가 아니라 프로토콜 의미 설계 문제다. `launchStart`, `launchEnd`, `battleCountdown`, `battleLive`처럼 메시지를 분리하는 것이 맞다.

##### 3. 재접속 복구가 사실상 `battle/countdown` 일부만 다룬다

`SpinGame.onPlayerRejoin()`은 현재 `battle` 또는 `countdown`에서만 `battleStart`를 다시 보낸다. 그 외 단계는 복구가 없다.

- `lobby`: 로비 상태 동기화 패킷 없음
- `launching`: 남은 시간, 내 충전값, 현재 화면 복구 없음
- `result`: 결과 화면 재동기화 없음
- `eliminated`: 탈락자 개별 상태 복구 없음

모바일 `rejoin` 핸들러 역시 색상 점만 다시 세팅하고 현재 화면이나 게임 상태를 복원하지 않는다. 플랫폼 규약상 요구되는 로비 재접속 프리징 가드 관점에서 완성도가 낮다.

##### 4. 타이머 정리와 중도 이탈 처리도 미완성이다

`SpinGame._startLaunchCountdown()`과 `_startBattleCountdown()`은 `setInterval`/`setTimeout` 핸들을 인스턴스 필드로 보관하지 않는다. 따라서 아래 상황에서 잔여 타이머가 늦게 발화할 위험이 있다.

- 런칭 도중 리셋
- 데모 도중 강제 종료
- 로비 복귀 직후 이전 카운트다운 콜백 지연 발화

또한 `onPlayerLeave()`는 로비 UI만 갱신하고, 배틀 중 실제 스피너 제거/탈락 처리/순위 재계산을 하지 않는다. 즉, 경기 도중 영구 이탈자가 생기면 유령 팽이가 필드에 남을 가능성이 있다.

##### 5. `SpinDemoSimulator`는 의도는 좋지만 운영 도구로는 거칠다

현재 데모 모드는 "버튼으로 봇 3명을 넣고 자동 플레이를 돌린다"는 출발점까지는 도달했다. 하지만 다음 문제가 있다.

- 파일명이 규약형 `DemoSimulator.js`가 아니라 `SpinDemoSimulator.js`다.
- `SpinGame.onPhaseChange()`는 `this._isDemo`를 보지만, 시뮬레이터는 그 값을 세우지 않는다.
- 시뮬레이터가 `game._players`, `game.sdk._players`, `game._playerNicknames`, `game.sdk._messageHandlers` 같은 내부 구현에 직접 접근한다.
- 데모 버튼은 시작만 가능하고, 프로젝트 요구사항에 있는 중단 배너/실제 유저 양도 규칙이 없다.

즉, 지금 구조는 "시연용 프로토타입" 수준이며, "플랫폼 표준 Attract Mode" 수준까지는 아직 올라오지 못했다.

## 2. [대중성 강화 요소]

### 제안 1. 실시간 타격 피드백 패키지

가장 우선해야 할 개선이다. 현재 플레이어는 전투 중 자기 RPM, 충돌 피해, 아이템 적용 상태를 손에 쥐고 느끼기 어렵다. 이 때문에 패배가 갑작스럽고 억울하게 느껴질 수 있다.

구체 제안:

- 호스트가 5Hz~10Hz 수준의 `battleState` 또는 `rpmUpdate` 패킷을 모바일에 송신
- 충돌 강도에 따라 진동 강도, 게이지 흔들림, 짧은 플래시를 계층화
- 아이템 획득 시 `에너지 충전`, `쉴드 활성`, `톱니 강화` 토스트 노출
- RPM 위험 구간에서 게이지 색상, 배경 펄스, 경고 사운드 활성화

기대 효과:

- 내가 왜 밀리고 있는지 즉시 이해 가능
- 패배 수용성이 올라가고 재대결 전환이 쉬워짐
- 짧은 경기에서도 손맛이 살아남

### 제안 2. 10초 이해형 온보딩과 페이즈 동기화 재설계

지금은 게임 룰 자체보다 "언제부터 흔들고 언제부터 조종하는지"가 더 혼란스럽다. 대중성 강화의 핵심은 규칙을 더 많이 설명하는 것이 아니라, 플레이어가 헷갈리지 않게 타이밍을 맞추는 것이다.

구체 제안:

- 프로토콜을 `allReady`와 실제 시작 이벤트로 분리
- `launchStart`, `launchTick`, `battleCountdown`, `battleLive` 메시지로 의미를 명확화
- 조작 문구를 하나로 통일
  - 예: "흔들어 RPM 충전 → 기울여 조종"
- 모바일 런칭 시작 전에 0.5~1초 중심 보정 또는 민감도 캘리브레이션 추가
- 아이템 아이콘 의미를 로비와 결과 화면에서 반복 노출

기대 효과:

- 첫 판 이탈률 감소
- 가족/지인 모임에서 설명 부담 감소
- 센서형 게임 특유의 억울함 감소

### 제안 3. 승부 감정선 강화 패키지

지금 결과 화면은 승패는 전달하지만 감정은 남기지 못한다. 파티 게임은 "누가 이겼는지, 어떻게 이겼는지, 왜 다시 한 판 해야 하는지"를 남겨야 한다.

구체 제안:

- 플레이어 닉네임 또는 별칭 입력 도입
- 호스트 결과 화면에서 `id.slice(0, 6)` 대신 닉네임/컬러 배지 사용
- 우승자 세리머니, 마지막 충돌 하이라이트, 아이템 MVP 등 짧은 결과 카드 추가
- 짧은 승리/패배 사운드와 리벤지 CTA 제공
- 브랜드 문구를 통일
  - `Top Battle`, `Spin Battle`, `팽이 배틀` 혼용 정리

기대 효과:

- 승부의 기억점이 생김
- 영상/사진 공유 시 인지도가 좋아짐
- "한 판 더"로 이어지는 감정 동력이 강해짐

### 3.3 토론 핵심

회의에서 가장 크게 합의된 점은 다음 세 가지다.

1. 현재 문제의 핵심은 "콘텐츠 부족"보다 "상태 전달 부족"이다.
2. 대중성 강화는 새로운 룰 추가보다 페이즈 정렬과 손맛 보강이 더 큰 효과를 낸다.
3. 결과 연출은 중요하지만, 그것만 먼저 붙이면 근본 문제인 이해 비용과 억울함은 해결되지 않는다.

또한 TechAnalyst와 SeniorGameDev는 공통적으로 아래 기반 보수 없이는 상위 개선이 불안정하다고 보았다.

- `allReady`와 실제 게임 시작 신호 분리
- `battleStart`를 `battlePrepare`/`battleLive`로 재설계
- `lobbyState`, `launchState`, `battleState`, `resultState` 계열의 재접속 동기화 패킷 추가
- `SpinDemoSimulator`의 비공개 내부 접근 제거

### 4.3 🤖 `DemoSimulator.js` 개선점 및 수정 가이드라인

현재 구현 파일은 `SpinDemoSimulator.js`다. 파일명 자체보다 중요한 것은 책임과 생명주기지만, 프로젝트 전체 규약과 재사용성을 생각하면 `DemoSimulator.js` 표준 진입점으로 통일하거나 최소한 alias 파일을 두는 편이 낫다.

#### 1. 데모 활성 상태를 단일 소스로 통일

현재 `SpinGame.onPhaseChange()`는 `this._isDemo`를 보지만, 시뮬레이터는 `this.isDemo`만 관리한다. 이 불일치 때문에 데모 전투 AI와 결과 후 자동 복귀가 누락될 수 있다.

가이드:

- `SpinGame`은 `this._demoSimulator?.onPhaseChange(to)`를 항상 호출하고, 내부에서 `isDemo`를 판단하게 한다.
- 또는 `startDemo()`에서 `game._isDemo = true`, `stopDemo()`에서 `game._isDemo = false`를 명시적으로 관리한다.
- 두 방식 중 하나만 남기고 중복 상태는 제거한다.

#### 2. 비공개 내부 필드 직접 접근 제거

지금 시뮬레이터는 `_players`, `_playerNicknames`, `sdk._players`, `sdk._messageHandlers`에 직접 손댄다. 이는 SDK 구조 변경에 매우 취약하다.

가이드:

- `SpinGame`에 데모 전용 공개 API를 추가한다.
- 예시:
  - `beginDemoSession(botProfiles)`
  - `endDemoSession()`
  - `injectDemoLaunch(playerId, rpm)`
  - `injectDemoTilt(playerId, tiltX, tiltZ)`
- 시뮬레이터는 오직 이 공개 API만 호출하고, 내부 `Map` 구조는 몰라도 되게 만든다.

#### 3. 모든 타이머와 인터벌을 명시적으로 정리

데모의 신뢰성은 "언제든 중단 가능하고, 중단 후 깨끗하게 복구되는가"에 달려 있다.

가이드:

- `SpinGame`에 아래 핸들을 필드로 저장한다.
  - `_launchTimeout`
  - `_launchInterval`
  - `_battleCountdownTimeout`
  - `_battleCountdownInterval`
  - `_itemSpawnTimer`
- `onReset()`, `stopDemo()`, 강제 종료, 실제 플레이어 입장 시점에 공통 정리 메서드를 호출한다.

#### 4. 실제 플레이어 입장 시 데모를 즉시 양도

프로젝트 요구사항상 데모는 실제 플레이를 방해하면 안 된다. 현재는 QR을 흐리게 만들 뿐 실제 유저 합류 정책이 없다.

가이드:

- 실제 플레이어가 1명이라도 입장하면 데모를 즉시 중단한다.
- 호스트 로비에 `데모 중단됨: 실제 플레이어 입장` 배너를 2~3초 노출한다.
- 데모 버튼은 `실행`/`중단` 토글형으로 바꾸고, 상태를 텍스트로 명확히 표시한다.

#### 5. 데모를 "시연용"이 아니라 "검증용"으로 승격

Attract Mode는 보여주기만 하는 기능이 아니라, 로비부터 결과까지의 전이를 자동 확인하는 검증 루프여야 한다.

가이드:

- 시나리오를 고정된 단계로 스크립트화한다.
  - `lobby -> ready -> launchStart -> countdown -> battle -> result -> reset`
- 단계별로 디버그 로그와 배너를 남긴다.
- 랜덤 모드와 별도로 `seed` 기반 결정론 모드를 두어 회귀 테스트에도 재사용한다.
- 재접속 복구 리허설도 포함한다.
  - `demoMode=rejoin-lobby`
  - `demoMode=rejoin-battle`
  - `demoMode=leave-midbattle`

#### 6. 모바일 동기화 프로토콜 정리 후 데모를 연결

데모 품질은 결국 실게임 프로토콜 품질 위에 서야 한다.

가이드:

- 먼저 실제 게임에서 아래 패킷을 정리한다.
  - `launchStart`
  - `launchState`
  - `battleCountdown`
  - `battleLive`
  - `battleState`
  - `resultState`
  - `lobbyState`
- 그 다음 데모는 이 패킷을 그대로 소비하거나 검증하게 한다.

### 4.4 권장 수정 방향

실제 개선 작업은 아래 순서가 가장 안전하다.

1. 페이즈 프로토콜 재설계
   - `allReady`는 시작 가능 상태로만 사용
   - 실제 시작은 `launchStart`
   - 전투 개시는 `battleLive`
2. 모바일 상태 구조 리팩터링
   - `MobileBaseGame` 기반 또는 동등한 상태 머신 구조로 전환
   - 런칭/카운트다운/전투/탈락/결과/복구를 명시 상태로 분리
3. 전투 상태 피드백 추가
   - 실시간 RPM, 버프, 위험 상태, 아이템 토스트, 햅틱 계층화
4. 재접속 및 이탈 처리 보강
   - `lobbyState`, `launchState`, `battleState`, `resultState`
   - 영구 이탈자 스피너 정리 및 순위 정책 확정
5. 결과/정체성 강화
   - 닉네임, 하이라이트 카드, 승리 세리머니, 리벤지 CTA
6. 데모 시뮬레이터 재구성
   - 공개 API 기반, 타이머 소유권 정리, 실제 유저 양도 정책 반영

최종 결론:

> `spin-battle`은 새 룰을 더 얹기보다, 지금 있는 재미를 더 정확하게 전달하는 쪽이 효과가 크다. 페이즈 의미를 바로잡고, 모바일 피드백과 데모 운영 품질을 보강하면 대중성은 상당 폭 상승할 가능성이 높다.
