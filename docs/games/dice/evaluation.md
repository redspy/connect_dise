# 주사위(`dice`) 게임 평가 및 개선안

- 작성일: 2026-07-06
- 분석 범위: `games/dice/host/main.js`, `games/dice/host/DiceDemoSimulator.js`, `games/dice/host/index.html`, `games/dice/mobile/main.js`, `games/dice/mobile/index.html`, `src/style.css`
- 분석 방식: 소스 코드 정적 분석 기반 평가. 실제 다기기 실기기 QA, 브라우저 시각 검증, 센서 민감도 실측은 본 문서 범위에 포함하지 않았다.

---

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`dice`의 현재 코어 루프는 매우 직관적이다.

1. 호스트가 세션을 생성하고 공용 화면에 QR을 띄운다.
2. 플레이어는 모바일로 입장한 뒤 센서 권한을 허용하거나, 권한이 없으면 더블탭/수동 버튼으로 폴백한다.
3. 플레이어가 폰을 강하게 휘두르거나 화면을 조작하면 호스트 화면의 3D 주사위가 굴러간다.
4. 모바일은 진동과 자기 색상 글로우로 "내 입력이 반영됐다"는 감각을 받고, 공용 화면은 큰 주사위 연출로 공간 전체의 시선을 모은다.

이 구조는 첫 체험의 임팩트가 강하다. "폰을 흔들면 TV에서 주사위가 굴러간다"는 설명이 10초 안에 끝나고, 모바일 센서 입력과 대형 스크린 결과가 즉시 연결되기 때문이다. 특히 아래 요소는 분명한 장점이다.

- 학습 비용이 매우 낮다. 룰북 없이도 시연이 가능하다.
- 공용 화면 적합성이 높다. `@3d-dice/dice-box` 기반의 대형 물리 연출이 시선 집중을 만든다.
- 모바일 손맛이 있다. 흔들기, 스윙, 더블탭, 수동 버튼, 진동이 모두 준비되어 있어 체험 실패율이 낮다.
- 색상 기반 소유감이 있다. 입장 시 부여된 플레이어 색이 모바일 주사위와 호스트 글로우에 반영된다.
- 센서 권한 거부에 대한 폴백이 있다. 이 점은 행사장 환경에서 중요하다.

반면, 지금 단계의 `dice`는 "재미있는 인터랙션"이지 "완성된 게임"이라고 보기는 어렵다. 핵심 이유는 승부 구조가 거의 비어 있기 때문이다.

- 누가 먼저 던지는지, 몇 라운드인지, 무엇을 목표로 경쟁하는지가 없다.
- 주사위 결과가 점수, 승패, 다음 선택지로 이어지지 않는다.
- 플레이어가 보내는 `strength` 값이 결과에 반영되지 않는다.
- 100ms 주기로 전송되는 `gyroData`도 호스트에서 사용되지 않는다.
- 모바일은 자신의 결과를 직접 받지 못하고, 오직 공용 화면을 봐야만 결과를 알 수 있다.
- 한 번 던진 뒤 `Retry`를 눌러야 다음 루프가 이어지므로 템포가 끊긴다.

즉, 현재 구현은 "센서를 써서 주사위를 굴리는 체험"으로는 설득력이 있지만, 여러 명이 반복해서 붙는 파티 게임 구조로는 얕다. 재미 축이 결과 경쟁이 아니라 입력 체험 자체에만 몰려 있기 때문이다.

#### 재미 요소 평가 요약

| 평가 항목 | 판단 | 코멘트 |
| --- | --- | --- |
| 즉시 이해도 | 매우 높음 | 설명 한 줄로 플레이가 시작된다. |
| 첫 체험 임팩트 | 높음 | 모바일 센서와 TV 주사위 연동이 강한 첫인상을 만든다. |
| 공용 화면 적합성 | 높음 | 같은 공간에서 함께 보는 재미가 분명하다. |
| 조작 손맛 | 중상 | 흔들기/더블탭/진동/색상 피드백이 있다. |
| 다인 경쟁성 | 낮음 | 플레이어 간 상호작용 구조가 없다. |
| 규칙 밀도 | 매우 낮음 | 라운드, 점수, 승리 조건이 없다. |
| 재플레이성 | 중하 | 몇 번 던지면 새로움이 빠르게 소진된다. |

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

현재 구현은 빠른 프로토타입으로는 효율적이지만, 플랫폼 규약과 장기 확장성 측면에서는 미완 상태가 많다.

#### 장점

- 호스트와 모바일 책임 분리가 명확하다.
  - 호스트는 3D 주사위 렌더링과 세션/QR 노출을 담당한다.
  - 모바일은 센서 입력과 현지 피드백에 집중한다.
- 파일 수가 적고 흐름이 단순해서 추적이 쉽다.
- 센서 권한 실패에 대한 폴백 입력이 준비돼 있어 실제 플레이 실패율이 낮다.
- `DiceDemoSimulator.js`가 존재하고, 60초 유휴 시 자동 데모가 시작되는 Attract Mode 의도도 반영돼 있다.
- `LevelIndicator`를 사용해 모바일 기울기 정보를 시각적으로 드러내고 있어, 단순 데모 기준으로는 입력 감각을 돕는다.

#### 구조적 약점

##### 1. 플랫폼 라이프사이클 규약 활용이 약하다

프로젝트 권장 패턴은 `HostBaseGame`/`MobileBaseGame` 기반의 `setPhase()`/`showScreen()`, `ready`, `allReady`, `reset`, `rejoin` 흐름인데 `dice`는 이를 거의 사용하지 않는다.

- 호스트는 `HostSDK`를 직접 사용한다.
- 모바일도 `MobileSDK`를 직접 사용한다.
- 모바일에서 `ready()`를 호출하지 않으므로 실제 준비 완료 루프가 없다.
- 호스트의 `"Player(s) connected and ready!"` 문구는 실제 상태와 다르다. 현재는 단순 접속자 수만 카운트한다.
- `playerRejoin`/`rejoin` 시 UI 복구나 상태 동기화 패킷이 없다.
- 로비/플레이/결과 같은 페이즈 모델이 없어 향후 룰 확장 시 상태 폭증 가능성이 높다.

##### 2. 메시지 설계와 실제 사용이 맞지 않는다

- 모바일은 `gyroData`를 100ms마다 보내지만 호스트는 전혀 소비하지 않는다.
- 모바일이 보내는 `strength`도 호스트 물리나 점수 계산에 반영되지 않는다.
- 호스트는 굴린 결과를 모바일에 되돌려주지 않는다.
- 결과적으로 네트워크 메시지와 실제 게임 가치가 분리돼 있다.

이 상태는 두 가지 문제를 만든다.

- 성능 측면: 의미 없는 스트리밍 트래픽이 지속된다.
- 설계 측면: "내가 세게 흔들면 더 세게 굴러간다"는 기대가 성립하지 않는다.

##### 3. 동시 입력 및 타이머 경쟁 상태에 취약하다

현재 호스트는 `throwDice`를 받으면 즉시 UI를 숨기고 `diceBox.roll('1d6')`을 호출한다. 하지만 다인 플레이를 위한 턴 락, 입력 큐, 라운드 상태 머신이 없다.

- 여러 플레이어가 거의 동시에 던지면 주사위 롤 호출이 겹칠 수 있다.
- `playerStatus`를 3초 뒤 복원하는 타이머가 각 투척마다 독립적으로 생겨, 뒤늦은 타이머가 최신 상태를 덮어쓸 수 있다.
- `uiRestoreTimer`는 10초 뒤 UI를 복구하지만, 연속 투척 시 체감 로직이 꼬일 가능성이 있다.

즉, 1인 또는 느린 템포 시연에는 버틸 수 있어도, 실제 여러 명이 동시에 달아오르는 파티 상황을 안정적으로 제어하는 구조는 아니다.

##### 4. UI 전환 규약과 CSS가 어긋난 부분이 있다

모바일 코드는 `instructionMain`, `instructionSub`, `manualControls`, `btnRetry`에 `.hidden`을 토글한다. 하지만 공통 `src/style.css`에는 전역 `.hidden { display: none !important; }` 규칙이 없다.

실제로 현재 존재하는 것은 아래 수준이다.

- `.center-status.hidden`
- `.qr-container.hidden`
- `.modal.hidden`

따라서 모바일의 안내 문구와 수동 컨트롤은 클래스가 붙어도 실제로 안 숨겨질 가능성이 높다. 이는 프로젝트 규약에도 어긋난다.

##### 5. 데모 시뮬레이터가 SDK 내부 구현에 결합돼 있다

`DiceDemoSimulator.js`는 `host._messageHandlers.get('throwDice')`에 직접 접근해 봇 투척을 강제 실행한다. 이 방식은 다음 문제가 있다.

- SDK 내부 구현이 바뀌면 데모가 쉽게 깨진다.
- 실제 "봇 입장 -> 준비 완료 -> 라운드 시작 -> 결과 -> 리셋"을 재현하지 못한다.
- 데모 중 실제 플레이어 입장 시 자연스럽게 양도할 장치가 없다.
- 데모 종료 시 `playerCount`를 0으로 되돌리는 방식이라, 실플레이어가 섞인 경우 상태가 꼬일 수 있다.

현재 데모는 "잘 보이는 연출"이지 "핵심 게임 루프를 검증하는 시뮬레이터"는 아니다.

##### 6. 디버그와 프로덕션 경계가 흐리다

- 호스트 화면에 `test-roll-btn`이 상시 노출된다.
- 주사위 엔진 미준비 시 1초 뒤 `2d6`를 굴리는 예외 경로가 있다. 평소 `1d6`와 규칙 일관성이 깨진다.
- 인라인 스타일이 많아 UI 리뉴얼이나 상태 분리 시 유지보수 비용이 커진다.

#### 아키텍처 평가 요약

| 평가 축 | 판단 | 코멘트 |
| --- | --- | --- |
| 프로토타입 속도 | 높음 | 파일이 적고 진입 장벽이 낮다. |
| 플랫폼 규약 준수 | 낮음 | `BaseGame`, `ready`, `rejoin`, `phase` 체계 활용이 약하다. |
| 메시지 설계 일관성 | 중하 | `gyroData`, `strength`가 실제 규칙에 연결되지 않는다. |
| 멀티플레이 안정성 | 낮음 | 동시 입력 제어와 상태 머신이 없다. |
| UI 전환 안정성 | 중하 | `.hidden` 공통 규칙 부재로 화면 전환 신뢰도가 떨어진다. |
| 데모 모드 완성도 | 중하 | Attract Mode는 있으나 검증 도구 수준은 아니다. |
| 확장성 | 낮음 | 점수전/라운드전 추가 전에 구조 재정리가 필요하다. |

#### 종합 평가

`dice`는 "호스트 대형 연출 + 모바일 센서 조작"이라는 플랫폼 특성은 잘 잡았지만, 아직 게임 시스템보다는 인터랙션 데모에 가깝다. 구조적으로는 지금 기능을 계속 덧붙이는 방식보다, 짧은 라운드형 승부 게임으로 룰을 재정의하고 상태 모델을 다시 세우는 편이 훨씬 안전하다.

## 2. [대중성 강화 요소]

대중성 강화는 "더 화려하게"보다 "왜 다시 한 판을 하게 되는가"를 먼저 해결해야 한다. 아래 세 가지를 우선 제안한다.

### 2.1 3라운드 승부 구조와 TV 점수판 도입

현재 `dice`에는 승리 조건이 없다. 가장 먼저 필요한 것은 규칙의 최소 골격이다.

권장안:

- 3라운드 또는 5라운드 고정 매치
- 라운드마다 각 플레이어 1회 투척
- 높은 눈이 승점 1점을 획득
- 동점 시 공동 승점 또는 재투척
- 최종 우승자를 호스트에서 크게 연출

왜 효과적인가:

- 룰 설명이 여전히 짧다.
- 공용 화면에서 "이번 라운드", "현재 1위", "최종 우승"이 생겨 관전 밀도가 올라간다.
- 여러 플레이어가 동시에 접속해도 질서 있는 경쟁 구조가 생긴다.
- 결과가 축적되므로 한 번의 던지기가 의미를 갖는다.

구현 포인트:

- 호스트를 authoritative state로 두고 `lobby`, `roundIntro`, `waitingThrow`, `rolling`, `roundResult`, `matchResult` 페이즈를 명시
- 모바일은 `waiting`, `myTurn`, `thrown`, `roundResult` 스크린으로 단순화
- 결과를 모바일에도 브로드캐스트해 개인 피드백 강화

### 2.2 입력 강도 연동 손맛 패키지

지금은 흔들기 자체는 재미있지만, 센서 데이터가 결과나 연출에 거의 연결되지 않는다. 이 문제를 해결해야 조작감이 게임성으로 이어진다.

권장안:

- 모바일에서 흔들기/스윙 강도를 로컬 계산
- 호스트에는 연속 `gyroData` 대신 `throwIntent` 같은 이산 이벤트 전송
- `power`, `swingType`, `tiltStability` 정도만 보내고 실제 연출에 반영
- 힘이 강할수록 호스트 카메라 쉐이크, 주사위 이펙트, 사운드 레이어, 글로우가 달라지게 설계

왜 효과적인가:

- 플레이어가 "세게 던지면 더 세게 반응한다"는 인과를 느낀다.
- 현재 존재하는 `LevelIndicator`도 단순 장식이 아니라 "안정적으로 잡고, 제대로 스윙하라"는 준비 피드백으로 의미를 얻는다.
- 불필요한 스트리밍 메시지를 줄이고 네트워크 설계도 단순해진다.

구현 포인트:

- `gyroData`를 유지할지 폐기할지 먼저 결정
- 유지한다면 결과 계산 또는 에임 연출에 반드시 연결
- 폐기한다면 모바일 로컬 계산 후 단일 투척 이벤트만 전송

### 2.3 첫 30초 온보딩 + 결과 연출 + 사운드 패키지

대중성은 깊은 시스템뿐 아니라 첫 30초의 감정 품질에서 크게 갈린다. 지금 `dice`는 연출의 방향은 맞지만, "사람들이 웃고 반응하는 포인트"를 더 압축할 필요가 있다.

권장안:

- 모바일 첫 화면에 3단계 초간단 가이드 제공
  - `1. 흔들거나 더블탭`
  - `2. TV에서 결과 확인`
  - `3. 라운드 승점을 모아 승리`
- 호스트에 라운드 시작 카운트다운, 큰 숫자 팝업, 승자 하이라이트 추가
- 주사위 착지 시 짧은 SFX, 승리 시 환호음/칩 획득음 추가
- 모바일 `Retry`는 수동 버튼 중심이 아니라 자동 복귀를 기본으로 바꾸고, 예외 상황에서만 버튼 노출

왜 효과적인가:

- 처음 보는 사람도 바로 따라온다.
- 관전자에게 지금 무슨 일이 벌어졌는지 전달이 쉬워진다.
- 결과 순간의 감정 고저가 커져 "한 판 더" 유도가 쉬워진다.

구현 포인트:

- 시각 연출은 짧고 굵게 유지
- 사운드는 300~800ms 길이의 짧은 효과 위주로 설계
- 결과 텍스트는 숫자 중심으로 단순하게 유지

#### 대중성 강화 우선순위

| 제안 | 우선순위 | 이유 |
| --- | --- | --- |
| 3라운드 승부 구조 + 점수판 | P0 | 게임으로서의 목적과 반복 동기를 만든다. |
| 입력 강도 연동 손맛 패키지 | P0 | 센서 조작의 설득력을 실제 재미로 연결한다. |
| 온보딩/결과 연출/사운드 패키지 | P1 | 구조가 정리된 뒤 붙을 때 효과가 가장 크다. |

### 3.3 주요 쟁점 정리

#### 쟁점 A. 가장 먼저 보강해야 하는 것은 연출인가, 게임 구조인가

결론은 게임 구조 우선이다. 참석자 전원이 "지금도 첫 인상은 충분히 좋다"는 점에는 동의했지만, 반복 플레이를 만드는 동력은 구조 쪽에 있다고 봤다. 따라서 연출 증설보다 라운드 구조 고정이 선행돼야 한다는 데 합의가 이뤄졌다.

#### 쟁점 B. 센서 데이터를 더 많이 쓰는 것이 좋은가

결론은 "많이"가 아니라 "의미 있게"였다.

- `gyroData`를 계속 보내되 아무 데도 쓰지 않는 것은 반대
- 입력 강도를 룰 또는 연출에 실제 반영한다면 유지 가능
- 그렇지 않다면 모바일 로컬 계산 후 `throwIntent`만 보내는 편이 낫다

즉, 센서 활용은 확대가 아니라 정제 방향으로 결정됐다.

#### 쟁점 C. 온보딩과 사운드는 후순위인가

후순위이긴 하지만 중요도는 높다. 특히 공용 화면 기반 파티 게임은 첫인상과 관전자 이해도가 곧 체류 시간을 좌우한다. 다만 구조 없는 연출은 체감 수명이 짧으므로, 라운드 구조 정착 후 같은 스프린트 내 후속 적용이 적절하다는 의견으로 정리됐다.

### 3.4 최종 의사결정

| 안건 | 결정 | 우선순위 | 반영 조건 |
| --- | --- | --- | --- |
| 3라운드 승부 구조 + 점수판 | 채택 | P0 | 라운드 상태, 순번, 승점, 결과 브로드캐스트를 호스트 권한으로 관리 |
| 입력 강도 연동 손맛 패키지 | 채택 | P0 | `strength` 또는 대체 입력값을 실제 연출/결과에 연결하고, 무의미한 스트리밍은 축소 |
| 첫 30초 온보딩 + 결과 연출 + 사운드 | 채택 | P1 | 구조 정리 후 도입, 결과 순간의 감정 피크를 강화 |

### 3.5 PMOrchestrator 최종 결론

`dice`는 연출 부족으로 아쉬운 게임이 아니다. 이미 시연성은 충분하다. 문제는 그 연출을 다시 반복하게 만들 "짧고 선명한 승부 구조"가 없다는 점이다. 따라서 다음 릴리즈의 핵심 목표는 화려함 추가가 아니라, **센서 체험을 라운드형 경쟁 게임으로 승격시키는 것**으로 확정한다.

### 4.3 🤖 데모 시뮬레이터(`DemoSimulator.js`) 개선점

현재 파일명은 `DiceDemoSimulator.js`지만, 프로젝트 운영 관점에서는 게임별 데모 시뮬레이터를 공통 규약에 맞춘 `DemoSimulator.js` 체계로 수렴시키는 편이 관리에 유리하다. 파일명 자체보다 중요한 것은 책임 범위다.

현 상태의 데모는 다음 한계를 가진다.

- 봇 입장, 준비 완료, 라운드 진행, 결과 정산, 리셋까지 재현하지 못한다.
- 내부 `_messageHandlers` 맵에 직접 접근한다.
- 실제 플레이어가 들어와도 데모를 자동 중단하지 않는다.
- 데모 종료 시 실플레이어 수와 무관하게 `playerCount`를 0으로 리셋한다.
- 검증용 시나리오보다 "굴러가는 모습을 보여주는 연출"에 가깝다.

### 4.4 데모 시뮬레이터 수정 가이드라인

#### 1. 공개 API 기반으로 재작성

데모는 SDK 내부 자료구조를 건드리지 말고, 게임 로직이 노출하는 공개 메서드만 사용해야 한다.

권장 방향:

- 호스트 게임 로직 클래스를 별도 분리
- `receiveThrow(player, payload)` 또는 `simulateBotThrow(bot, payload)` 같은 공개 진입점 마련
- 실플레이와 데모가 같은 처리 경로를 통과하도록 통합

#### 2. "보여주기"가 아니라 "게임 루프 재현"으로 확장

권장 시퀀스:

1. `lobby`
2. 봇 2~4명 입장
3. 준비 완료
4. 라운드 시작 카운트다운
5. 순차 또는 동시 투척
6. 결과 정산 및 점수판 반영
7. 최종 우승 연출
8. `onReset()` 또는 로비 복귀

이 시퀀스를 재현해야 데모가 곧 핵심 루프 검증 도구가 된다.

#### 3. 실플레이어 유입 시 즉시 양도

데모 모드는 Attract Mode일 뿐, 실제 유저 유입을 방해하면 안 된다.

필수 규칙:

- 실제 플레이어 입장 시 `stopDemo('real-player-joined')`
- 플레이어 활동 감지 시 남은 봇 액션 즉시 취소
- QR, 상태 문구, 버튼, 강조 이펙트를 모두 정상 로비 상태로 복구

#### 4. 모든 타이머를 추적하고 종료 시 전부 정리

현재는 interval 중심으로 동작한다. 앞으로는 아래 항목을 모두 필드로 관리해야 한다.

- 초기 카운트다운 타이머
- 라운드 시작 타이머
- 봇 액션 타이머
- UI 복구 타이머
- 자동 리셋 타이머

`stopDemo()`는 항상 위 타이머를 전부 해제하고, 중간 단계에서 종료돼도 화면이 안정적으로 복귀해야 한다.

#### 5. 디버그 모드와 전시 모드를 분리

데모는 두 종류가 필요하다.

- 전시 모드: 랜덤 봇 행동, 화려한 연출, 관전 중심
- 검증 모드: 고정 시드, 예측 가능한 결과, 회귀 테스트 중심

이렇게 분리하면 같은 시뮬레이터를 QA와 행사 데모 양쪽에서 재사용할 수 있다.

#### 6. 수정 우선순위

가장 안전한 수정 순서는 아래와 같다.

1. `BaseGame` 기반 상태 모델 정리
2. 공통 `.hidden` 규칙과 모바일 화면 전환 버그 수정
3. 멀티플레이 라운드/입력 락 도입
4. 결과 브로드캐스트 및 점수판 추가
5. 그 위에서 데모 시뮬레이터를 표준형 `DemoSimulator.js`로 재작성

### 4.5 최종 수정 방향 요약

`dice`의 다음 개선 스프린트는 아래 목표를 기준으로 잡는 것이 적절하다.

- 목표 1: 센서 데모를 3라운드 경쟁 게임으로 승격
- 목표 2: 센서 입력을 실제 연출 또는 결과와 연결
- 목표 3: 재연결, 화면 전환, 데모 양도까지 포함한 플랫폼 규약 준수 복원

이 세 가지가 충족되면 `dice`는 지금의 "보여주기 좋은 프로토타입"에서 벗어나, **짧고 강하며 반복 플레이가 가능한 공용 화면용 파티 게임**으로 발전할 수 있다.
