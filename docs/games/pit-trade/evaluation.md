## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`왁자지껄 거래소 (Pit Trade)`의 현재 구현은 고전 보드게임 `Pit`의 핵심 감각을 `Host TV + N Mobile` 구조로 옮긴 형태다. 공용 화면은 시장의 공기와 거래판을 보여주고, 각 플레이어는 모바일에서 자신의 패를 비밀리에 관리하면서 같은 장수의 카드 묶음을 시장에 올리거나 상대 거래를 즉시 받아치는 방식으로 독점을 노린다.

이 게임의 코어 재미는 네 가지 축에서 뚜렷하게 발생한다.

| 축 | 현재 구현의 작동 방식 | 평가 |
| --- | --- | --- |
| 비대칭 정보 | 호스트는 "누가 몇 장을 교환하려는가"만 공개하고, 카드 종류는 끝까지 비밀이다. | 심리전과 추측의 재미가 살아 있다. |
| 실시간 압박 | 시장 등록과 수락이 비동기적으로 계속 이어지고, 거래 타이밍을 늦추면 원하는 매물을 놓칠 수 있다. | 리듬이 빠르고 긴장감이 좋다. |
| 손패 최적화 | 같은 종류 카드를 모으되 `bull` 조커와 `bear` 패널티를 함께 계산해야 한다. | 단순 수집 게임보다 한 단계 더 입체적이다. |
| 공용 화면 드라마 | 호스트의 가격판, 벨, 결과 랭킹이 라운드의 승패를 큰 화면에서 확정한다. | 같은 공간에서 같이 지켜보는 맛이 분명하다. |

특히 플랫폼 적합성이 좋다. TV는 "시장 전체의 공기"를, 모바일은 "개인 손패와 결단"을 담당한다. 모두가 같은 가격판과 거래판을 바라보면서도 실제 선택은 손안에서 비밀리에 이뤄지기 때문에, 이 프로젝트가 지향하는 "같은 공간에서 시선을 교환하는 보드게임형 디지털 플레이"와 잘 맞는다.

현재 구현 기준으로 재미를 지탱하는 요소는 다음과 같다.

| 구분 | 관찰 |
| --- | --- |
| 강점 | 상대가 카드 종류를 숨긴 채 "2장", "3장"만 공개하기 때문에 계산과 눈치싸움이 자연스럽게 발생한다. |
| 강점 | `bear` 카드를 받았을 때 햅틱과 적색 플래시를 주는 모바일 피드백은 비밀 패널티의 감정을 잘 살린다. |
| 강점 | 가격 변동 시스템 덕분에 같은 독점 성공이라도 어떤 상품을 모았는지에 따라 보상이 달라져 전략적 욕심이 생긴다. |
| 강점 | 종을 울리는 승리 연출은 라운드 종료의 감정 곡선을 분명하게 만든다. |
| 약점 | 실제 거래 방식은 "소리치며 동시에 교환"하는 원작의 혼돈보다는 "시장 게시판을 보며 탭하는 UI 거래"에 가깝다. 즉흥적 아수라장 감각은 다소 약하다. |
| 약점 | 가격 변동이 플레이어 행위와 무관한 랜덤 이벤트 중심이라, 실력감보다 운의 개입으로 느껴질 수 있다. |
| 약점 | 모바일이 동일 종류 카드만 교환 가능하다는 규칙을 UI로는 알려주지만, 첫 판 기준으로 왜 선택이 초기화됐는지 직관적으로 설명하지 않는다. |

가장 중요한 디자인 관찰은 이 게임이 이미 "거래소 시뮬레이터"가 아니라 **즉시성 중심의 파티형 실시간 교환 배틀**로 성격이 정리돼 있다는 점이다. 이 방향은 대중성 측면에서 오히려 유리하다. 다만 현재 UX는 그 장점을 충분히 증폭하지 못한다. 첫 판 플레이어는 규칙을 이해하는 데 시간을 쓰고, 숙련자는 UI 연출보다 내부 계산을 더 의식하게 된다.

또한 구현 세부를 보면 게임 밸런스와 재미를 해칠 수 있는 요소가 있다.

| 관찰 포인트 | 영향 |
| --- | --- |
| `bull`/`bear` 주입이 "임의 카드 2장 대체"라는 주석과 달리 실제로는 카드 풀의 첫 두 장을 고정 대체한다. | 사실상 첫 상품인 `diamond` 수량만 항상 줄어들어 밸런스가 기울 수 있다. |
| 승리 조건 계산이 `poolCount - 1` 기준이라 상품별 실제 카드 수 감소가 곧바로 난이도 차이로 이어진다. | 높은 점수 상품이 더 쉬운 독점 목표가 될 가능성이 생긴다. |
| 라운드 점수는 누적 구조처럼 보이지만, 실제 UX는 단판 승부에 가깝고 `reset` 시 점수를 모두 비운다. | "누적 경기"인지 "원라운드 축제"인지 정체성이 약간 흔들린다. |

종합하면, 코어는 충분히 살아 있다. 특히 시선 교환, 비밀 손패, 벨 승리라는 세 요소는 강하다. 다만 대중적 흥행을 노린다면 규칙 전달, 타격감, 관전자 연출을 더 공격적으로 다듬어야 한다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

구조 자체는 비교적 정돈되어 있다. 호스트는 `HostBaseGame`, 모바일은 `MobileBaseGame`을 상속받아 phase/screen 전환 규약을 따르고 있으며, 게임 고유 상태는 호스트가 단일 권한으로 관리한다. `Map` 기반 상태 보관, 거래 트랜잭션 락, 모바일의 햅틱 피드백, 데모 시뮬레이터 분리 파일 존재는 모두 긍정적이다.

아키텍처 관점의 장점은 다음과 같다.

| 항목 | 평가 |
| --- | --- |
| Host/Mobile 역할 분리 | 호스트는 시장 상태와 판정, 모바일은 손패 조작과 개인 피드백에 집중한다. |
| 상태 구조 | `_playerHands`, `_activeTrades`, `_scores`, `_prices` 등 상태가 분리되어 있어 읽기 쉽다. |
| 동시성 방어 | `executeTrade`에 단일 락을 둬 중복 거래 레이스를 줄이려는 의도가 분명하다. |
| UI 전환 규약 준수 | 호스트 `setPhase()`, 모바일 `showScreen()` 패턴을 따르고 있고 `.hidden`도 정의돼 있다. |
| 데모 모드 존재 | 로비 버튼과 별도 `DemoSimulator.js`가 있어 최소한의 운영용 진입점은 마련돼 있다. |

반면 구현 완성도는 아직 "안정적인 시연용 빌드" 수준에 가깝다. 특히 아래 항목들은 실제 운영과 반복 플레이에서 문제가 될 가능성이 높다.

#### 1. 플레이어 상태 소스가 이중화돼 있어 리셋/재접속 흐름이 취약하다

호스트는 플랫폼이 이미 `this.players`를 관리하고 있는데, 게임 내부에서 다시 `_playersList`를 별도로 들고 간다. 이 자체는 가능하지만, 현재 구현에서는 두 상태가 지속적으로 동기화되지 않는다.

핵심 문제는 다음과 같다.

| 관찰 | 영향 |
| --- | --- |
| `onReset()`에서 `_playersList`를 빈 배열로 초기화한다. | 리셋 후에도 실제 연결 플레이어는 `this.players`에 남아 있지만 로비 목록은 0명으로 보일 수 있다. |
| 리셋 이후 기존 연결 플레이어는 `onPlayerJoin()`이 다시 호출되지 않는다. | 다음 라운드 시작 시 `_playersList`가 비어 있어 시작 조건과 실제 접속 상태가 어긋날 수 있다. |
| `onPlayerRejoin()`도 `_playersList`를 복원하지 않는다. | 재접속 유저가 있어도 로비 인원/상태가 정상 복구되지 않는다. |

즉, 현재 구조는 "플랫폼의 진실 상태"와 "게임 내부 표시 상태"가 분리돼 있고, 이 분리가 라운드 반복성에 직접적인 리스크를 만든다.

#### 2. 재접속 복구는 게임 중 일부만 고려되어 있고, 로비/결과 복구가 비어 있다

모바일 클래스는 `onJoin()`과 `onRejoin()`을 구현하지 않는다. 현재는 사용자가 `입장하기` 버튼을 누를 때 수동으로 `waiting` 화면으로 넘어가고, 게임 중에는 호스트가 `tradeExecuted`를 보내면 `_renderHand()`가 호출되면서 자연스럽게 `game` 화면으로 이동한다.

이 방식의 문제는 다음과 같다.

| 상태 | 현재 동작 | 리스크 |
| --- | --- | --- |
| 로비 재접속 | `MobileSDK`는 `rejoin` 이벤트를 주지만 모바일 게임은 이를 처리하지 않는다. 호스트도 로비 상태 동기화 패킷을 보내지 않는다. | 새로고침 후 `setup` 화면에 머무르거나, 이미 입장한 플레이어가 다시 입장한 것처럼 보일 수 있다. |
| 게임 중 재접속 | 호스트가 손패를 다시 보내기 때문에 복구 가능성이 있다. | 거래판 상태나 준비 맥락은 부분 복구에 그친다. |
| 결과 화면 재접속 | 호스트가 결과 재전송을 하지 않는다. 모바일도 결과 상태 복원 로직이 없다. | 결과 페이즈에서 새로고침하면 최종 결과를 잃고 초기 화면으로 떨어질 수 있다. |

프로젝트 규약의 "로비 재연결 프리징 가드" 관점에서 보면, `pit-trade`는 재연결 설계가 아직 미완이다.

#### 3. 핵심 게임 규칙 일부가 호스트 권한이 아니라 모바일 UI에만 기대고 있다

현재 모바일은 다음 규칙을 잘 안내한다.

- `bear`는 단독 1장 교환만 가능
- 일반 카드는 동일 종류만 함께 교환 가능
- `bull`은 조커처럼 섞일 수 있음
- 한 번에 최대 4장까지만 교환 가능

그러나 호스트 검증은 "정말 그 카드를 들고 있느냐"와 "개수가 맞느냐" 정도에만 머문다. 즉, 변조된 클라이언트는 혼합 카드 묶음이나 5장 이상 거래를 보낼 수 있다. 이 게임은 서버가 내용을 모르는 플랫폼 구조라 하더라도, **게임 규칙의 최종 판정은 반드시 호스트가 가져야 한다.**

평가하면 다음과 같다.

| 항목 | 현재 상태 | 평가 |
| --- | --- | --- |
| 소유 카드 검증 | 있음 | 양호 |
| 동일 종류 교환 검증 | 없음 | 보완 필요 |
| `bear` 단독 교환 검증 | 없음 | 보완 필요 |
| 최대 4장 제한 검증 | 없음 | 보완 필요 |
| 독점 선언 검증 | 있음 | 양호 |

#### 4. 문서와 구현의 스펙 싱크가 맞지 않는 부분이 있다

`docs/games/pit-trade/plan.md`와 실제 구현을 대조하면 불일치가 보인다.

| 항목 | 문서 | 실제 코드 |
| --- | --- | --- |
| 6~8인 상품 구성 | `wood`까지 6종으로 서술 | 실제 코드는 `sugar`, `spices`까지 최대 8종 사용 |
| `bull`/`bear` 주입 | 임의 카드 대체로 읽힌다 | 실제는 카드 풀 첫 두 칸 고정 대체 |
| `tradeExecuted` payload | `hand` 중심 서술 | 실제는 `gotBear`, `poolCounts`도 함께 전달 |

문서-구현 불일치는 단순한 문장 문제가 아니다. 밸런스, QA 기대치, 향후 유지보수 기준점에 직접 영향을 준다.

#### 5. 데모 시뮬레이터는 존재하지만 운영형 Attract Mode로는 아직 부족하다

`DemoSimulator.js`가 분리된 점은 좋다. 하지만 현재 방식은 "실제 사용자 흐름을 검증하는 데모"보다 "호스트 내부 상태를 직접 조작하는 봇 스크립트"에 더 가깝다.

주요 한계는 다음과 같다.

| 관찰 | 영향 |
| --- | --- |
| `players`, `sdk._players`, `_playerNicknames`를 직접 수정한다. | 실제 SDK 이벤트 경로와 달라 회귀 검증력이 낮다. |
| 실제 플레이어가 연결된 상태에서도 데모 시작을 막지 않는다. | 행사장 운영 중 실제 세션을 덮어쓸 위험이 있다. |
| "중단 배너"와 명시적 `데모 중단` 버튼이 없다. | 프로젝트 규약상 요구되는 운영 제어성이 부족하다. |
| 시드 고정이나 시나리오 프리셋이 없다. | 같은 문제를 반복 재현하기 어렵다. |
| 데모 종료가 `resetSession()` 중심이 아니라 내부 상태 정리에 치우쳐 있다. | 실제 라운드 종료/리셋 루프와 멀어질 수 있다. |

### 1.3 종합 판정

| 항목 | 평가 | 코멘트 |
| --- | --- | --- |
| 코어 플레이 잠재력 | 높음 | 실시간 거래와 비밀 핸드 구조가 강하다. |
| 플랫폼 적합성 | 매우 높음 | TV는 시장, 모바일은 손패라는 역할 분리가 자연스럽다. |
| 첫 판 대중성 | 중 | 규칙 전달과 조작 피드백이 아직 거칠다. |
| 구현 안정성 | 중 | 정상 루프는 보이지만 리셋/재접속/데모 운영 완성도가 낮다. |
| 문서-구현 정합성 | 보완 필요 | 실제 상품 구성과 프로토콜 확장이 문서에 충분히 반영되지 않았다. |
| 운영 친화성 | 중 | 데모 버튼은 있으나 현장형 attract mode의 제어성과 안전장치가 약하다. |

한 줄로 정리하면, `pit-trade`는 **재미의 씨앗은 강하지만, 반복 플레이와 운영 품질을 떠받칠 구조 마감이 아직 덜 된 게임**이다.

## 2. [대중성 강화 요소]

대중적 흥행을 노릴 때 가장 먼저 보완해야 할 것은 "첫 판 이해", "손맛", "구경하는 맛"이다. 아래 3가지는 현재 코드 구조 위에 비교적 현실적으로 얹을 수 있으면서도 체감 개선 효과가 큰 항목들이다.

### 2.1 제안 1: 첫 20초 온보딩과 규칙 압축 UI

현재 게임은 실제 규칙이 복잡해서 어렵다기보다, 초보자가 즉시 파악해야 할 규칙이 숨겨져 있어 어렵게 느껴진다. 특히 "같은 종류만 교환 가능", "`bear`는 단독 처리", "같은 장수끼리만 거래 성립"은 UX 상 더 직접적으로 보여줄 필요가 있다.

구체 제안:

| 적용 포인트 | 구체 방법 | 기대 효과 |
| --- | --- | --- |
| 모바일 입장 직후 | `1. 같은 장수끼리 교환`, `2. 같은 종류 카드만 묶기`, `3. 9장 모이면 종 울리기`를 3장 카드 슬라이드로 노출 | 사회자 설명 없이도 첫 판 이해 가능 |
| 카드 선택 UX | 다른 종류를 탭했을 때 기존 선택을 지워버리기보다, "같은 상품만 함께 거래 가능" 토스트를 1초 노출 | 선택 초기화가 왜 일어났는지 바로 이해 |
| 거래판 라벨 | "3장 교환 희망" 아래에 "나도 정확히 3장을 내야 함" 보조문구 추가 | equal-count 규칙 체감 강화 |
| 승리 가이드 | 벨 패널이 열리기 전에도 "현재 최다 6/8" 같은 근접도 배지 표시 | 승리 조건 학습이 빨라짐 |

이 제안은 규칙을 단순화하는 것이 아니라, **규칙을 플레이어 머릿속에 빠르게 정착시키는 UX 개선**이다.

### 2.2 제안 2: 거래 체결과 종 울림의 타격감 강화

이 게임의 핵심 감정은 "지금 거래가 성사됐다"와 "내가 독점했다"의 두 순간에 몰린다. 그런데 현재 모바일은 카드 갱신은 되지만 거래 성공의 감정 보상이 충분히 크지 않다. 호스트도 벨 연출은 있으나, 거래가 살아 움직이는 시장의 박동감은 조금 더 올릴 수 있다.

구체 제안:

| 적용 포인트 | 구체 방법 | 기대 효과 |
| --- | --- | --- |
| 모바일 거래 성공 | `tradeExecuted` 수신 시 거래 성공/실패 종류별 짧은 햅틱과 카드 재배치 애니메이션 추가 | "손에 들어온 맛" 강화 |
| `bear` 인계 | 현재 적색 플래시에 사이렌성 짧은 효과음 또는 아이콘 흔들림 추가 | 비밀 패널티의 감정선 증폭 |
| 호스트 거래판 | 새로운 거래 등록 시 카드가 튀어나오듯 등장하고, 체결 시 두 카드가 중앙으로 빨려 들어가는 마이크로 애니메이션 추가 | 시장이 살아 있다는 인상 강화 |
| 벨 승리 순간 | 벨 흔들림과 함께 화면 전체에 짧은 금빛 파동, 승자 카드의 스포트라이트 연출 추가 | 라운드 종료의 카타르시스 증폭 |

이 패키지는 규칙을 바꾸지 않으면서도 파티 게임다운 즉시 만족감을 크게 올려준다.

### 2.3 제안 3: 관전자 드라마를 키우는 시장 해설 HUD

`pit-trade`는 플레이어만 재미있으면 반쪽짜리다. TV 주변에서 보고 있는 사람도 "누가 지금 유리한지"를 이해해야 다음 판 참여 욕구가 올라간다. 현재 호스트의 `최다 n장` HUD는 기초 정보는 주지만, 드라마를 만들어내기에는 다소 조용하다.

구체 제안:

| 적용 포인트 | 구체 방법 | 기대 효과 |
| --- | --- | --- |
| 플레이어 HUD | `최다 6장`만 보여주지 말고 `독점 임박`, `곰 보유 의심`, `3연속 거래 성공` 같은 짧은 상태 태그 추가 | 구경하는 사람이 서사를 읽기 쉬워짐 |
| 시장 뉴스 | 가격 변동 외에도 `홍길동, 4장 거래 등록`, `선두가 바뀌었습니다` 같은 배너형 콜아웃 추가 | 관전자 몰입 상승 |
| 라운드 피날레 | 누군가 임계치 직전이면 화면 테두리와 뉴스 티커가 붉게 변하는 "위기/찬스" 연출 추가 | 종 직전 긴장감 확대 |
| 결과 화면 | 단순 순위 외에 `최다 거래왕`, `곰 카드 생존왕`, `고가 상품 독점상` 같은 보조 타이틀 부여 | 결과 회고의 재미 강화 |

이 제안은 게임 룰을 복잡하게 만들지 않으면서 TV 앞 군중의 반응을 키우는 방향이다. 행사장, 방송형 시연, 사내 이벤트 환경에서 특히 효과가 크다.

| SeniorGameDev | "호스트 검증이 약해 규칙 위반 패킷을 막지 못하는 구조는 먼저 손봐야 한다. 그 위에서 온보딩과 관전자 HUD를 올리는 순서가 맞다." |

### 3.3 쟁점 토론

#### 쟁점 A. 가장 먼저 올려야 할 것은 규칙 설명인가, 연출인가

토론 결과, 회의는 **규칙 압축 UI와 거래 타격감 패키지를 동시 P0**로 보았다.

- 온보딩만 강화하고 손맛이 약하면 "이해는 했는데 심심한 게임"이 된다.
- 타격감만 강화하고 규칙 안내가 약하면 첫 판 이탈률이 그대로 남는다.

즉, `pit-trade`는 "이해"와 "흥분"을 동시에 보강해야 대중성이 올라간다는 결론이 나왔다.

#### 쟁점 B. 관전자 HUD는 지금 붙여도 되는가

UIUXDesigner와 OnlineGameProducer는 즉시 도입을 원했지만, TechAnalyst와 SeniorGameDev는 조건부 찬성을 냈다.

핵심 논점은 다음과 같았다.

- 호스트가 현재도 `최다 n장` 정도의 근접 정보를 갖고 있으므로 HUD 확장은 기술적으로 어렵지 않다.
- 그러나 재접속/리셋 상태 불일치가 남아 있으면 HUD가 잘못된 인원을 보여줄 수 있다.

따라서 결론은 **구조 보정과 함께 P1로 추진**하는 방향으로 정리됐다.

#### 쟁점 C. 데모 시뮬레이터도 대중성 강화 논의에 포함해야 하는가

PMOrchestrator와 TechAnalyst는 "예"라고 판단했다. 이유는 명확하다.

- 이 프로젝트는 공용기기 기반 플랫폼이라 현장 시연 품질이 곧 게임 인상이다.
- 데모 모드가 실제 규칙을 왜곡하거나 실플레이와 다른 상태를 만들면, 대중성 이전에 신뢰도가 흔들린다.

즉, 데모 개선은 단순 개발 편의가 아니라 흥행 준비 작업으로 봐야 한다는 데 합의했다.

### 3.5 회의 결론

회의는 `pit-trade`를 "새로운 룰을 더 얹어야 하는 게임"으로 보지 않았다. 오히려 이미 있는 코어를 더 잘 전달하고, 더 잘 보이게 만들고, 반복 플레이에도 무너지지 않게 고치는 것이 우선이라고 판단했다. 최종적으로는 아래 순서가 가장 합리적인 로드맵으로 채택됐다.

1. `_playersList` 제거 또는 `this.players`와의 단일화, 로비/결과 재접속 상태 동기화 추가
2. 호스트 권한 기반 거래 규칙 검증 보강, `bull`/`bear` 주입 로직의 실제 랜덤화 수정
3. 모바일 온보딩과 거래 타격감 패키지 반영
4. 호스트 시장 해설 HUD와 피날레 연출 강화
5. 데모 시뮬레이터를 운영형 attract mode + 회귀 검증용 deterministic mode로 분리 또는 이중화

## 4. [테스트 결과 및 수정 방향]

### 4.1 현재 품질 판단

정적 분석 기준으로 볼 때, `pit-trade`는 기본 게임 루프 자체는 성립한다.

- 세션 생성과 QR 표시 구조가 있다.
- 모바일 닉네임 설정, 준비, 거래 등록/수락, 벨 승리, 결과 표시까지 흐름이 이어진다.
- `bear` 카드 인계 피드백과 `tradeState` 공개 구조도 작동 의도가 분명하다.

그러나 반복 플레이와 예외 흐름에서는 다음 리스크가 두드러진다.

| 리스크 | 판단 |
| --- | --- |
| 리셋 후 동일 플레이어로 즉시 다음 판 진행 | 불안정 가능성 높음 |
| 로비/결과 재접속 복구 | 미흡 |
| 규칙 위반 패킷 방어 | 미흡 |
| 데모 모드의 실세션 안전성 | 미흡 |
| 문서-구현 일치도 | 보완 필요 |

따라서 아래 시나리오를 기준으로 수동 회귀 테스트를 설계해야 한다.

### 4.2 게임 전체 동작 검증 시나리오

| ID | 검증 시나리오 | 절차 | 기대 결과 |
| --- | --- | --- | --- |
| T01 | 로비 진입과 세션 생성 | 호스트 진입 후 QR/방 코드 확인 | 세션이 생성되고 QR과 코드가 즉시 표시된다. |
| T02 | 최소 인원 시작 | 모바일 3대 접속, 닉네임 설정, 준비 완료 | 호스트가 게임 페이즈로 전환되고 각자 9장 손패를 받는다. |
| T03 | 거래 등록/취소 | 한 플레이어가 2장 거래 등록 후 취소 | 호스트 거래판과 모바일 거래판에서 즉시 반영된다. |
| T04 | 정상 거래 체결 | A가 2장 등록, B가 정확히 2장 선택 후 수락 | 양쪽 손패가 교환되고 시장 매물이 제거된다. |
| T05 | `bear` 인계 피드백 | 거래를 통해 상대가 `bear`를 받게 만듦 | `gotBear` 수신 기기에서 햅틱과 적색 플래시가 발생한다. |
| T06 | 독점 승리 | 특정 플레이어가 승리 조건을 만족한 뒤 종 울리기 | 호스트가 승리 검증 후 결과 화면으로 넘어가고 전원 결과가 표시된다. |
| T07 | 강제 종료 | 게임 중 3명 미만이 되도록 퇴장 | 호스트가 라운드를 강제 종료하고 파행 메시지를 보여준다. |
| T08 | 로비 재접속 | 로비에서 모바일 새로고침 | 재접속 플레이어가 로비 대기 상태로 복구되고 호스트 인원 표기가 유지된다. |
| T09 | 게임 중 재접속 | 거래 진행 중 모바일 새로고침 | 손패, 거래판, 승리 가능 상태가 다시 동기화된다. |
| T10 | 결과 화면 재접속 | 결과 화면에서 모바일 새로고침 | 결과와 순위가 재표시되거나 최소한 결과 페이즈가 보존된다. |
| T11 | 리셋 후 재시작 | 결과 화면에서 호스트 `대기실로 복귀` 후 같은 플레이어들로 다시 준비 | 로비 인원, 닉네임, 다음 게임 시작이 정상 동작한다. |
| T12 | 규칙 위반 패킷 방어 | 개발자도구에서 5장 이상 또는 혼합 카드 `registerTrade`/`executeTrade` 전송 | 호스트가 거부하고 상태가 오염되지 않는다. |
| T13 | 데모 시작/중단 | 로비에서 데모 시작, 중도 중단, 다시 실제 플레이 전환 | 데모 봇과 실제 유저 상태가 섞이지 않고 원상복구된다. |
| T14 | 밸런스 점검 | 여러 판 반복하며 `diamond` 독점 난이도와 점수 편차 관찰 | 특정 상품이 비정상적으로 쉬운 승리 루트가 아닌지 검증한다. |

### 4.3 우선 수정 방향

테스트 시나리오를 기준으로 가장 먼저 손봐야 할 항목은 아래 다섯 가지다.

| 우선순위 | 수정 방향 | 이유 |
| --- | --- | --- |
| P0 | `_playersList`를 제거하거나 `this.players` 기반으로 재구성 | 리셋/재접속 불일치의 근본 원인이다. |
| P0 | 모바일 `onJoin()`/`onRejoin()` 구현 및 호스트 `lobbyState`/`resultState` 동기화 추가 | 로비와 결과 재접속 복구가 비어 있다. |
| P0 | 호스트 거래 검증에 동일 종류, 최대 4장, `bear` 단독 규칙을 추가 | 규칙 권한을 모바일 UI가 아니라 호스트가 가져야 한다. |
| P0 | `bull`/`bear` 카드 주입을 실제 랜덤 치환으로 수정 | 상품 밸런스 왜곡 가능성이 있다. |
| P1 | 결과 화면과 로비 화면에 준비 상태, 독점 임박, 거래 성공 등의 해설 UI 보강 | 관전자 재미와 첫 판 이해도를 높인다. |

### 4.4 `DemoSimulator.js`의 개선점

현재 `DemoSimulator.js`는 "돌아가긴 하는 시뮬레이션"에 가깝고, 프로젝트 규약이 요구하는 운영형 Attract Mode로 보기에는 부족하다.

| 개선 포인트 | 현재 상태 | 문제점 |
| --- | --- | --- |
| 시작 조건 가드 | 실제 플레이어 유무와 무관하게 실행 가능 | 현장 운영 중 실세션 상태를 덮어쓸 수 있다. |
| 중단 UX | 시작 버튼 텍스트만 바뀌고 별도 중단 배너/버튼이 없다 | 운영자가 즉시 상태를 제어하기 어렵다. |
| 상태 주입 방식 | `players`, `sdk._players`, `_playerNicknames`를 직접 수정 | 실제 세션 이벤트 경로를 통과하지 않아 회귀 검증력이 낮다. |
| 시나리오 다양성 | 랜덤 거래 루프 1종 | 곰 카드 인계, 강제 종료, 재접속, 종료 후 복구 같은 예외 분기를 검증하기 어렵다. |
| 재현성 | 시드 고정이 없다 | 같은 장면을 반복 재생산하기 어렵다. |

### 4.5 `DemoSimulator.js` 수정 가이드라인

아래 순서로 보강하는 것이 가장 현실적이다.

1. **운영형 데모 라이프사이클을 완성한다.**
   - 로비에 `🤖 데모 진행 중` 배너와 `데모 중단` 버튼을 추가한다.
   - 실제 플레이어가 1명 이상 연결돼 있으면 데모 시작을 막는다.
   - 데모 종료 시 내부 맵 직접 정리보다 공용 리셋 루틴을 우선 사용한다.

2. **실제 게임 상태 머신과 같은 경로를 최대한 재사용한다.**
   - 봇 입장, 준비, 거래 등록, 거래 수락, 종 울리기를 각각 메서드화해 "실제 메시지 핸들러를 호출하는 드라이버"로 재정리한다.
   - `sdk._players` 직접 수정은 최소화하고, 불가피하다면 한곳에 격리해 유지보수 비용을 줄인다.

3. **시나리오 프리셋을 최소 4종으로 늘린다.**
   - 정상 독점 승리 시나리오
   - `bear` 인계 강조 시나리오
   - 플레이어 이탈로 인한 강제 종료 시나리오
   - 재접속/리셋 복구 검증 시나리오

4. **시드 기반 결정론 옵션을 추가한다.**
   - `Math.random()` 기반 전체 흐름 대신 시드를 받는 랜덤 유틸을 두면, 버그 재현과 QA 보고서 작성이 쉬워진다.

5. **호스트 화면에 데모 상태 배지를 노출한다.**
   - 예: `DEMO / ROUND 1 / MARKET ACTIVE / EXPECTED WINNER: bot_2`
   - 브라우저 검증 시 "지금 어느 단계인지"를 한눈에 파악할 수 있다.

6. **연출 검증용 데모와 회귀 검증용 데모를 분리한다.**
   - 현장 attract mode는 보기 좋은 타이밍과 빠른 리듬을 우선한다.
   - 회귀 검증 모드는 예외 분기 커버리지와 재현성을 우선한다.
   - 두 역할을 하나의 랜덤 루프가 모두 맡게 두면 어느 쪽도 충분히 만족시키기 어렵다.

### 4.6 최종 수정 방향 요약

`pit-trade`는 새 규칙을 더 얹는 것보다, 현재 규칙을 더 안정적으로 반복 가능하게 만들고 더 신나게 전달하는 쪽이 맞다. 따라서 다음 순서가 가장 합리적이다.

1. 플레이어 상태 소스를 단일화하고 재접속/리셋 복구를 완성한다.
2. 호스트 권한 기반 규칙 검증과 카드 풀 밸런스 로직을 바로잡는다.
3. 모바일 온보딩과 거래 타격감 패키지를 붙인다.
4. 관전자 해설 HUD와 데모 모드를 운영 친화적으로 다듬는다.

이 네 단계가 정리되면 `pit-trade`는 현재의 "좋은 아이디어가 보이는 프로토타입"을 넘어, 반복 시연과 대중 반응까지 견딜 수 있는 파티형 대표 콘텐츠로 올라갈 가능성이 높다.
