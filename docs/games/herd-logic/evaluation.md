# `herd-logic` 평가 및 개선안

- 작성일: 2026-07-07
- 분석 대상:
  - `games/herd-logic/host/main.js`
  - `games/herd-logic/host/DemoSimulator.js`
  - `games/herd-logic/host/index.html`
  - `games/herd-logic/host/style.css`
  - `games/herd-logic/mobile/main.js`
  - `games/herd-logic/mobile/index.html`
  - `games/herd-logic/mobile/style.css`
  - `tests/herd-logic/demo.spec.js`
  - `docs/meetings/meeting_minutes_rev4.md`
- 분석 방식: 정적 코드 리뷰 + `npm run build` 검증
- 검증 한계:
  - 실제 다기기 동시 접속, P2P 직결 로그, 브라우저 시각 QA는 이번 문서 범위에 포함하지 않았다.
  - 기존 Playwright 스크립트는 호스트 단독 데모 루프 위주라 실제 모바일 상호작용 품질을 충분히 대표하지 않는다.

## 1. [게임 평가]

### 1.1 코어 플레이 방식 및 재미 요소 분석

`허드 로직`의 코어 재미는 "정답을 맞히는 게임"이 아니라 "다른 사람들의 평균적인 생각을 예측하는 게임"이라는 점에서 나온다. 플레이어는 자기 취향을 적는 대신, 같은 공간에 있는 사람들의 집단적 상식과 심리를 읽어야 한다. 이 구조는 TV/태블릿 공용 화면과 모바일 개인 입력이라는 플랫폼 구조에 잘 맞는다.

현재 구현의 핵심 루프는 단순하고 직관적이다.

1. 호스트가 질문을 제시한다.
2. 각 모바일은 "남들이 가장 많이 적을 답"을 텍스트로 제출한다.
3. 호스트가 전원 제출 후 답을 한 번에 공개한다.
4. 다수파는 점수를 얻고, 유일하게 튄 플레이어는 핑크 카우를 받는다.
5. 3라운드 후 최종 순위를 발표한다.

이 구조가 잘 작동하는 이유는 다음과 같다.

| 항목 | 평가 |
| --- | --- |
| 사회적 예측 재미 | 자기 취향이 아니라 남의 평균을 추론해야 하므로 대화와 눈치 싸움이 자연스럽게 발생한다. |
| 공용 화면 관전성 | 답변이 호스트 카드 그리드에서 동시에 뒤집히는 구조라, "누가 평범했고 누가 튀었는지"가 한눈에 드러난다. |
| 짧은 룰 학습 비용 | "가장 평범한 답을 적어라"라는 한 문장으로 설명 가능하다. |
| 핑크 카우 서사 | 점수 경쟁에 더해 "지금 누가 핑크 카우를 들고 있는가"가 다음 라운드의 심리 압박으로 이어진다. |

특히 `host/main.js`의 동시 공개 구조와 `mobile/main.js`의 제출 후 대기, 결과 진동 피드백은 파티 게임으로서 필요한 최소 루프를 충실히 만든 편이다. 호스트 카드 플립과 모바일 진동도 "내 답이 먹혔는지"를 즉시 체감하게 해 준다.

다만 현재 버전은 첫 판의 재미는 분명하지만, 대중적으로 크게 흥행하려면 아래 약점이 뚜렷하다.

| 관찰 포인트 | 평가 |
| --- | --- |
| 라운드 수 | `_maxRounds = 3` 고정이라 워밍업이 끝날 즈음 종료된다. 긴장감이 커지기 전에 게임이 닫히는 느낌이 있다. |
| 질문 풀 | 질문 풀이 10개뿐이라 반복 플레이 시 금방 패턴이 읽힌다. |
| 규칙 설명 | 동률 다수파 처리, 핑크 카우 유지/이전 조건이 UI에 충분히 설명되지 않는다. 결과가 맞더라도 납득성이 약해질 수 있다. |
| 입력 판정 | 공백·구두점·일부 조사 제거는 있지만, 동의어나 표현 차이까지는 흡수하지 못해 "의미는 같지만 점수는 다른" 답이 자주 나올 수 있다. |
| 추천 인원 감각 | 레지스트리상 2인 시작이 가능하지만, 이 장르의 진짜 재미는 3인 이상에서 훨씬 강하게 살아난다. |

종합하면 `허드 로직`은 코어 컨셉 자체는 매우 건강하다. "같은 공간에서 서로의 평균을 읽는 심리 동조 게임"이라는 목표는 달성했다. 문제는 현재 구현이 그 재미를 서비스급 밀도로 증폭시키는 단계까지는 아직 가지 못했다는 점이다.

### 1.2 Host/Mobile 코드베이스의 아키텍처 및 구현 완성도 평가

호스트 구현은 프로젝트 컨벤션에 비교적 잘 맞는다.

- `HostBaseGame`를 상속하고 `setPhase('lobby' | 'playing' | 'result')`로 화면 책임을 분리했다.
- `onPlayerRejoin()`에서 최소한의 `lobbyState`, `rejoinState`를 보내 로비 프리징을 방지하려는 의도가 보인다.
- 호스트 CSS는 `.hidden` 규약과 `position: relative; z-index: 10;` 규약을 만족한다.
- 로비, 플레이, 결과 화면이 분리되어 있어 유지보수 관점에서 읽기 쉽다.

하지만 모바일과 데모 구조는 완성도가 한 단계 낮다.

- 모바일은 `MobileBaseGame`를 상속하지 않고 `MobileSDK`를 직접 사용한다.
- 재접속 복구는 메시지 핸들러 몇 개에 의존하며, 라이프사이클 훅 기반의 표준 패턴을 충분히 활용하지 못한다.
- 데모는 존재하지만 "실제 운영 가능한 Attract Mode"라기보다 "호스트 단독 시연용 스크립트"에 더 가깝다.

구현 완성도를 축별로 보면 아래와 같다.

| 평가 축 | 판정 | 근거 |
| --- | --- | --- |
| 코어 컨셉 적합성 | 높음 | 공용 질문, 개인 입력, 집단 공개라는 구조가 플랫폼과 잘 맞는다. |
| 호스트 상태 관리 | 중상 | 라운드, 질문, 핑크 카우, 점수 상태가 비교적 단순한 `Map` 중심 구조로 정리되어 있다. |
| 모바일 상태 관리 | 보통 이하 | 단일 파일 수동 DOM 토글 구조라 기능 추가와 복구 처리 확장에 약하다. |
| 재접속 복원 | 미흡 | 작성 단계 복구는 일부 있으나, 공개 단계와 결과 단계 복구가 빠져 있다. |
| 데모 모드 완성도 | 미흡 | 데모가 자동 완주하지 않고, 실플레이 상태를 덮어쓰는 방식이라 운영 안전성이 낮다. |
| 테스트 대표성 | 낮음 | 현재 E2E는 호스트 데모 화면만 검증하며 실제 모바일 메시지 경로를 증명하지 않는다. |

현재 코드에서 중요하게 보이는 리스크는 다음 다섯 가지다.

#### 1. 재접속 복구가 "진행 중 일부 상태"까지만 복원된다

`onPlayerRejoin()`은 `_gameActive`가 `true`일 때만 `rejoinState`를 보내고, 그 외에는 무조건 `lobbyState`를 보낸다. 이 구조의 문제는 다음과 같다.

- 답변 공개 단계(`_roundPhase === 'revealed'`)에 재접속해도 모바일은 공개 결과를 복구받지 못한다.
- 결과 화면(`setPhase('result')`)에서는 `_gameActive`가 이미 `false`라서, 재접속 플레이어가 결과가 아니라 로비 상태를 받는다.
- 이미 제출한 답의 실제 텍스트, 매칭 성공 여부, 현재 공개 단계인지 여부가 모바일에 전달되지 않는다.

즉, "세션이 끊겨도 게임이 계속된다"는 플랫폼 목적에 비해 복구 설계가 절반만 구현되어 있다.

#### 2. 모바일이 공통 베이스 게임 패턴을 벗어나 있다

`mobile/main.js`는 자체 `showScreen()`을 구현해 화면을 전환하고, `connect`, `reset`, `newQuestion`, `rejoinState`를 직접 엮어 관리한다. 동작은 가능하지만 아래 이점을 포기한다.

- `onJoin`, `onRejoin`, `onAllReady`, `onReset` 훅 기반의 일관된 복구 흐름
- 공통 홈 버튼, 재접속 정책, 화면 상태 유지 패턴의 재사용
- 기능 확장 시 화면 책임 분리

현재 파일 규모에서는 버티지만, 튜토리얼, 결과 복기, 개인 점수판, 사운드 토글 같은 옵션이 붙는 순간 급격히 복잡해질 가능성이 높다.

#### 3. 저장된 닉네임 자동 복원 경로에 순서 경쟁이 있다

모바일은 `connect` 이벤트 직후 `localStorage`의 닉네임을 읽어 `setProfile`을 먼저 전송한다. 그런데 `MobileSDK`는 `connect` 이벤트를 `platform:joined`보다 먼저 발생시킨다. 그 결과 저장된 닉네임 자동 복원 시 아래 상황이 가능하다.

- 아직 stable player ID가 확정되기 전에 `setProfile`이 호스트로 간다.
- 서버는 이 메시지를 일단 `socket.id` 기반으로 호스트에 전달할 수 있다.
- 이후 실제 세션 입장 ID와 이름 매핑이 엇갈리면 로비 카드나 복구 시 이름 싱크가 흔들릴 수 있다.

치명적인 결함으로 단정할 수준은 아니지만, 운영 중 간헐 버그를 만들기 쉬운 구조다.

#### 4. 입력 검증과 렌더링 안전성이 얕다

현재 닉네임과 답변은 모바일 UI에서 길이 정도만 제한하고, 호스트는 이를 `innerHTML` 기반 카드 마크업에 그대로 삽입한다. 이 구조는 두 측면에서 아쉽다.

- 서비스 관점: 공백, 반복 제출, 비정상 문자열, 동의어 처리에 대한 서버/호스트 방어가 약하다.
- 보안 관점: 사용자 입력 문자열이 HTML 렌더링 경로에 직접 들어가므로 이스케이프 처리 강화가 필요하다.

파티 게임이라 가벼워 보여도, 공용 화면에 누구나 문자열을 띄울 수 있는 구조에서는 이 부분을 가볍게 보면 안 된다.

#### 5. `DemoSimulator.js`가 규약상 존재는 맞지만, Attract Mode로는 아직 불완전하다

현재 데모는 다음 한계를 가진다.

- 봇 입장과 답변 제출만 자동화하고, 답변 공개와 다음 라운드 진행은 사람이 계속 눌러야 한다.
- `game.players`, `sdk._players`, `_playerNicknames`, `sdk._messageHandlers` 같은 내부 상태를 직접 만진다.
- 실제 플레이어가 있는 로비에서 실행되면 세션 상태를 덮어쓸 위험이 있다.
- 최종 결과 후 자동으로 로비로 복귀하는 완전한 시연 루프가 없다.

즉, "데모 버튼이 있다"는 요구사항은 충족했지만, "혼자서 핵심 루프와 연출을 한눈에 검증하는 운영 가능한 데모 모드"라는 목표까지는 아직 도달하지 못했다.

### 1.3 종합 판정

`허드 로직`은 코어 재미와 플랫폼 적합성 면에서는 좋은 출발점이다. 특히 텍스트 입력형 게임 중에서는 공용 화면 활용도가 높고, 답변 공개 순간의 파티성이 확실하다. 다만 상용 완성도 기준으로 보면 아래 세 축이 더 필요하다.

1. 공개 순간의 쇼맨십 강화
2. 재접속·데모·입력 검증 같은 운영 품질 보강
3. 질문 덱과 룰 설명의 대중화

점수로 요약하면 다음과 같다.

| 항목 | 점수(10점 만점) | 코멘트 |
| --- | --- | --- |
| 코어 게임성 | 8.3 | 심리 동조 장르의 핵심 재미를 잘 살렸다. |
| 첫 판 직관성 | 7.6 | 기본 룰은 쉽지만, 세부 판정 규칙 설명이 더 필요하다. |
| 관전성 | 7.4 | 카드 공개는 좋지만, 대박 장면을 키우는 연출이 부족하다. |
| Host 구현 완성도 | 7.2 | 구조는 단정하지만 복구 디테일과 로비 피드백이 아쉽다. |
| Mobile 구현 완성도 | 5.8 | 동작은 되나 표준 패턴과 확장성 면에서 약하다. |
| Demo/Test 신뢰성 | 4.3 | 데모와 E2E가 실제 플레이 품질을 충분히 대표하지 못한다. |
| 상품화 잠재력 | 8.1 | 질문 덱, 연출, QA 체계만 보강하면 대중성이 크게 올라갈 수 있다. |

한 줄 총평:

> `허드 로직`은 이미 재미의 씨앗은 분명하지만, 지금 상태는 "좋은 플레이어블 프로토타입"에 더 가깝고, 대중 앞에서 반복 시연해도 강해지는 서비스형 파티 게임으로 가려면 연출과 운영 품질을 한 단계 더 밀어 올려야 한다.

## 2. [대중성 강화 요소]

대중적으로 더 강하게 터뜨리려면 새 규칙을 무리하게 늘리기보다, 현재 코어를 더 잘 보여 주고 더 쉽게 이해시키고 더 오래 반복하게 만들어야 한다. 우선순위가 높은 세 가지는 아래와 같다.

### 2.1 제안 1: 답변 공개 쇼타임 패키지

이 게임의 하이라이트는 모든 답이 한 번에 열리고, 핑크 카우가 누구에게 가는지가 드러나는 순간이다. 현재도 카드 플립은 있지만, 그 장면이 "기억에 남는 쇼"로까지는 커지지 않는다.

구체 제안:

- 호스트에 `3, 2, 1` 짧은 공개 카운트다운 추가
- 카드 플립을 동시에 뒤집기보다 80~120ms 정도 스태거로 뒤집어 긴장감 형성
- 핑크 카우를 현재 홀더에게 즉시 배지로 붙이는 대신, 날아가 붙는 이동 애니메이션과 짧은 효과음 추가
- 다수파 답은 초록 파동, 실패 답은 붉은 테두리, 동률 다수파는 금색 배지로 시각 구분
- 최종 순위 발표 시 우승자만이 아니라 핑크 카우 보유자, 최고 동조율 플레이어도 함께 발표

기대 효과:

- 호스트 화면만 봐도 현재 무슨 일이 벌어졌는지 관전자가 즉시 이해하게 된다.
- "누가 튀었는가"가 숫자 판정보다 사건처럼 느껴져 웃음 포인트가 커진다.
- 행사장 시연, 스트리밍, 가족 모임에서 클립성이 훨씬 강해진다.

### 2.2 제안 2: 규칙·입력 UX 간소화 패키지

이 게임은 쉬워 보이지만, 실제 첫 판에서는 사람들이 자주 헷갈린다. "내 생각이 아니라 남들의 평균을 적어야 한다"는 점, 동률 처리, 핑크 카우 유지 규칙을 짧고 정확하게 가르쳐야 한다.

구체 제안:

- 모바일 첫 진입 시 20초 내 튜토리얼 카드 2~3장 제공
- 로비에 "추천 인원 3~6명"과 "가장 평범한 답을 적으세요"를 크게 노출
- 입력창 아래에 `예: 사과 / 강아지 / 커피` 같은 형식 예시와 글자 수 가이드를 인라인 제공
- 제출 후 "의견 잠금 완료" 배지, 공개 직전 "곧 공개됩니다" 마이크로 애니메이션 추가
- 동률 다수파와 핑크 카우 유지 규칙을 호스트 HUD 또는 결과 하단에 한 줄로 항상 설명

기대 효과:

- 사회자가 길게 설명하지 않아도 첫 판이 훨씬 매끄럽게 시작된다.
- 텍스트 입력형 게임에서 자주 생기는 답변 품질 편차와 오해를 줄일 수 있다.
- "왜 이 사람이 점수를 받았는지"에 대한 납득성이 높아져 판정 불만이 줄어든다.

### 2.3 제안 3: 질문 덱 확장 + 파티 모드 레이어링

현재 질문 풀이 10개인 상태로는 대중적 체류 시간을 오래 가져가기 어렵다. 코어 룰은 유지하되 질문과 모드 변주를 늘려 반복 플레이 수명을 키워야 한다.

구체 제안:

- `일상`, `학교`, `음식`, `연애/우정`, `직장`, `세대 공감` 등 테마 질문 덱 추가
- `쉬움/보통/엉뚱함` 난이도 태그를 붙여 모임 분위기에 맞게 선택 가능하게 함
- 3라운드 고정 외에 `5점 선취`, `핑크 카우 탈출전`, `스피드 라운드` 같은 경량 모드 추가
- 질문 공개 전에 짧은 키워드 아이콘이나 카테고리 색을 함께 보여 사고 시간을 줄임
- 결과 화면에 "이번 판에서 가장 많이 겹친 답", "가장 튄 답" 복기 카드 제공

기대 효과:

- 같은 모임에서 여러 판 연속 플레이해도 금방 질리지 않는다.
- 연령대와 모임 성격에 맞춰 질문 난도를 조절할 수 있다.
- 결과 복기가 다음 판의 웃음거리와 대화 소재가 되어 재대결 동력을 만든다.

### 3.3 핵심 쟁점 토론

#### 쟁점 1. 세 가지 대중성 강화 요소를 모두 즉시 반영할 수 있는가

회의 결론은 "아니다"였다. 이유는 콘텐츠 확장보다 먼저 정리해야 할 기반 이슈가 있기 때문이다.

1. 공개 단계와 결과 단계 재접속 동기화 보강
2. 저장 닉네임 자동 복원 순서 안정화
3. 데모 시뮬레이터의 자율 완주 및 세션 오염 방지

이 세 가지가 정리되지 않으면 시연 중에는 좋아 보여도, 실제 모임 플레이나 QA 반복에서 신뢰성이 떨어진다.

#### 쟁점 2. 무엇을 먼저 반영해야 대중 체감이 가장 빨리 올라가는가

합의된 우선순위는 `B -> A -> C`였다.

- `B`는 첫 판 이탈률을 낮추고 판정 불만을 줄이는 효과가 가장 즉각적이다.
- `A`는 잘 이해된 룰 위에서 관전성과 화제성을 크게 키운다.
- `C`는 장기 체류 시간을 늘리는 핵심이지만, 현재 질문 덱 품질 관리와 결과 복기 UX가 먼저 잡혀야 효과가 크다.

#### 쟁점 3. 2인 시작 허용을 메인 경험으로 둘 것인가

결론은 "기술적으로 허용하되 메인 추천 경험으로 밀지는 않는다"였다.

- 2인에서는 다수파 예측의 사회적 밀도가 낮다.
- 동률과 상호 눈치 싸움은 3인 이상에서 훨씬 풍부해진다.
- 따라서 로비와 문서에는 `3~6명 추천`을 전면 표기하는 편이 적절하다는 데 의견이 모였다.

### 4.3 🤖 `DemoSimulator.js`의 개선점

현재 `games/herd-logic/host/DemoSimulator.js`는 시연용 시작점으로는 쓸 수 있지만, 운영 가능한 Attract Mode이자 신뢰 가능한 QA 도구로 보기는 어렵다.

| 개선 포인트 | 현재 상태 | 문제점 |
| --- | --- | --- |

### 4.4 `DemoSimulator.js` 수정 가이드라인

가장 안전한 개선 방향은 아래 순서다.

1. **완전 자율 시연 루프로 바꾼다.**
   - `봇 입장 -> 준비 완료 -> 라운드 시작 -> 답변 제출 -> 자동 공개 -> 다음 라운드 -> 결과 발표 -> 자동 리셋`까지 손대지 않아도 한 바퀴 돌아야 한다.
   - 지금처럼 호스트가 매 라운드 버튼을 눌러야 하는 구조는 Attract Mode 목적에 맞지 않는다.

2. **호스트 액션을 공용 메서드로 추출한다.**
   - `_revealAnswers()`, `_handleNextRound()`, `_startGame()` 같은 흐름을 데모와 UI 버튼이 같은 경로로 호출하도록 정리한다.
   - 데모 전용 분기에서 내부 상태를 직접 조작하지 말고, 실제 게임 액션을 재사용해야 한다.

3. **세션 스냅샷/복원 계층을 둔다.**
   - 데모 시작 전 실제 플레이어 목록과 닉네임 맵을 보관하고, 종료 시 원상복구한다.
   - 실제 유저가 1명이라도 있으면 데모 실행을 차단하거나 별도 "강제 시연 모드" 확인 절차를 둔다.

4. **시나리오를 최소 4종으로 늘린다.**
   - 정상 다수파 일치
   - 단일 튀는 답으로 핑크 카우 이전
   - 복수 고유 답으로 핑크 카우 유지
   - 동률 다수파 처리
   - 이 네 가지는 현재 룰의 핵심 분기이므로 반드시 데모에서 재현 가능해야 한다.

5. **공개 단계와 결과 단계 시각 표지를 넣는다.**
   - 호스트 상단에 `DEMO RUNNING`, `ROUND 2`, `REVEAL`, `RESULT AUTO-RESET IN 5s` 같은 작은 배너를 두면 QA 효율이 높아진다.
   - 데모 중단 버튼도 현재 단계와 남은 시간을 함께 보여 주는 편이 좋다.

6. **테스트와 데모의 목표를 분리한다.**
   - 현장 시연용 `Attract Demo`와 재현성 중심 `Deterministic QA Demo`를 하나로 뭉치지 않는 편이 낫다.
   - 전자는 연출 우선, 후자는 분기 커버리지와 안정성 우선으로 설계해야 한다.

### 4.5 우선 수정 방향 요약

가장 먼저 손봐야 할 항목은 아래 여섯 가지다.

1. `onPlayerRejoin()`에 공개 단계와 결과 단계 복구 패킷을 추가한다.
2. 모바일을 `MobileBaseGame` 패턴으로 정리하거나, 최소한 `join/rejoin/reset` 기준 화면 책임을 분리한다.
3. 저장 닉네임 자동 복원은 `platform:joined` 이후에 프로필 동기화가 일어나도록 순서를 안정화한다.
4. 사용자 입력 문자열의 정제와 호스트 렌더링 이스케이프를 강화한다.
5. `DemoSimulator.js`를 완전 자율형으로 고치고 실유저 세션 오염 방지 가드를 넣는다.
6. 기존 Playwright E2E를 "호스트 단독 데모 완주"에서 "실제 모바일 1대 이상이 참여하는 라운드 검증"까지 확장한다.

이 여섯 가지를 정리하면 `허드 로직`은 단순히 아이디어가 좋은 게임을 넘어서, 반복 시연과 실제 파티 플레이 모두에서 설득력 있게 버티는 플랫폼 대표작으로 올라갈 가능성이 높다.
