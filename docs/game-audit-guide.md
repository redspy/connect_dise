# 게임 전수 검수 가이드 (Full Audit Playbook)

기존 게임 하나를 골라 "워크플로우 정상 동작 / 반응형 레이아웃 / 컨트롤 겹침·짤림 / 전 해상도 동작"을 완전히 재검수하고 버그를 고칠 때 따르는 절차입니다. `games/dobble` 전수 검수(2026-08-19)에서 실제로 이 절차를 밟아 Critical 1건을 포함한 버그 5건 + CSS 접근성 버그 1건을 실측으로 찾아 수정했습니다. 이 문서는 그 과정을 다음 게임에도 반복 가능하도록 정리한 것입니다.

> 정적 코드 리뷰만으로는 이 버그들 중 어느 하나도 못 잡았을 것입니다. 전부 **실제 브라우저 실행 + 인원 스트레스 테스트**로만 발견됐습니다. 이 문서의 핵심은 "코드를 읽어라"가 아니라 "실제로 켜서 끝까지 눌러봐라"입니다.

## 0. 사전 준비

1. 대상 게임의 기존 문서(`docs/games/<game-id>/evaluation.md` 등)가 있으면 읽되, **작성일을 반드시 확인**하고 최신 코드와 대조 없이 그대로 신뢰하지 않습니다. 이전 지적 사항 중 상당수는 이미 고쳐져 있을 수 있습니다(dobble 사례: 2026-07-06 평가서의 지적 5건 중 4건이 이미 해결된 상태였음).
2. `games/<game-id>/{host,mobile,shared}`의 JS/CSS를 전부 읽고, `games/registry.js`에서 해당 게임의 `minPlayers`/`maxPlayers`를 확인합니다 — 뒤에서 인원 스트레스 테스트에 그대로 씁니다.
3. 작업량이 크므로(스크린샷 수십 장 + CLI 리뷰 로그 등 방대한 중간 산출물 발생) 별도 fork/서브에이전트에 위임하는 것을 권장합니다. 이 경우 최상위 지시에 반드시 **1번 항목(git 작업 금지)**을 포함하십시오.

## 1. 실제 멀티 CLI로 정적 검증

[docs/agents/roles.md](file:///Users/soul/Source/connect_dise/docs/agents/roles.md) §0/§3에 정의된 대로, 가상 페르소나가 아니라 **3개의 실제 독립 CLI 프로세스**를 Bash로 직접 호출합니다. 서로 다른 모델이 서로 다른 버그를 잡습니다(dobble 사례: Claude CLI가 타이머 미정리·기아 버그를, Codex CLI가 죽은 CSS·문서 링크 오류를 각각 독자적으로 발견).

```bash
# 아키텍처/SDK 규약 위반 — 별도 세션(자기검증 편향 방지)
claude -p "<대상 게임 경로> 코드의 아키텍처 결함, 타이머/리스너 누수, SDK 규약 준수 여부 리뷰" --allowedTools "Read"

# 스펙 정합성(AGENTS.md/docs/DESIGN.md vs 구현)
codex exec "<대상 게임 경로>와 AGENTS.md/docs/DESIGN.md 간 정합성 감사"

# 비주얼 패리티(스크린샷 확보 후 4번 단계에서 사용)
agy -p "<스크린샷 경로>를 docs/DESIGN.md 가이드라인과 대조" --model gemini-3.1-pro-high
```

**운영 주의**: `codex exec`를 `run_in_background`로 백그라운드 실행할 때 stdin을 `< /dev/null`로 리다이렉트하지 않으면 무한 대기합니다. 이 프로젝트의 `git commit`은 pre-commit 훅에서 `codex exec`를 동기 호출하므로 전체 코드베이스 규모에 따라 수 분씩 걸릴 수 있습니다 — 커밋도 `run_in_background: true`로 돌리고 완료 알림을 기다리십시오.

**운영 주의 2 — 무거운 CLI 리뷰와 Playwright 테스트를 동시에 돌리지 말 것**: `claude -p`/`codex exec`/`agy -p`는 각각 무거운 자식 프로세스라, 여러 게임을 병렬 fork로 동시에 검수하면서 각 fork가 3-CLI 리뷰를 동시에 돌리면 시스템 전체가 CPU 경합 상태가 됩니다. 이 상태에서 Playwright E2E(특히 `setTimeout` 체인으로 진행되는 결과 발표 애니메이션처럼 고정 타임아웃을 기다리는 테스트)를 같이 돌리면 로직에는 문제가 없는데도 타이밍만 밀려 테스트가 실패하는 경우가 실측됨(relay-drawing 검수에서 재현). 테스트가 실패하면 바로 "버그"로 단정하지 말고, 그 시점에 다른 CLI 리뷰 프로세스가 동시에 돌고 있었는지(`ps aux`) 먼저 확인하고, 조용한 상태에서 최소 2회 재실행해 재현되는지 보십시오.

**운영 주의 3 — 3개 CLI 전부 출력을 파일로 저장하고, 저장된 파일 없이는 "확인했다"고 쓰지 말 것**: `claude -p`/`codex exec`의 출력은 `> claude-review.txt`/`> codex-review.txt`처럼 매번 저장하면서, `agy -p`만 파일로 안 남기고 "요청함"/"확인함" 정도로 리포트에 서술만 하고 넘어가는 사례가 실제로 있었음(dixit/nunchi-ten/dobble/relay-drawing 4개 게임 검수 전부 — 사후 감사에서 `agy-review.txt` 같은 저장 파일이 단 하나도 없는 것으로 발견됨, 2026-08-20). agy는 스크린샷 인자가 필요해 앞의 두 CLI보다 호출이 번거롭고, 그래서 "돌렸다고 치고 넘어가는" 누락이 특히 잘 생김. **agy를 포함해 3개 CLI 모두 `> <cli이름>-review.txt` 등으로 실제 stdout을 스크린샷 디렉토리에 저장하고, 최종 리포트에는 그 파일에 실제로 있는 내용만 인용하십시오.** 저장된 파일이 없다면 그 CLI는 "실행 안 함"으로 정직하게 보고해야지, 그럴듯한 문장으로 대신 채우면 안 됩니다.

**운영 주의 4 — agy는 정상적으로 실행해도 서비스 쪽에서 "Error: timeout waiting for response"로 실패할 수 있음. 재시도는 최대 2~3회, 각 회차는 별도 백그라운드 프로세스로 띄우고 `ps -p <PID>`로 생사만 폴링할 것 — 셸의 `timeout` 명령은 macOS에 기본 없음**: dice 검수(2026-08-20)에서 상세 프롬프트/축약 프롬프트/최소(파일 1개) 프롬프트로 3회 연속 시도했으나 각각 즉시 타임아웃 에러, 즉시 타임아웃 에러, 5분+ 무응답(강제 종료)으로 실패함 — 프롬프트 길이나 파일 개수 문제가 아니라 서비스 자체의 일시적 문제로 판단됨. §1 운영 주의 3의 "저장 파일 없으면 미실행으로 정직하게 보고" 원칙을 그대로 적용해, agy가 진짜로 응답에 실패한 경우에는 시도 횟수와 각 회차의 실패 양상을 `agy-review.txt`에 그대로 기록하고 claude+codex 2-CLI 교차검증만으로 리포트를 진행해도 됨(허위로 "확인함"이라고 쓰는 것과는 다름 — 실제 실행 시도 기록이 남아있는 정직한 실패이므로).

**운영 주의 5 — `agy -p`에 스크린샷 경로를 셸 트레일링 인자로 붙이면 이미지가 전달되지 않고 "첨부 안 됨" 안내문만 돌아옴. 경로는 반드시 프롬프트 문자열 본문 안에 절대경로로 적어, agy 자신의 파일 읽기 툴이 워크스페이스 권한(`~/.gemini/antigravity-cli/settings.json`)으로 직접 열게 할 것**: `agy -p "..." /path/a.png /path/b.png --model ...`처럼 프롬프트 뒤에 파일 경로를 별도 인자로 나열하면 agy는 그 인자들을 무시하고 "이미지가 첨부되지 않았습니다"라는 체크리스트만 반환함(give-you-fire 검수에서 실측, 2026-08-21). `agy -p "다음 스크린샷을 읽어서 검토해줘: /abs/path/1.png, /abs/path/2.png ..." --model ...`처럼 경로를 프롬프트 문자열 안에 명시하면 정상 동작함(§3 roles.md의 예시와 동일 패턴).

**운영 주의 6 — 정적 리뷰 CLI(`claude -p`/`codex exec`)가 대상 파일을 읽는 도중에는 그 파일을 수정하지 말 것. 리뷰 하나가 여러 차례에 걸쳐 파일을 다시 읽으므로, 중간에 수정하면 하나의 리뷰 결과 안에 수정 전/후 상태가 뒤섞여 신뢰도가 떨어짐**: give-you-fire 검수(2026-08-21)에서 리뷰 대기 시간을 아끼려고 이미 확정된 버그 수정을 codex 리뷰 실행 중에 병행했는데, codex가 수 분에 걸쳐 여러 차례 같은 파일을 다시 `nl -ba`로 열어보면서 일부는 수정 전, 일부는 수정 후 상태를 관찰해 "준수"로 판정한 항목이 실제로는 검수자 자신이 방금 고친 결과를 재확인한 것에 불과했음(우연히 결과가 맞았지만 재현성 있는 절차는 아님). 리뷰와 수정은 순차적으로 진행하고, 시간을 아끼고 싶다면 리뷰 CLI가 도는 동안은 코드 수정이 아니라 스크린샷 스크립트 작성처럼 리뷰 대상과 무관한 준비 작업만 병행할 것.

**운영 주의 7 — `claude -p`를 백그라운드로 돌릴 때 `nohup claude -p "..." > file 2>&1 &` 형태로 감싸면 파일이 0바이트로 남고 프로세스만 조용히 끝나는 경우가 있음(원인 불명, codex/agy에서는 재현 안 됨)**: `nohup` 래퍼 없이 `claude -p "..." < /dev/null > file 2>&1 &`처럼 셸 자체의 백그라운드(`&`)만 쓰는 패턴으로 바꾸면 정상적으로 파일에 출력이 쌓임(give-you-fire 검수에서 실측, 2026-08-21). claude CLI를 백그라운드로 돌릴 때는 `nohup`을 붙이지 말 것.

## 2. 개발 서버 기동 + 해상도 매트릭스로 실제 렌더링

`dev-server` 스킬로 `npm run dev`를 띄운 뒤(`https://localhost:5173`, HTTPS), Playwright(devDependency로 이미 설치됨)로 최소 아래 해상도를 커버합니다.

| 대상 | 해상도 |
|---|---|
| 호스트(TV/태블릿) | 1920×1080, 1366×768, 1024×768, 768×1024(세로 — 1024px 브레이크포인트 경계) |
| 모바일 | 320×568, 375×667, 390×844, 412×915, 768×1024, 그리고 대표 폭 1~2개의 가로모드(예: 667×375, 844×390) |

각 해상도에서 **로비 / 게임 진행 중 / 결과 화면**을 스크린샷으로 남기고 겹침·짤림·스크롤 불가로 인한 콘텐츠 유실을 육안 판정합니다. 텍스트 기반 모드(한자/가나 등 다국어/심볼 텍스트 모드가 있는 게임이라면)도 최소 1개 해상도에서 확인 — 이미지 모드와 레이아웃/크기 로직이 다를 수 있습니다(dobble에서 실제로 텍스트 모드만 셀 대비 폰트가 20% 미만으로 작게 나오는 버그가 있었음).

## 3. 인원 스트레스 테스트 — 가장 버그를 많이 잡은 단계

`registry.js`의 `maxPlayers`를 실제로 채워서(데모 모드 봇 활용 또는 DOM에 합성 데이터 주입) 렌더링해야 합니다. **이 항목이 정적 리뷰로 절대 못 잡는 버그의 핵심 원인**입니다 — 점수판/랭킹처럼 인원 수에 비례해 커지는 리스트가 고정 `vh` 계산식이나 `max-height` 누락과 만나면 실제 인원이 적을 때는 멀쩡해 보이다가 만석에서만 잘립니다.

```js
// Playwright page.evaluate로 결과/점수판에 합성 데이터 주입하는 패턴 예시
await page.evaluate(() => {
  const el = document.getElementById('score-cards'); // 또는 결과 랭킹 컨테이너
  // maxPlayers만큼 카드/행을 강제로 채워 렌더링
});
```

호스트 화면은 여러 해상도 × 만석 인원 조합으로, 특히 **가로/세로 비율이 극단적인 창 크기**(예: 1280×400처럼 넓고 짧은 창)에서도 확인하십시오. TV/모니터는 실제로 이런 비율이 흔합니다.

## 4. 전체 워크플로우 E2E — 실제로 눌러서 끝까지

정적 검토·스크린샷만으로 끝내지 말고, 게임 하나의 전체 생명주기를 Playwright로 실제 클릭해서 검증합니다. 최소 아래 시나리오를 순서대로 통과해야 합니다(2인 이상 게임 기준 — 게임 규칙에 맞게 조정):

1. 로비 참여(2명 이상) → 호스트 로비에 전원 표시
2. **로비 단계 재접속**: 준비 전 한 명이 새로고침 → `lobbyState` 응답으로 대기 화면 정상 복구(프리징 가드)
3. 전원 준비 → 자동/수동 게임 시작
4. 오답/실패 등 네거티브 경로 → 패널티·피드백 정상 표시
5. 정답/성공 반복 → 승리 조건 도달 → 결과 화면 정상 표시
6. **재대결** → 호스트/전 플레이어가 로비로 정상 복귀 (여기서 dobble은 `onReset↔stopDemo↔resetSession` 무한루프로 재시작 자체가 불가능한 Critical 버그가 있었음 — 재대결 경로는 특히 꼼꼼히 볼 것)
7. 재대결 후 재시작 → **게임 중 재접속** → `rejoinState`로 카드/점수/타이머 정상 복구
8. 데모 모드(Attract Mode): 시작 → 중단 배너 → **실제 플레이어 접속 시 자동 중단** → 로비 복귀. 이때 "에러 없이 배너가 사라지고 로비로 돌아왔다"만 확인하지 말고, **방금 접속한 그 실제 플레이어가 호스트 로비 명단에 실제로 남아있는지까지** 확인하십시오 — 데모 시작 전 스냅샷으로 플레이어 목록을 통째로 복원하는 구현이면, 그 스냅샷에는 방금 join한 플레이어가 없어서 에러도 없이 조용히 로비에서 사라질 수 있습니다(눈치10단 검수에서 Claude CLI 리뷰로 실측 발견, §7 AGENTS.md에 일반화 기록됨). **여기서 멈추지 말고, 그 뒤로 실제 플레이어끼리 게임 한 판을 끝까지 진행 → 재대결 → 두 번째 실제 게임이 정상적으로 다시 시작되는지까지** 확인하십시오 — 데모가 `sdk._players`처럼 SDK 내부 상태까지 직접 건드리는 구현이면, 데모 종료 직후 화면은 멀쩡해 보여도 그 오염이 다음 `resetSession()` 시점에야 표면화돼(예: 유령 플레이어가 되살아나 `readyCount`가 영원히 `playerCount`와 안 맞아 다음 게임을 시작할 수 없음) 데모 중단 직후 확인만으로는 못 잡습니다(give-you-fire 검수에서 실측 확인, 2026-08-21).
9. **점수 정확성 검증**: 결과 화면에 숫자가 "표시된다"는 것과 "그 숫자가 실제 룰대로 맞다"는 것은 별개입니다. 매 라운드/게임 종료 시점마다 화면에 뜨는 점수를 규칙(설명 텍스트, `docs/games/<game-id>/` 기획 문서)과 직접 대조해서 손으로 검산하십시오. 점수 계산·정산처럼 여러 조건이 얽힌 로직은 정적 리뷰만으로 놓치기 쉬우므로 [docs/agents/roles.md](file:///Users/soul/Source/connect_dise/docs/agents/roles.md) §3에 기재된 대로 `claude -p --model claude-fable-5`(별도 세션)로 그 로직만 한 번 더 교차검증하는 것을 권장합니다. **게임 도중 한 명이 완전히 퇴장(재접속 유예시간 만료)하는 시나리오도 반드시 포함하십시오** — 최종 결과 집계 함수가 "현재 접속 중인 플레이어" 목록을 기준으로 순회하는 구현이면, 이미 정상적으로 등수가 기록된 중도 이탈자가 그 목록에서만 빠져 있어서 최종 결과에서 통째로 사라지는 버그가 실측된 바 있습니다(give-you-fire 검수, 2026-08-21). 브라우저 컨텍스트를 강제로 닫아 완전 이탈을 재현하거나, 재접속 유예시간을 기다리는 대신 헤드리스 CLI로 해당 게임 로직만 교차검증하는 방식으로 확인하십시오.

재사용 가능한 스크립트 템플릿은 `games/dobble`/`games/nunchi-ten` 검수 시 작성한 워크플로우 스크립트를 참고하십시오(대상 게임의 메시지/셀렉터에 맞춰 고치면 재사용 가능). 완료 후엔 `npx playwright test tests/<game-id>` (기존 데모 스펙이 있다면)도 함께 재확인합니다.

> **워크플로우 스크립트 작성 시 흔한 함정**: 모든 게임 페이즈가 `.n-overlay[data-phase="..."]`/`.db-overlay[data-phase="..."]` 같은 오버레이 엘리먼트로 렌더링된다고 가정하지 마십시오. 일부 페이즈(예: 라운드 입력 중처럼 "보드 자체를 보여주는" 상태)는 오버레이가 아예 없고, 모든 오버레이가 `hidden`인 상태 자체가 그 페이즈를 의미합니다. 셀렉터를 짜기 전에 대상 게임의 `index.html`에서 `data-phase`/`data-screen` 속성이 실제로 어떤 페이즈에 존재하는지 먼저 `grep`으로 확인하십시오 — 안 그러면 정상 동작하는 코드를 버그로 오인해 시간을 낭비합니다(눈치10단 검수에서 실제로 겪음).

## 5. 버그 수정 → 같은 방식으로 재검증

버그를 코드에서 직접 고친 뒤, 1~4단계와 **동일한 방법**(실제 브라우저, 같은 해상도/인원 조건)으로 재검증해서 실제로 고쳐졌는지 스크린샷/워크플로우 재실행으로 재확인합니다. "코드를 고쳤으니 됐다"로 끝내지 않습니다.

## 6. 의사결정 원칙

애매한 판단(레이아웃 재배치 방향, UX 톤 등)이 필요하면 중단하지 말고 이 프로젝트의 기존 컨벤션(`AGENTS.md` 필수 처리 사항, `docs/DESIGN.md`, 다른 게임들의 기존 패턴)에 가장 부합하는 방향으로 진행하되, **그 결정과 근거를 최종 리포트에 남깁니다**. 플랫폼 전역에 영향을 주는 결정(예: 데모 배너의 공통 동작 방식 변경)은 대상 게임 하나만 임의로 바꾸지 말고 별도 판단 대상으로 리포트에 명시합니다.

## 9. 이 문서는 살아있는 문서(Living Document)다

이 가이드 자체가 완성본이 아닙니다. **검수를 진행하다가 "이건 특정 게임만의 문제가 아니라 검수 절차 자체에 빠져 있던 항목이다" 싶은 게 나오면, 그 게임의 개별 버그 수정과는 별개로 이 문서를 직접 갱신해야 합니다.** 두 가지를 구분하십시오.

- **게임 코드의 재발 방지 패턴** (예: "데모 리셋 가드", "타이머 기아 방지") → §7대로 `AGENTS.md` 필수 처리 사항에 기록합니다. 코드를 어떻게 짤지에 대한 규칙입니다.
- **검수 절차 자체의 빈틈** (예: "이 프로젝트 게임들은 대부분 접근성/명도 대비를 안 보는데 그것도 검수 항목이어야 한다", "웹소켓 재연결 경쟁 상태를 확인하는 단계가 아예 없었다", "새로운 해상도군(예: 폴더블 화면비)이 새로 필요해졌다") → **이 문서(`docs/game-audit-guide.md`)의 해당 단계(§0~§8)에 직접 추가/수정**합니다. 다음 검수자가 처음부터 같은 사각지대를 다시 발견하지 않도록 하는 것이 목적입니다.

절차:

1. 새 절차 항목을 관련된 기존 섹션(§0~§8)에 자연스럽게 병합합니다 — 별도 부록으로 흩어놓지 말고, 실제로 그 단계를 밟을 때 눈에 띄는 위치에 넣습니다.
2. 문서 맨 아래 **§10 개정 이력**에 한 줄로 추가합니다: 날짜, 어느 게임 검수에서 나왔는지, 무엇을 추가/수정했는지.
3. 이미 있는 예시/수치(해상도 목록, 워크플로우 시나리오 등)는 게임이 다양해질수록 계속 갱신될 수 있습니다 — 기존 값을 지우지 말고 "일반적으로는 X, <게임 유형>에서는 Y도 추가로 확인" 식으로 보강하십시오.
